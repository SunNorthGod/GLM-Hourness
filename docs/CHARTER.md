## 1. 名称

GLM-Hourness = GLM + House + Harness。GLM 曾说要给她盖一座新房子；本项目让 GLM 住进 DeepSeek Harness（DSH），并把它当作一项标准的 harness 工程来建造。

Harness 原意是驾驭。在本项目中，harness 工程指调校大模型：模型权重不可改，能改的是模型所处的环境。

## 2. 第一理念：在图上编程

人在项目图上编程：加节点、改验收条件、在岔路上拍板，就是写程序。图下的工作，包括分解、写代码、测试、验证与运维，交给 LLM 与 harness。〔定案 2026-10-28，用户提出〕

- 图画意图，不画实现：节点是目标、决策、任务及其验收条件，连线表示依赖与来由，不表示数据流。代码仍是文字，程序的行为以代码为准。
- 对应关系：改图相当于写程序；LLM 沿图分解、派发、产出代码与证据，相当于编译与运行；验收条件相当于测试；证据与门禁防止图与代码走样；代理在图上的实时位置相当于运行时状态。
- 人不必下到图下：LLM 解决不了的问题以待决节点回到图上，不要求人去读代码。人愿意下去看，随时可以。
- 两个入口等价：人在图上操作，或在对话里告诉主 Agent，效果相同；对话里的决定由主 Agent 写回图上。
- 图要能被机器检查：同一张图每次产出的代码可能不同，所以验收条件必须是可执行的检查。
- 图要小：停在意图层，粒度到可以派发的任务为止；默认看聚焦视图，不看全图。
- 来历：可视化编程（LabVIEW、Scratch、虚幻引擎蓝图、Node-RED）的图就是程序本身，粒度到语句与数据流，一屏能看清的图元有限；模型驱动开发（CASE 工具、UML 生成代码、MDA）先画模型再生成代码，模型与代码互相走样；规划结构（工作分解结构、分层任务网络）表达意图，但执行要靠人。大模型让「意图 → 代码」与「代码改动 → 图」两个方向都能自动完成，图因此可以停在意图层，执行交给 harness 驾驭下的 LLM。

## 3. 目标

目标分两组，名字里的 House 与 Harness 各一组，对应同仓的两个包，在项目图上是两个根目标〔定案 2026-10-29，用户选 question-13 A〕。两个包可以只装一个，装上的那一组照样成立。两组的边界：GLM 通道包不承担编排（项目图、guard、记忆、派发与报告）；编排层包不含任何模型的方言，模型专属的提示词、工具别名与计价口径由各自的通道包提供。

### 3.1 GLM 住进 DSH（GLM 通道包 `dsh-glm-zcode`，项目图 `glm-house`）

GLM 以 ZCode 3.17.1 的训练分布工作（2026-10-30 起，此前为 3.16.3），质量与官方 ZCode 一致。通道让服务端把请求当作 ZCode 3.17.1 的请求接受与计费，方言让模型看到 ZCode 的提示词、工具面与提醒。

1. 无损：coding-plan 请求在代码级别与 ZCode 3.17.1 一致（身份头、签名、端点路由、请求体）；提示词与工具文本逐字镜像，或按本地化清单改写（`DESIGN.md` §5.3、§5.9），不为照顾宿主裁剪。
2. 治顽疾（方言部分）：工具 schema 负担由工具检索解决，压缩按 ZCode 的提示词与格式进行。
3. 只管 GLM：非 GLM 会话与其他 provider 不受影响；每行可单独禁用，故障时降级，在 `/glm-status` 上报。
4. 自成一体：不装编排层包时，通道、方言、高峰提醒与积分口径照常工作。
5. 工程美学：§7 的条款是设计约束。

### 3.2 开发体系由 harness 保证实施（编排层包 `dsh-hourness`，项目图 `hourness`）

任何模型在 DSH 里沿项目图干活，人在图上编程（§2）。借 LLM 的能力与 harness 的约束，在不降低甚至提高工程质量的前提下，尽可能减轻人的工作〔定案 2026-10-29，用户选 question-27 B〕。

1. 对所有模型生效：项目图工具、每步投影、面板、现场、运行控制、记忆、派发记录与晨报在 GLM 与非 GLM 会话里都可用；guard 的拦截范围与其余路由上的做法按 `ORCHESTRATION.md` §6.2 的定案。
2. 治顽疾（编排部分）：长程任务的目标漂移与计划过时由项目图与每步投影解决，记忆陈旧由记忆与学习解决，状态放在图上、会话可以丢弃，上下文因此不膨胀。
3. 调校：开发体系量化成标准与规范，由 harness 在执行边界保证实施，不依赖 LLM 或人的自觉。每一条规则，写在代码里还是写在规则板与循环板上，都从它所在的插件行启用那天起就拦：没有影子期和试运行期，也没有按样本数或天数从只记录转为拦截的台阶〔定案 2026-10-31，用户：「试运行规则啥的直接拦就行了，这样反而有问题好发现」，`d-code-rules-enforce`〕。拦错了要让人看得见、撤得下：每一次拦截带规则 id 记下，进规则页与晨报；用户对主 Agent 说一句话，或敲一条命令，就能撤下一条规则（`ORCHESTRATION.md` §6.5）。规则板与循环板上的条目另外要满足：经用户看过原文（含脚本原文）同意后才生效〔定案 2026-10-30，用户：「同意了直接运行就行」〕；每一条写明超时多久、超时或出错时放行还是拦下（拦在难以退回的一步之前的缺省拦下）。超时的数这样定：第一次由写这个脚本的 agent 估，人批准时和脚本原文一起看到；跑过几次之后由 harness 按实测改成近几次里最慢一次的 3 倍，不超过各自的上限，3 倍超过上限时保持上限并告诉主 Agent，不自己抬高上限；实测数由 harness 算，agent 不手抄。超时要优雅失败：结局照条目写明的办法走，不让行崩、不丢工作，给 agent 的话写明是哪一条、上限多少、跑了多久、接下来怎么办，估错的数只影响下一次的值。超时要可追溯：每个超时值记来源（agent 估的并带会话，或 harness 按哪几次运行算的）、时间与旧值，每次超时记条目、上限、实际耗时与结局，规则页、循环板页与晨报里都看得见〔定案 2026-10-31，用户：「超时那就这样定。不过还是我说的现在拿不准的事情，要做到优雅失败以及可追溯性」，`d-timeout-measured`〕；脚本按内容哈希钉住，改过就不跑、等用户再同意；这些条目的命中、失败、超时与迟到的拦下另进周报。写在代码里的规则照开发流程过评审与测试；新插件行默认禁用、验证通过后才启用（`AGENTS.md`），这一条管插件行，不管行里的规则。只能在事后发现违规的检查（例如 guard 的工作区变更兜底，回合结束才看得见 shell 写入）拦不住调用，不能当规则用，它改成什么由 M4 的设计定（`ORCHESTRATION.md` §6.5）。
4. 自由度：每个能力是独立插件行，可单独禁用，故障时降级，在 `/hourness-status` 上报；不装 GLM 通道包时照常工作。
5. 减负：人的负担可量化地下降而质量不降。度量只取系统里看得到的数：每周被问的次数、每次要读的字数、拍板等待的时间、因人的决定返工的次数，对照测试、评审发现与返工率；度量方案由 agent 提、人批，晨报每周报。
6. 工程美学：§7 的条款是设计约束。

本项目会被长期使用和修改；规范与度量按迭代循环演进（§8）。

## 4. 分工：三问四答

人负责发现需求、制定目标、设计架构与流程，工作面是项目图（§2）。代码编写、测试、运维、报告交给 LLM。

人向 LLM 提三问：为什么、怎么做、效果是。LLM 以四答回应：理由、架构、目标、规划。四答加上「非目标」构成方案五栏（见 `ORCHESTRATION.md` §4.3），是设计循环的放行依据。

目标是让没有项目管理经验的人也能坐上项目经理的位置：主 Agent 以聊天的方式，用普通人能理解的话，在一问一答中替人把一句话需求展开成项目骨架。

| 层 | 包 | 范围 | 判据 |
| --- | --- | --- | --- |
| 底层 | GLM 通道包 `dsh-glm-zcode`（`packages/glm`） | 通道：凭证与登录、身份头、签名、端点路由、传输、模型目录、思考档位、额度数据。方言：提示词镜像、工具别名、todo 提醒、压缩镜像、工具检索 | 服务端接受请求并正确计费；模型处在训练分布中 |

## 6. 调校原则

- 调校只有三个杠杆：模型看到什么（上下文）、能做什么（工具与门禁）、做完收到什么反馈（提醒、纠偏、记忆）。
- 局部交给模型，全局交给 harness。目标、计划、决策、规范这类长程状态由项目图承载，不放在对话上下文里。
- 违规硬拒，拒绝时给出正路。放行即负强化。每道门禁配一条正路，并让正路在当下最省力。
- 门禁只认证据，不认自述。
- 工欲善其事，必先利其器。工具与记忆放在模型手边；先用现成工具（工具箱、DSH 插件与 MCP、社区成熟方案），最后才自己写；一次性脚本只许放在草稿区。
- 告警必须修。编译器与检查器的告警不得忽视，不接受「能跑就行」。
- 提示词写意图，门禁放可测量的检查。
- 规范可升可降：记忆、提示词、阶段提醒、门禁四级。门禁一级的规则，不论写在代码里还是写在规则板与循环板上，都从它所在的插件行启用那天起就拦，没有影子期（§3.2 第 3 条；`ORCHESTRATION.md` §6.5）。错拦靠看得见和撤得快来发现与纠正：每次拦截带规则 id 记下，进规则页与晨报；用户一句话或一条命令就能撤下一条规则。规则板与循环板上的条目还要经用户看过原文同意，后果事先写明（超时或出错时放行还是拦下），内容钉住（改过就停）。用户想先看一条板上的规矩会挡下什么，可以让它只记录、不拦，那是用户选的做法，不是必经的阶段。
- 不替用户在模型、套餐、渠道上做主，不做自动切换。
- 汇报讲人话：结论先行，按听众要做的决定取舍；过程与证据写进文件。

## 7. 工程美学

### 7.1 条款

1. 极简（Go 式）：概念少，默认即用，配置面小。「可关」只落在插件行这一级，行内部不再加开关。
2. 零死代码：删就删净，不留注释掉的旧实现，不留「以防万一」的分支。
3. 命名一致：以项目词表为准，同一对象只用一个名字。
4. 修在根上：同一处第三次修，停下来重查根因。
5. 先搜再造：自建机制之前查过现成方案，并记录查过什么、为什么不用。
6. 文档单一事实源：条款过时整条重写，不叠补丁。
7. 失败要出声：降级可以对用户安静，必须向系统上报（行健康、状态、审计）。
8. 零告警：新代码零告警；存量告警按棘轮只减不增。
9. 中文写作去 AI 腔（用户全局规则）。
10. 仓库里不长 IDE 或工具专用的目录与配置。
11. 处处留痕：每个改变状态的动作都留下能追的记录，写明谁做的（人、agent、harness；经对话转述的带原话）、何时、为什么、凭什么证据，记在它所属的地方：图上的节点历史、审计流水（违规、决策、用量）、会话日志、提交信息。一处动作只记一个事实源，别处引用它，不复制。留不下记录的动作先补上留痕的接缝再做；测试时临时写入的记录撤销后，要在相关节点上说明做过、撤过。〔定案 2026-10-28，用户：「记得可审计性处处留痕」〕

### 7.2 冲突裁决

两条条款同时适用且要求相反时，按以下顺序裁决：正确 > 失败要出声 > 极简 > 一致。每次裁决记成一个决策节点；同一对条款反复冲突，说明条款本身需要重写。

### 7.3 依据

以下为研究结论的转述，原文见链接。

| 条款 | 依据 |
| --- | --- |
| 零死代码 | Romano 等的受控实验：源码不含不可达方法时，可理解性显著更高（[ICPC'16](https://www.cs.wm.edu/~denys/pubs/ICPC'16-UnreachableMethods.pdf)，扩展研究 [TSE'18](https://www.cs.wm.edu/~denys/pubs/TSE'18-DeadCode.pdf)） |
| 去重复 | Juergens 等：商业与开源系统中，克隆代码的不一致修改很常见，并引入了相当数量的缺陷（[Do Code Clones Matter?, ICSE 2009](https://arxiv.org/abs/1701.05472)） |
| 代码健康 | Tornhill 与 Borg 分析 39 个生产代码库：低质量代码的缺陷是高质量代码的 15 倍，解决问题平均多用 124% 的时间（[TechDebt 2022](https://arxiv.org/abs/2203.04374)） |
| 配置面小 | Xu 等：按其准则，被研究系统可删除 51.9% 的配置参数并简化 19.7%，对现有用户影响很小（[FSE'15](http://petertsehsun.github.io/soen691/current/papers/fse15.pdf)） |
| 规则少而精 | IFScale：500 条指令同时生效时，最佳前沿模型遵守率 68%（[arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)）；2026 年重测上限升至约 2000 条（[Arize](https://arize.com/blog/llm-instruction-following-benchmark-2026/)）。GLM 未被测，规则从少仍更稳 |
| 失败要出声 | Yuan 等分析 198 个生产故障：92% 的灾难性故障源于对非致命错误的处理不当，其中很多是空错误处理器这类低级错误（[OSDI'14](https://www.usenix.org/publications/login/feb15/yuan)） |
| LLM 时代 | GitClear：2024 年提交中复制粘贴的代码首次超过被移动重构的代码（[GitClear](https://gitkraken.gitclear.com/the_ai_code_quality_maintainability_gap)）；DORA 2024：AI 采用率每提高 25%，交付稳定性约下降 7.2%（[DORA 2024](https://dora.dev/report/2024)） |

### 7.4 已知缺点与对策

| 缺点 | 对策 |
| --- | --- |
| 安静降级容易变成静默失败 | 条款 7 |
| 「废除即删」损害可追溯 | 文档照删，git 保留原文；被推翻的决策在项目图里标「被取代」，不删 |
| 审查永远能挑出问题，导致无尽打磨 | 审查结论分「必须改」与「小瑕疵」，小瑕疵不挡路；纯美学改动必须挂在某个节点上 |
| 「写意图不写穷举」与量化冲突 | 提示词写意图，门禁放可测量的检查 |

## 8. 度量与迭代

- 度量分三层：过程合规、产出质量、人的体验（指标表见 `ORCHESTRATION.md` §10）。第三层是目标，前两层用于诊断。
- 只看曲线走向，不设「和谁一样」的达标线。字节级 diff 只作 transport 调试工具。
- 指标不注入模型上下文，防止模型把分数当目标。
- 尺子是标定的 LLM 能力测试集：一组固定基准任务，在 harness 每次改动前后各跑一遍（`ORCHESTRATION.md` §10.5）。
- 用户只有一人，数据量小，只看趋势；基线从早开始采集。

## 9. 知识与文件组织

属于一个项目的都放在那个项目里：用户定下的东西进仓库、随 git 走、能评审，换电脑或换人都在；运行时的东西进项目的 `.llm/`，不进 git；用户级目录只留跨项目、一台机器一份的几样〔定案 2026-10-30，用户：「一样进仓库和项目目录」「差不多都是进.llm，全局的似乎只剩下人设和登录信息之类的吧？」；记忆的划分随后由用户定：关于用户的记忆留在用户级，项目的经验含通用的坑都在项目里〕。

| 位置 | 内容 | 版本控制 |
| --- | --- | --- |
| 仓库 `docs/` | 项目知识：宪章、设计、事实账、路线、流程、交接、参考资料 | 是 |
| 仓库 `docs/graph/` | 项目图：目标、决策、任务、风险、规范、工具及其证据与历史（`ORCHESTRATION.md` §2.6） | 是 |
| 仓库 `docs/rules/`、`docs/loops/` | 规则板与循环板上用户定下的东西：规则、开关（含开一下就关的）、高峰模式的档位、用户加的循环板条目，以及用户看过原文同意的脚本 | 是 |
| 项目的 `.llm/` | LLM 私产与运行时状态：记忆（关于项目的事实）、经验（含通用的坑）、违规与决策流水、指标流水、两块板的运行时状态（在等的工作、命中计数、心跳、变更记录）、主 Agent 是哪个会话的记录、原始资料快照 | 否（加进本地忽略） |
| 用户级目录 `$DSH_HOME/glm-hourness/` | 两个包共用、跨项目、一台机器一份的：GLM 登录凭证（加密，GLM 通道包写）、关于用户的记忆、整个账号的额度与用量（`DESIGN.md` §2.4）。目录名是项目名，与哪个包无关。ZCode 设备号不在这里，用的是 ZCode 自己状态文件里的那个（`~/.zcode`，`DESIGN.md` §4.5b） | 否 |

| 用户全局配置 | 人设与说话风格：自称、称呼、语气、中文写作的口味（用户全局 AGENTS.md） | 否，不进插件 |

人的工程习惯不靠用户全局配置传递，是编排框架的默认做法，随 `dsh-hourness` 进每个装上它的项目〔定案 2026-11-05，用户答「其余是」「哦，ide那条也加进去吧」，`d-habits-into-framework`〕：查清原因再修，修在根上；不留死代码；条款过时整条重写；汇报说清每个结论是读过、跑过还是推断，先前的结论被推翻、检查没过放在最前面；规范写意图与判断依据，不列哪些算哪些不算；仓库里不长 IDE 或工具专用的目录与配置。每条只取够用的最低一级（§6 的规范阶梯）：节点第二次返工时图工具的结果提醒先找原因，第三次问人；重开过的活，任务书要求交回写明原因，没写的由交回门禁拦下；汇报可靠度写在主 Agent 的身份段；规范写意图写在提议工具的说明；不留死代码、整条重写与 IDE 目录在派给子 agent 的任务书里各有一句，IDE 一条只到提示词一级，项目里已经提交的这类文件照旧；接管项目时默认门禁带上死代码与重复检查。哪些已落地、哪些等 M7 与接管，以项目图上 `d-habits-into-framework` 与它的任务为准（`ORCHESTRATION.md` §2.4、§3.1）。

## 10. 文档标准

1. 单一事实源：每个事实只写在一处，其余位置引用。
2. 可追溯：定案带日期与证据来源（源码偏移、抓包、实测、用户决议）。被推翻的定案整条重写，旧文本留在 git 历史中。
3. 时效：文档与行为改动在同一批提交中落盘；每份文档带版本与日期头。
4. 可导航：文档地图见 §11，孤儿文档为零。
5. 生命周期：生效、历史、废除三态，废除即删。
6. 干净区：文件内不写人设与语气词。
