# 接缝核对：规则板设计 0.9 与循环板设计 0.5（2026-10-30）

对照的文件：`.agents/tasks/rules/design.md`（0.9）、`.agents/tasks/schedules/design.md`（0.5）、`docs/CHARTER.md`（0.7）、两份记图草稿 `rules/graph-ops-v09.json` 与 `schedules/graph-ops-v05.json`。依据的裁定：`design-context.md` 的「Seam rulings between designs」「Both boards are hook-style; storage scope」「Main agent and peak; stale entries; hook seam」，以及核对进行中编排方新加的「Check entries seam」。

做法：每一点归哪一边按 hook 接缝裁定定（循环板管条目形状、事件表、筛选与脚本执行器；规则板管哪些事件拦路、拦路结果的意思、怎样进 `checkCall`；同意的路一条）。对不上时改在归属的一边，另一边改成引用它的节号；重抄对方契约的段落删去，换成引用。两份设计的修订记录都记了这次的修正（循环板 §19.4 第二张表末几行与 §20 的 0.5 一行；规则板 §20 的 0.9 一条末项与附录 G 末表）。没有提交、推送，没有写项目图，没有碰源码。

## 没有定下的

1. CHARTER §9 用户级一行列的是 GLM 凭证、ZCode 设备号、关于用户的记忆、整个账号的额度与用量；循环板的 `<userHome>/loops/machine/`（机器锁、登录状态、已说过的账号提醒、最近走步的项目）按「整个账号的额度与用量」一类放在用户级。两稿与 CHARTER 按这个归类是一致的，但 `d-memory-scope` 说的是「恰好这几样」，这一类要不要在 CHARTER 里点名，留给评审。
2. `repin` 拍板时的做法两板不同（第 10 点）。都不会让没看过的字节跑，没有改；评审若要一致，归各板自己的存储，不是共用执行器的契约。
3. 规则板没有图时带原文的提议 `/rules accept` 改为打两次（第 11 点 (c)），人在规则板上会看到这个变化。这是照循环板已有的做法与「同意的路一条」补的，评审请确认。
4. 人加的检查（第 19 点）等 M4 下一稿给三样：按工具节点读出检查命令的读法、按载荷填占位的纯函数、可选的整理输出的纯函数（名字由 M4 定）；节点上的命令要能不经 shell 直接起（`npx` 这类 `.cmd` 在 Node 22 上不经 shell 起不了，循环板 V19 未核实）。M4 自带的检查器与人加的检查挂同一个工具节点时那一条会跑两次，循环板页面写明，没有去重。
5. M3 下一稿要做的两样两稿说法已一致：`rules:` 的提议也带 `detail` 并过第 5a 步、拍板带摘要；`AttachDetail` 的上限照循环板 §3.1。M3 的文件没改。
6. 项目图上的状态没有写：两份记图草稿已按上面的修正改好，由编排方记。规则板作者留下的两件仍在：`hourness` 验收第 3 条与改写后的宪章不一致（要人改）；违规流水搬进项目 `.llm/` 是数据目录服务与 guard 的事，图上没有对应节点。
