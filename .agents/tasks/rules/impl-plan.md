## 1. 分步原则

1. 一个步一个关注点，一个或两个提交，带独立评审。
2. 一个步合入后仓库处于可构建、`npm run build`、`npm run preflight`、`npm test` 全绿的状态；没有调用方的新导出只许出现在设计自己的先后里（纯函数先于它的第一个调用方），每一处在步里写明由哪一步接上。
3. 凡是只有「同意的路」（M3 第 6 步的 `propose_to_human` 带 `attach`、`record_human_answer`）才能产生数据的东西，本轮不建，列入被挡：这是规则板 0.10 §16 对 R4 写的「没合入时 R4 等，不另写没有 `attach` 的退路」的延伸，延伸的理由见 Interpretations 第 1 条。
4. 新行默认 `disabled: true`；代码里的规则（`loops:schedule-tools`、`loops:files-only`、`rules:files-only`）从所在行启用那天起就拦，没有影子模式（`d-code-rules-enforce`）。
5. 评审级别：「深」= 崩溃安全与审计、权限、会改宿主状态的操作（goal 暂停恢复、定时任务的删改）、guard 类的门；「标准」= 其余。所有步都要独立评审（任务书），深浅只决定评审要查什么。
