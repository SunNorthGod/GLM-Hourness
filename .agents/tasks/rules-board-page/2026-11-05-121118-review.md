### 「项目流水」在几种配置下解析到哪里

`projectHomeFor` 的次序是行的 `home`、会话项目的 `<根>/.llm`、数据目录服务的 `projectHome`；`composeViews` 传的是 rules 行自己的 `config.home`：

```ts
const projectHome = projectHomeFor(ctx, config.home, cwd)
const records = journals([projectHome === undefined ? undefined : auditPaths({ projectHome }).violations,
                          auditPaths(dataHomes(ctx, config.home)).violations])
```

guard 状态视图与 guard 行的门用的是 guard 行的 `config.home`，metrics 行传 `undefined`。几种配置下：

```
配置                               guard/metrics 写到        规则页读的两本                     结果
出厂补丁 + 用户 profile（都不配）   <根>/.llm                 <根>/.llm + data projectHome      对
探针（guard 等配 <dir>/home）        <dir>/home（metrics: <根>/.llm）  <根>/.llm + <dir>/home     对（第二本碰巧是 guard 的）
rules 行配了 home H                 <根>/.llm                 H + H                             第 4 组读不到 guard、metrics
guard 配了 G，data projectHome≠G     G                         <根>/.llm + data projectHome      第 4 组读不到 guard
```

后两种是非默认配置，今天没有人这样配，所以不挡落地（confirmed：几处代码都读到了；生产上出现的可能低）。§16.14 现在写「guard 行的状态视图（同页的 `rules/denials`）读的也是它」，没有写这个前提，读文档的人会以为任何配置下两处都同源。

### 缓存的寿命

`journalsReader()` 在行激活时建一次，`cache` 以去重后的文件路径串为键。项目的会话全部结束后，`composeViews` 不再问这个项目，它的条目却留到行卸载，里面是整本流水的 `GuardRecord[]`。桌面版宿主一次开着的项目不多，影响低（likely）；改法是每次 `composeViews` 记下用到的键，结束时删掉其余的。

### 测试覆盖

新加的 L2 一例把数据目录服务的 `projectHome` 设在项目之外、rules 行不配 `home`，核对了项目流水里 guard 式的拒绝计入、两本都有的一行只算一次、门自己那本里的一行计入人设规则、追加之后重读。没有覆盖：rules 行自带 `home` 的情形（上面第一条）；缓存命中时不读文件（只核了追加后会重读，没核没变时不读）。
