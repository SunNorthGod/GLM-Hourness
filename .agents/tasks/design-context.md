# Design context for parallel design runs (2026-10-29)

Every design run reads this file first. It lists the decisions already made by the human that every design must honour, so briefs do not go stale. The project graph (`npm run -s graph -- show <id>`) is the source of truth; if a node there says something newer, the node wins.

## Product shape

- Two plugins (split question-17 B): `dsh-glm-zcode` (GLM channel and ZCode dialect) and `dsh-hourness` (orchestration layer, for every model). Shared library `src/shared/`, built into each. Design: `.agents/tasks/split/design.md` v0.3 and `.agents/tasks/split/design-addendum-q17b.md` v0.5. The split is merging into main now.
- guard belongs to the orchestration package and applies to every route and model when installed (question-14 G3).
- Two root goals (question-13 A): `glm-house` (GLM channel) and `hourness` (orchestration). The orchestration goal includes: less human work without lower quality, measured only by system-observable numbers (question-27 B).

## Division of labour

- The human finds and shapes requirements, sets goals, decides acceptance and non-goals, releases designs, sets rules, and answers the must-ask categories (docs/ORCHESTRATION.md §2.9.1). Everything else goes to LLMs and the harness. The CHARTER stays as it is.
- Workers' plans are approved by the main agent, checked by the harness (d-plan-approval). The main agent runs on the stronger model, workers may use cheaper ones, and people are reminded of that.
- The main agent has no Write/Edit-style tools; guard blocks shell writes as backstop (question-26 C). Persona applies only to the main agent's replies (m3-main-persona).
- Rules are written only by the human; detectors write signals only; agents may propose (d-rules-human-only). Rules board design: `.agents/tasks/rules/design.md` (being cut down, see next line).
- Correction (human, 2026-10-29): the rules board ships as a concept and mechanism with exactly one built-in default rule, GLM peak pricing. Presence detection ("human is using the computer"), CPU/memory throttling, default budgets, Job Objects and off-peak queues were the human's examples, not features to build; do not design them in as defaults or depend on them. Rules scope is question-32 C: rules per project, only physically single shared things (the desktop app, the sandbox) are machine-wide.
- Lessons board (feature `lessons`, M5): agents add, the main agent merges, the human sees and deletes; every agent including workers can query it on demand.

## Engineering principles

- d-failure-plans and docs/DEVELOPMENT.md §1.1: design for detection, graceful retry, recovery and after-the-fact traceability instead of enumerating cases. Reviews block only on unmet acceptance, unprevented irreversible loss, or failure without detection, recovery or traceability. A loop whose must-fix count does not drop stops for the human; question-11 adds a third pass automatically.
- Designs name the disciplines and standards they draw on (ORCHESTRATION.md §4.3 architecture column); reviews check against them.
- question-28 C: as much parallelism as is free of side effects; code touching the same files, the desktop or the sandbox is serialised by the orchestrator.
- Credits for verification (calibration, ablation, live checks) are pre-authorized (norm-decision-tiers); the desktop may be used without asking the human, one holder at a time (risk-shared-desktop).

## Option lists for the human (d-option-card, d-recommend-last)

Every choice shown to the human, including the open-decisions section of a design, is a table: columns 选项 / 怎么做 (bold, at most 20 characters) / 得到 / 代价, plus at most one column for a dimension where the options really differ; numbers and concrete examples, no evaluative words, no filler options. One line 取决于 under the title: the crux question only the person can answer. One line under the table: 是 → X；否 → Y. The recommended option is last. Keep the number of human questions small: decide reversible details yourself and record them as agent decisions.

## Questions become conversation (d-chat-not-cards, human 2026-10-30)
- The product and the orchestrator stop using question cards and option lists. The agent proposes a few points and one plan in the design-loop form (reason, architecture, goal, plan, non-goals), says which points it decided for the person, which point is most likely wrong, and the alternative it did not take in one sentence; the person agrees, adds or rejects. When the person answers loosely, the agent restates "I'll record it as ..." before writing the graph; the graph keeps the person's words.
- Consequences being worked out with the person: option and card fields are no longer required for human-decided questions; the interview is chat; the five keys become five kinds of things the person says; the panel only shows what waits for the person and links into the main agent's chat. Do not invest further in card formats; keep any card-related parts isolated.
- How the agent asks the person (human 2026-10-31, d-ask-three-gates, a trial the person will judge: 「都没问题。先这样改和试行吧，我看看效果」). It replaces the fixed layouts of d-chat-not-cards (bold conclusion, points, the three labelled lines 推荐/疑问/不做) and of d-plain-questions (the four lines 背景/推荐/疑问/不做 with bold key words) and the ban on listing alternatives. Three gates:
  1. Whether to ask. Ask only what is the person's: the goal, what counts as done, what is not done; spending money, actions that cannot be taken back, actions outside the project; taste and trade-offs of value. A reversible technical choice within the person's intent is decided by the agent and told in one sentence in the next batch ("我定了：X，因为 Y，不对就说"). After the person says 「这类你定」 for a kind of question, that kind is only reported, never asked; this is stored as a preference the person can revoke, and it applies to reversible matters only.
  2. When to ask. At natural stopping points (a design round finished, the morning report), at most three items per message; questions are separate from the report and come last.
  3. How to ask, by kind, no shared template: (a) confirming a recommendation: one yes-or-no question with the recommendation and its reason inside, plus one sentence of real cost only when there is one; 「可以」 accepts it. (b) choosing a direction when a real trade-off exists: two or three ways, one line each saying what the person would see, the recommended one marked. (c) asking what the person wants: offer a guess for the person to correct (「我猜你……，对吗？」). (d) judging how something looks or feels: show a mockup or sample and ask what is wrong with it.
  Record and message are separate: the graph record keeps its fields (what was asked, recommendation, reason, cost, the ways not taken, the person's words) and the harness checks the record; the text the person reads follows the shapes above and the harness enforces only hard limits: one decision per item, at most three per message, plain words (the plain-words list), a length cap. A short reply such as 「嗯」 to a matter that cannot be taken back is restated 「那我记成：……」 before it is recorded (M3, unchanged). One-page notes (d-onepage-concrete) use these shapes in their 「要你定的」 section instead of four-line items.
- Superseded layout, kept for the record (human 2026-10-30, d-chat-not-cards): a bold one-line conclusion; 2 to 4 one-line points; then exactly three labelled lines named 推荐, 疑问, 不做; one closing question; no alternatives listed. Do not build new work on it.
## Peak mode and clock facts (human and orchestrator, 2026-10-30)
- d-peak-mode: the peak reminder to the model stays. A person-chosen peak mode has three levels: 无影响 (inform only); 少做 (the default: during peak, fewer concurrent workers and no heavy work such as calibration, ablation and large reviews; necessary work continues); 不做 (no GLM work during peak, queued and resumed after). The onboarding tells the person about the mode and the default. The main agent always knows, from the harness's per-step notice, whether it is peak now and which level is set. The rules design owns the setting and its enforcement; M6 owns the reminder and the peak computation.
- Clock (orchestrator check): DSH desktop sessions with the standard preset get dsh-time-context, a user-role message with the current time to the second, the browser time zone and the elapsed time, on the first step of a turn and at most every 10 minutes (reference/dsh-desktop-0.2.1-rc.3/dsh-time-context/README.zh.md). Of the last 120 non-probe sessions, all 6 standard-preset sessions (GLM included) carry it; the 104 sessions without a preset (headless runs, sandboxes, calibration) do not. ZCode itself only gives the date. Do not rely on the model computing peak or schedule times from the clock; the harness computes them.
- Schedules: DSH already ships a schedule service (reference/dsh-desktop-0.2.1-rc.3/dsh-schedule, client page dsh-client-ui-schedule) with once, every, daily, weekly and cron triggers delivered to the original session, surviving restarts. The schedules feature reuses it for time triggers and adds event triggers itself.

## Both boards are hook-style; storage scope (human, 2026-10-30)
- d-boards-as-hooks (the person: 「循环板和规则板都借鉴hook和dsh插件的理念」, then 「同意了直接运行就行」): every entry on the rules board and the loop board has the same shape: when (an event from one shared event table, or a time trigger) + an optional filter + an action. The action is either built in (the fixed vocabulary: block, queue, record, tell the main agent, run a check) or a script the main agent has a subagent write. A script works like a hook: it receives the event as JSON on stdin; on gating events (before a tool call, before dispatch, before main advances) its exit code says allow, block (with a reason on stderr) or queue; on other events it does work and its output goes to the main agent or to the agent named by the entry. The person reads the exact script text in a four-line proposal and agrees; it then runs live at once, with no trial phase (this supersedes shadow-first for person-approved entries; CHARTER §6 is rewritten in the same batch). Agent decisions (reversible): scripts live in the repository next to the board files; the approved text is pinned by hash and a changed script does not run until the person agrees again (the board says so); gating scripts have a timeout (default 10 s) and each entry states what happens on timeout or crash (default allow, shown on the board); scripts run as separate processes in the project directory without DSH credentials; DSH plugins are not used for this (they run inside DSH with full access). Built-in rules in code stay as they are and are listed.
- d-rules-in-repo and storage scope (the person: 「一样进仓库和项目目录」, 「差不多都是进.llm，全局的似乎只剩下人设和登录信息之类的吧？」): everything that belongs to a project lives in the project: rules, switches, person-added loop entries and their scripts in the repository; runtime state (waiting tickets, hit counts, heartbeats, change journals, the violation journal, the metrics log, the main agent holder record) in the project's .llm/, not in git. User-level (global) keeps only: GLM login credentials, the ZCode device id, the persona setting, account-wide quota and usage, plugin configuration in the DSH profile; whether cross-project lessons and memory about the person stay global is being confirmed with the person.

- Hook seam (orchestrator ruling, reversible): the loop board owns the shared entry shape (the `Trigger` type in one module, the runtime event table, filters) and the script runner in one shared module that both boards import (stdin JSON envelope, separate process in the project directory, no DSH credentials or GLM keys in its environment, content-hash pin with re-approval on change, timeout and the per-entry timeout/crash behaviour, output capture and size limits). - d-alignment-rounds (human 「全都没问题」): after rules 0.9 and loop board 0.5, the orchestrator opens small alignment runs for M3, M6, M7, metrics, bootstrap, user journey and the panel, each changing only what conflicts with d-boards-as-hooks, d-rules-in-repo, d-main-agent-peak-exempt and d-memory-scope, each with one independent review; a needed large change stops and asks the person.
- d-script-timeout (human 「没问题」 to the orchestrator's plan, 2026-10-30; decided, not an open point): a gating script past its timeout (default 10 s) gets the entry's timeout behaviour (default allow) but is not killed; it keeps running up to a hard cap (proposed 10 minutes); a late block verdict is recorded and the main agent is told at once with the reason; reaching the cap is recorded as not finished and reported. Gates in front of hard-to-reverse steps (before main advances) default to block on timeout. Non-gating entries have per-entry timeouts; on timeout the result says not finished and goes to the main agent; the event stays in the inbox and the next trigger runs again. Timeouts and late blocks count in the weekly report; an entry that times out repeatedly is proposed for fixing. Owner: the loop board's runner; the rules board defines the gating meaning.
