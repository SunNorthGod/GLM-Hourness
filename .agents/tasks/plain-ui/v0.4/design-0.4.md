编排方转来的定法（不是原话）：选项卡是一张表，表头「选项 / 怎么做（加粗）/ 得到 / 代价」，至多再加一列选项之间真正不同的维度，所有行都一样的列删掉；格子用数字与具体例子，不用评价词；每个选项都有别的选项给不了的「得到」，不放凑数的选项；题目下面一行「取决于」（只有人能回答的那个关键问题），表格下面一行「是 → X；否 → Y」，这两行替换为什么与反方，对每张人定的题都这样；单向门只多一句「以后改起来很贵」的提示，并优先进入先想后看；窄面板竖排。先想后看：中性顺序，取决于先给人看，结论行与推荐折起，人选了或点「看推荐」才出现。对话里用 DSH 的问题卡（放不下表格）：按钮写字母加加粗短语，说明写得到与代价，题目说明写取决于一行，结论行只在普通问法时写在题目说明里。引擎字段由 card-fields-table 重做：选项 `label`、`gain`、`cost`，可选 `dimension`，题上 `crux`、`verdict`、`weight`；agent 自己拍板的题免 `crux`、`verdict`、`weight`。讲细点、说重点在对话里是追问，在面板上是展开与收起；选项字母处处可见，因为人用字母回答。设计文档要写明依据的学科与标准，评审按它们核对（§2.6）。每份设计的待人定事项也写成这种表（`.agents/tasks/design-context.md`），能逆转的细节由 agent 自己定并记下。访谈里的选择题（`d-interview-cards`）：主 Agent 调卡片工具（`decision_card` 的一种模式或新工具 `interview_choice`，由 M3 定），由 `src/design/cards.ts` 经 `userQuestions.ask` 按表格版规则写出（推荐在最后、不加后缀、不预选）；主 Agent 的工具面在组装时按角色去掉 `ask_user_question`；不带选项的追问也经 `userQuestions.ask`；M3 标定的模拟人在待决卡上按图上的 `recommend` 选、在访谈题上选最后一项。

## 0. 摘要

- 首页一页看完，不再分四个页签。从上到下：效果是（每个目标一句人话，和「做完 18 件，还剩 20 件」）、要你定的、现在（谁在跑）、怎么做（接下来的三件）、上次看之后（变化）。每一项都能「讲细点」展开、「说重点」收起；再讲细点就是节点页；节点页最后是底账（类型、id、状态、证据、历史、正文），追问「凭什么」时才看到。规则板与经验板是第 2 层的页，从首页页脚进入。
- 一套词：人问的三问（效果是、怎么做、为什么）是首页的节名与节点页的节名；人在面板上的动作是五键（批准、拒绝、补充、讲细点、说重点）。
- 选项卡（`d-option-card` 最终定稿）是一张表：题目一句；下面两三句背景（这道题关于哪一块、从哪来、为什么问你，新字段 `background`）；一行「取决于：<只有人能回答的关键问题>」；表头「选项 / 怎么做 / 得到 / 代价」，至多再加一列真正有差别的维度，所有行都一样的列不显示；怎么做加粗；表格下面一行结论「是 → C；否 → B · agent 推荐 C」。推荐项是最后一行，表格里不标它，推荐只在结论行末尾出现一次。单向门只多一句「以后改起来很贵」的提示。窄于表格所需宽度时每行竖排。没有默认选中。三档详略：说重点（题目、背景、取决于、选项与怎么做两列、结论行），默认（整张表），讲细点（再加题目的来由与依据）；首页上的卡从说重点起步（先想后看的那张从整张表起步），节点页从整张表起步。五键：选一个再批准、都不要（写一句理由）、补充、讲细点、说重点。对话里用 DSH 的问题卡：按钮「A · 怎么做」，说明「得到：…；代价：…」，题目说明依次写背景、取决于与结论行。对话里的卡（待决卡与访谈里的选择题）都由 harness 的 `cards.ts` 写，主 Agent 没有 DSH 自带的 `ask_user_question`（`d-interview-cards`），推荐在最后由代码保证。题里不用「验收」「标定」「门禁」「投影」「补遗」这类词，换成人话（§2.2 换词表），写法检查在题目字段里查它们。
- 先想后看（`d-inertia-breaker`）：最近 10 次由人拍板、带推荐的题里有 8 次以上选了推荐时，下一张要人拍板的题（单向门优先）换一种问法：选项按打乱后的顺序排、改用数字 1、2、3 标号，取决于照常先给人看，结论行与推荐折起来，人选了或点「看推荐」才出现，卡上一句人话说明这次为什么不一样；每步投影同时提醒 agent 先问人自己的看法、按说法确认。每次拍板记下 harness 要求的问法与人实际看到的问法，以后对照两种问法下的跟随率、拍板用时与返工。今天的图上最近 10 次里 9 次选了推荐，上线后第一张卡就会触发。
- 人话的来源：节点的 `title` 本身改写成人话，非待决的节点加一行 `why`（为什么做）；待决加两三句 `background`（前因后果），它的为什么由取决于与结论行表达；状态、先后、变化由模板从图算出，不调模型；引擎检查 agent 写的人话字段（不许里程碑编号、节点 id、代码名、引擎状态词，限长，表格格子不许评价词，题目字段里不许换词表上的词），先提醒，现有节点改完后再拒绝；图工具里提待决的说明带一道完整的人话例题。现有节点：一次改开着的那些（此刻 56 个），人看一张对照表。
- 定期的事：任务加 `repeat`（每几天一次），跑完一次可以带证据从进行中回到已批准；没到期的不算「可以开工」，`graph_open` 另列「定期的事」带到期日，agent 不会提前再跑。`repeat` 只能在提出时设，之后只有人或带原话的 agent 能改，agent 没法把一件卡住的事改成定期藏起来。
- 新手引导：两个插件各管各的引导，单装、合装都成立。编排层：新会话开场画面里、输入框正上方的「把这个工作区交给主 Agent」卡片（`/wish` 的醒目入口，带「主 Agent 用强一点的模型」的提醒）、会话开始后输入框下方常驻的「交给主 Agent」按钮、第一次打开项目图时的上手页。GLM：开场画面工作区那一行右端的「GLM · 上手」小按钮，会话里输入框下方的 GLM 按钮第一次也写「GLM · 上手」，点开是三步（登录、选模型、发一句话）。不弹窗，不自动打开侧栏，没有需要例行点掉的东西；上手页只自动出现一次，之后在首页页脚「上手说明」里再打开。
- 要人定的（§14，三组，每组先说前因后果）：P2 人话从哪来；P4 定期的事；P6 这两件事怎样算做完。原来的 P1（首页怎么组织）、P3（现有节点怎么改）、P5（`/wish` 入口放哪）、P7（先想后看什么时候触发）都能逆转，按共用清单改为 agent 定、人可推翻（§13 第 19–22 条）。

## 2. 原则、词表与依据

### 2.1 看与用

`d-ui-look-not-operate`：节点类型、连线、历史是 LLM 的工作记忆与审计底账。人「用」的只有几种时刻：回答卡片与「要你定的」、确认需求、放行方案、设规则或撤规则。其余都是「看」：现在在做什么、上次看之后变了什么、主 Agent 接下来打算做什么、离目标还差多少，都用人话。人追问「为什么」「凭什么」时才往下走。

### 2.2 一套词

宪章 §4：人问三问（为什么、怎么做、效果是），LLM 答四答（理由、架构、目标、规划），加上非目标是方案五栏（`ORCHESTRATION.md` §4.3）；人用五键回应（批准、拒绝、补充、讲细点、说重点，§4.4）；晨报按四答对账（§12）。人在访谈、放行、面板、晨报与选项卡里遇到的是同一套词：

| 人问 | 首页 | 节点页 | 选项卡 | 数据从哪来 |
| --- | --- | --- | --- | --- |
| 怎么做 | 「怎么做 · 接下来」；计划页 | 「怎么做」：定下的做法与规划 | 「怎么做」一列（加粗） | 选项的 `label`；决策与已拍板的待决；子节点按先后排 |
| 效果是 | 第一节；还剩几件 | 「效果是 · 怎样算做完」 | 「得到」「代价」两列与维度列 | 选项的 `gain`、`cost` 与维度值；目标与节点的 `acceptance`；还剩几件由模板算 |
| 为什么 | 每一项的「讲细点」 | 「为什么」 | 背景、「取决于」一行与结论行 | 节点的 `why`（待决不带）；待决的 `background`、`crux` 与 `verdict`；来源连线 |
| 不做什么（非目标） | — | 最后一节 | — | `nonGoals` |

换词表（人定 `d-plain-questions`，2026-10-29T16:14Z 带原话「B」写入；`.agents/tasks/design-context.md`「Plain words in questions」）：面板、卡片、对话与本稿 §14 里给人看的字不用左边的词，用右边的说法；图工具与主 Agent 身份文本把它原样交给模型，写法检查在待决的字段里查左边的词（§4.3 `jargon`）。

| 不说 | 说 |
| --- | --- |
| 验收、验收条件、acceptance | 怎样算做完 |
| 标定、标定集、calibration | 练习题（固定的几道小项目，系统自己做一遍、由脚本代人点卡片，用来查改动有没有把系统改坏） |
| 补遗、附录、addendum | 说出它是什么（例「M3 方案的补遗」改成「方案批了以后又定了几件事，补在一页里」） |
| 门禁、gate | 合入前的检查 |
| 投影、projection 与其他内部叫法 | 说出它是什么（例：投影是「每一步给 agent 的项目摘要」）；非用不可时当场一句话解释 |

上手页只解释面板自己不得不显示的词（主 Agent、子 agent、取决于、底账，§7.4）；人回答任何一道题都不需要先读上手页。

五键在面板上：批准、拒绝、补充用于提议与要你定的事；待决上「批准」是先选一项再批准所选，「拒绝」是「都不要」（写一句理由）；讲细点、说重点用于读。规则的增删改在规则板（§7.6）。

设计阶段的「讲细点」「说重点」会写进汇报细度画像（§4.4）；面板上的同名按钮只改这一处显示的详略，不写画像（§13 第 1 条）。

### 2.3 选项卡（`d-recommend-last`、`d-option-card`）

人定的格式（2026-10-29 最终定稿，取代 `d-counter-line` 与 `question-29` C 的短卡、完整卡两档），本稿照做：

- 题目一句话。
- 题目下面两三句背景（`background`，人在 2026-10-29 要求「带上前因后果」）：这道题关于系统的哪一块；从哪个更早的决定或发现来（说出它是什么，节点 id 只和人话标题一起出现）；为什么由你定、不由 agent 定。
- 然后一行「取决于」：只有人知道答案的那个关键问题（`crux`）。
- 一张表：表头「选项 / 怎么做 / 得到 / 代价」。怎么做是一段加粗短语（`label`，不超过 20 字）；得到是这个选项给出、别的选项给不了的东西（`gain`）；代价是它的代价（`cost`）。至多再加一列几个选项真正不同的维度（`dimension`）。所有行都一样的列删掉。格子用数字与具体例子，不用评价词；不放凑数的选项。
- 表格下面一行结论：「是 → X；否 → Y」（`verdict`）。取决于与结论行替换原来的为什么与反方，每张人定的题都这样。
- 推荐项放最后（`d-recommend-last`）。
- 单向门的题（`weight: one-way`：改目标、验收或非目标，或以后改起来很贵的方向岔路，`ORCHESTRATION.md` §2.9.1 第 1、5 类）只多一句「以后改起来很贵」的提示，并优先进入先想后看（§3.9），别的不加。
- 五键：选一个（批准）、都不要并写理由（拒绝）、补充条件（补充）、讲细点、说重点。详略分三档（§3.8.1）：说重点留题目、背景、取决于、字母与加粗短语、结论行；默认是整张表；讲细点再加题目的来由与依据。讲细点往细走一档，说重点往简走一档。首页上的卡从说重点起步，讲细点一次就是完整的表（编排方第 2 轮转述的「讲细点展开成完整表格」）；节点页上的卡从整张表起步。
- 窄面板竖排。
- 对话里用 DSH 的问题卡：按钮写字母加加粗短语，说明写得到与代价，题目说明依次写背景、取决于与结论行。
- 题里只用人话：换词表（§2.2）左边的词不出现。
- 四答（理由、架构、目标、规划）加非目标是设计放行卡的版式，事前验尸只放在那里。
- 选项字母（A、B、C）处处可见：人用字母回答。

agent 自己拍板的题没有 `background`、`crux`、`verdict`、`weight` 也行（`d-option-card`；`background` 同理），面板按有什么显示什么（§3.8.1）。

依据：Anthropic 2026-10-27 的研究里，人在两个都说得通的选项之间 86% 跟随 agent 的倾向；本图 36 张由人拍板、带推荐的待决里 30 张选了推荐项。背景让人不用翻记录就知道这道题从哪来；取决于把人的注意力放在只有他能回答的那个问题上，结论行让「答完就能选」，不必先读 agent 的理由。减负最大的一步仍是大多数事根本不送到人面前（决策分级，`ORCHESTRATION.md` §2.9.1）。选项卡字段与引擎核对已由 card-fields-table 实现（`e22282f`）；本稿负责显示（§3.8）、人话检查与 `background`（§4.2、§4.3）、先想后看（§3.9），以及对话里的卡怎样写（§3.8.4，`d-interview-cards`）。

### 2.4 规则只有人能动

`d-rules-human-only`：规则只有人能加、改、撤；agent 觉得该有一条规则时，只能经图上的待决提给人。引导里把规则写成「你定下的规矩」，入口指向规则板；agent 提的规则提议照常出现在「要你定的」里。

### 2.5 主 Agent 用强一点的模型

人的原话：「需要强提醒人类用贵一些的模型当主Agent，便宜的去干活都行」。开主 Agent 的每个地方都写这一句；主 Agent 已经开着而用的是便宜档时，流程条与首页「现在」带提醒，换了模型就消失（§7.5.5）。插件不替人选模型，所以只提醒，不切换。

## 3. 信息架构

### 3.1 选型（原 P1，改为 agent 定，§13 第 19 条）

- A 严格三问分区：首页三节「效果是」「怎么做」「为什么」，要你定的事只在顶上一个计数。词表最纯；但「为什么」默认是空的，首页常空一节；「上次看之后」没有位置；要你定的事要多点一次才看到，而它是人唯一要动手的地方。
- B 按注意力排，各节用自己的叫法（摘要、需要你、计划、最近变化）。第一眼的先后对；但面板、访谈、放行、晨报各说各的，人要学两套词。
- C 按注意力排，节名用三问；节点页统一按四答加非目标排；讲细点、说重点是唯一的展开与收起，取代按节点类型分的页签（推荐）。先后服从注意力：先说离目标多远，再给要你动手的，再给现在与接下来，最后是变化。名字服从词表：节名就是人问的问题。

本稿按 C 写。四个页签删去：页签是按节点类型分的导航，正是要下沉的东西。

### 3.4 计划（`mockup-plan.svg`）

计划是「怎么做」的全文：还剩的每一件编号，分五组。

| --- | --- | --- | --- |

| 还没细分 | 已批准、没有工作子节点、没有未完成依赖的特性 | 创建时间 | 无 |
| 定期的事 | 带 `repeat` 的任务（§6），不编号，不算进还剩几件 | 下次到期日 | 「上次 10 月 29 日 · 下次 11 月 5 日」；到期了写「到期了（11 月 5 日）」；正在跑写「在做（这一次）」；从没跑完过写「还没跑过」 |

叶子工作：类型是任务或特性，状态不是废弃、被取代，没有这样的工作子节点，在一个没关闭的目标下面。未完成的依赖：`depends` 连线指向的节点状态不是完成；祖先的依赖也算（`m3` 依赖 `split` 时，`m3-1` 也等它）。只认完成与今天的规则一致（`docs/ORCHESTRATION.md` §2.9，`src/graph/projection.ts`:197、300）；废弃、被取代的依赖仍算挡路，状态行请 agent 处理。算上祖先是对已批准规则的改动，与 `gatesOf`、`openItems`、§2.9 文档同批改（§13 第 6 条）。

几个目标：所有没关闭的目标下的件排在同一份计划里，编号连续；有两个以上目标还有剩下的件时，每个目标单独一段，段头是目标的人话标题，段内照上表分组。今天只有 `hourness` 还有剩下的件，所以没有段头。

「要等」一组的排序：先把「在做」与「可以开工」编号；「要等」的每一件取一个排序键：挡住它的节点里，在本页已编号的最小号；挡路节点本身不在本页（不是叶子的特性、等批准的提议、别的目标下的节点）时，取它子树里在本页已编号的最小号；都没有时键为无穷大。然后按依赖先后编号：组内用 Kahn 拓扑排序，一件只在挡住它的、同在这一组的件都编过号之后才编号，可以同时编号的几件里先取键小的，键相同按创建时间。所以「等第 n 件」里的 n 总比它自己的编号小（例：X 等第 1 件、Z 等 X，则 X 先编号，Z 写「等第 k 件」，k 是 X 的号）。依赖成环时，环上剩下的件按键与创建时间接在最后（§3.10）。这条规则进 `planOf` 的 L2 用例。

展开一件（讲细点）多出：为什么（`why`）；在等它的（谁的依赖里有它；在本页的写编号，不在的写人话标题）；它在等的；最后一行「讲细点 · 打开这一件」。

页头「怎么做：还剩 20 件」（`mockup-plan.svg` 是 13:04Z 的图，写的是 21 件），下面一行灰字「有依赖的按依赖排，其余按加进来的先后；agent 改了依赖，这里跟着变」。这句话告诉人顺序是算出来的，不是 agent 另写的一份计划；agent 要表达先后，就加依赖连线（写进图工具说明，§4.3）。

### 3.5 节点页（`mockup-drilldown.svg`）

目标、特性、任务用同一个排法：

- 页头：「说重点」、「在图上看」（打开整张图并对准它）。
- 祖先一行：从根目标到父节点，依次是它们的人话标题，用「 › 」隔开，整行最前面加「效果是：」三个字（表示第一段是目标）；每段照全文，放不下就换行，不截断；每段可点，点了在这一摞里打开那一件。例（`split`）：「效果是：AI 按规矩推进项目，你只管要什么和拍板 › 按项目图干活：规划、分工、检查都有规矩」。节点本身是目标时没有这一行。然后是人话标题；一行状态（同计划的状态行；任务另写今天的在场说明，例「这个会话里没有 agent 在做它」，`ui/src/graph/model.ts` 的 `presenceText`）。
- 效果是 · 怎样算做完：`acceptance` 原文。这几条要能让机器检查（宪章 §2），不改写，下面一行灰字「这几条要能让机器检查，照原文显示」。
- 怎么做：「定下的做法」列这件事下面的已拍板待决、已采纳决策，以及来源连线指向它的这两类节点；待决一行是题目，下一行「选了 B：<说法>」，决策一行是标题；右边写谁定的（你拍的、你在对话里说的、agent 定的），agent 定的点开能推翻。「规划」列子节点，排法同计划；没有子节点时写「这一件没有再拆成小步」。已关闭的待决照原文显示（§4.5 只改开着的节点），它们只在第 2 层。
- 为什么：`why`；起因（来源连线指向的节点，写成「起因：你问过「…」，定的是「…」」或「起因：「…」」）。
- 不做什么：`nonGoals`。
- 四节总在，空的写「没写」。人一眼看得出哪一栏缺了，与五栏缺栏不能放行是同一个意思。
- 还能做的：任务的运行控制（从这里开始做、暂停、按现在的「怎样算做完」重做，`ORCHESTRATION.md` §2.10）原样放在这里；首页不出现。
- 进展：批注的条数与最近一条的时间（「27 条记录，最近一条 1 小时前」），正文在底账里。
- 底账：§3.6。

其他类型：

| 类型 | 排法 |
| --- | --- |
| 待决 | 选项卡（§3.8），没拍板时带动作；拍过时卡上结论行下面标「当前：B」，可以改选（推翻）；下面是提出它的那件事 |
| 决策 | 定了什么（标题）；为什么（`why`、起因）；验证到哪（还没验证、在沙盒里验过、在真机上验过、被推翻了、被「…」取代）；它管着哪些事（来源连线指向它的节点）。设计决策（M3 的五栏落在它上面）按五栏排：理由、架构、效果是（`acceptance`）、规划（来源连线指向它的节点）、不做什么，最后一行「如果失败，最可能是因为：…」（正文里以 `如果失败：` 开头的一行，§12 M3 第 7 条）；没有这一行时不显示，不写「没写」 |

#### 3.8.1 面板上的卡

自上而下：

1. 题目：待决的 `title`，一句话，粗体。
2. 背景：`background` 原文，两三句，正文字号、次要文字色（DSH 的 secondary text token，对比度仍按正文 4.5:1），自动换行，不截断。没有 `background` 的题（agent 自己拍板的题、字段改版之前的旧待决）不显示这一段，不写「没写」。
3. 单向门的题：一行灰字「这件事以后改起来很贵，多看一眼」。双向门与没标分量的不显示。
4. 取决于：一行「取决于：<`crux`>」，正文字号。没有 `crux` 的题不显示。
5. 表格：列依次是「选项」「怎么做」「得到」「代价」，有维度时再加一列，列头是维度名。每行一个选项，按存储顺序。「选项」格是单选圈与字母；「怎么做」格是 `label`，加粗；「得到」「代价」格是 `gain`、`cost`；维度格是这一行的维度值。某一列在所有行都相同（去掉首尾空白后逐字相同）时整列不显示；「选项」「怎么做」两列总在（`label` 不会全同：引擎要求选项各不相同）；维度列不会全同（引擎的 `dimensionRefusal` 拒绝全同的维度，`src/graph/engine.ts`:326）。
6. 结论行：表格下面一行。`verdict` 是 card-fields-table 定的一行文字（「是 → C；否 → A」），面板照原文显示，只把每个 `→` 后面的选项键换成这一行的标号（§4.4 `cardView`，平时标号就是字母，所以文字不变），末尾接「 · agent 推荐 C」：「是 → C；否 → A · agent 推荐 C」。没有 `verdict` 的题只写「agent 推荐 C」；没有 `recommend` 的题不写这一行。
7. 拍板过的题：结论行下面一行「当前：B」（今天的写法），这是事实，不是推荐。
8. 动作行：「批准所选」（选中之前是禁用的样子，旁边灰字「先选一项才能批准」）、「都不要」、「补充」；右边「讲细点」或「说重点」。

样子的规则：

- 表格各行同样的字号、颜色、行高与单选圈；没有默认选中；推荐行没有颜色、粗细、标签、图标、底色。推荐只在结论行末尾出现一次，读在所有选项之后。今天 `common.tsx`:270 的「推荐」标签删去。
- 详略分三档，`cardView` 的 `detail` 是 `brief`、`default`、`full`。说重点（`brief`）：题目、背景、单向门提示、取决于、「选项」「怎么做」两列、结论行与动作行；背景、取决于与结论行留下，因为「先知道前因后果、答关键问题、再按结论选」本来就是最短的那条路。默认（`default`）：上面 1–8 条，整张表。讲细点（`full`）：再加待决的正文（为什么要问，超过十行折叠）、起因（来源连线）与提出它的那件事。讲细点往细走一档、说重点往简走一档，到头时那个按钮不显示。起步的档：首页上的卡是说重点，先想后看的那张是默认（结论行折起之后，人要看得到得到与代价才能自己判断）；节点页上的卡是默认。格子不截断：长度上限（§4.2）让它们本来就短，放不下就在格内换行。卡片自己的讲细点、说重点只改这一张。
- 字母：显示存储的选项键（`A`、`B`、`C`；键是别的写法时照写，例 `G3`）。先想后看时改用数字（§3.9.2）。
- 顺序：按存储顺序。引擎要求新提的人定待决推荐在最后（`recommend-last`，`44e8601`）；已拍板的旧待决不迁移，推荐可能在第一行，结论行照样写「agent 推荐 A」。界面不重排（先想后看除外）：重排后选项与历史里的「选了 A」对不上。
- 旧待决（字段改版之前写的，选项只有 `consequence`）：表格是「选项」「怎么做」「效果是」三列，「效果是」格是 `consequence`；没有背景与取决于；结论行只写「agent 推荐 C」；正文（包括写在正文里的取决于）在讲细点里。面板不从 `consequence` 或正文里拆字段：那是没有约定的格式，拆错了没人知道。已拍板的不迁移（card-fields-table 的评审备注）；14:20Z 时开着的 `question-37` 就是这种写法（它 15:33Z 已拍板，不再迁移）。以后仍开着的旧写法待决由编排者迁移成新字段并补背景（§15 第 10 条）；不迁移时按旧格式显示，不会出错。
- agent 自己拍板的题：没写 `background`、`crux`、`verdict` 时不显示那几行，结论行写「agent 选了 C · 可以推翻」（已拍板）或「agent 来定」（没拍板）。
- 列表行里不出现倾向：agent 自己定的事、计划、变化与首页收起的卡都不写「倾向 X」（删去 `Decisions.tsx`:29 那一段），只写「agent 来定」或「等你拍板」。

#### 3.8.2 窄面板竖排

卡片量自己内容区的宽度（`ResizeObserver`）。表格所需的最小宽度是 40 + 110 × 内容列数（px；内容列是「怎么做」「得到」「代价」与维度列里没被删掉的那些，3 列是 370，4 列是 480）；内容区窄于它时改为竖排：每个选项一块，第一行单选圈、字母与加粗的怎么做，下面一行「得到：…」，一行「代价：…」，有维度时再一行「<维度名>：<值>」；被删掉的列在竖排里也不出现。题目、背景、单向门提示、取决于、结论行与动作行不变。右侧栏最窄 320 px（WCAG 1.4.10）时竖排没有横向滚动。40 与 110 是一个常量对，取自单选圈加字母约 40 px、一个中文格子 13 px 字号下放得下 8 个字约 110 px。`gain`、`cost` 的上限是 60 个码点（`CARD_LIMITS`），写满时一格约 8 行；L4 在 320、480、宽面板三种宽度各截一张，另截一张每格都写到上限的卡（§11.3 第 1 项）。宽排里任何一格超过 5 行就算宽度不够，改为竖排：组件在宽排渲染后量各格高度（`ResizeObserver` 回调里读 `scrollHeight`），超过 5 行高时切到竖排，切换只往竖排一个方向，宽度变化后重新判断，所以不会来回抖。40、110 与 5 行按截图调。宽排与竖排读同一个视图模型（`cardView`），读屏顺序相同。

#### 3.8.3 结构与读屏

- 外层是 `<fieldset>`，`<legend>` 是题目（样子同题目）。背景、单向门提示与取决于在 `<legend>` 之后、表格之前，`<fieldset>` 以 `aria-describedby` 依次指向它们，进入这组单选时读一次。
- 宽排是原生 `<table>`：一行 `<thead>`，列头 `<th scope="col">`，每个列头带 id（`th-gain`、`th-cost`、`th-dim`）；每行第一格一个原生 `<input type="radio">`（这张题的所有单选同一个 `name`），后面是字母。每个单选的名称（`aria-labelledby`）是字母格与怎么做格；说明（`aria-describedby`）依次是列头与数据格成对的 id：`th-gain cell-A-gain th-cost cell-A-cost`，有维度时再加 `th-dim cell-A-dim`。可访问说明按 id 的顺序把各元素的文字用空格连起来，所以读作「A 全机一个规则库，单选按钮，3 之 1；得到 跨项目的规则只写一次 代价 给一个项目写的规则可能误伤另一个项目」，列头读得出来。被删掉的列在名单里也去掉。L2 钉住 id 的顺序（`cardView` 给出每行的 `describedBy` 列表）。
- 竖排是同一个 `<fieldset>` 里每个选项一个 `<label>` 块，单选与名称同上；竖排没有列头，「得到：」「代价：」写在每块的可见文字里，说明直接指向这两行。
- 用原生单选、不用 `role="radio"`：方向键在同名单选之间移动、Tab 进出整组、没有选中时 Tab 落在第一项，都由浏览器给，不用自己写。Tab 不会先落到推荐行。
- 读屏顺序：题目、背景、单向门提示、取决于、各行（存储顺序）、结论行、当前结果、动作行。结论行与推荐在所有选项之后读到。
- 对比度：单选圈、选中标记与焦点框不低于 3:1；表格线是装饰，用 DSH 的 border token（§1.3）。

#### 3.8.4 对话里的卡（DSH 的问题卡）

对话里给人的卡有两种：主 Agent 的 `decision_card`（图上的待决）与访谈里的选择题。两种都由 harness 出卡：主 Agent 调卡片工具，参数是选项（`label`、`gain`、`cost`，可选维度）、`recommend`、`background` 与 `crux`（待决卡另带 `verdict`、`weight`），文字由 M3 的卡片构造写（`src/design/cards.ts`，M3 设计 §2.1 的文件表），经 DSH 自己的问题卡（`userQuestions.ask`）出，样子由 DSH 定。访谈里的选择题走哪个工具（`decision_card` 的一种模式或新工具 `interview_choice`）由 M3 定（`d-interview-cards`）。主 Agent 的工具面在组装时按角色去掉 DSH 自带的 `ask_user_question`（做法同 `question-26` C 去掉写工具；M3 设计 §3.1.3 的组装监听器今天已经对非主 Agent 去掉两个设计工具，第 226 行）。理由：DSH 的 `ask_user_question` 参数说明要模型「If you recommend one, put it first and append "(Recommended)" to that label」（tool-ask-user lib/index.js:94、250），客户端认出这个后缀就加「推荐」标签（client-ui-user-questions client.js:672–682、1122–1125），第一项带它时在初稿里预选（684–687、788–791），人直接提交就选了推荐；身份文本里写「推荐放最后」与工具说明相反，模型照哪条做没有保证。不带选项的追问也经 `userQuestions.ask`（它支持没有选项的问题，M3 设计 R2-M1）。访谈里的选择题不是图上的待决：不进「要你定的」，不算进跟随率，也没有先想后看；写法与下面相同，推荐在最后由卡片工具核对：`recommend` 不是最后一个选项时工具以 `invalid` 拒绝，提示与引擎的 `recommend-last` 那一句相同（`src/graph/engine.ts` `questionRefusal`），模型改了再调。选拒绝而不是替模型重排：重排之后模型在文字里说的「A」与卡上的位置对不上，一个规则一个说法，模型只学一次。

DSH 的问题卡依次渲染 `header`、`question`（标题）、`detail`（Markdown）与选项按钮；单选题每个按钮左边有一个按位置编的数字（1、2、3），按钮里先是 `label`、后是 `description`，两者在同一行内换行〔实读〕（client-ui-user-questions client.js:1016–1023 标题、1078–1083 `detail`、1084–1133 选项与 `optionIndex + 1`；样式表 `_description` 无行数限制、`_optionLine` 为 `flex-wrap`）。按人定：

- `header`：待决卡「要你拍板」，访谈题「先问清楚 · 第 N 步」；`question`：题目（M3 设计 §3.5 第 4 步原来把题目放在 `header`，改为放在 `question`，标题字号才是题目）。
- `detail`：先是背景（两三句）；单向门一行「这件事以后改起来很贵，多看一眼」；一行「取决于：<crux>」；普通问法下最后一行结论「是 → C；否 → A · agent 推荐 C」（访谈题没有 `verdict` 时写「agent 推荐 C」）。DSH 把 `detail` 渲染在选项之前，所以对话里结论行在选项之前读到；这是人定的位置，对话里没有选项之后的位置可放（选项之后只有自由文字输入行，client.js:1139 起）。面板上结论行在表格之后。
- 选项按存储顺序：按钮文字「A · <label>」，说明「得到：<gain>；代价：<cost>」；有维度时说明末尾加「；<维度名>：<值>」。对话里没有讲细点可以展开，维度又是选项之间真正的差别，所以放进说明（§13 第 23 条）。不加「（推荐）」字样：DSH 会把说法里的 `(Recommended)` 解析成推荐标签并在初稿里预选（client.js:783–795、1090、1122–1125）。
- 第二问：不带选项的「都不要或补充（可以跳过）」。DSH 的单选题只交选项或文字之一，所以理由放在第二问（M3 设计 R2-M1）。
- 讲细点、说重点是人在对话里的追问，由 agent 回答。
- DSH 的按位置数字与字母并存（按钮左边「1」，文字「A · …」）。键是 A、B、C 时两者一一对应；人说「选 1」或「选 A」都行，agent 按说法确认。
- 先想后看时的写法见 §3.9.3。

宿主的两处限制〔实读〕，对话里做不到、只能记下：每个选项按钮的 `aria-label` 就是说法（client-ui-user-questions client.js:1096 `"aria-label": display.label`），说明（得到与代价）不进可访问名称，读屏只读「A · 只限速」，读屏用户要在对话里追问讲细点；说法的字重是 500（样式表 `_optionLabel`），不是加粗，人定的「怎么做加粗」在对话里只做到中等字重。两处都记进 §8，L4 第 9 项核对。

这一节是本稿对 M3 卡片构造的要求，记在 §12 M3 第 1 条。

### 3.9 先想后看（`d-inertia-breaker`）

人的原话：「如果选择推荐的次数多了，harness自动提醒llm下次换个问法用来打断这种思维惯性」。由 harness 执行，不靠 agent 自觉；跟随率高不一定是坏事（可能只是推荐得准），所以只偶尔加一点阻力，平时保持普通问法。依据：认知强制函数的研究（§2.6）显示，先让人自己判断再给 AI 的建议能减少过度依赖，代价是更慢、更费力。人定的先想后看样子（`d-option-card` 最终定稿）：中性顺序，取决于先给人看，结论行与推荐折起，人选了或点「看推荐」才出现；单向门优先。

#### 3.9.1 什么时候触发（原 P7，改为 agent 定，§13 第 22 条）

- 计数的拍板：带 `recommend` 的待决，它最后一次 `decide` 是人做的（身份 `human`，或带原话转述的 `llm`），不论 `decider` 写的是谁（agent 定的题被人改选也算：那是人看着推荐做的选择）。跟随：那次选的键等于当前的 `recommend`（拍板之后再改推荐的极少，不追溯）。取数（2026-10-29T14:20Z，最后一次拍板 13:25Z）：36 次，30 次跟随；按拍板时间最近 10 次里 9 次跟随（`question-30` 推荐 C、人选了 B）。36 次里 35 次是对话里的转述，所以转述必须算进去。
- 窗口：上一次「要求先想后看」的计数拍板之后的拍板，取最近 10 次；从没有过时取全图最近 10 次。窗口不满 10 次不触发。
- 阈值：窗口里跟随 8 次以上（含 8 次）就触发。今天 9 次，上线后第一张人定的卡就会触发。
- 复位：一次计数的拍板，只要写入之前 harness 要求的问法（`asked`，§3.9.4）是先想后看，窗口就清零，要再攒满 10 次才可能再触发。所以每 11 张人定的卡里至多 1 张先想后看。转述的拍板也清零：DSH 之外的编排方与对话里的主 Agent 都收到了先问人看法的指令（§3.9.3），面板与卡片又照样执行；人实际看到的是哪种问法另记在 `shown` 里，以后对照时只用记了 `shown` 的条目（§3.9.4）。
- 选哪一张：触发时，在开着的人定待决（已批准或进行中，决定者是人，带推荐，至少两个选项）里取单向门中最早提出的一张；没有单向门就取最早提出的一张。14:20Z 的图上开着两张：`question-37`（13:03Z 提出，正文写了「以后改起来很贵」，迁移时会标单向门）与 `question-38`（双向门，14:19Z），`question-37` 会以先想后看显示（`mockup-home.svg` 的第一张卡）；不迁移时两张都没有单向门，按最早提出取的也是 `question-37`。`mockup-cards.svg` ⑤⑥⑧ 画的是 13:04Z 时的 `question-35`，那张题后来按人的更正不做了，留作版式例子。同一时刻只有一张。新来一张更早的不可能（提出时间在后）；新来一张单向门会顶替一张双向门，原来那张回到普通显示。
- 实现：纯函数模块 `src/graph/inertia.ts`（新），宿主与客户端共用（先例 `src/graph/parse.ts`）：`followWindow(graph)` 返回窗口里的拍板与跟随数；`thinkFirstOf(graph)` 返回 `{id, followed, size} | null`；`neutralOrder(question, seed)` 返回显示顺序；`resetPointOf(graph)` 返回上一次复位点（最近一次 `asked` 为 `think-first` 的计数拍板的 `at`，没有时是空串），种子由它算（§3.9.2）。`listOpenItems` 的结果多一个 `thinkFirst`（同上，或 `null`），`graph_open` 与命令行 `open` 都带它，在 DSH 之外工作的编排方读得到；有值时结果里另带一个英文 `thinkFirstHint`，内容同 §3.9.3 的每步提醒，读到输出的人或 agent 都看得到该怎么问。

#### 3.9.2 面板上的样子

- 卡上背景下面一句灰字（`role="note"`）：「这次先不告诉你 agent 推荐哪个：最近 10 次里你有 9 次选了推荐。先按你自己的想法选；这次选项用数字标号，选完就能看到结论和推荐。」数字取自 `thinkFirstOf`。
- 背景与取决于照常显示：取决于就是要人先想的那个问题。
- 选项按 `neutralOrder` 排：以待决 id 与上一次复位点（`resetPointOf`）为种子做均匀洗牌（FNV-1a 散列加 mulberry32，Fisher–Yates）。复位点只在一次先想后看的拍板写入时变，所以卡片开着时别的题上来一次拍板（例：编排方在对话里转述了另一题）不会让这张卡当着人重排，`shownOrder` 就是人最初看到的顺序；两次复位之间顺序相同，下一次先想后看换一个顺序。洗牌可能恰好把推荐排在最后；位置因此不再带信息，这是要的效果。
- 标号改用数字 1、2、3（按显示位置），不用字母。照存储的键显示会露出推荐（推荐总在最后，键的字母常常最大）；把字母按显示位置重排又会和存储的键对不上，人在对话里说「选 B」，agent 按键写入的是另一项。数字不和任何键冲突。拍板之后卡片回到存储的顺序与字母（与历史一致），底账的历史写明当时的显示顺序。
- 结论行（含末尾的推荐）先折起来；动作行多一个「看推荐」。人选中一项或点「看推荐」后结论行出现，用显示数字：`cardView` 按 `verdictMarks` 给出的每个键的位置（§4.4）把键换成显示数字，其余文字原样，「有 → B；没有 → A」显示成「有 → 2；没有 → 1 · agent 推荐 1」；人可以改选，再点「批准所选」。回答文字里的大写字母不会被换（例「只吃 CPU → A」里的 `CPU`）：只换 `→` 后面的那一个键。单向门提示照常显示（它不带倾向）。读到的结论行里有 `→` 后面不是选项键的（旧文件或手改的文件，引擎写入时会拒绝），先想后看把结论行整行折起，人选了之后照原文显示，底账提示；只有这种情况会出现字母与数字混用。
- 说重点、讲细点照常；讲细点不展开结论行。

#### 3.9.3 对话里的样子

- `decision_card`（访谈题不参与先想后看，§3.8.4）：M3 的卡片构造调 `thinkFirstOf`；是这张题时，`detail` 是背景、上面那句说明（不提数字标号，DSH 自己按位置编号）、单向门提示与取决于，不写结论行；选项按 `neutralOrder`，按钮文字只写 `label`，不带字母（DSH 按显示位置给的 1、2、3 就是标号），说明照常是得到与代价；最后多一个按钮「先看推荐再选」。人选了它，卡片按普通样子重新问一次（存储顺序、字母、结论行），这次拍板记为先看了推荐。
- 每步投影（`src/graph/reminder.ts`）在触发期间多一行给 agent 的英文提醒，大意：「人最近 10 次里 9 次选了你的推荐。问「<题目>」时先请人回答取决于那一问、说自己的看法，再给结论与推荐；面板与卡片这次用打乱的顺序和数字标号，确认时按选项的说法，不按数字或字母。」只在触发状态或目标题变化时重注（沿用投影只在变化时注入的约定）。agent 在对话里用文字问人时，这一行是唯一的约束；它的拍板仍按上面的规则计数。
- DSH 之外的编排方（今天本仓库的编排方在 Kiro 里经命令行读图）：命令行 `open` 的输出带 `thinkFirst` 与 `thinkFirstHint`；`graph_open` 的工具说明加一句「when thinkFirst is set, ask the human for their own view on the crux before you show your verdict, and confirm the choice by its phrase」。仓库的 `AGENTS.md` 由编排者另加一句同样的话（§12，§15 第 8 条）。

#### 3.9.4 记下问法

- 引擎在每次计数的 `decide`（§3.9.1 的定义）写历史时加 `asked`：`'think-first'`（写入之前的图上 `thinkFirstOf` 指的就是这张）或 `'standard'`。这是 harness 要求的问法，由引擎自己算，调用方不能指定，agent 改不了它。
- 面板与卡片在 `decide` 请求里另带三个可选字段：`shown`（`'think-first'` 或 `'standard'`，人实际看到的问法）、`shownOrder`（显示顺序，存储的键的数组，必须是选项键的一个排列）与 `peeked`（布尔，选之前点了看推荐）。只接受身份 `human` 的请求（面板经 `/graph-apply`，卡片由 harness 以人的身份写，M3 D3）；`llm` 带它们被拒（`invalid`，`field` 为 `shown`、`shownOrder` 或 `peeked`，`hint`「只有面板与卡片能带」）。引擎原样记下：它们是当时显示的事实。转述的拍板没有 `shown`，底账写「不知道你看到的是哪种」。`asked` 与 `shown` 不一致时（面板显示之后图变了，或转述）两样都留。
- 拍板用时（从待决提出或批准到拍板）与因决定返工的次数都从历史算，不另存。对照报告进晨报（M7），不在本稿。

### 3.10 边界情况

- 空图（目录在、没有节点）：效果是一节写「这张图还是空的」，下面是 `/wish` 的一句与按钮（§7.5）；其余各节不显示。
- 目标都关了：效果是写「目标都关了」，列最近关闭的一个；计划为空。
- 节点还没有人话标题（旧节点）：照原标题显示；写法提示只在底账里。
- 依赖成环：引擎校验会报错，图照常可读；推导带访问集合，环上的节点进「要等」，状态行写「等「X」（依赖成环，让 agent 看一下）」。
- 没有现场投影（graph-panel 行没启用）：「现在」写「看不到现场（现场投影没有注册）」，其余照常。
- 先想后看的题被 agent 改了选项：种子不变，按新的选项集合重新洗牌；人已选中的那一项不在了就清空选择。
- 选项卡的字段不全（读入时的文件规则放过的旧格式，或 card-fields-table 之后又加的字段）：`cardOf` 只取认得的字段，认不出的选项按旧格式显示（§3.8.1），整张卡不因为一个字段读不出而不显示；读不出的那一项在底账里提示。
- 结论行指向不存在的键：引擎会拒绝这种写入（`questionRefusal`，`src/graph/engine.ts`:403–410）；万一读到，平时结论行照原文显示，先想后看时整行折起直到人选了（§3.9.2），底账提示。
- 表格所有内容列都被删掉（例：各项的得到、代价都相同，这本身就被引擎拒绝）：至少留「怎么做」一列，所以表格不会变空。
- 多个窗口：本机记录按图目录存，同一台机器的窗口共用；一个窗口写下的「离开面板」时间，另一个窗口下次到达时才用（§7.10）。

## 4. 人话从哪来、怎样保持真

### 4.1 选型（P2，人定，§14）

- A 渲染时调模型：每次图变就让模型写一段摘要。代价：每看一眼都花积分；要几秒；写的是上一版图；说错了没处核对；客户端调不了模型，要经宿主命令，每次在对话里留一张命令卡（审计 F-02 同类问题）。
- B 只用模板：句子全由代码拼。代价：模板不知道一件事为了什么，标题还是「M3 设计循环最小闭环」。
- C 另存一份人话标题：`title` 留给 agent，再加一个给人看的标题。代价：同一件事两个名字（宪章 §7.1 第 3 条：同一对象只用一个名字），每次提议写两遍，两边会走样。
- D 标题本身改写成人话，`why` 写为什么；状态、先后、变化由模板从图算；引擎检查 agent 写的人话字段（推荐）。只有 agent 知道一件事为了什么，这部分由它写、存在节点上、由引擎查写法；会变的部分（状态、先后、进度、谁在做）每次从图算，不会过时。

本稿按 D 写。agent 照样读得懂人话标题：投影每行带着类型与 id（`ORCHESTRATION.md` §2.5），技术细节在正文里。

### 4.2 字段

- `title`（已有）：改为写给人看的一行，规则见 §4.3。
- `why`（本稿新增）：一行人话，说这件事为什么做、做成后有什么不同。目标、特性、任务、决策、风险、规范、工具、复盘可带；待决不带：人定的格式里待决的为什么由取决于与结论行表达，`d-counter-line` 的反方与待决的 `why` 都不进引擎（`d-option-card` 最终定稿；`m3-base-card` 的 `de0ccf6` 曾给待决加 `why`，card-fields-table 重做时去掉）。非空白，一行，不超过 80 个码点。写出顺序紧跟 `title`。目标的 `why` 就是许愿访谈第 2 步的「问题」（M3 设计 §3.2 写在正文标签 `问题：` 里，改写进 `why`，§12 M3 第 3 条）。
- `background`（本稿新增，只在待决上）：两三句人话，说这道题关于系统的哪一块、从哪个更早的决定或发现来、为什么由人定。非空白，不含换行，不超过 150 个码点（`PLAIN_LIMITS.background`）。决定者是人的待决必须带：第一阶段缺了给警告，第二阶段缺了拒绝（§4.3，与人话检查同一个开关）；agent 自己拍板的题可以不带。写出顺序紧跟 `title`。选新字段而不是写进正文开头：面板不从正文拆字段（§3.8.1），而且引擎查得到它在不在。不用 `why`：`d-option-card` 定了待决不带 `why`，背景讲的是来龙去脉，不是「为什么做」。
- 选项卡字段（card-fields-table 已实现并合入，`e22282f`；本稿只读，经 `cardOf` 一处读）。按 main 上的 `src/graph/schema.ts`：选项 `DecisionOption {key, label, gain?, cost?, consequence?}`（:62–72），新写入要 `gain`、`cost`，带 `consequence` 被拒（`optionRefusal`），旧待决的 `consequence` 照读；维度 `CardDimension {name, values: Record<key, string>}`（:75–78），所有格都相同时引擎拒绝（`dimensionRefusal`）；题上 `crux?: string`、`verdict?: string`（:163–165）、`weight?: 'one-way' | 'two-way'`；人定的题必须有 `crux`、`verdict`、`weight`（`questionRefusal`）。上限 `CARD_LIMITS = { label: 20, gain: 60, cost: 60, dimensionName: 12, cell: 20, crux: 60, verdict: 120 }`（:55，码点）；面板不按这些数截断，只靠格内换行（§3.8.2 的 5 行规则与 L4 写满上限的一张卡）。
- `verdict` 是一行文字（「是 → A；否 → B」），引擎按每个 `→` 后面的键核对：键都是选项键，推荐键在其中（`verdictKeys`，`src/graph/engine.ts`:295–297，正则 `/→\s*([A-Za-z0-9][A-Za-z0-9-]{0,31})/gu`）。面板不另定格式，用同一个解析：本稿第 2 步把这个函数从 `engine.ts` 移到新的纯函数模块 `src/graph/verdict.ts`，宿主与客户端都导入，改为返回每个键的位置 `verdictMarks(verdict): readonly {key: string, index: number, length: number}[]`（`index` 是键在字符串里的 UTF-16 下标，等于 `match.index + match[0].length - key.length`），引擎改用 `verdictMarks(v).map(m => m.key)`，行为不变，现有的引擎测试照跑。规则只实现一次（`ORCHESTRATION.md` §2.9）。
- `repeat`（本稿新增，§6）。
- 历史条目的 `asked`、`shown`、`shownOrder`、`peeked`（本稿新增，§3.9.4）。
- 权限：`why`、`background` 与 `title` 同权（`ORCHESTRATION.md` §2.9 `edit` 行）：LLM 能改目标以外节点的 `why` 与待决的 `background`；目标的 `why` 只有人或带原话的 LLM 能改。`repeat` 不同，见 §6。
- 投影不带 `why` 与 `background`：投影每行只有类型、id、状态、标题（§2.5），加上它就要随每次改动重注入；`graph_show` 返回的节点带着它。

### 4.3 写法规则与引擎检查

规则写进图工具说明（`graph_propose` 的 `node.title`、`node.why`、`node.background`、`node.crux`、`node.verdict`、`node.options[].label`、`node.options[].gain`、`node.options[].cost` 与维度；`graph_edit` 的 `set.title`、`set.why`、`set.background`、`set.crux`、`set.verdict`、`set.options` 与维度）。选项卡字段本身的写法提示（推荐放最后、`verdict` 怎样写、`weight` 何时标）已由 card-fields-table 写在引擎的拒绝提示里（`src/graph/engine.ts` 的 `LABEL_HINT`、`CRUX_HINT`、`VERDICT_HINT` 等）；本稿在 `graph_propose` 的说明里加人话这一段、换词表与一道完整的例题。今天的说明只有字段格式的例子（「for example task-3」、`{"A": "1 天", "B": "3 天"}`），没有一道给人的完整题，字段名本身又是内部词（acceptance），模型写题时就照着用（`.agents/tasks/design-context.md`「Plain words in questions」的发现）。图工具说明是英文，大意：

> title、why、background、crux、verdict、选项的 label、gain、cost 与维度是给人看的：用这个项目的人听得懂的话，说做成以后有什么不同、为什么要做。不写里程碑或章节编号（M3、3.1、§4）、发现编号（V-01）、节点 id、代码名与文件名、引擎的英文状态词；这些写进 body。title 一行、不超过 40 个字；why 一句、不超过 80 个字。gain、cost 与维度值写数字和具体例子（「多评审 1 轮」「约 1,800 积分」），不写「更好」「更稳」「更简单」这类评价。先后用依赖连线表示，面板按它排「接下来」。
>
> A question the human decides opens with background: two or three plain sentences on which part of the system it concerns, which earlier decision or finding it comes from (name the thing, not the document), and why the human decides it rather than an agent; at most 150 characters. In question fields write the right-hand words, not the left: 验收 / acceptance → 怎样算做完; 标定 / calibration → 练习题（固定的几道小项目，系统自己做一遍、由脚本代人点卡片，用来查改动有没有把系统改坏）; 门禁 / gate → 合入前的检查; 补遗 / addendum, 投影 / projection and other internal labels → say what the thing is, or explain it in one sentence on the spot. The human never needs a tutorial to answer a question. A complete example:

例题（图工具说明里原样带着，取自图上真实的 `question-38`，按人话改写）：

| 字段 | 内容 |
| --- | --- |
| `title` | 子 agent 交回的活，审不审由主 Agent 定吗 |
| `background` | 这一块是子 agent 交回活之后的检查：现在每件都派一次评审，评审用的模型比干活的高一档。你问过能不能让主 Agent 自己决定审不审、审多深。这会决定哪些错可能漏过去，所以由你定。 |
| `crux` | 主 Agent 看错风险漏审了，事后才发现，你能接受吗？ |

检查是 `src/graph/plain.ts`（新，纯函数，宿主与客户端都导入）的 `plainIssues(text, field, ids)`，返回违反的规则：

| 规则 | 判据 | 例 |
| --- | --- | --- |
| `code` | `(?<![A-Za-z0-9])M\d+(\.\d+)*(?![A-Za-z0-9])`；开头 `\d+(\.\d+)+\s`，后面紧跟量词或单位（倍、%、个、次、秒、分、小时、天、周、元、积分、万、千、亿、k、K、M、G、x）时不算；`§\s?\d`；`(?<![A-Za-z0-9])[A-Z]{1,2}-\d{2}(?!\d)` | `M3 设计…`、`3.1 主 Agent…`、`（V-01）`；`1.5 倍用量…`（`risk-signing` 的标题）不算 |
| `id` | 文字里有图上已有的节点 id，这个 id 含数字或连字符，前后不紧挨 `[A-Za-z0-9-]` | `m3-1`、`question-17`、`d-dispatch`；`split`、`rules` 这类普通词不算 |
| `identifier` | 反引号；`\b[a-z0-9]+_[a-z0-9_]+\b`；`\b[a-z]+[A-Z][A-Za-z0-9]*\b`（放行词表里的词除外：macOS、iOS、iPadOS、iPhone、iPad）；`\b[\w.-]+\.(ts\|tsx\|js\|mjs\|cjs\|json\|md\|ya?ml)\b` | `graph_focus`、`graphLive`、`panel-row.ts`；`/wish`、`ZCode`、`DeepSeek`、`GLM-5.3`、`dsh-glm-zcode`、`macOS`、`iPhone` 不算 |

| `evaluative` | 只对 `gain`、`cost` 与维度值：含评价词（更好、较好、最好、更优、最优、最佳、更稳、稳妥、更简单、简单、更安全、安全、优雅、合理、理想、完美、方便、灵活、强大、高效、友好、推荐；英文 better、best、simpler、safer、cleaner、elegant、robust、recommended，单词形式） | 「更稳」「方案更简单」；「多评审 1 轮」「约 1,800 积分」不算 |

什么时候查、查谁：

- 只查 `llm` 与 `harness` 的写入：`propose` 的上述字段，`edit` 改到的上述字段；带转述的 `llm` 写入也查。人在面板上的写入不查：怎么写是人的事，面板也没有改标题的编辑器。
- 第一阶段（提醒）：违反时照常写入，结果多一个可选的 `warnings`（字符串数组，英文，写明规则、字段路径与改法）。图工具的输出 schema 加这个字段（在 rc.3 校验的子集内：`type`、`items`）。
- 第二阶段（拒绝）：引擎以 `invalid` 拒绝，`field` 是字段路径（例 `node.title`、`set.why`、`node.options[2].label`），`hint` 写规则与改法。检查排在「写后的节点与整图校验」那一步，在权限、状态转换与证据之后（`ORCHESTRATION.md` §2.9 检查顺序），只看身份的拒绝仍然先出。card-fields-table 的长度与必填核对是结构规则，从它合入起就拒绝，不分阶段。
- 两个阶段由引擎里的一个常量切换，在现有节点改完（§4.5）之后的那个提交里切。之前切，agent 改写旧标题的那一批写入本身就要先过检查，顺序会打结。
- 读入时：没关闭的节点（提议、已批准、进行中）违反规则时报一条提示（同「文件不是规范写出的样子」，只提示，不算错误），面板只在底账里显示；已关闭的节点不查，它们是历史。
- 正文改了、人话没改：`edit` 改了 `body` 或 `acceptance` 而没改 `title`、`why` 时，结果带一条提醒「标题和 why 还对吗」，从不拒绝。
- 对话里的卡：M3 的卡片工具（`decision_card` 与访谈卡片）在出卡之前对同样的字段调同一个 `plainIssues`，阶段跟引擎同一个常量：第一阶段卡照出、工具结果带 `warnings`，第二阶段工具以 `invalid` 拒绝（§12 M3 第 1 条）。访谈题不写进图，所以这是它们唯一的检查。

## 6. 定期的事（P4，人定，§14）

发现：引擎的状态转换表（`src/graph/engine.ts`:106 `TRANSITIONS`）里进行中只能去完成或废弃，定期任务在两次运行之间只能停在进行中，「正在做」显示它，其实没人在做（`reading-digest` 的批注）。

- A 每次运行建一个子任务（例 `reading-2026-11-05`），父任务不动。代价：一年多 52 个节点，图要小（宪章 §2）；父任务的状态仍然说不清。
- B 只改界面：很久没动静的进行中节点收进「挂着的」。代价：状态仍然不对，LLM 的投影与「进行中若干轮没变化就提醒」（`ORCHESTRATION.md` §2.4）照样误报。
- C 新增一种「空闲」状态。代价：状态枚举、校验、标签、筛选、投影、渲染每处都要改，为一个小需求动整套状态机。
- D 任务加 `repeat`，这类任务跑完一次可以带证据从进行中回到已批准；没到期时不算可以开工（推荐）。

D 的细则：

- 字段 `repeat`：可选，正整数，1–366，单位天，只用于任务；写出顺序在 `outputSchema` 之后。类型不对的文件按 §2.6 不进节点表，与其他已知字段一样。
- 谁能设：`propose` 时由提出者设（LLM 也行）；LLM 改自己仍为提议的节点照旧什么都能改（`src/graph/engine.ts`:587 的 `ownProposal`）；此外只有人或带原话的 LLM 能改，不进 `LLM_EDITABLE`。不带原话的 LLM 给任何已批准或进行中的任务设、改、删 `repeat` 都被拒（`forbidden`，`field` 为 `set.repeat`，`hint`「定期任务在提出时设 repeat；之后要改，请人在对话里说，带上原话」）。理由：否则 agent 能给一件卡住的进行中任务设 `repeat: 366`，再带一条通过的检查挪回已批准，它就从「在做」与还剩几件里消失一年（第 3 轮评审 P3-08）。`repeat` 的改动都列在变化里（§4.4），人看得见。
- 转换：带 `repeat` 的任务允许进行中 → 已批准，这次写入必须带至少一条通过的证据（同标完成），意思是「这一次跑完了」。不带 `repeat` 的照旧拒绝（`bad_transition`，`hint` 写「定期任务先设 repeat」）。完成仍表示不再定期做了。返工次数只数完成 → 进行中，不受影响。
- 到期：纯函数模块 `src/graph/repeat.ts`（新，宿主与客户端共用）。`lastRunOf(node)` 是最近一次进行中 → 已批准的时间；`nextDueOf(node)` 是它的本地日期加 `repeat` 天；`isDue(node, now)` 在从没跑完过、或 `now` 的本地日期不早于下次到期日时为真。本地日期按运行它的进程的时区（宿主与客户端在同一台机器上）。
- 不提前派发：`listOpenItems(graph, now)` 多一个参数 `now`（引擎用 `openEngine` 已有的 `now` 选项，`src/graph/engine.ts`:59；图工具与命令行用当前时间；面板用 `useNow` 的时间，`ui/src/graph/agents.ts`:60）。`ready` 不列带 `repeat`、还没到期的任务；结果多一个 `recurring`：每个带 `repeat`、状态为已批准或进行中的任务一项 `{ref, lastRun, nextDue, due}`。`graph_open` 的工具说明加一句：「recurring tasks are listed under recurring; run one only when due is true」。到期的任务同时出现在 `ready` 与 `recurring`（`due: true`）。
- 显示：计划「定期的事」一组；首页「怎么做」与「还剩几件」不算它；跑完一次在变化里写一行。
- 谁提醒到期：今天是 Kiro 钩子，以后是 DSH `schedule`（`ORCHESTRATION.md` §11.4、§12），不在本稿。
- 迁移：`reading-digest` 设 `repeat: 7`，带第一次运行的证据回到已批准，由编排者做（§15）。

### 7.5 `/wish` 入口（`m3-1` 验收第 4 条，原 P5，改为 agent 定，§13 第 21 条，`mockup-wish.svg`）

#### 7.5.1 选型

- A 只在新会话的开场画面里。代价：会话开始后就看不到；`m3-1` 验收要「没有开启主 Agent 的会话里」都有显眼的提示，开始后的会话不满足。
- B 输入框上方一整行提示，每个没开主 Agent 的会话都有。代价：本仓库这样直接写代码的会话也一直顶着一行；和 DSH 的待办条、目标条、排队条挤在一处。
- C 新会话开场画面里输入框正上方的卡片（醒目）、会话开始后输入框下方常驻的小按钮（不打扰）、面板「现在」一节的一句；主 Agent 会话里按钮变成「主 Agent」，点开能退出（推荐）。开场画面是人决定这次要干什么的时刻，卡片放在那里，与输入框同宽；会话开始后只留一个和 GLM 按钮一样大的按钮，不弹、不闪、没有角标，但一直在。

本稿按 C 写。第 1 轮评审指出卡片放不进 `conversation.hero.options`（那是工作区行右端的紧凑横排，client.js:17386 `.heroOptions{flex:none;…;margin-left:auto;display:flex}`），0.2 改放 `conversation.input.dock`。

#### 7.5.2 开场卡片

- 注册：与 M3 流程条同一写法（M3 设计 §3.6.4）：`ctx.slots.inject('conversation.input.dock', () => ctx.slots.register({ name: 'conversation.input.dock', id: 'hourness-wish', order: 40, label: '交给主 Agent', inject: (sessionId) => ({ sessionId }) }, WishCard))`。这个槽是列表、会话作用域（client.js:19938–19941），会话与输入都在时渲染（17846–17849、17909），在开场画面里位于工作区行与输入框之间，在普通会话里位于输入框上方。DSH 自己的待办条 order 0（19487）、目标条 10（ui-goal client.js:604–609）、排队条 20（17269），M3 流程条建议 30（§12 M3 第 5 条），卡片排在它们之后。
- 什么时候出现：组件每次渲染判断，全部成立才出现，否则返回 `null`：
  1. 会话是空白的：标准 prop `useSession` 读快照，`blank` 为真、`promptAttempted` 为假、`running` 为假（快照字段见 api-session-controller lib/types/client/sessions/session.js:832–835；DSH 的排队条就是这样收到 `useSession` 的，client.js:16954）。拿不到 `useSession` 时退到已用的 `sessions.list`：`getSnapshot().byId[sessionId].blank`（api-session-controller lib/client.js:4153–4158）。发出第一句话后两者都变为假，卡片随之消失，不依赖开场画面卸载。
  2. 这个会话不是主 Agent：会话投影 `hournessMainAgent`（M3 设计 §3.1.2）不在或为关。执行 `/wish` 不一定让会话离开空白状态，这一条保证开启后卡片消失。

#### 7.5.3 按钮做什么

- 「写一句你想做的」：输入框是空的时，把 `/wish ` 写进输入框并把焦点放进去，人接着打一句话、回车。输入框里有没发出的字时什么都不改，按钮下方提示「输入框里还有没发出的字」。写入用会话槽的标准 prop `inputActions.setDraft`，空不空用标准 hook `useInput` 读（conversation README 87 行：`ctx.uiSession.provide()` 提供输入源并给出 `inputActions` 这个标准 prop；client.js:14941–14953）。
- 拿不到 `inputActions` 或 `useInput` 时（第三方组件能否收到属〔推断〕，L4 核对）：不执行任何命令，按钮换成一行「在输入框打 /wish，后面跟一句你想做的」与「复制 /wish」，复制用 ui-primitives `writeClipboard`（`ui/src/primitives.d.ts`:52），结果写在旁边（「已复制」或「复制失败，请手动输入」）。
- 「接着推进现有项目」：直接执行 `/wish`（不带话），主 Agent 从图上的阶段接着做（M3 设计 §3.1.1 的空输入一行：先 `graph_open`，按阶段推进）。
- 都是人的点击，经 `remote.commands.execute` 或人自己回车发出，身份是人；模型发不出斜杠命令（`ORCHESTRATION.md` §2.10）。
- 面板里的同名按钮（上手页第 3 块、首页「现在」）走同一个动作；面板正文拿不到输入框时用上面的复制退路。

#### 7.5.5 模型提醒

- 主 Agent 会话里，主 Agent 最近一步的模型（`graphLive` 的模型，来自请求头）属于便宜档时，M3 的流程条末尾加黄字「现在是 GLM-5.3-Flash；主 Agent 建议换强一点的模型」与链接「这次就用它」，首页「现在」第二行同一句。换了模型，下一步请求头一变就消失。「这次就用它」只在这个会话里收起（内存里按会话记，重启后再提醒）。
- 便宜档怎么认：M7 的档位映射服务（split 0.3 §11 列为不在本次的事）落地之前，用一个常量：模型 id 转成小写，按 `[-_./:\s]` 切成词，有一个词等于 `flash`、`mini`、`lite`、`haiku`、`small`、`nano` 之一的算便宜档。按词比而不是按子串：`gemini-2.5-pro` 含子串 `mini`，按词切开是 `gemini`、`2`、`5`、`pro`，不命中。命中的例：`GLM-5.3-Flash`、`gpt-4o-mini`、`claude-3-5-haiku`、`gemini-2.0-flash-lite`；不命中：`GLM-5.3`、`gemini-2.5-pro`、`deepseek-chat`。认不出的不提醒；入口上那一句静态提醒总在。

「上次看之后」的算法是 `ui/src/graph/seen.ts` 里的纯函数状态机 `nextSeen(state, event, now)`，事件是挂载、面板变为可见、面板变为不可见：

- 面板可见：面板正文的根元素与视口相交（`IntersectionObserver`）且 `document.visibilityState` 为 `visible`。在面板里点进第 2、3 层仍是同一块面板，可见性不变。
- 一次到达：挂载时；或面板变为可见、且离上一次变为不可见已经 10 分钟以上。到达时 `since` 取本机记录（没有记录就是「最近一天」）。不到 10 分钟的来回（切到别的页签看一眼、窗口失焦一下）不算新的到达，`since` 不变。
- 一次离开：面板连续可见 5 秒以上之后变为不可见，或卸载。离开时写下当前时间，只给下一次到达用。
- 到达之后 `since` 一直留在内存里，这次停留期间新来的变化接着加进去。

## 9. 失败怎样被发现、怎样退

`d-failure-plans`：不穷举情况，确保失败看得见、有退路。评审只有三类发现挡路：验收条件没满足；会造成不可逆损失而没有预防；失败了没有途径发现或没有恢复办法。

本稿里不可逆的动作只有写图，写图都经引擎（修订号、校验、留历史），可以用 git 还原；本稿不新增别的写入。会花钱的是 agent 提前再跑定期任务，由 `ready` 的到期判断挡住（§6）。其余失败都是显示上的，下表按「哪里会坏」列发现的办法与退路。
