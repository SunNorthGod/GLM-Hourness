## 0. 摘要

- 面板只给人看，不给人操作。人要做的事只有一件：在主 Agent 的对话里回话。面板上没有批准、拒绝、选项、运行控制或改规则的按钮；「需要你」一节列出在等人回话的事，每件下面一个链接，点了打开主 Agent 的对话。
- 首页一页看完，没有页签。从上到下：效果是（每个目标一句人话加「做完 18 件，还剩 20 件」）、需要你、现在（谁在跑、此刻是不是 GLM 高峰与高峰模式）、怎么做（接下来的三件）、上次看之后（变化）。每一项都能「讲细点」展开、「说重点」收起，这两个按钮只改显示，不写任何东西；节点页最后是底账。
- 「需要你」列三种事：图上在等人回话的待决（提议式的显示题目与背景、推荐、疑问、不做四行，各自成段，每行重点几个字加粗；旧的选项式只显示题目与背景）；主 Agent 在对话里交给人、人还没回话的确认需求与放行方案（从主 Agent 那个会话的现场投影读出）；等人批准的提议。没有选项、没有字母、没有推荐标签。
- 第 2 层有两块板：规则板（你定下的规矩、插件带来的默认规则与高峰模式、合入前的检查清单与必须全审清单这两道门、写在代码里的规则）与循环板（改完文件就跑的检查器、晨报、周报、夜间巡检、合入后的完整检查等）。插件带来的条目标「<插件>带来的 · 只能看」；人能改的地方（高峰模式的档位、人自己加的条目）写成一句「要改：跟主 Agent 说……，或在输入框打 ……」。两块板的内容归规则板与循环板设计，本稿定入口、版面约定与只读。经验板照旧留位置。
- 人话的来源：节点的 `title` 改写成人话，非待决的节点加一行 `why`；人定的待决带一行 `background`（不超过 60 个码点，不算加粗记号），这是三份设计共用的字段与上限（P4-01）；状态、先后、变化由模板从图算。引擎查 agent 写的人话字段（编号、节点 id、代码名、引擎状态词、换词表上的词、长度、人定的题缺背景），先警告；现有节点改完、M3 与规则板都按这个字段写之后才切到拒绝。换词表只在 M3 的 `src/graph/plain-question.ts` 定义一次。
- 跟随率与先想后看取消。人在对话里的回话由 M3 的 `record_human_answer` 按三种固定记号写进图（同意、补充、否掉）；记号只在 `src/shared/answer-marks.ts` 定义一次，面板的变化一节与指标流水都读它。
- 反复做的事归循环板（原 P4 由此回答）；本稿不再给任务加 `repeat`，计划里没有「定期」一组。
- 新手引导：两个插件各管各的。GLM：开场画面工作区那一行右端「GLM · 上手」与会话里的 GLM 按钮，三步（登录、选模型、发一句话），与 0.4 相同。编排层：第一次打开项目图时的上手页（六块：一眼看懂、你要做的只有回话、让主 Agent 接手、规则板与高峰模式、循环板、去哪看进度），高峰模式一块写明三档、默认少做、少做是什么、在哪里改；M3 开场卡片底部「第一次用？看看项目图怎么用」一行（本稿导出组件，M3 的卡片放进去）；没有项目图的工作区的开场卡片（本稿自己登记，`hourness-nograph`）。`/wish` 入口的卡片、按钮、主 Agent 按钮与模型提醒全部归 M3 附录 §2.6。
- 要人定的只剩一件（§13）：这两件事的「怎样算做完」写进节点前，你要不要先看人话版。原来的 P2 由 `m8-plain-language` 节点正文回答（「图上写给人看的文字要有人话的一层，写法规则进图工具的说明」），P4 由循环板回答。

## 1. 需求

### 1.1 现状

- 面板按节点类型分四个页签（需要你、agent 定的、正在做、图），人第一眼看到路线编号与内部叫法（「M3 设计循环最小闭环」）。开着的 80 个节点里大部分标题以路线编号开头。
- 「需要你」把待决画成选项卡：推荐项带蓝色「推荐」标签（`ui/src/graph/common.tsx`:270），「agent 定的」写「倾向 A …」（`ui/src/graph/Decisions.tsx`:29），面板上可以点选、批准、拒绝（`ui/src/graph/apply.ts`:20 经 `/graph-apply`）。任务节点页有运行控制（`ui/src/graph/NodeDetail.tsx`:52 `RunControls`，经 `/graph-run`）。`d-chat-not-cards` 之后这些都不该在面板上。
- M3 附录 0.3 把问人改成聊天：主 Agent 用 `propose_to_human` 交给人四行，人回话之后用 `record_human_answer` 带原话记进图；要人定的事是图上的「提议式待决」（没有选项，存背景、推荐、疑问、不做四个字段与结论）。M3 第 6 步只给面板加了最小的显示（`common.tsx`、`model.ts`、`Decisions.tsx`），整体改版留给本稿。
- 定期的事（`reading-digest`）在两次运行之间只能停在进行中（`src/graph/engine.ts`:110 `TRANSITIONS`）；这件事由循环板解决。
- 装上插件之后没有任何引导。没有项目图的工作区只有一句「建一个空目录就是一张空图」。

### 1.2 功能需求

A（`m8-plain-language`）

- A1 首页一页：先说离目标还差多少，再给需要你回话的事，再给现在谁在做什么、接下来做什么，最后给上次看之后的变化；细节点了才展开。
- A2 面向人的文字不出现里程碑编号、节点 id、节点类型名、引擎状态词与代码名；这些在底账里，追问时看得到。
- A3 人话怎样产生、怎样检查、怎样跟着图变；现有节点怎样换成人话。问人的话的背景字段与上限由本稿定，M3 与规则板照用。
- A4 面板只看不操作：不写图、不写规则、不跑命令；「需要你」列出在等人回话的事，点开到主 Agent 的对话。
- A5 需要人回话的事按聊天的样子显示：题目一段，背景、推荐、疑问、不做各一段，每段重点几个字加粗；不显示选项、字母与推荐标签。
- A6 一个项目只有一个主 Agent：面板认得出它在哪个对话，跳得过去；不在时说怎样开。
- A7 两块板是第 2 层的页，项目里生效的规矩都在其中之一上看得到；插件带来的条目只能看；人能改的地方写明怎样改。
- A8 变化一节写出人在对话里同意、补充、否掉了什么；三种说法的认法只定义一次，指标流水共用。
- A9 现有视图（需要你、agent 定的、正在做、现场、图、节点详情）各有去向。

B（`onboarding`）

- B1 两个插件装上后的第一次：先看到什么；GLM 怎么登录；项目面板是干什么的；人要做的只有在主 Agent 的对话里回话；规则板、循环板在哪；高峰模式（三档、默认少做、在哪里改）；去哪看进度。
- B2 没有项目图的工作区是什么样。
- B3 以后再来：不唠叨，能重新打开引导。
- B4 单装 `dsh-glm-zcode`、单装 `dsh-hourness`、两个都装，三种都成立；不增加例行点击；可以跳过。
- B5 开主 Agent 的地方提醒「主 Agent 用强一点的模型」；子 agent 的模型由主 Agent 派活时选，不提醒人。`/wish` 入口本身归 M3，本稿只给引导里的那几处。
- B6 上手页可以指向主 Agent 人设的设置位（`m3-main-persona`）；设置位本身不在这一稿。

### 1.3 非功能

依据与条款见 §3.4。

- 风格贴近 DSH 原生：ui-primitives 组件与 `--dsw-*` 主题 token，深浅主题都可读；正文与背景对比度不低于 4.5:1；焦点框与链接的非文字部分不低于 3:1（WCAG 2.2 1.4.11）；框线是装饰，用 DSH 的 border token。颜色从不单独表达意思。动效只用 CSS，`prefers-reduced-motion` 下关闭。右侧栏最窄 320 px 时文字换行、没有横向滚动。
- 键盘：讲细点、说重点、链接与按钮都在 Tab 顺序里；Esc 等于说重点；打开节点页后焦点落在「说重点」，关闭后回到打开它的元素（沿用 `ui/src/graph/Panel.tsx` 的做法）；焦点框可见，不被吸顶的页头盖住；可点区域不小于 24×24 px。
- 第一眼的量：首页每节至多 5 行；「需要你」在首页至多 3 件（与 M3 一条回复至多三件、`d-design-onepage` 一次至多三题一致）。
- 模板在每次图快照时重算，按图修订号缓存；177 个节点，开销可以忽略。
- 不新增依赖；不新增 Remote 服务、waterfall 或会话事件（第三方做不到，`docs/ORCHESTRATION.md` §13）。新增两个会话投影值（`graphLive.awaiting` 与 `hournessProject`，§4.9），都由已有的投影机制给出。
- 面板只读：不执行任何命令，不写任何文件；看过没有、收起了什么这类界面状态存在本机 `localStorage`，不进图、不进 git。

### 1.4 验收（建议写进两个节点，§13）

`m8-plain-language`：

1. 打开项目图，首页从上到下依次是效果是、需要你、现在、怎么做、上次看之后；没有页签。1280×800 的窗口、右侧栏默认宽度下，不滚动就看得到效果是一节与需要你第一件的题目和背景一行。L4 截图核对。
2. 首页、计划、变化三段里模板自己写的文字（嵌进句子的标题除外）没有 `M\d` 编号、`\d+\.\d+ ` 开头的编号、图上已有的节点 id、节点类型名（「特性」「任务」「待决」「规范」「复盘」「节点」与英文类型名）与英文状态词。L2：模板以占位符代替嵌入的标题（§5.4 `quote`），对三段的全部文字跑 `plainIssues(text, 'generated', ids)`，结果为空；第 2 步用造的图，第 3 步改写现有节点的那个提交把改写后的真实图快照加进同一个测试。
3. 「怎么做」按依赖排：自己或祖先有未完成（状态不是完成）的依赖的件排在「要等」并写明等谁；`graph_open` 的「可以开工」与 `graph_show` 的依赖门用同一个口径。L2。
4. 「上次看之后」只列人上次离开面板之后的变化，人自己的操作（身份 human）不列；第一次打开时列最近一天；在面板里点进第 2、3 层再回来，列表不变。L2（状态机与模板）与 L4。
5. 每件事都能「讲细点」展开、「说重点」收起，两者不写任何东西；节点页最后的底账有类型、状态、id、证据、历史与正文。L4。

## 3. 原则与词表

### 3.1 看，不操作

`d-ui-look-not-operate` 与 `d-chat-not-cards` 第四点：节点类型、连线、历史是 LLM 的工作记忆与审计底账；人在面板上只看。现在在做什么、上次看之后变了什么、主 Agent 接下来打算做什么、离目标还差多少，都用人话。人要定的事在主 Agent 的对话里定：主 Agent 把一件事写成四行交给人，人用自己的话回，主 Agent 复述、带原话记进图（M3 附录 §3）。

面板因此没有任何写入：不经 `/graph-apply` 写图，不经 `/graph-run` 开停任务，不经 `/rules-apply` 改规则，不往对话里发东西。人要做这些事有两条路，都是人自己的动作：在主 Agent 的对话里说一句（主 Agent 带原话写，harness 核对原话，M3 附录 §3.6、§3.8）；或在输入框打人的命令（`/graph-run`、`/rules`、`/wish`，模型发不出斜杠命令，`docs/ORCHESTRATION.md` §2.10）。面板在每个人可能想动手的地方写明这两条路中的一条。

保留的两类点击都不写东西：展开与收起（讲细点、说重点）；导航（打开节点页、打开第 2 层的板、打开主 Agent 的对话、打开整张图）。上手页的「复制 /wish」只写剪贴板。

### 3.2 一套词

宪章 §4：人问三问（为什么、怎么做、效果是），LLM 答四答，加上非目标是方案五栏（`docs/ORCHESTRATION.md` §4.3）；问人的四行（背景、推荐、疑问、不做）是 `d-chat-not-cards` 定的。面板、上手页、对话与晨报用同一套词：

| 词 | 首页 | 节点页 | 数据从哪来 |
| --- | --- | --- | --- |
| 效果是 | 第一节；还剩几件 | 「效果是 · 怎样算做完」 | 目标与节点的 `acceptance`；还剩几件由模板算 |
| 需要你 | 第二节 | 待决的节点页 | 人定的待决、主 Agent 会话的 `graphLive.awaiting`、等人批准的提议 |
| 怎么做 | 「怎么做 · 接下来」；计划页 | 「怎么做」：定下的做法与规划 | 决策与已拍板的待决；子节点按依赖排 |
| 为什么 | 每一项的「讲细点」 | 「为什么」 | 节点的 `why`；目标没有 `why` 时取正文的「问题：」一节；来源连线 |
| 不做什么 | — | 最后一节 | `nonGoals` |
| 背景、推荐、疑问、不做 | 「需要你」里的每件 | 待决的节点页 | 提议式待决的 `background`、`proposal`、`doubt`、`notTaken`（M3 附录 §3.3） |

五键（批准、拒绝、补充、讲细点、说重点）按 `d-chat-not-cards` 第三点变成人在对话里会说的五种话（M3 附录 §3.7）。面板上不做批准、拒绝、补充。「讲细点」「说重点」两个字仍用作面板的展开与收起按钮：人在对话里说这两句也是要多讲或少讲，同一个意思用同一个词；它们只改这一处的详略，不写汇报细度画像（§12 第 1 条）。

### 3.3 换词表

`d-plain-questions`：给人看的字不用人没学过的词。换词表只在 M3 的 `src/graph/plain-question.ts` 定义一次（`PLAIN_WORDS`，M3 附录 §2.8），本稿的写法检查调它的 `plainWordsIn`，不另写一份（P4-03）。五项：

| 不说 | 说 |
| --- | --- |
| 验收、acceptance | 怎样算做完（目标一级说「怎样算做成」） |
| 标定、calibration | 练习题（固定的几道小项目，系统自己做一遍，用来查改动有没有把系统改坏） |
| 门禁、gate | 合入前的检查 |
| 投影、projection | 每一步给 agent 的项目摘要 |
| 补遗、附录、addendum | 说清它是什么 |

节点页的节名「效果是 · 怎样算做完」对任务与特性照写；目标的节点页写「效果是 · 怎样算做成」，与 M3 需求卡的标签「成功（怎样算做成）」一致（P4-03 的目标一级说法）。

上手页只解释面板自己不得不显示的三个词：主 Agent、子 agent、底账（§6.4）。0.4 的第四个词「取决于」随选项卡一起不再出现在面板上。

| 决策与人因 | 自动化偏差（Parasuraman、Manzey 2010）；对一个具体方案凭直觉挑错比在几个选项间权衡省力（`d-chat-not-cards` 17:16Z 编排方的更正） | 不给眼睛跳到推荐的捷径；一个方案、写明最没把握的一处 | 面板不显示选项与推荐标签，四行里的「疑问」原样显示（§4.3） |
| 打扰 | 平静技术（Weiser、Brown 1996） | 信息待在边缘，需要时才到中心 | 开场卡片只在开场画面里；高峰一行只在高峰时（§4.2、§6） |
| 写作 | ISO 24495-1:2023 简明语言 | 读者能找到、读懂、用上；用读者认识的词，必要的术语当场解释 | 人话字段与写法检查（§5.2、§5.3）；模板句子（§5.4） |
| 本项目 | 宪章 §4、§7.1（同一对象一个名字）；`docs/ORCHESTRATION.md` §2.9.1（决策分级） | — | §3.2、§5.1 |

### 4.3 需要你

纯函数 `needsOf(graph, awaiting, now)`（`src/graph/plain-view.ts`，§5.4）给出列表，三种条目按「从什么时候起等人」从早到晚排：

| 种类 | 哪些 | 从什么时候起 | 显示 |
| --- | --- | --- | --- |
| 待决 | 类型待决、状态已批准或进行中、决定者不是 agent | 最后一条 `propose` 或 `edit` 历史的时间（人要回的是最新那一版） | 提议式（有 `proposal`、`doubt`、`notTaken`，M3 附录 §3.3）：题目一段，背景、推荐、疑问、不做四行各一段；选项式（有 `options`，字段改版前后的旧写法）：题目、有 `background` 时的背景一行，与一行「这道题还按旧的选项写着，在主 Agent 的对话里回话就行」 |
| 确认与放行 | 主 Agent 那个会话的 `graphLive.awaiting` 里 `kind` 为 `confirm` 或 `release` 的条目（§4.9） | 那次 `propose_to_human` 返回的时间 | 一行「主 Agent 在对话里等你确认需求」或「等你放行方案」，下面是那次交给人的题目与四行 |
| 等批准的提议 | 状态为提议、不是待决、父节点不是提议（只列最上面那一个，写「连同下面 N 件」）、且不在一个有效阶段为 `wish`、`interview` 或 `design` 的目标的子树里（目标本身在这三个阶段时也不列） | `propose` 的时间 | 「等你批准：<标题>」，下面一行 `why`（没有时不显示）。它的 `why` 就是它的背景（P4-08） |

几条细则：

- 去重：`awaiting` 里 `kind` 为 `question` 的条目不列，图上那张待决已经在第一种里。
- 访谈与设计中的目标子树不列提议：M3 的访谈在图上提议目标与需求，设计阶段提议决策与任务，它们都随「确认需求」「放行方案」一次定下（M3 附录 §3.5 的放行集合）。在这期间把每个提议都列成「等你批准」会把同一件事拆成几十条，也会让人以为要逐个批。阶段用 M3 已在 main 上的 `goalOf` 与 `effectiveStage`（`src/graph/stage.ts`:97、90）。
- 四行的样子按人定（`d-chat-not-cards` 17:27Z）：题目单独一段，粗体；背景、推荐、疑问、不做四行各自成段，标签「背景：」不加粗，后面的字照原文，`**…**` 里的字加粗（用 M3 的 `splitBold`，`src/graph/proposal.ts`）。行内找不到加粗记号时照原文显示。结构是 `<article>` 里一个 `<h3>`（题目）与四个 `<p>`，加粗用 `<strong>`，读屏按顺序读出标签与内容。
- 每件下面一行去主 Agent 的对话（§4.9）；首页至多 3 件，其余「还有 N 件 · 讲细点」打开第 2 层的「需要你」全部列表（同样的条目，不截）。
- 没有任何按钮写东西：没有选项、字母、推荐标签、批准、拒绝、补充。人回话之后，提议式待决由 `record_human_answer` 记成做完或留着（人补充、否掉时主 Agent 改方案再提，M3 附录 §3.5），列表跟着图变；确认与放行在人发出下一条消息时从 `awaiting` 里消失（§4.9）。
- 首页上每件从说重点起步：题目与背景一行，下面「讲细点」展开推荐、疑问、不做三行。第一件例外，四行都显示：人一眼要看到第一件的方案。第 2 层的全部列表都是四行。这样首页「需要你」在 3 件时约 16 行，第一屏放得下效果是与第一件（验收第 1 条）。

### 4.4 计划（`mockup-plan.svg`）

计划是「怎么做」的全文：还剩的每一件编号，分四组。

| 组 | 哪些 | 组内顺序 | 状态行 |
| --- | --- | --- | --- |
| 在做 | 进行中的叶子工作 | 主 Agent 的焦点所在的一件在前，其余按最近一条历史从新到旧 | 「在做 · N 小时前有进展」；主 Agent 的焦点在它上面时「在做 · 主 Agent 在这里」；有未完成的依赖时「在做 · 还要等「X」做完」（X 在本页有编号时写「第 n 件」）；三天以上没有任何历史时「在做 · 3 天没有动静」 |
| 可以开工 | 已批准的叶子任务，自己和祖先的依赖都已完成 | 创建时间 | 「可以开工」 |
| 要等别的先做完 | 已批准的叶子工作，自己或祖先有未完成的依赖 | 见下面的排序规则 | 挡路的都在本页有编号时「等第 1 件」「等第 1、12 件」；有不在本页的时「等「X」」，不止一件时「等「X」等 N 件」；X 不做了或被取代时「等「X」（它不做了，主 Agent 会处理）」 |
| 还没细分 | 已批准、没有工作子节点、没有未完成依赖的特性 | 创建时间 | 无 |

叶子工作：类型是任务或特性，状态不是废弃、被取代，没有这样的工作子节点，在一个没关闭的目标下面。未完成的依赖：`depends` 连线指向的节点状态不是完成；祖先的依赖也算（`m3` 依赖 `split` 时，`m3-1` 也等它）。只认完成与今天的规则一致（`src/graph/projection.ts`:197、300）；废弃、被取代的依赖仍算挡路。算上祖先是对已批准规则的改动，与 `gatesOf`、`listOpenItems`、`docs/ORCHESTRATION.md` §2.9 同批改（§12 第 6 条）。

反复做的事（每周读文章、晨报、巡检）不在计划里，在循环板上（`schedules`）；计划页底部一行灰字「到点或碰到某件事就做的例行活在循环板上 ›」（循环板装上时可点）。

几个目标：所有没关闭的目标下的件排在同一份计划里，编号连续；有两个以上目标还有剩下的件时，每个目标单独一段，段头是目标的人话标题。

「要等」一组的排序（0.4 第 3 轮 P3-11 定的规则，不变）：先把「在做」与「可以开工」编号；「要等」的每一件取一个排序键：挡住它的节点里在本页已编号的最小号；挡路节点本身不在本页时取它子树里在本页已编号的最小号；都没有时键为无穷大。组内用 Kahn 拓扑排序编号，一件只在挡住它的、同在这一组的件都编过号之后才编号，可以同时编号的几件里先取键小的，键相同按创建时间。依赖成环时，环上剩下的件按键与创建时间接在最后（§4.10）。

展开一件（讲细点）多出：为什么；在等它的（在本页的写编号，不在的写人话标题）；它在等的；最后一行「讲细点 · 打开这一件」。

页头「怎么做：还剩 20 件」，下面一行灰字「有依赖的按依赖排，其余按加进来的先后；agent 改了依赖，这里跟着变」。

### 4.5 节点页（`mockup-drilldown.svg`）

目标、特性、任务用同一个排法：

- 页头：「说重点」、「在图上看」（打开整张图并对准它）。
- 祖先一行：「效果是：」加从根目标到父节点的人话标题，用「 › 」隔开，每段可点，放不下就换行，不截断。节点本身是目标时没有这一行。然后是人话标题；一行状态（同计划的状态行；任务另写今天的在场说明，`ui/src/graph/model.ts` 的 `presenceText`）。
- 效果是 · 怎样算做完（目标写「怎样算做成」）：`acceptance` 原文，下面一行灰字「这几条要能让机器检查，照原文显示」。
- 怎么做：「定下的做法」列这件事下面已拍板的待决、已采纳的决策，以及来源连线指向它的这两类节点；提议式待决一行是题目，下一行「定了：<结论>」；选项式待决一行是题目，下一行「选了 B「说法」」；决策一行是标题；右边写谁定的（你在对话里说的、你在面板上拍的、agent 定的）。agent 定的写「要推翻：跟主 Agent 说」。「规划」列子节点，排法同计划；没有子节点时写「这一件没有再拆成小步」。
- 为什么：`why`；目标没有 `why` 时取正文里「问题：」一节（M3 访谈第 2 步写在那里，用 `src/graph/stage.ts`:61 的 `labeledSections` 读，与需求卡门禁同一个解析，不另写）；起因（来源连线指向的节点，「起因：你问过「…」，定的是「…」」）。
- 不做什么：`nonGoals`。
- 四节总在，空的写「没写」。
- 任务的运行：一行状态（在跑、停着、没开始），下面一行灰字「要停或重做：跟主 Agent 说，或在输入框打 /graph-run stop <id>、/graph-run redo <id>」（`/graph-run` 的输入是 `start|stop|redo <id>`，`src/graph/run.ts`:13 的 `RUN_ACTIONS`，`src/graph/panel-row.ts`:16–18）。今天的 `RunControls` 按钮删去（§12 第 5 条）。
- 进展：批注的条数与最近一条的时间，正文在底账里。
- 底账：§4.6。

待决的节点页：

- 提议式：题目、四行（同 §4.3）；拍过板时下面是「定了：<结论>」、「你说的：「<原话>」」（最后一次 `decide` 的 `relay`）与「主 Agent 记成：<结论>」（同一条，`conclusion` 就是主 Agent 复述的那一句，M3 附录 §3.5 `recordedAs`）；人补充或否掉过时列出每次的批注（「你在对话里补充：「…」」）；没拍板时下面一行去主 Agent 的对话（§4.9）。
- 选项式：题目、背景（有时）、「选了 B「说法」」或「agent 来定」；选项、推荐与卡片字段只在底账里照原文列出，不画表、不标推荐。
- 下面是提出它的那件事。

决策：定了什么；为什么；验证到哪；它管着哪些事；设计决策按五栏排（理由、架构、效果是、规划、不做什么），正文里以 `如果失败：` 开头的一行显示成「如果失败，最可能是因为：…」（M3 附录第 9 步的正文标签），没有时不显示。风险、规范、工具、复盘：标题、`why`、一行状态，其余在底账。

### 4.6 底账

节点页最后一节，默认收起，标题「底账 · agent 的工作记录，追问「凭什么」时看」。展开后是今天节点详情里的全部技术内容：类型、状态（带起始日期）、id（等宽字体）、阶段、验证、派发属性、分量、依赖与来源（id 加状态，可点）、证据、正文（Markdown，超过十行折叠）、历史（今天的 `historyText`，含「你（经对话）」与原话引用）、批注（只读，没有输入框：给 agent 留话就在主 Agent 的对话里说）、选项式待决的选项与卡片字段原文。读入时的写法提示（§5.3）也在这里。

### 4.7 两块板与经验板（`mockup-boards.svg`）

位置：规则板、循环板与经验板都是第 2 层的一页，从首页页脚、上手页第 4、5 块与首页「现在」里那块板的一行进入。四个页签删去后没有「第五个视图」，规则设计 §9.1 的最小版按这里实现。

板块登记表：编排层客户端包里的模块 `ui/src/graph/boards.ts`（包内模块，不是宿主接口）：

```ts
interface Board {
  readonly id: 'rules' | 'loops' | 'lessons'
  readonly label: string                        // 页脚上的名字：规则板、循环板、经验
  available(sessionId: string): boolean         // 板块的数据在不在（规则板看 hournessRules 投影，循环板与经验板由各自的设计定）
  homeLine?(sessionId: string): string | null   // 首页「现在」的一行，至多 60 个码点；没有就不显示
  guideLine?(sessionId: string): string | null  // 上手页那一块的一行此刻状态（规则板：高峰模式此刻的档位）
  readonly Page: ComponentType<{ sessionId: string }>
}
```

面板只读这张表：页脚与上手页只列 `available` 为真的板块；打开就是把 `Page` 压进第 2 层的那一摞，外面包一个错误边界（一块板出错只影响它自己那一页）。各块板的实现往表里登记自己。

各板页面的共同约定（本稿定，规则板、循环板、经验板的设计照做；`d-defaults-readonly`、`d-rules-visible`、`d-ui-look-not-operate`）：

- 页头：板名与一句它管什么。规则板：「规则板 · 一件事要发生时，让不让做」；循环板：「循环板 · 到点了或碰到某件事，就去做一件事」（两块板的分界取 `schedules` 2026-10-29T17:59Z 的批注）。
- 每个条目一行人话标题，下面一行它此刻的样子（规则：条件此刻成不成立、最近 7 天挡了几次；循环：上次与下次、上次的结果），再一行灰字写它从哪来：「<插件名>带来的 · 只能看」（插件名用插件管理器里显示的名字，例「项目编排」「GLM 通道」）、「项目图上的规范「<标题>」· 你批过的」或「你定的」。
- 页面没有写入控件：没有开关、单选、删除、放行、取消、新建按钮。插件带来的条目不能改、停、删（`d-defaults-readonly`），所以下面没有任何改法；人能改的条目（你定的、高峰模式的档位、规范节点里的清单）下面一行「要改：跟主 Agent 说「……」，或在输入框打 ……」，括号里是一句能直接照说的话，命令是那块板已有的人的命令（规则板 `/rules`，规则设计 §9.2）；没有命令的只写跟主 Agent 说。
- 规则板分组的次序：会挡住动作的门（合入前的检查清单 `norm-merge-gate`、必须全审清单 `norm-review-floor`，各自一组，列出规范节点 `acceptance` 的每一条原文）；默认规则（GLM 高峰时段按全价计积分）与高峰模式（此刻的档位、谁在什么时候选的、三档各半句后果、要改的那一行）；你定的规则；写在代码里的规则（只能看）；在等的工作；提议与恢复。具体字句、读法与每组的内容归规则设计。
- 循环板分组的次序：碰到某件事就做的（改完文件就跑的检查器、合入主干之后跑一遍完整检查等）；到点做的（晨报、周报、夜间巡检）；本项目加的（例每周读文章）。具体条目、触发与结果归循环板设计。
- 板上的字照 §3.3 的换词表与规则设计 §9.1 末段的换词（「门禁」写「合入前的检查」，「影子」写「试运行」等），目录 id 只作小字跟在人话后面。

高峰模式在面板上只显示、不选：档位是人选的设置（`d-defaults-readonly` 的例外，「档位当然能选」），选的动作是人在对话里说一句（主 Agent 经 `rules_propose` 提出、人同意后记下，规则设计 §3.6）或在输入框打 `/rules peak 无影响|少做|不做`（规则设计 §9.2）。规则设计 0.5 §9.1 页面上的三个单选改为显示加改法一行（§11 规则第 1 条）。理由：面板只看不操作是人对 `d-chat-not-cards` 第四点说的「没问题」；三个单选是面板上唯一会写东西的控件，留着它就要给面板留一条写入路径。代价：改档位从一次点击变成说一句话或打一条命令。

经验板（`lessons`，M5）：给人看本项目踩过的坑与解法；人删条目也在对话里说（M5 定）。本稿只留位置。

### 4.9 跳到主 Agent 的对话

一个项目只有一个主 Agent（`d-one-main-agent`）。M3 在用户级目录记下它是哪个会话（持有者记录 `<userHome>/main-agent/<sha256(projectKey) 前 16 位>.json`，`{version: 1, sessionId, graphDir, since, commandId}`，M3 附录 §2.4），客户端不知道这个路径。做法：

1. 宿主侧：图面板行（`src/graph/panel-row.ts`，已经注册 `graphLive` 投影，:122–130）多注册一个会话投影 `hournessProject`。它的 `init(header)` 用图行服务的 `dirFor(header.cwd)` 取这个会话的图目录，再用 M3 导出的 `holderFileOf(userHome, dir)` 算出持有者记录的绝对路径；`apply` 不看事件（返回原状态）。值是 `{holderFile: string}`，会话没有图目录或 M3 的模块不在时是 `{holderFile: null, reason: string}`。投影单元的 `init` 只拿到会话头与继承的事件数（session-projection lib/index.js:58、73〔实读〕；规则设计 §9.1 的 `hournessRules` 用同一个办法给面板文件路径）。
2. 客户端：面板经 `sessions.list` 的 `projectionsBySession[sessionId].values.hournessProject` 拿到路径（同 `ui/src/graph/agents.ts`:30–37 读 `graphLive` 的取法），用 `remote.workspaceFiles.readBytes(sessionId, holderFile, {})` 读出记录（这个服务不对读文件做工作区范围的限制，由组合出来的文件系统决定能不能读，workspace-files README:40〔实读〕；桌面版的组合允不允许读用户目录下的这个文件属〔推断〕，L4）。读的时机：面板挂载时、面板变为可见时、可见期间每 30 秒一次。
3. 结果三种：
   - 记录在、`sessionId` 是这个对话：「在这个对话里回话」，不显示按钮。
   - 记录在、指向别的对话：按钮「去主 Agent 的对话回话 ›」，点了调客户端服务 `uiWorkspace.openSession(sessionId)`（ui-workspace README:74、lib/client.js:1471〔实读〕；子 agent 面板就这样打开子会话，ui-subagent lib/client.js:936–942 的 `inject` 含 `uiWorkspace`、:966 调用〔实读〕；第三方客户端包注入它属〔推断〕，L4）。主 Agent 的对话打开后，右侧栏的项目图在那个对话里照常可用。
   - 记录不存在：「还没有主 Agent：在输入框打 /wish」。
4. 读不出（路径为空、`readBytes` 被拒或抛错、内容不合 M3 §6 的形状）时的退路：在 `sessions.list().getSnapshot().byId` 里找 `projectionValues.hournessMainAgent` 为真、`cwd` 规整后与这个对话相同的会话（规整同 M3 的 `projectKey`：`\` 换 `/`、去掉末尾 `/`、Windows 上转小写）；恰好一个时当作主 Agent 用上面的按钮，旁边小字「按会话状态认的」；零个或多于一个时写「找不到主 Agent 的对话：<原因>」，不给按钮。记录读不出的原因写进控制台一次（§8.1）。

`awaiting`（「需要你」的第二种）：`graphLive` 的折叠函数（`src/graph/live.ts` `foldLive`）多记一项 `awaiting`。它是这个会话里 `propose_to_human` 成功交给人、之后人还没发过消息的那几件：

- `tool/call` 的工具名（经 `shownName`）等于 `PROPOSE_TO_HUMAN`（`src/shared/tool-names.ts` 的常量，M3 第 6 步建）时，把参数里的 `kind`、`title`、`background`、`proposal`、`doubt`、`notTaken`、`goal`、`question` 记进这次调用的待定项（每个字符串至多保留 200 个码点，防投影变大；不是字符串的字段当作没有）。
- 对应的 `tool/result` 不是错误时，把它移进 `awaiting`，带上 `event.time`；至多留最近 3 件（M3 一条回复至多三件）。是错误时丢掉。
- `user/message` 且 `isPersonMessage(event)` 为真（`data.source.kind === 'user'`、没有 `data.source.form`，判法与 M3 的 `personMessages` 同一个函数，§11 M3 第 4 条）时，`awaiting` 清空。依据：桌面版上人在输入框发的话 `source` 是 `{kind: 'user', rpcId, …}`（api-session-controller lib/index.js:3224–3229〔实读〕），headless 的任务消息是 `{kind: 'user'}`（headless lib/index.js:345〔实读〕），插件的提醒带 `form: 'notice'`。
- `turn/end` 不清空：人还没回话时它一直在。继承自分叉父会话的事件照旧跳过。
- `liveProjection.stateVersion` 由 2 升到 3；`parseView` 与 `parseState` 加 `awaiting` 的形状检查（数组，每项 `{kind, title?, lines?, goal?, question?, at}`），读到旧检查点时 `init` 重算。

面板读主 Agent 那个会话的 `graphLive.awaiting`：`projectionsBySession[holderId].values.graphLive`，还没有值时调一次 `sessions.refreshProjections(holderId)`（api-session-controller lib/client.js:3899〔实读〕，`agents.ts` 今天对子会话就这样做）。

为什么从会话日志折叠，而不是让主 Agent 把确认与放行写进图：M3 定 `confirm`、`release` 不写图，给人看了什么只在会话日志里（M3 附录 §3.4 末段）；投影是 harness 从已提交的事件算出来的，模型改不了，重启之后由检查点与事件重建。

### 4.10 边界情况

- 空图（目录在、没有节点）：效果是一节写「这张图还是空的」，下面一句「在输入框打 /wish，后面跟一句你想做的」与「复制 /wish」；其余各节不显示。
- 目标都关了：效果是写「目标都关了」，列最近关闭的一个；计划为空。
- 节点还没有人话标题（旧节点）：照原标题显示；写法提示只在底账里。
- 依赖成环：引擎校验会报错，图照常可读；推导带访问集合，环上的节点进「要等」，状态行写「等「X」（依赖成环，主 Agent 会处理）」。
- 没有现场投影（图面板行没启用）：「现在」写「看不到现场（项目图面板 glm-hourness/graph-panel 没有启用）」，需要你的第二种与主 Agent 的链接都没有，其余照常。
- 主 Agent 的对话里 `propose_to_human` 是经 `DeferredToolCall` 包着调的（它在 GLM 上常驻，平常不会）：参数取不到四行，`awaiting` 那一项只有 `kind` 与时间，显示「主 Agent 在对话里等你回话」与链接。
- 人回话之后主 Agent 复述「那我记成……」等人确认：这时确认与放行已从 `awaiting` 里消失（人发过消息），人看对话就知道在等他；提议式待决仍在图上开着，照样在「需要你」里。
- 提议式待决被 agent 改了四行：从什么时候起等人按最后一条 `edit` 算，条目移到列表后面，这是对的：人要回的是新的一版。
- 读到的提议式待决缺了四行之一（手改的文件，引擎写入时会拒绝）：缺的那行写「没写」，底账提示。
- 一块板的 `Page` 抛错：错误边界只罩住那一页，写「这块板显示不出来：<原因>」与「重新加载」。
- 多个窗口：本机记录按图目录存，同一台机器的窗口共用（§6.8）。

## 5. 人话从哪来、怎样保持真

### 5.1 选型（原 P2，改为由节点正文回答）

0.4 把「面板上的话从哪来」留给人定（A 渲染时调模型写摘要；D 标题本身改写成人话、加一行 `why`，状态与先后由模板从图算，引擎查写法）。这道题已有人的回答：`m8-plain-language` 的正文（人批过的节点）写「图上写给人看的文字（标题、摘要）要有人话的一层，写法规则进图工具的说明」，就是 D。本稿按 D 写，不再问人（§12 第 16 条，人可推翻）。比较过的另两种：只用代码拼句子（标题还是「M3 设计循环最小闭环」）；另存一份给人看的标题（同一件事两个名字，宪章 §7.1）。

### 5.2 字段

- `title`（已有）：写给人看的一行，规则见 §5.3。
- `why`（本稿新增）：一行人话，说这件事为什么做、做成后有什么不同。目标、特性、任务、决策、风险、规范、工具、复盘可带；待决不带（待决的前因后果在 `background`）。非空白，一行，不超过 80 个码点。写出顺序紧跟 `title`。权限与 `title` 相同：LLM 能改目标以外节点的 `why`；目标的 `why` 只有人或带原话的 LLM 能改。
- `background`（问题的背景，三份设计共用，本稿定形状与上限，P4-01 的裁定）：只在待决上；一行，非空白，不含换行；去掉加粗记号 `**` 之后不超过 60 个码点（`PLAIN_LIMITS.background`）。可以带 `**…**`：提议式待决的背景是四行之一，M3 要求恰好一处加粗（M3 附录 §3.3），由 M3 的 `proposalLineRefusal` 查；别的待决不要求加粗。决定者是人的待决必须带：写法检查第一阶段缺了警告，第二阶段缺了拒绝（§5.3）；agent 自己拍板的题可以不带。写出顺序紧跟 `title`。

  上限从 0.4 的 150 改为 60：`d-chat-not-cards` 定稿之后背景是「一行一句短话」，人给的例子「高峰时 GLM **更费积分**，现在会提醒模型」是 18 个码点，M3 给推荐、疑问、不做三行定的上限是 40；背景要多说一句「从哪来、为什么问你」，所以给到 60。三处都只读这一个常量：M3 的 `proposalLineRefusal` 对背景一行取 `PLAIN_LIMITS.background`（M3 附录 §3.3、§2.9）；规则板的 `rules_propose` 写进节点的 `background`（规则设计 0.5 §9.3）；本稿的 `length` 规则（§5.3）。0.4 里「两三句」的说法随之作废，它来自 `d-chat-not-cards` 之前的定法（design-context「Questions for the person carry their background」），四行的格式是人之后定的。
- `PLAIN_LIMITS = { title: 40, why: 80, background: 60 }`，放在 `src/graph/schema.ts` 的 `CARD_LIMITS` 旁边。M3 第 6 步与本稿第 1 步谁先合入谁建它（M3 附录 §2.9 已这样写），另一方直接用。
- 提议式待决的四行与 `conclusion`（M3 附录 §3.3 建）：本稿只读，加写法检查（§5.3）。
- 投影不带 `why` 与 `background`：每步投影只有类型、id、状态、标题（`docs/ORCHESTRATION.md` §2.5）；`graph_show` 返回的节点带着它们。M3 让 `openItems.questions` 对提议式待决另带四行（M3 附录 §3.3），主 Agent 每步看得到在等人回话的方案。

### 5.3 写法检查（`src/graph/plain.ts`）

检查是纯函数 `plainIssues(text, field, ids)`（新，宿主与客户端都导入），返回违反的规则：

| `background` | 决定者是人的待决 | 没有 `background` | 字段改版之前的旧待决 |
| `length` | `title`、`why`、`background` | 超过 `PLAIN_LIMITS`（`background` 先去掉 `**` 再数）；含换行 | — |

一共 9 条规则；`typeWord` 只查模板文字，引擎查 agent 写入的是其余 8 条（P4-05）。`term` 里不再有「投影」：它在换词表里，由 `jargon` 报，带着换法。四行与 `conclusion` 的长度、加粗与必填由 M3 的 `proposalLineRefusal` 与 `decide` 的检查管，从 M3 合入起就拒绝，不分阶段；本稿只加上面这几条内容规则。0.4 的 `evaluative`（表格格子里的评价词）删去：给人看的表格没有了。

`jargon` 只查待决与提议：人要读、要回话或要批准的只有这两种。进行中的任务与特性的标题 agent 自己也读，换成「练习题」反而让它认不出说的是标定集；它们在首页出现时由 §5.5 的改写与 `code`、`id` 规则管（§12 第 19 条）。状态为提议的节点要人批准，人要读懂它，所以查（P4-08）。

什么时候查、查谁：

- 只查 `llm` 与 `harness` 的写入：`propose` 的上述字段，`edit` 改到的上述字段，提议式待决 `decide` 的 `conclusion`；带转述的 `llm` 写入也查。身份 human 的写入不查。
- 第一阶段（警告）：违反时照常写入，结果多一个可选的 `warnings`（字符串数组，英文，写明规则、字段路径与改法）。图工具的输出 schema 加这个字段（在 rc.3 校验的子集内：`type`、`items`）。
- 第二阶段（拒绝）：引擎以 `invalid` 拒绝，`field` 是字段路径（例 `node.title`、`set.why`、`node.background`），`hint` 写规则与改法。检查排在「写后的节点与整图校验」那一步，在权限、状态转换与证据之后（`docs/ORCHESTRATION.md` §2.9 的检查顺序）。
- 例外：`conclusion` 两个阶段都只警告。它是人同意之后主 Agent 记下的那一句（`record_human_answer` 的 `recordedAs`）；记下人的决定不因措辞被挡，措辞不对时警告留在工具结果里，主 Agent 可以之后改。
- 两个阶段由 `src/graph/plain.ts` 里一个常量切换，切换是单独一个提交（§9.2 第 8 步），前提全部满足才切：（a）§5.5 的现有节点改写已写入，开着的节点在第一阶段读入时没有警告；（b）M3 第 6 步已合入 main，`propose_to_human` 把背景写进 `background` 字段，它的 L3 场景 `glm-design-question` 在第二阶段的常量下通过；（c）规则板的 `rules_propose` 写进 `background` 并且合 60 个码点的上限，它的 L2 契约测试（规则设计 §9.3：`proposalQuestion` 组出的待决交给真实的引擎提一次）在第二阶段的常量下通过。缺一条就不切，第一阶段照常警告；任何一方以后不合，退回第一阶段只改这个常量。
- 读入时：没关闭的节点违反规则时报一条提示（同「文件不是规范写出的样子」，只提示），面板只在底账里显示；已关闭的节点不查。
- 正文改了、人话没改：`edit` 改了 `body` 或 `acceptance` 而没改 `title`、`why` 时，结果带一条提醒「title 与 why 还对吗」，从不拒绝。

### 5.6 人回话的三种记号（`src/shared/answer-marks.ts`）

M3 的 `record_human_answer` 把人的回话按三种固定说法写进图（M3 附录 §3.5）：同意写在 `decide`、`approve`、`edit` 的 `reason` 开头「人在对话里同意」；补充与否掉写在批注开头「人在对话里补充：」「人在对话里否掉：」。面板的变化一节（§4.8）要认它们，指标流水要数它们（`d-chat-not-cards` 第五点：原样同意、补充、否掉的比例）。三处各写一份字面，会走样。

所以把记号放进公共库的一个新模块（纯文字与纯函数，两个包都编进去，同 `src/shared/tool-names.ts`）：

```ts
export const ANSWER_MARKS = { agree: '人在对话里同意', add: '人在对话里补充：', reject: '人在对话里否掉：' } as const
export type AnswerKind = keyof typeof ANSWER_MARKS
/** 一条历史是不是人在对话里的回话，是哪一种；按 reason（decide、approve、edit）或 text（comment）的开头认 */
export function answerKindOf(entry: { readonly op: string, readonly reason?: string, readonly text?: string }): AnswerKind | undefined
```

M3 的 `src/design/record.ts` 用这几个常量拼 `reason` 与批注，不另写字面（§11 M3 第 3 条）；谁先合入谁建这个模块。指标流水按 `answerKindOf` 数（§11 指标流水）。面板不显示比例。

### 6.8 本机记录

都存在本机 `window.localStorage`（DSH 自己把每个会话的右侧栏布局存在那里，sidebar-right README 74 行）。键名带版本，值是 ISO 时间字符串：

| 键 | 谁写 | 意思 |
| --- | --- | --- |
| `glm-hourness.onboarding.glm.v1` | GLM 客户端包 | GLM 上手完成、跳过或自动收起的时间 |
| `glm-hourness.onboarding.glm.seen.v1` | GLM 客户端包 | 开场小按钮出现过的会话 id，JSON 数组，至多 3 个；读不出当作空数组 |
| `glm-hourness.onboarding.hourness.v1` | 编排层客户端包 | 上手页看过的时间 |
| `glm-hourness.panel.seen.v1:<图目录的绝对路径>` | 编排层客户端包 | 上次离开面板的时间；路径取 `readBytes` 返回的 `absolutePath` 所在的 `nodes` 目录 |
| `glm-hourness.nograph.v1:<工作区路径>` | 编排层客户端包 | 没图的开场卡片出现过的时间；路径取会话的 `cwd`，规整为小写、正斜杠 |

「上次看之后」的算法是 `ui/src/graph/seen.ts` 里的纯函数状态机 `nextSeen(state, event, now)`（与 0.4 §7.10 相同）：面板可见是面板正文的根元素与视口相交（`IntersectionObserver`）且 `document.visibilityState` 为 `visible`；挂载时、或离上一次变为不可见 10 分钟以上再变为可见时是一次到达，`since` 取本机记录；连续可见 5 秒以上之后变为不可见或卸载是一次离开，写下当前时间；到达之后 `since` 留在内存里。

## 8. 失败怎样被发现、怎样退

`d-failure-plans` 与 `docs/DEVELOPMENT.md` §1.1：不穷举情况，确保失败看得见、有退路、事后查得到。本稿新增的写入只有引擎里的写法检查（警告或拒绝，留在工具结果里）与本机 `localStorage`；面板不写图、不写规则、不跑命令，所以面板这一侧没有不可逆的动作。开场卡片的「建一张项目图」执行的是接管项目的命令，它的失败与回退归接管项目设计。

### 8.1 运行时

| 哪里会坏 | 怎样发现 | 退路 | 人看到 | 记录 |
| --- | --- | --- | --- | --- |
| 模板对某种图的形状算错（空图、成环、多个目标、旧格式、提议式缺字段） | L2 用造的图与改写后的真实图跑；渲染出错由面板已有的错误边界接住（`tab.tsx` 的 `Boundary`） | 模板函数对单个节点抛错时跳过这个节点，底账提示「这件事显示不出来」 | 首页其余部分照常 | 控制台 `console.error` 一次 |
| `hournessProject` 投影没有值（图面板行没启用、M3 的持有者模块不在） | 值缺席或 `holderFile: null` | 走 §4.9 第 4 条的退路：按会话状态找主 Agent | 「需要你」每件下面写退路的结果 | `reason` 写进控制台一次 |
| 读持有者记录失败（读被拒、文件损坏、形状不对） | `readBytes` 抛错或返回 `ok: false`；JSON 与形状检查 | 同上；可见期间 30 秒后重读 | 「找不到主 Agent 的对话：<原因>」或「按会话状态认的」 | `console.warn` 每种原因一次 |

| `openSession` 抛错 | `try` | 写「打不开主 Agent 的对话：<原因>；可以在左边的会话列表里找「<标题>」」 | 一行错误文字 | `console.warn` |

### 8.2 外部输入的校验

| 输入 | 必填 | 规则 | 不满足时 |
| --- | --- | --- | --- |
| 节点 `why` | 否 | 字符串，一行，非空白，不超过 80 个码点；不在待决上；agent 写入另过 §5.3 | 读入时结构不对按 `docs/ORCHESTRATION.md` §2.6 不进节点表；待决带它是跨字段错误，只报告；写入时 `invalid`，`field` 为 `node.why` 或 `set.why` |
| 待决 `background` | 决定者是人的待决必须带（第一阶段警告，第二阶段拒绝）；其余否 | 字符串，非空白，不含换行，去掉 `**` 后不超过 60 个码点；只在待决上；提议式另由 M3 查加粗 | 结构不对同 `why`，`field` 为 `node.background` 或 `set.background`；非待决带它是跨字段错误，只报告；缺了按阶段警告或 `invalid` |
| agent 写的 `title`、`why`、`background`、四行、`conclusion` | 已有规则之外 | §5.3 | 第一阶段警告，第二阶段 `invalid`（`conclusion` 只警告） |

| `graphLive.awaiting`（检查点与线上的值） | — | 数组，至多 3 项；每项 `kind` 为 `question`、`confirm`、`release` 之一，`at` 为数，其余字段是至多 200 个码点的字符串或缺席 | `parseView` 抛错，投影机制按它的规则丢掉检查点重算（session-projection README:69） |

23. 选项式的旧待决在「需要你」里只显示题目与背景，不列选项（§4.3）。
24. 高峰模式的档位在面板上只显示，改档位是人在对话里说或打 `/rules peak`（§4.7）。理由：面板只看不操作；三个单选是面板上唯一会写的控件。这一条是本稿最可能不对的一处：人说过「档位当然能选」，他也许想在面板上点。要是这样，只在规则板页面上为档位留三个单选，经 `/rules-apply` 写，是面板唯一的写入例外。
