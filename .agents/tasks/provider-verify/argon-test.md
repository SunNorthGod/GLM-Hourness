# argon-test: dsh-vertex-argon install-verified in a scratch profile (rc.3)

Date: 2026-11-10 · Lane: verification (fallback due diligence) · Base: origin/main 8dd308ae · Installed runtime: DeepSeek Harness desktop 0.2.1-rc.3

Prerequisite reading: [findings.md](<findings.md>) (same directory, origin/provider-verify) — the rc.3 pi-ai protocol table, the community survey, and the two known OpenAI-compat gaps (region routing, thoughtSignature replay) all come from there; this lane does not repeat them.

Question: does dsh-vertex-argon 1.6.4 actually install into a profile next to the two repo bundles, compose, register its provider and models, dispatch, and report health sanely — and is its source clean enough to be the fallback?

Answer in one line: **YES, with caveats — it installed via the desktop's own pnpm flow into a scratch profile, composed silently, registered `google-vertex-argon` with its model in the catalog surfaces, dispatched both the Gemini API and the Vertex AI route to the real wire (dummy keys rejected with clean 400/401 auth errors, never config errors), wrote bounded diagnostics inside the scratch home only, and its source implements the thoughtSignature replay and region handling that the OpenAI-compat layer lacks.**

## 1. Scratch profile construction (the layout that worked)

- Installer: the **desktop's own bundled pnpm 11.28.5** (`resources\runtime\primary-runtime\dependencies\pnpm\bin\pnpm.cjs`, run under system node 22.20.0) — the same flow the desktop CLI uses for profiles (DEVELOPMENT.md §3). npm 11.12.1 was tried first and rejected `link:` outright (`EUNSUPPORTEDPROTOCOL`); npm cannot produce this layout.
- Result: `node_modules/dsh-glm-zcode` and `node_modules/dsh-hourness` are **junctions to the main checkout's `packages/glm` and `packages/hourness`** (dist prebuilt at 8dd308ae); `node_modules/dsh-vertex-argon` is a junction into the pnpm virtual store holding the **real registry copy of 1.6.4** plus its one runtime dep `ajv 8.20.0` (nested, pnpm isolated layout); `pnpm-lock.yaml` written in the profile. 6 packages resolved, 3.8 s.
- Boot per `sandboxCommand`: `DeepSeek Harness.exe <desktop>\resources\app.asar\dsh\node_modules\@deepseek-ai\dsh\lib\bin.js --profile argon-test --patch <overlay> ...` with `ELECTRON_RUN_AS_NODE=1`, `DSH_HOME=<scratch>`. No desktop processes; `~/.dsh` untouched (see §5).
- Overlay rows (per-run generated, JSON-values YAML): `llm-pi-ai` patch declaring the route the plugin detects; `agent-default-model` pointing at the argon provider; two inserted probe rows (catalog reader + the repo's `scripts/probe/probe-net.mjs`). Two lane-specific loader lessons: an inserted probe row must declare `inject: [llm]` **in the row definition** (module-level `export const inject` alone is not honored for file-path rows — first run errored `cannot get property "llm" without inject`); and adapter registration lands **asynchronously relative to row apply** — a probe reading `ctx.llm.listProviders()` at its own activation sees `[]`/`NO_ADAPTER`, so the catalog probe polls for up to 20 s before recording.

## 2. Empirical verification (dummy keys only, scratch homes only)

### Run A — Gemini Developer API route (the person's scenario)

Overlay: `llm-pi-ai` gets a `google` provider route (`apiKeyEnv: GOOGLE_API_KEY`, one model `gemini-4-argon`, contextWindow 1048576, maxTokens 65536); `agent-default-model` = `google-vertex-argon` / `gemini-4-argon-google`; env `GOOGLE_API_KEY=dsh-scratch-dummy`.

1. `--dump-config` → **exit 0, stderr empty**. Composed tree shows a `# == dsh-vertex-argon` section with row `local-vertex-argon` resolved to `file:///.../profiles/argon-test/node_modules/dsh-vertex-argon/index.js` (the npm-installed copy), both repo bundles' rows present, and the patched rows carrying the declared route verbatim. The package's own `dsh.bundle.patch` (`- insert: - id: local-vertex-argon, name: './index.js'`) was picked up by the loader without any manual wiring.
2. Model catalog surface: probe row after adapters registered — `ctx.llm.listProviders()` → `["deepseek-official", "deepseek-account", "google", "google-vertex-argon"]`; `ctx.llm.listModels("google-vertex-argon")` → `[{ id: "gemini-4-argon-google", name: "Gemini 4 Argon (Gemini API)", inputModalities: ["text", "image"] }]`; `listModels("google")` → the pi-ai route's own `gemini-4-argon`. The models appear in the same surface the settings page reads. (Full record: `%TEMP%\argon-verify\out\catalog.json`.)
3. `headless --json "Reply with exactly one word."` → session → turn → step → **`turn_end` reason `{"kind":"error","code":"INVALID_REQUEST"}` carrying Google's verbatim body**: `400 API key not valid ... reason: API_KEY_INVALID, service: generativelanguage.googleapis.com`; exit 1. Net log (probe-net): two requests to `https://generativelanguage.googleapis.com/v1beta/models/gemini-4-argon:streamGenerateContent` — the **native GenerateContent protocol**, not OpenAI-compat. Reading: no `UNKNOWN_MODEL`, no `MISSING_CREDENTIAL`, no config error — the dummy key passed the credential seam, the model resolved from the argon catalog, the request reached Google's real endpoint and came back as a clean auth error. Two wire requests per run = the plugin's zero-delivery initial retry (README §GenerateContent item 3) firing once before failing; bounded, observed, not a loop.

### Run B — Vertex AI route (Express-key variant)

Same shape with a `google-vertex` provider route (`apiKeyEnv: GOOGLE_CLOUD_API_KEY`), default model `gemini-4-argon`, env `GOOGLE_CLOUD_API_KEY=dsh-scratch-dummy`.

1. Catalog: `listProviders` → `[..., "google-vertex", "google-vertex-argon"]`; `listModels("google-vertex-argon")` → `[{ id: "gemini-4-argon", name: "Gemini 4 Argon", inputModalities: ["text", "image"] }]`. (`listModels("google-vertex")` → `[]`: the pi-ai vertex route exposes no chat models on rc.3 — detection reads the declared config, not the list, so the argon catalog is unaffected. Record: `catalog-vertex.json`.)
2. Dispatch → two requests to `https://aiplatform.googleapis.com/v1beta1/publishers/google/models/gemini-4-argon:streamGenerateContent` (global endpoint, `v1beta1` = the long-decode API version), rejected `401 CREDENTIALS_MISSING ("API keys are not supported by this API")`, surfaced as `AUTH`, exit 1. With a real Express key this is the endpoint pair Google's Vertex Express flow documents; that positive path is **inferred, not tested** (no real key).

### Health / diagnostics (the row's equivalent of a status surface)

After each run the scratch home gained `storages/vertex_argon_diagnostics/requests/<uuid>.json` (6 records total = 2 per run). Sample content: association (session id, provider `google-vertex-argon`, model `gemini-4-argon-google`), `sessionHash` (sha256, truncated), route `google-generative-ai`, protocol `generate-content`, apiVersion `v1beta`, thinkingLevel `MEDIUM`, hop table (status 400, `outcome: "api-error"`, `bodyBytes` as a count), `responseCapture: disabled`. **No URL, no header, no body, no credential** — matches the source allowlist (§3). This is the plugin's own health reporting working end to end inside the scratch home; the repo's `/glm-status` does not show third-party rows and was not exercised (headless cannot run slash commands; the previous lane did not either).

## 3. Source audit (npm tarball 1.6.4, shasum 20977188…, 32 files)

Citations are `file:line` in the unpacked tarball copy (`%TEMP%\argon-verify\src\package\`).

### The two known OpenAI-compat gaps — both closed by design

- **thoughtSignature replay: implemented.** `google-signatures.js` is a full signature bridge: standalone signature-only Parts captured off the stream (`observe` L121-137, both `thoughtSignature`/`thought_signature` spellings L127), replayed into outbound payloads through a versioned codec that never reaches Google (`restorePayload` L110-120, codec comment L43-44), bound to exact history and content digests so a replay can never attach to a different turn (L5, L59-65, and the `ARGON_SIGNATURE_REPLAY` failures L115, L118), bounded at 64 MiB / 32768 events / 8192 blocks (L87, L91, L105, L125), with cross-protocol demotion of tool rounds to user-text instead of bare `functionCall`/`functionResponse` (L21-41). Installed over the host via `installGemini4PiAiPatch` (`adapter.js` L335-393: wraps `PiAiAdapter.prototype.current` and every gemini-4 provider's `streamSimple`; dispose restores originals L383-393) plus a GoogleGenAI apiClient `requestStream` patch for long-decode (`adapter.js` L146-183).
- **Region routing: delegated to the SDK/env, not a fixed compat region.** Vertex model baseUrl default is the template `https://{location}-aiplatform.googleapis.com` (`adapter.js` L640); pi-ai's Vertex API leaves `{location}` templates to the SDK (`google-vertex-api.js` L309-315, extracted from rc.3's asar). With an Express API key the SDK client is built without project/location (`createClientWithApiKey` L285-292) — express-mode default, observed empirically as the global `aiplatform.googleapis.com` endpoint (Run B); with ADC, `GOOGLE_CLOUD_LOCATION` is hard-required (`resolveLocation` L348-354). The Gemini API route is `https://generativelanguage.googleapis.com/v1beta` (`adapter.js` L655) — global, no region concept. The Interactions path defaults location to `global` (`google-connection.js` L17-20).

### Credentials

- Resolution order per secret: DSH `credentials` service → launch environment (`adapter.js` L563-568, with the explicit comment "A failed credential store must never silently select an ambient account" — the credential-service failure propagates rather than falling back). Google API key: detected `apiKeyEnv` from the pi-ai route, else `GOOGLE_API_KEY`, else `GEMINI_API_KEY` (`adapter.js` L616-619). Vertex: Express `GOOGLE_CLOUD_API_KEY` or ADC (`GOOGLE_APPLICATION_CREDENTIALS` + project + location; pi-ai `google-vertex.js` L59-83). Proxy key namespace reserved and isolated (`googleKeyEnvironment` L77-81; proxy never falls back to Google keys, `adapter.js` L470-472). Missing Gemini-API credential is fail-loud `MISSING_CREDENTIAL` (`adapter.js` L472). `~/` expansion in `fileExists` is read-only (`adapter.js` L570-575).
- **No file writes anywhere**: the only fs import is `access` (`adapter.js` L1); no `writeFile`/`mkdir`/`process.env` mutation in any module (grep over all 27 js files); `google-connection.js` L6-7 states the contract ("never copy private keys or mutate process.env"). Everything it persists goes through the host `storageDomain` rows (`index.js` L61-106): `vertex_argon_diagnostics` (bounded 200 records), `vertex_argon_responses` (opt-in, 20 records / 64 MiB / 16 MiB per record), `vertex_argon_interactions` (creation locks + cursors). Empirically all landed under the scratch home's `storages/`.

### Telemetry / privacy

- No network endpoints besides Google's official ones (`generativelanguage.googleapis.com`, `aiplatform[.<location>].rep.googleapis.com`) and the Antigravity proxy default `http://127.0.0.1:8045/v1beta` (URL-literal grep over all sources; the proxy is off unless `proxyEnabled` or an explicit route enables it). No telemetry of its own.
- Diagnostics are allowlist-only by construction (`diagnostics.js` L24 comment, transport error-code allowlist L25-33, `sessionHash` = sha256 L4-6); the response store is documented and coded to never receive headers/bodies/credentials (`response-store.js` L5), and the Interactions endpoint rejects URLs containing credentials/query/fragment (`interaction-transport.js` L19).
- Minor: the Interactions principal hash persisted in the diagnostics domain is `sha256([route, apiKey || keyFilename || 'ADC', project, location])` (`google-connection.js` L35) — a credential-derived value stored locally (unsalted, but not practically reversible; interactions path only).

### Packaging

- No lockfile in the tarball (32-file list has none); single runtime dep `ajv` pinned exact `8.20.0` (`package.json` L85-87); all eight peers marked optional (`peerDependenciesMeta` L98-123) and resolved from the running host at runtime, never a second copy (`runtime.js` L24-49; `@google/genai` resolved adjacent to the host pi-ai manifest L35-42). Verified against the installed rc.3 asar: every peer is shipped by the host (`@deepseek-ai/schemastery`, `dsh-llm`, `dsh-llm-pi-ai`, `dsh-launch-environment`, `dsh-typert-protocol`, `@earendil-works/pi-ai` with `providers/google*.js` present, `@google/genai`, `zod`).
- rc.3 host facts this design leans on (extracted from the asar, read-only): the llm-pi-ai catalog ships `google` (`GEMINI_API_KEY`, `generativelanguage.googleapis.com/v1beta`) and `google-vertex` as builtin providers (`PROVIDER_DATA`, `pi-ai-index.js` L2601-2684), so a profile's `google` route is a catalog route and never touches the hand-declared protocol table that excludes google.

### Behavioral notes worth knowing

- Model scope is the `gemini-4-argon` family only: `isGemini4Model` matches `/^(?:models\/)?gemini-4\b/i` on the google apis (`adapter.js` L68-75) and route detection looks for ids matching `/^(?:models\/)?gemini-4-argon\b/` in the pi-ai route's model list (`adapter.js` L101). It wraps/serves nothing else — `gemini-2.5-*` stays on the zero-plugin OpenAI-compat route from findings.md §3.
- An `agent/request` hook rewrites `reasoningEffort: "max"` to `"high"` for gemini-4 models (`index.js` L135-146; README L16 documents it).
- One swallowed construction failure: `new ArgonDiagnosticsService(...)` in `try {} catch {}` (`index.js` L116-118) — UI-side diagnostics only, generation path unaffected; noted because it deviates from fail-loud.
- While active it patches two host prototypes (`PiAiAdapter.prototype.current`, GoogleGenAI `apiClient.requestStream`) and restores them on dispose; a second plugin patching the same prototypes could interact (guarded: dispose only unwraps its own wrapper, `adapter.js` L175-176).

## 4. Verdict

**dsh-vertex-argon is fit as the fallback: yes, with caveats.** Install-verified end to end on the installed rc.3 without a real key: profile install via the desktop's bundled pnpm, silent composition, provider + models in the catalog surfaces, both routes dispatching to the real native-protocol wire with clean auth failures, bounded diagnostics in the home's storages, and a clean source (no writes outside storage domains, no telemetry, no lockfile, one exact-pinned dep, host-resolved peers). It is the plugin that natively covers exactly the two gaps the zero-plugin OpenAI-completions route has (signature replay, region handling) — but only for the `gemini-4-argon` family; for Gemini 2.5-era models the zero-plugin route remains the answer, so the two are complements, not substitutes.

Caveats (all verified as stated): gemini-4-family-only scope; host-prototype monkey-patching while active; `max`→`high` effort rewrite; the swallowed diagnostics-service construction error; Interactions principalHash storing a sha256 over credential material; peer deps are host-provided, so a future DSH that stops shipping any of them breaks the row (`engines.dsh >=0.2.0-rc.2` is the author's contract). Not exercised (no real key / headless): real Express-key Vertex acceptance, Interactions protocol, long-decode continuation beyond the one zero-delivery retry, and the settings UI — all marked inferred above where relevant.

**Install note (if the person ever chooses it).** Install into the desktop profile with the sanctioned flow (`dsh plugin --profile desktop add dsh-vertex-argon` per its README §安装, or `plugin_manager` install_bundle); put the key in the environment the desktop inherits — `GOOGLE_API_KEY` (or `GEMINI_API_KEY`) for the Gemini Developer API, `GOOGLE_CLOUD_API_KEY` (Express) or `GOOGLE_APPLICATION_CREDENTIALS`/`GOOGLE_CLOUD_PROJECT`/`GOOGLE_CLOUD_LOCATION` (ADC) for Vertex — and declare the matching route in the profile's `llm-pi-ai` patch so the plugin detects it: a `google` (or `google-vertex`) provider whose `models` list one entry with id `gemini-4-argon`, `contextWindow: 1048576`, `maxTokens: 65536` (its own schema requires the id; the catalog has no such model, so it must be declared), then point `agent-default-model` at provider `google-vertex-argon` with model `gemini-4-argon-google` (Gemini API) or `gemini-4-argon` (Vertex). Check first, in order: `--dump-config` composes with the `# == dsh-vertex-argon` section and no stderr; the model picker / models page shows the **Vertex Argon** group with `gemini-4-argon-google`; the first real request's diagnostics appear under `~/.dsh/storages/vertex_argon_diagnostics/requests/` (that directory is the row's health surface; `/glm-status` does not show it). Keep `proxyEnabled` off — the Antigravity proxy pair is a separate third-party channel that was never enabled in this verification.
