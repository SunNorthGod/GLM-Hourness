### Findings

1. HIGH, blocking. The M7 seam contradicts M7 0.3. Where: design.md §4.1 (295–325), §5.3 (400–410), §2.4 rows 4–9 (198–203), §16 M7 line (814); M7 0.3 §2.5 (m7/design.md:211–238) and §3.11.1 (832–849).
   M7 0.3 already defines the loop-board contract and the design ignores it:
   - Ownership. M7 0.3 keeps its ten defaults as data in `src/execute/entries.ts` and `src/operate/entries.ts` and hands them over with `glmHournessLoops.contribute(source, entries)`; events go in through `glmHournessLoops.emit(event)` (m7:221, 235). The design hard-codes eleven entries in `src/loops/defaults.ts` and offers only `recordRun` and `acceptProposal` on `glmHournessLoops` (design.md:486). The same behaviour would be defined in two code tables.
   - Missing entries. M7 0.3's `execute.reviewed` (review passed or skipped → build the commit, `check_commit`, fast-forward) and `execute.tasks-closed` (all tasks closed → dispatch the goal's acceptance review) are not on the board. M7 0.3 runs its own table only when the loop board is absent (m7:237), so with the board installed nobody prompts the main agent at those two points. That is an unmet requirement of `d-auto-drive` (the drive stalls after review and before the completion gate) with no detection beyond the morning report.
   - Harness actions. M7 0.3 entries carry harness actions run through `glmHournessExecute.runAction(id, event)`: `execute.start-drive` (`goals.create` plus the "自动推进已开始" comment), `execute.trunk-check`, `execute.reconcile` (m7:221, 742, 798–810, 843). The design's `Action` union (design.md:165–169) has no such kind, and §2.4 rows 7–8 say these stay in M7, without saying who triggers them when the board is installed.
   - Events. M7 0.3 emits `hourness.design-released` from its own `agent/pre-step` listener, `hourness.handback` with `depth` and `reviewTask`, `hourness.review-passed`/`review-skipped`, `hourness.stopped` with `kind`/`rounds`, `hourness.tasks-closed`, `hourness.trunk-advanced`, `hourness.host-started` (m7:227–233). The design names different ids and payloads, has M3 (not M7) emit `design-released` (design.md:407), and detects trunk advances by polling git every 30 s (design.md:229) although M7 records every checked advance and every outside advance exactly (m7:703–706).
   - Trunk check semantics. M7 `execute.trunk` runs every `$` and `when` line after each checked advance (m7:843). The design's entry 4 skips when "every `$` line including those with `when` ran and exited 0" (design.md:247), but M7's `check_commit` runs a `when` line only when the paths touch it (m7:672), so the skip almost never applies and a 30-minute full check holds the shared gate lock after nearly every merge, queueing the next `check_commit` (gate lock waits up to 60 min, m7:662).
   - Prompt texts differ for the same entries (M7 uses `propose_to_human`; the design uses four-line prose and `loop_note`).
   Fix: adopt M7 0.3's split and name the final interface here (M7 0.3 says "名字以循环板设计为准，M7 只改 entries.ts"): (a) `glmHournessLoops.contribute(source: {plugin, row}, entries: readonly LoopEntryDefinition[])` and `emit(event)`; the board validates contributed entries like the GLM ones and lists them under the contributing plugin; (b) add `{kind: 'harness', action: string}` to `Action` (optionally with a `tell-main` follow-up), executed through `glmHournessExecute.runAction`, outcome `delegated`; (c) make the event table the union: M7's eight `hourness.*` events with M7's payloads, plus the board's own `waiting-on-human`, `file-changed`, `files-edited`, `peak-changed`, channel events and an `outside-advance` event fed by M7's `{by: 'outside'}` record (drop the 30 s git poll, or keep it only as the fallback when the execute row is off); (d) list the union of entries: M7's ten plus the board's `deps-after-merge`, `remind-waiting`, `checks-after-edit`; (e) pick one trunk-check rule: run after `hourness.trunk-advanced` and after outside advances, skip only when M7's check record for that exact tip ran every line the norm marks always-run (`$`) and all `when` lines matching `O..N`; (f) rewrite §16's M7 line against 0.3.

2. HIGH, blocking. The GLM seam contradicts M6 0.3 and leaves M6-L1–L5 and M6-R5 unanswered. Where: design.md §3.4 (260–293), §4.2 (327–339), §1.5 (106), §16 M6 line (817); M6 0.3 §5 (m6/design.md:398–501), §8 (694–744), §4.4 (306–308), line 37.
   - Contract. M6 0.3 puts the defaults on the pricing service as `UsagePricing.loopDefaults: ChannelLoopDefault[]` with `runBy: 'channel' | 'loop-board'`, `tell` with `{line}`, triggers `peak-start`, `command`, `quota-low`, `login-rejected`, and `loopDefaultsOf` (m6:409, 477–497). The design defines a second service `glmHournessChannelLoop` with push `subscribe` and different types (design.md:266–286).
   - Entries. M6 0.3 ships four GLM entries (`glm:peak-reminder` and `glm:quota-on-command` run by the channel and only listed; `glm:quota-low`, `glm:login-rejected` run by the board) and keeps the two peak start/end entries out of the GLM package because they depend on the level (m6:708–724). The design ships three, puts `glm:peak` with action `peak-mode` in `src/glm-llm/loop-defaults.ts`, and does not show the GLM package's own peak reminder or quota-on-command behaviour on the loop board. The brief's rule is that every behaviour the GLM plugin would otherwise hard-code is a visible default entry naming its plugin; quota-on-command is visible nowhere.
   - Quota reading. M6 0.3 has the board read quota after a new GLM usage record once the last reading is 15 min old (M6-L2, m6:37, 306, 733). The design says M6 decided "only when someone looks" (design.md:106, 339) and reads only on command, morning report and upstream limit, so the five-hour window's "提前说" mostly fires after the fact.
   - Login. M6 0.3 exposes `quota({read: false}).login.state` (`rejected` after a server rejection, m6:391, 857) and asks the board to poll it each minute (M6-L3). The design instead asks M6 to push `login-lost` from `zcode.ts`:382–385 and 544–548, which are the "credential empty" and "project token unavailable" paths, a different condition.
   - Delivery. M6-L4 asks that account-level notices go once to the most recently active project's main agent; the design delivers per project, so N projects produce N notices.
   Fix: drop `glmHournessChannelLoop` and `subscribe`; read `loopDefaultsOf(pricingService(ctx))` and map `ChannelLoopDefault` into `LoopEntryDefinition` in one function (M6 0.3 says only `channel-loop.ts` and `loop-defaults.ts` change if the board wants another shape; if so, give the final shape here). Implement M6-L1–L5 item by item: list `runBy: 'channel'` entries read-only with "GLM 通道包自己执行，这里只列出"; derive `quota-read` and `login-lost` events inside the loop row from `quota()` on the 60 s tick (`read: false`) and after new GLM usage (≤ every 15 min); add a machine-level "already told" record so one notice goes to the most recently active project's main agent; register the peak start/end entry under `dsh-hourness` with source text "GLM 峰谷定价（GLM 通道包）与高峰模式（规则板）". Remove §1.5's line about background reads and rewrite §16's M6 line against 0.3.

7. MEDIUM, blocking (acceptance 5 cannot be met as specified). Where: design.md §5.2 reconcile item 3 (393), acceptance 5 (80), §10.2.
   `schedule.update` decodes `expected` with `decodeScheduleRecord`, whose decoders require the exact record keys (`hasExactKeys`, schedule:74–77, 124–127, 356–364); a malformed `expected` returns `{code: 'invalid_rule', message: 'expected must be a complete valid Schedule record.'}` (schedule:1809–1815). ### Verified assumptions

- `schedule` service: constructed as `"schedule"` (schedule:1992); `create` needs exactly one selector, refuses `subagent_session`, emits `schedule/changed` and drives (2083–2114); title ≤ 120 (23); `every_seconds` ≥ 60 (21); daily/weekly selectors use exact keys `time`, `time_zone`, `weekdays` (1052–1059, 1118–1122).
- `catalog()` returns record fields plus `sessionId`, `status`, `lastDelivery?`, sorted by `scheduledAt` then id (2129–2136).
- `delete` is a hard delete including delivery history, returns `schedule_not_found` for a wrong binding (2164–2182); `update` compares the full expected record, returns `schedule_not_found`, `schedule_ended`, `schedule_conflict`, no-op for equivalent rules (2197–2224, 1806–1837; README:53–55).
- `schedule/changed` has no payload and listener errors are caught (2231–2237).
- Delivery: `resolveAgent` (1576), user message with `source: {kind: 'schedule'}` (1586–1595), `followup` (1596), `sessions.flush` false means failure (1597), recurring tasks of one session batched (1571), failures logged and excluded from the timer until another write or restart (1627–1640; README:153), run inside `agents.withoutInitiator` (1531).
- Reminder framing `[SCHEDULE REMINDER]`, `schedule_id_json`, `occurrence_at`, `reminder_prompt_json`, batch `reminders_json` (1386–1418).
- Only the latest missed occurrence is delivered after restart (590, 656, 687, 821; README:12); at-least-once only (README:154); cannot mount headless (README:26).
- Archive deletes the session's active tasks through `workspace/session-stop` (2056–2058, 2273–2292; dsh-workspace:623).
- `schedule_delete`/`schedule_update` act on the caller's session only (tool-schedule:581–600, 637–647).
- `agents.get` (agent:596), `withoutInitiator` (414), `currentInitiator` asserts then reads the async store (370–373), `agent/created` is serial with `{agent, source, signal?}` (581–585).
- Agent status, `followup`/`steer`/`inject` targets and wake flags (agent-loop:790–814); claim takes all next-step plus one next-turn (103–111); `agent/pre-step` waterfall with claimed messages (902–927); pending next-step messages extend the turn and pending inbox starts another (1000–1008, 1037); `agent/error` emitted at 880.

### Findings

1. F57 — NIT. Where: design.md §9.3 (the read-and-recover table) and §9.1 (the `repo-written.json` bullet). The §9.3 table adds no row for `repo-written.json` being absent or unreadable while `journal.jsonl` survives. Row 1 (file equals the journal's last `fileSha256`) still fires for entries in their committed state, so the only reachable states are entries whose working-tree file does not equal the journal's last version. For those, with `repo-written` absent, 「`repo-written.json` 里这一项的 `fileSha256` 也与最后一条不同」 is satisfied (an absent record differs), so a file sitting at the previous journal version (a git revert or checkout) falls into row 2 (owed-write) and is 補写n with only an info log — the exact F44 failure mode, reintroduced when `repo-written.json` alone is lost. This is narrow and fails toward recoverability: the realistic loss paths (`git clean -fdX`, fresh clone, new machine) remove the whole `.llm/loops/` so `journal.jsonl` is lost too and entries take the safe 「从没出现过」 adoption path; `git status` still shows the clobbered revert; and `repo-written.json` is written atomically, so partial corruption is unlikely. It stays a NIT because every realistic path is already safe and the harm is git-recoverable. Fix: add a §9.3 row — when `repo-written.json` is absent or unreadable but the journal is present, rebuild it by seeding `fileSha256` from each file that equals the journal's last version, and treat every other entry whose file differs from the journal's last as an outside change (`entry-changed`, not 補写) until the person acts.

2. F58 — NIT. Where: design.md §2.2 (the glob paragraph) and §1.4 acceptance 36. §2.2 states 「`matchesFilter` 的 L2 用例见验收第 36 条」, but acceptance 36 only feeds the two `loop_propose` examples through `validateWhen`/`validateEntry` and runs example 2's script through `runScript` with the envelope supplied directly; it never exercises `matchesFilter`, so it does not pin the new `**`-matches-zero-directories rule (`docs/**/*.md` ⊇ `docs/setup.md`). The actual `matchesFilter` glob coverage lives only in §15's L2 list (「glob 的 `*` 与 `**`」). The cross-reference is wrong; the coverage exists but is pointed at the wrong item. Fix: point §2.2 at §15, or add to acceptance 36 an explicit `matchesFilter('docs/**/*.md', 'docs/setup.md') === true` case (and one for `**/x.json` matching a root-level `x.json`).

3. F59 — NIT. Where: design.md §9.2 step 5 versus §6.6 and §9.3. Step 5 says an entry accepted while a git operation is in progress 「已经生效（判定按变更记录）」 even though its `docs/loops/scripts/<id>` write is deferred, while §6.6 `runScript` reads the script bytes from `docs/loops/scripts/<id>` and §9.3 gates running on the file. For a script entry accepted during an active merge or rebase, a trigger that fires before the operation completes therefore yields `refused` (`script-missing`), not a run, which contradicts the plain reading of 「已经生效」. The window is tiny and the outcome fails safe and is visible (the page shows 「条目文件待写回」), so it is a NIT. Fix: in §9.2 step 5 state that a script or check entry accepted while a git operation defers the file is listed as 「待写回」 and its triggers yield `refused` (`script-missing`/`check-missing`) until the file lands, or run the private copy from the proposal's stored bytes (`journal` `after.scriptText`) during the defer window.
