## 发现

### F15 MEDIUM：「git 写不出新的撤下」不成立，晨报的对账又查不到换回旧版本

位置：§3.5 第 720 行「`git checkout`、`git restore` 只能把文件换成历史里存在过的版本，写不出新的撤下」；§3.10 第 773 行对账（「逐行用 `at`、`rule`、`action` 去对流水里的 `LiftRecord`」，只报「lifts.jsonl 里有流水没有的撤下」）；§11 第 1636 行「撤下一条规则」的剩余一栏；§1.2 `m4-gate` 验收第 4、7 条。

问题：

- `lifts.jsonl` 只追加，一条规则的状态是它最后一行的 `action`。文件里依次是 `lift X`、`restore X` 时，`git checkout <旧提交> -- docs/guard/lifts.jsonl` 把文件换回只含 `lift X` 的版本，X 又处于撤下状态，没有人说过话。`git stash pop`、`git revert`、合入一条把文件改回旧版本的分支同样如此。
- `git apply`、`git am`、`git cherry-pick`、`git merge` 能把任意新的一行带进文件。`lift-files-only` 的 shell 一路只查 file-tools-only 判为写的命令，这些 git 命令不在其中（设计自己说「M4 的规则一律不判 git」），所以它们不被拦。
- 设计说发现的办法是对账。对账只查一个方向：文件里的每一行要能在流水里找到对应的 `LiftRecord`。换回旧版本之后，文件里剩下的行在流水里都有记录，被丢掉的是 `restore` 那一行，查不出来；晨报「撤下的规则」读流水，写的是 X 已恢复，而门读文件，X 已撤下，两边对不上也没有任何提示。`git apply` 带进来的新行能被现在的对账查到，但只在下一份晨报，之前规则已经停拦。
- 循环板对同类情形有明确处理（循环板设计 §14.2 第 33 条 (e)：生效、提交之后外面 `git revert`，条目当成「在循环板之外变了」，不跑）。M4 的 `lifts.jsonl` 是同样的「进 git 的人的决定」，却只写了一句不成立的说明。

这不是 F14 的复发（写工作树里的副本已拦住），是 F14 的修法所依赖的「写不出」假设里剩下的一半。按评审标准它是「有失败而没有检测」：实际可能发生（主 Agent 或 worker 为别的目的跑 `git checkout`、`git stash`），代价是一条被人恢复过的规则静默停拦，可逆，但没有人知道。

修法：

1. 把第 720 行那句改成真话，并把它列入已知边界：「git 命令不判。`git apply`、`git am`、`git cherry-pick`、`git merge` 能带进新的一行，`git checkout`、`git restore`、`git revert`、`git stash pop` 能把文件换回含有撤下的旧版本。这与读法看不见的 shell 写法同属已知边界（§11、§15），靠对账发现。」§11 第 1636 行的剩余一栏同样加上。
2. §3.10 的对账改成比终态，两个方向都查：对每条规则，取文件里最后一行的 `action`（没有行等于未撤下）与流水里最后一条 `LiftRecord` 的 `action` 比；另逐行查文件里有而流水没有的行，以及流水里有而文件里没有的行（被回退掉的 `restore` 属于这一类）。任何一项对不上，晨报写一行「lifts.jsonl 与流水对不上：<规则 id> 文件里是撤下，流水里最后一条是恢复」（或反过来）。换电脑、切分支之后两边天然不同，同样只是提醒，不作废那些撤下，沿用现在的写法。
3. §3.5 的 L2 加两例：①临时仓库里文件有 `lift X`、`restore X` 两行，流水有对应的两条 `LiftRecord`；测试里（不经 harness）把文件换回只含 `lift X` 一行的版本，晨报列出 X 的终态对不上；②用 `git apply` 往主检出的文件里加一行 `lift Y` 的补丁，晨报列出「文件里有流水没有」的 Y。
4. 不要求门去拒绝流水里没有记录的行：换电脑后流水不在，会把人真实的撤下全部作废。这一条在 §16 记为没选的做法即可。
