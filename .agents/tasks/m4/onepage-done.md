# 补拦截、补检查：七件活「怎样算做完」的人话版

设计 0.6（第三遍）。这是 design.md 第 1.2 节那七件活、合计 35 条做完条件的人话说法，意思不变，只换了词。你定过这些条件之后再改要你出手，所以放行时一起看。想改哪条，直接说「第几件第几条改成……」，不用等下一轮；你改了哪条，就照你的原话写进项目图。逐条的完整字句在 design.md 第 1.2 节。

## 第一件：拦截与撤下（m4-gate，7 条）

1. 规则不再分「试运行」和「真拦」两种状态：经统一安装的规则判为拒绝就拦下，调用不执行。能认出项目目录的会话里，每次拦下在违规记录里恰好留一条，带规则编号、时刻、工具、命令或目标、作用范围和路由、纠偏的原因。记录一时写不进时不静默：丢了几条挂在这个会话的健康状态上，下一次写成功时在记录里补一行「这里丢了几条、哪段时间、各是哪类」，晨报和规则板都读这份记录，所以看得到；认不出项目目录的会话不计数，只在健康状态里写「没有项目目录，拦下没落盘」。规则声明里列出所有没被撤下的规则；记录里不再出现旧版试运行那种标记。
2. 每拦下一次，都记这个 agent 下一步模型发出的第一次调用走对没有，分四种：走对了正路、原样重试、做了别的、没有下一步。GLM 上包了一层的调用先拆开再比；和被拦调用同一步发出的调用不算；拦下之后这一回合就结束、没有下一步时记「没有下一步」。晨报按规则写「拦截后下一步走对 x/y（另有 n 次停下来交给人或上级）」，分母不含「没有下一步」。跟进、申请、放行、撤下这些记录不算进晨报的违规数；规则板真拦的算，排队的不算，晚到的拦下算、另列一行，只记录不拦的单独计数。
3. 拦错看得见：晨报按规则写拦下几次、下一步走对的比例、最近一次拦下的样子（工具、命令或目标的前 60 个字、时刻），原样重试过的另写一行次数；一条命令能列出某条规则每次拦下的完整记录；晨报、命令行和规则板读的是同一份统计。
4. 撤下一条规则只有一条路：对主 Agent 说一句要放开它的话（主 Agent 的工具把你的原话拿去核对：必须是客户端送来的最近一条你说的消息里的一段、带放开的意思、至少 4 个字，一条消息最多换一次撤下），或在规则板上打 /rules lift 规则编号；恢复同理。撤下记在仓库里一份只追加的文件，此后这条规则在本项目（含派出去的工作树）不再拦、不在规则声明里；编号不对就拒绝并列出能撤的编号。撤下记录本身被一条专门的规则护着，agent 用工具或命令写任何一份检出里的这份文件都被拦下。撤下和恢复各在违规记录里留一条（原话、经哪条路），晨报写「撤下的规则」。这份文件被 git 操作改得和记录对不上时，下一份晨报对每条对不上的规则写一行，点名规则和两边的状态，两个方向都查；对账和「撤下的规则」读的是整份记录、不限当天，所以三天前撤下、和记录一致的规则不报对不上，仍列在「撤下的规则」里；换过电脑、早于本机第一条记录的行合成一行提醒，不逐条报。
5. 只能事后才发现的拦截：有一条兜底在一轮结束时发现 shell 写出了没有任何文件工具碰过的文件，就在违规记录里记一条「晚到的拦下」（带文件和调用），并在这个 agent 下一步之前送一条纠正提醒（点名文件、说明这些写入已经发生、正路是用文件工具）；没有下一步时只留记录；没装这个兜底时不做，健康状态写明。
6. 规则总表列出 guard 这套框架的全部规则（guard 行六条、图行一条、循环板两条、指标流水一条、接管行一条），都经同一个安装口装上，条目没有「模式」一栏，和规范节点里的规则标签一一对应；主 Agent 的八条规则和 M7 的那道检查各在自己的表里，三张表合起来编号不重复。
7. 违规记录写在会话所在项目的 `.llm/` 下：两个项目各写各的，派出去的工作树里的会话写主检出那个项目的；撤下记录那份文件放在主检出的仓库里，系统只读写这一份，它在每一份检出里的位置都被护着；护的时候按目标所在那份检出的根来判。

## 第二件：三条规划规矩（m4-rules，3 条）

1. 三条新规则一启用就拦，各留一条拒绝记录：新写的跳过检查的注释没写理由、也没挂图上的节点；改检查工具的配置或基线文件；在草稿区以外新建一次性脚本。相邻的正常情形放行、不记录（注释带了「-- 理由 节点」、改普通源文件、在已有同类文件的目录里新建）。后两条的拒绝带一个申请编号（见第三件）。读登录密钥文件放行、也不记录，没有这条规则。
2. 同一件活被从「做完」改回「在做」第 3 次（第 3 次返工要开始）时，这个节点下出现一张给人的待决：题目带前因后果，再加推荐、疑问、不做各一行，不带任何选项；题目、四行和正文里不出现你没学过的内部词；疑问那一行写出一个「一变方案就要换」的事实；节点标题里有你没学过的词、编号或文件名时，题目写「这件活要修第 3 次了」、把标题移进「附」。主 Agent 把它放进下一批交给你的事（一次至多三件），只问「先停下查原因，可以吗？」。你同意、补充、否掉或说不用定，都有记法。这张待决没关掉之前，再返工不再加。装了循环板时，它的页面列出这一项，每提一次报一次。
3. 规范文档里那张规划规矩表的每一行，都写明在哪一行实现、什么状态。

## 第三件：写工作区外文件的申请（m4-request-card，10 条）

1. 工作区圈禁拒绝时，纠偏带一个申请编号，点名申请工具和它的四个字段；它从不指向这个会话没有的通道（普通子 agent 把编号交回给派它的 agent，M7 的 worker 用 ask_main 把编号交给主 Agent 并等回答）。改检查配置、在草稿区外建脚本被拒时同样带编号，字段一样。
2. 申请工具返回一段系统写好的方案文字：题目，背景、推荐、疑问、不做各自成段，最后一句问话；写明解析后的路径、文件在不在、多大或多少行、覆盖前会不会备份，你的目的、能不能撤回、影响面，试过的替代用引号标成原话；疑问那一行写出一个「一变就不该放行」的事实；系统自己写的部分不出现你没学过的内部词；题目里的路径和背景里的焦点标题是数据（路径原样显示，焦点标题不合格就省去那半句）；文字写不出来（任何出错）时就不登记、返回「暂不可用」。这个会话从你上一条消息以来已经出示过一次方案时，返回「正忙」。工具说明里带一道示范，示范也过真实的检查。
3. 只有你的下一条消息能批准：它来自客户端输入、紧跟在那段方案文字后面的最后一条助手消息、去掉首尾空白和句末标点后恰是「可以」一类的同意词；这时同一派发链里同一个调用（同一工具、同一组参数）在 30 分钟内放行一次，agent 这一步收到一条说明，带被拒调用的工具和参数；第二次同样的调用、任何不同的调用仍被拒。回别的话、在方案之后又说了别的、方案被改过，都不放行，各收到一条说明；申请开着、这一回合第一步没有你的消息时，每一回合都提醒 agent 回合末再出示一次。
4. 放行只有这一个来源：往违规记录里追加任何记录（含伪造的申请和回答）、改项目图、模型自己写的任何文字，都不产生放行。
5. 用的时候重新核对目标：存在与否、大小、修改时间和申请文字里的不一样时，这次调用被拒、放行作废；一样时，目标存在且不大于 10 MiB 就先把旧内容复制到项目的 `.llm/` 下，复制失败就拒这次调用、放行不作废。
6. 进程重启或插件重新加载之后，没答的申请和没用的放行都没了，agent 重新申请拿新编号；重启后第一次给那个会话装提醒时，日志里还开着的申请收到一条「作废」提醒。申请、你的回话（原话）、放行的使用和作废各在违规记录里记一条，写明何时、哪个会话；晨报计数。
7. GLM 和非 GLM 路由上都成立；`str_replace_editor` 写工作区外和 write、edit 一样被圈禁拒绝。
8. 装了 M7 的项目里，worker 写出项目、被 M7 的写入范围拦下时，纠偏带编号；主 Agent 申请、你回「可以」后，worker 原样再调一次成功，第二次被拒。worker 写进项目里但出了自己工作树的文件（例如主检出）被拦下时，纠偏是 M7 的，没有编号、不问你。
9. 申请开着时，装了 M7 的主 Agent 的自动推进停下等你（原因里写编号），申请关了就恢复；你在方案出现之后回「可以」，放行成功；你一直不回，2 小时一到申请关闭、叫醒主 Agent，M7 恢复推进。
10. 申请的开和关都写在会话日志里：开是申请工具的结果，关是一条带结局（批了、回绝、关闭、过期、错过）的提醒；面板「需要你」从会话日志读出还开着的申请。

## 第四件：改完就跑的检查（m4-checks，8 条）

1. agent 用文件工具写成功、改的文件对得上一项已批准的检查行的适用范围时，这个 agent 的下一步带一条提醒：每个检查几处问题，至多 5 条带「文件:行」（落在这次改动行上的排前面），完整输出写在日志里的路径；没有问题就不出声，除非上一条提醒有问题。
2. 自带的检查只来自「批准、在做、做完」状态的工具节点上读得懂的检查行（读不懂的跳过，健康状态写明）。命令不经 shell：改动文件只作为单独的参数交给程序，文件名里的特殊符号原样到程序手里；程序本身是 shell 命令时不收文件参数。每个检查日志第一行是展开后的完整参数表；跑不起来、超时或输出读不懂时，提醒和健康状态写明；同一个检查在一个会话里因跑不起来或读不懂连续 3 次后，本会话不再跑它（超时不算这 3 次），下一次改动照常再跑，同一项上次还在后台跑时不起第二个。
3. 一步最多等多久见第八条，跑得慢的结果在之后的步里送到。整个进程同时至多 2 个检查，上限被调高的检查合起来至多占其中 1 个；还没开始跑的检查，提醒写「排在 N 个正在跑的检查后面」；排了一段时间仍没开始的检查不再等，记一条「没跑」，提醒和晨报写明，下一次改动照常再排。
4. 改了没有任何检查覆盖的语言的文件时，每个会话每种语言提醒一次，写明社区常用的检查器、以及怎样请主 Agent 提一个带检查行的工具节点。
5. 装了循环板时，它的页面列出「改完文件就跑检查」一项，展开是本项目每个已批准的检查行一行，加检查器自己的五条规矩（数由代码里的常量生成），来源写「项目编排带来的 · 只能看」；每次把结果交给 agent 时按每个检查报一次运行，超时报「失败」并写原因是超时。
6. 人加的检查（交给循环板）：系统能按已批准节点上的一条检查行读出命令参数表（节点或那行不在、不合语法、没批准、有几条又没指名时返回「没有」），能把占位的「文件」换成每个文件一项、以减号开头的名字前加「./」；人加的条目提议给你看时，看到的命令原文就是这条参数表，M4 不执行这类条目。
7. 「改完文件」这个事件带的是改过的文件（相对它所在检出的根）、检出的根、有没有截断，经投递进收件箱，没人听时不投；在工作树里改 src 下的文件，筛选 src 的条目就会跑。
8. 超时（这一条的取值、下限、上限和所有数只在设计 §6.3.1 和一个常量文件里）：你批准环境工具节点时，给你看的方案里每条检查行旁边有一句超时（例如「超时 9 秒（估 3 秒，乘 3）」），写明它从哪个估计算出来，没有估计时写明用上限；第一次的超时按估计的 3 倍算，跑过之后按最近几次里最慢的一次的 3 倍算；超时的那一次按「不短于当时上限」计，下一次的值随之升高；3 倍超过上限时保持上限，只告诉主 Agent，由主 Agent 决定：把这一项的上限调高并写明理由（调高不问你），或把检查拆小、收窄（那是改检查行，照常要你批准），提醒里把这两样分开写；调高和撤回在循环板页和晨报里立刻看得到，取这一项最后一次设置、不等下一次运行；每个超时值记一条（来源、时间、旧值、依据哪次运行），每次超时记一条（检查、上限、实际耗时、结局），循环板页和晨报都看得到；给 agent 的超时提醒写明检查名、上限、实际耗时和接下来怎样；超时不让这一行出错、不丢别的检查的结果。

## 第五件：环境分支与草稿区（m4-env，3 条）

1. 图上「环境」特性下的工具子节点，在每个 agent 的会话第一步、以及环境分支变动（工具节点或它的检查行增删改）后的下一步列出（至多 12 个、1500 字），带一行「改完哪些文件会跑检查」（指自带的检查器；循环板上人加的检查由循环板告诉主 Agent，不在这一行里）和一行草稿区在哪。
2. 会话所在仓库里，草稿区确实被 git 忽略；项目没忽略时，guard 行或 env 行第一次往这个项目的 `.llm/` 写东西之前，在本机的忽略文件末尾追加一行（已有就不重复加，重启多次也只一份），追加后再核对一次，仍没忽略时健康状态降级并写明原因。
3. 有一个办法能列出草稿区里的文件，供 M7 合入前的检查用。

## 第六件：跳过检查的注释计数（m4-suppressions，2 条）

1. 代码里跳过检查的注释，总数每天至多记一次（写在项目的 `.llm/` 下），按标记分类；装了指标服务时同时交一条计数事件。
2. 晨报写「跳过检查的注释 N 处（本期 +a / −b）」。

## 第七件：清理抓取脚本（m4-cleanup，1 条）

1. `.llm/docs/` 下的三个一次性抓取脚本和 `__pycache__` 删掉，抓下来的文件留着；删之前把重新抓取的办法、三个脚本里的地址和路径原样抄进一份参考文档；提交信息记下三个脚本的指纹。

## 合起来

七件都做完，这一整块（m4）就算做完；它本身没有单独的做完条件，随七件一起关掉，整批再过一次更强模型的逐条审查。

## 怎样改

最可能要你拿主意的是第三件第 9 条：申请开着时，装了 M7 的主 Agent 会停下自动推进等你回话。你要是不想因为一个申请就卡住推进，直接说，就改成不停、只在旁边标一条等你。想改别的哪条，说「第几件第几条改成……」。你定下之后再改这些条要你出手，所以放行时一起看。
