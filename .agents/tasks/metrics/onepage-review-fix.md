### 发现

1. **O1 MEDIUM：把一句不是人说的话当成人的原话引用。** 「替你定的」一节写「其中一件和你说的「启用那天起就拦」有出入」。人对这条决定（`d-code-rules-enforce`）的原话是「试运行规则啥的直接拦就行了，这样反而有问题好发现」（`CHARTER.md` §3.2 第 3 条、设计 §1.1 第 0.4 条依据）；「从所在插件行启用那天起就拦」是宪章与设计的转述，设计 §15 第 35 条写的是「`d-code-rules-enforce` 说的「从所在插件行启用那天起就拦」」，没有说是人的话。放行稿用「你说的」加引号，等于声称设计没有说的事；人读到会认不出自己说过这句话。改法：
   - 原文：`其中一件和你说的「启用那天起就拦」有出入。`
   - 改为：`其中一件和你定的规则一启用就拦有出入（你的原话是「试运行规则啥的直接拦就行了，这样反而有问题好发现」）。`

2. **O2 MEDIUM：样稿里 `/hourness` 给出的是「上周」的数，设计与代码都不是这样。** 样稿写「周一 09:10，你敲 /hourness」，输出的「/hourness 的末尾」第一行是「上周：派出 14 件，做完 11 件，等你 2 件，检查没过 1 次」。`/hourness` 的报告期是本地的当天（`src/report/index.ts:50`，`since` 取当天零点），设计 §7.3 让它改读指标流水，但没有改报告期，列出的也是「今天的用量计数」；按周给人的是 M7 的周报，设计 §7.3、§14 M7 ⑤ 写明它不读本流水。另外，设计里 `/hourness` 的「末尾一行」只是覆盖范围那一行（§7.3），派出几件与额度停住在报告正文里。人照样稿在周一早上敲 `/hourness` 等上周的汇总，看到的会是当天零点以来的数。改法（任选其一，推荐第一种，篇幅不变）：
   - 把场景改到当天：标题 `## 一个周一傍晚（示意）`；第一句 `你做什么：主 Agent 这几天在照片整理工具项目里做模块。周一 18:30，你敲 /hourness，再在命令行敲 npm run metrics -- summary。`；代码块第一段的标签由 `/hourness 的末尾` 改为 `/hourness 里`，第一行改为 `今天：派出 5 件，做完 3 件，等你 2 件，检查没过 1 次`，其余两行不变。
   - 或保留周一早上，删掉 `/hourness` 里的「上周」一行，另写一句「上周的汇总在主 Agent 的周报里，周报照旧，不读这份记录」。

3. **O3 MEDIUM：「下一次 /hourness 的末行就写出来」说早了。** 第 29 行写「缺了行、文件被删，下一次 /hourness 的末行就写出来」。设计里查出这些的是自查：指标行启动并第一次写成功之后在后台查一次前一天与当天的文件（§6.4 第一段），另有每天 10:00 一次的自查条目（§6.4 第二段、§15 第 20 条）；`/hourness` 的覆盖行只写「上次自查 <结果>」（§7.3），它自己不查。设计的说法是「人与主 Agent 在下一次会话里就看得到」。会话中途删了文件再敲 `/hourness`，末行仍是删之前那次自查的「没有问题」，与放行稿的说法相反。改法：
   - 原文：`缺了行、文件被删，下一次 /hourness 的末行就写出来。`
   - 改为：`缺了行、文件被删，启动后和每天一次的自查会查出来，写在 /hourness 的末行。`

4. **O4 NIT：两件共用一句「回「可以」就按我的建议定」。** `d-ask-three-gates` 要一件一个决定，「可以」接受的是那一件。两件放在一起时，人只想同意其中一件就不知道怎么回，主 Agent 记录时也要猜「可以」指哪件。改为：`每件回「可以」就按我的建议定，两件可以分开答。`

5. **O5 NIT：「本项目」指代不清。** 第 21 行「这些要等本项目改用自己的插件开发以后才动手做」紧跟在照片整理工具项目的场景之后，「本项目」容易读成照片整理工具。设计说的是本插件仓库的自举（§12，`d-dogfood-scope`）。改为：`指标记录要等这个插件仓库改用插件自己开发以后才动手做。`

6. **O6 NIT：「问话被退回」没说谁退给谁。** 样稿「问话被退回 2 次（太长）」与第 26 行「问话因太长、用词不合或一次超过三件被退回几次」，人可能以为是自己退回的。设计里这是 harness 在人看到之前拒掉主 Agent 的问话（`design.proposal-refused`，§4.5 M3 一节，`propose_to_human` 被拒不留 `design.proposal-shown`）。改为样稿 `主 Agent 的问话被系统退回重写 2 次（太长）`；第 26 行 `主 Agent 的问话因太长、用词不合或一次超过三件被系统退回几次`。

7. **O7 NIT：「会当场被拦」没有带上规则晚一步装的条件。** 第 28 行写「agent 去写、去删这些文件会当场被拦」，没有条件；同一页「替你定的」又说防误写的规则晚一步装、中间这段只能事后查出来（设计 §3.4 末段、§15 第 35 条）。两处相隔一节，读的人要自己对上。改为：`防误写的规则装上以后，agent 去写、去删这些文件会当场被拦，按规则编号记下。`

### 本遍新发现

8. **O8 MEDIUM：样稿让人在照片整理工具项目里敲 `npm run metrics -- summary`，设计里这条命令只在插件仓库里有。** 设计 §3.2 构件表把命令行写成 `src/metrics/cli.ts`、`scripts/metrics/cli.ts` 与「`package.json` 的 `metrics` 脚本」，§7.5 写「写法同 `npm run graph`」；根目录 `package.json` 的 `graph` 脚本是开发工作区的脚本，`packages/glm` 与 `packages/hourness` 的 `package.json` 都没有 `bin`，也没有 `metrics` 脚本。照片整理工具项目的 `package.json` 里没有 `metrics` 脚本（那个项目也不一定是 Node 项目），照样稿敲只会得到 npm 的 missing script 报错。在插件仓库里敲时，npm 把脚本的工作目录设为包的根目录（npm 文档 `npm run-script`：scripts are run from the root of the package folder），§3.3 第 6 条的 `--project` 默认取当前目录，得到的是插件仓库自己的记录；要看照片整理工具的数必须带 `--project`。样稿之后第 21 行「同意的比例……只在命令行里」与 ② 的代价「看比率只能自己敲命令」都落在这条命令上，人照样稿估这份代价时，少算了切到插件仓库、带上项目目录这一步。改法（约加 25 个码点，仍在上限内）：
   - 原文：`周一 18:30，你敲 /hourness，再在命令行敲 npm run metrics -- summary。`
   - 改为：`周一 18:30，你敲 /hourness，再到插件仓库的命令行敲 npm run metrics -- summary --project 加上照片整理工具的目录。`
