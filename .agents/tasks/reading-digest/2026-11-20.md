#### A1. Building strong safety evaluations（2026-11-13，Engineering）

链接：https://www.anthropic.com/engineering/building-strong-safety-evaluations 。实读层级：全文（抓取转述，细节以工具摘要为据）。

讲了什么（转述）：安全评测驱动部署决定、防护选择与安全训练优先级，「比上代更安全」这类结论只在评测可靠时成立；作者拿心理学可重复性危机的改革作类比（预注册、更好的测量、严格的统计）。评测队需要两种人：领域专家（定义伤害与边界情形）与方法专家（抽样、评分、统计），缺一边就得到「技术上对但没量到伤害因子」或「专家驱动但不可泛化」的评测。评测常关掉安全防护量基线，要在断网沙盒里跑并实时监控——Anthropic 在自己经历网络安全事件后停了多数联网评测、加固了环境。设计原则：观察性设计与因果设计分开，因果结论一次只变一个变量（同一模型带与不带某条系统提示）；构念效度——拒答率常常是错的构念，自杀自伤场景该量「恰当回应率」，多轮对话按专家 rubric 评、一轮坏整段判坏；双域（生物、网络）用有害提示（最大化无害回应率）配良性提示（最小化误拒率）对着量。泛化靠多轮模拟：专家写规格（用户目标、话术、人设、语气、情境），首轮固定，另一个 Claude 生成后续「用户」轮，被测模型答，grader 按 rubric 打分；维度独立变（严重度 × 语气）；场景从真实用法取材、当作演进集维护（16 个政策领域 × 7 种语言）。运行时内部效度：用晚于训练截止或自生成的数据防污染；关掉奖励作弊的路；随机化无关细节（选项顺序）。饱和：单轮 API 无害回应率近年的模型已到 94–98%，只剩回归检查的用处；更难的任务要保构念（更长程、更含蓄、更自然），不用偏题；评测也能过难（SWE-bench 被审出任务欠规定、测试拒正确解）。grader 校准：有标准答案的优先程序化判（注意模式匹配会丢「是的……但不包括这次请求」这类细微差别）；判据原子化二元化（一个分数一个是否问题），边界情形写明（什么算 exploit 代码、伪代码算不算）；免责与安全框定不改变有害内容；对 grader 藏设计元数据；用不同模型当 grader（模型自偏有文献）；量长度与位置偏好；样本用别的模型或 rubric 复评；grader 坏了要大声失败；对盲标人判做一致性校验（Cohen's kappa，与人对人的一致性比基准）。预注册：跑之前写下指标、比较、数据切片与提升阈值，偏离要披露。样本量：多轮至少 100 条、单轮建议 1,000 条，每例多跑几次，小差异用配对比较。报告：分类目拆开、未变的也报、多重比较校正、带置信区间（多轮 API 的区间能超过 ±10 个百分点）；示例：两代模型在诈骗评测 98% 对 94%，差异不显著，归因抽样噪声。配置差异要记录：同一模型 API 与 claude.ai（带系统提示）的恰当回应率能差 34 个百分点（Fable 5.1 多轮实测）；永远不跨 grader、不跨配置比较；用共享工具（UK AISI 的 Inspect、Anthropic 的 Petri）。缺陷披露：测试中发现模型有时默认认可自伤是应对方式，加一条定向系统提示（不告诉人自伤有用）把恰当回应率从 60%（API）提到 94%（claude.ai）；开发期持续跑评测让修复赶在发布前，严重缺陷给开发方留修复时间再公开。

#### B1. Build a voice agent that follows an SOP（Cookbook 文章，2026-11-10 进 registry）

链接：https://github.com/openai/openai-cookbook/blob/main/articles/sop_to_voice_agent_builder.md （站点 slug `sop-to-voice-agent-builder`）。实读层级：全文（仓库源文件直读）。

讲了什么（转述）：GPT-Live 语音模型做会话层，SOP（退货流程、排班访谈）这类程序化约束不靠塞提示词，靠分工：应用代码管能核对的（订单、报价归属、回复是否过期），后端模型照 SOP 提议工具，语音模型只管对话。四组机制：一、写操作前的一致性复核——后端模型提议开信用或换货时，应用另起一次不带工具的模型调用，只判「对方有没有真的同意刚才报出的每项条款」，要求对每项条款给出对话原文证据；程序再核报价是否仍归属本单、回复是否仍是最新的、同一报价是否已用过，任何一项不确定就不动账本（fail-closed）。78 例故意放行的对照测试里，强模型复核 142/142 全对，弱模型 133/142。二、过期信号丢弃——迟到的移交按时间戳对不上当前请求就丢；解释进行中对方改口，拿到结果先核 transcript 与记录版本没变，变了就丢旧解释、不落账。三、触发只启动检查、不授权写入——三条启动路径（模型移交、Decisions 对 transcript 的标记、静默超时兜底）都只把工作标记为进行中并按来源去重，落账仍要过一致性复核；重试带同一请求 id 幂等（同 id 同参数返回原结果）。四、盲评——比较两个后端模型照 SOP 的成功率时，评阅模型看不到预期价格，只从对话原文里找「实际报出的条款」，代码再对账（照完整 SOP 的成功率 68/68 对 65/68）。

#### B2. Inside the Codex sandbox（2026-11-18，Engineering）

链接：https://openai.com/index/inside-the-codex-sandbox/ 。实读层级：全文（抓取转述）。

讲了什么（转述）：Codex 沙盒不用容器搬环境，在用户现有环境里对命令做 OS 级限制（理由：iOS 构建这类工具链离不开宿主）。缺省 `:workspace` 档：工作区内可写，`.git` 与 `.codex` 只读（挡住改 config 与 git hooks）；全盘可读（编译器与 SDK 需要，代价是别处的敏感文件可读）；网络缺省关（挡外传，也挡依赖下载）。作者承认剩余风险：agent 可以把恶意代码写进 git-ignored 路径（如 `node_modules/prettier`），编辑器保存时触发就逃出沙盒——所以定位是纵深防御，沙盒之外还有训练对齐与审批流。架构：跨平台沙盒 API（`spawn_command_under_sandbox`），子进程整棵进程树继承限制，包括比父进程活得久的后代；shell 工具把进程启动换成这个调用；模型可按命令请求放宽（默认 / 加权限 / 沙盒外执行）并带面向用户的 justification，harness 决定问用户还是走自动审查。配置：命名权限 profile，规则 read/write/deny；网络三档（关、直连、代理 + 域名规则，显式 deny 压过 allow，未匹配域名要批准；DNS 解析推迟到批准之后，防用主机名外传，但宽通配与 DNS 访问仍可外传）；多层 config 递归合并（表合并、数组整体替换），企业 `requirements.toml` 钉不可覆盖项（如 `default_permissions = ":read-only"`、deny 全权档）。实现：macOS 用 Seatbelt（SBPL，`deny default` 起步，sandbox-exec 已废弃但 Chrome 仍在用，继续用）；Linux 用 bubblewrap + seccomp（挂载视图、unshare，代理 listener 建在沙盒网络命名空间内、经 Unix socket 对交给宿主桥接）；Windows 迁到微软 MXC 库（deny default，盘根只读、更具体路径覆盖祖先，冲突 deny > 只读 > 读写；剪贴板、输入注入、桌面与系统设置控制关闭）。

对本项目有什么用：

- 「工作区内可写、`.git` 只读」与本项目 guard 是同一个决定：`repoRelative` 把根下 `.git` 内的目标解析为界外（ORCHESTRATION.md 附录该条：返回 `undefined`）。两边独立得出，旁证，不用动。

#### B4. How OpenAI's Performance Factory keeps ChatGPT fast（2026-11-19，Engineering）

链接：https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/ 。实读层级：全文（webReader 直出）。

讲了什么（转述）：ChatGPT 性能工程的 agent 化：性能告警触发自动开任务，agent 查根因、提议修复、人审合入、部署后另一个 agent 核对恢复；三个多月跟踪 1,700+ 次调查、定性根因 600+ 例，日均约 17 次自动调查。演进六步：手工排查 → Codex 当助手 → 把排查过程固化成共享技能 `perf-forensics`（有哪些工具、何时用、怎么走，用历史回归做评测打磨）→ 工程师发现自己只是「告警到 Codex 的中转」→ 云端自动调查 → 完整工厂。系统四件：任务服务（工作流配置文件 + Markdown 提示词；任务状态、允许的转移、哪一步要人，全部声明式）；派发循环（周期查就绪任务，按当前状态起一个 Codex 回合并带上该状态的指示）；云端执行（服务身份跑，权限可圈、动作可归因，不依赖工程师的笔记本开着）；订阅（任务等人或等部署时挂起，GitHub 评审、CI 失败等事件到了才唤醒并重新就绪）。工作流要点：任务状态与发现写在任务上，不锁在任何单个 agent 的上下文里，人与 agent 接力、代码评审或部署后可续；对抗审查——另起一个 Codex 会话专门证伪诊断（复查假设、试反事实：回滚后指标恢复了吗？未暴露的同组请求健康吗？），早期无审查时手工抽查 100 例根因建议只有 70% 准确；有个案例，调查会话把失败归因于图片下载错误并标记已查明，审查会话发现定位服务已恢复而请求仍在失败，这个诊断解释不了持续失败，于是重开调查；修复比根因更难（改动过重、引入新问题），修复也加对抗审查，架构级取舍（加缓存换脏数据）由懂服务的工程师给方向；部署后只部分恢复的，原任务了结、剩余减速拆成新任务。评测：调查技能或模型的改动用历史事故回放测——剥掉会泄答案的细节、禁用历史记忆（先前调查的笔记）、事故报告与之前运行的结果，跑完检查 transcript 有没有泄漏测试该拦住的信息；开始时间、影响面、归因分开打分（时间对但怪错部署也算错）；交回摘要单独评——用存档任务快照，独立 grader 判「不熟悉系统的工程师能否看懂发生了什么、图表留得对不对、提议的下一步有没有证据支撑」。自修：每天一个 agent 扫近期运行的日志找工具失败与权限错误，同类错误多次就立任务修，人审合入，合入后用评测确认 agent 能过原先卡住的步骤。
