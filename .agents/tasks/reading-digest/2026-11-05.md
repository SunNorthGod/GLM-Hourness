#### A3. arXiv 2609.20804《An Empirical Study of Harness Design for Coding Agents》

链接：https://arxiv.org/abs/2609.20804 。版本：只有 v1（2026-09-17）。窗口内无新版本，窗口内无新引用（最近一篇引用是 2026-10-27）。

讲了什么（转述）：固定执行循环，只变规划、动作空间、上下文管理三个部件，四个模型在 SWE-Bench Verified 与 Terminal-Bench 2.1 上跑 176 组对照（五种上下文管理策略、四种窗口预算）。四条结论：上下文管理随窗口预算收紧而更有价值，收益主要来自防止溢出型失败；先做基于规则的省略、再做 LLM 摘要，效率最好，而把被省略的内容做成可恢复的机制，模型很少用，准确率也不涨；规划对弱模型是准确率脚手架，对强模型变成省钱手段；预置工具帮 bash 能力弱的模型，会用 bash 的模型只给 bash 也能干、而且便宜得多。轨迹分析：上下文管理拉长轨迹但不太改变行为，规划改变轨迹在哪里停，动作空间改变写代码的粒度。

对本项目有什么用：原批注记了第 1、3、4 条，漏了第 2 条，而第 2 条正好对着本周刚合入的两件事。

- `compact-recall`（2026-11-04 合入 main，`glm-hourness/transcript` 行默认禁用，节点 `doing`，待 L4 后由人定是否默认启用）：做法就是「压缩后给原文路径，模型用 Read 读回」（`docs/DESIGN.md` §5.6「压缩后读原文」）。论文的数据说这类可恢复机制模型很少用、不涨准确率。这不等于该删：本项目是照 ZCode 3.17.1 的逐字行为做的（方言贴训练分布，`CHARTER.md` §3 目标 1），GLM 在 ZCode 里见过这句话；论文的四个模型与任务（SWE 式单点修复、终端任务）也不是本项目瞄准的长程任务。但它给「是否默认启用」提供了一个可检验的预期：如果 L4 与以后的运行里 GLM 几乎从不 Read 导出的会话文件，就和论文一致。

#### A4. arXiv 2609.32459《Beyond the Model: Demystifying Harness Effects in Software Engineering Agents》

链接：https://arxiv.org/abs/2609.32459 。版本：只有 v1（2026-09-26），标题全名比 原批注多了「Beyond the Model:」。窗口内无新版本与新引用（4 条引用，最晚 2026-10-26）。

讲了什么（转述）：mini-SWE-agent 与 OpenCode 两个 harness、Qwen 与 DeepSeek 两族共十个开源权重模型，在 SWE-bench Pro、ProgramBench、GitTaskBench 上测；再搭一个模块化的 NanoHarness，分析工具注册表、上下文压缩、显式规划、子 agent、惰性 skills 五个部件。harness 的效果同时取决于模型能力与任务类型：模型越强，复杂 harness 在 SWE 式单点修复上的边际收益越小，但在更复杂、开放的仓库级任务上仍有帮助。部件层面，结构化工具使用与按任务定制的子 agent 收益最稳定，上下文压缩与通用子 agent 会伤害仓库生成任务的表现。组合起来 NanoHarness 在 Qwen3.7-Max 上比 mini-SWE-agent 高 7.37 个百分点、在 DeepSeek-V4-Pro 上高 6.21 个百分点。

#### A5. arXiv 2604.25850《Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses》与 arXiv 2608.25593《JIT-Agent: Scaling Harness Intelligence via Just-in-Time Harness Evolution》

链接：https://arxiv.org/abs/2604.25850 、https://arxiv.org/abs/2608.25593 。版本：AHE 最新 v4（2026-05-18），JIT-Agent 最新 v2（2026-09-03），窗口内都无新版本。

讲了什么（转述）：

- AHE：闭环的 harness 自动演化，靠三根「可观测性」支柱。组件可观测：每个可编辑的 harness 组件都有文件级表示，动作空间显式、可回退。经验可观测：把数百万 token 的轨迹蒸馏成分层、可下钻的证据库。决策可观测：每次编辑都附一条自报的预测，下一轮按任务结果核对，于是每次编辑都成了可证伪的合同。十轮迭代把 Terminal-Bench 2 的 pass@1 从 69.7% 提到 77.0%，超过人工设计的 Codex-CLI（71.9%）。冻结后的 harness 不再演化也能迁移：SWE-bench-verified 上少用 12% 的 token，换三个别家模型在 Terminal-Bench 2 上涨 5.1 到 10.1 个百分点。消融把收益定位在工具、中间件与长期记忆，而不是系统提示词；原文 "factual harness structure transfers while prose-level strategy does not"。
- JIT-Agent：训练一个专门的模型，在固定的四模块协议（记忆管理、规划策略、动作协议、工具与 skill 编排）下为任意现成模型即时生成、修复、自我演化 harness。摘要报告 GLM-5.2 最多涨 20.2 分，DeepSeek-V4-Flash 在两个基准上超过 GPT-5.6。

对本项目有什么用：

- AHE 的消融是本周最值得记的一条外部证据：可迁移的是事实性的结构（工具、中间件、记忆），提示词里的策略散文不迁移。本项目的规则板与代码规则（`d-code-rules-enforce`）、guard 四段式纠偏、M5 记忆都属于前者；`glm:persona` 汇报细度节、主 Agent 身份节（M3）属于后者。它支持「能进代码的规矩就进代码」，也提醒身份节写多了收益可能不迁移到下一代 GLM。
- AHE 的「每次编辑附一条预测、下一轮核对」与本项目的提议节点几乎同构，只差一个字段：提议现在写「为什么」（`why`）与验收，没有写「做完以后哪个数会变、变多少」。M5 学习流水线（`ORCHESTRATION.md` §8.5）把人的纠正变成规则提议，正好可以加这一条，让规则的收益可证伪。
- JIT-Agent 对本项目没有可用的东西：本项目的 harness 是逐字镜像 ZCode 的（方言），不是按任务即时生成的；GLM-5.2 的 +20.2 是在另一套 harness 上量的，对 GLM-5.3 加 ZCode 方言没有直接含义。

建议：

- AHE：提一个节点（提议，挂 `m5`，人定，新规范）：学习流水线产出的规则提议加一栏「预期效果」（哪个度量、往哪个方向、多久后核对），到期由 harness 按违规流水或标定结果核对，没达到就在晨报列出、建议撤下。理由：M5 的规则提议目前只有来源与理由，没有事后核对；加一栏预测是 AHE 消融里使演化不退化成试错的那一步，成本是提议多写一行、晨报多一项。
- JIT-Agent：不做。

窗口内引用 AHE 的新论文见 §D（2611.05139 Meta²、2611.03219 持续演化不遗忘、2611.03434「优化 harness 而不是模型」等）。

#### C2. A thousand fewer paths to root（2026-11-04）

链接：https://openai.com/index/a-thousand-fewer-paths-to-root/ 。读了摘要、方法、各阶段与「经验」各节，费用细表与附录没读。

讲了什么（转述）：OpenAI 用一个即将发布的网络安全模型搭了一条自动流水线，对 Linux 内核找漏洞、在隔离虚拟机里复现、评估可利用性、生成补丁，最后由人审。一次 2026 年 10 月中的运行复现了 1,724 个漏洞，做出 948 个能提权到 root 的利用，API 花费约 121 万美元。流水线按阶段分角色：scout agent 按「低权限用户可达、与安全相关」挑出约 7% 的代码作为审计目标；analyst agent 逐个目标读代码、建威胁模型、出候选发现（去重后 2,308 条）；triage agent 在带 KASAN 的虚拟机里写概念验证，反复改到复现或穷尽为止；ExploitDev agent 写完整利用；最后生成补丁。文中几条经验与 harness 直接相关：

- 「用错了 0-day」：早期一次运行报告 200 个成功的提权，人审发现其中 20 个拿到 root 用的是另一个漏洞，不是分配给它的那个。之后收紧任务约束，并加一道独立检查，确认最终利用用的是分配的漏洞。作者的结论是除了核对结果，还要核对通往结果的路径。
- 「更强的模型要的编排更轻」：给 GPT-5.5 Cyber 整理 103 种利用技术放进环境并提示它用，63 个候选上成功率从 76.2% 升到 88.9%；换 GPT-5.6 Cyber 后去掉这层，轻编排的结果反而超过 5.5 的重编排，加回去只多 1.5 个百分点。他们因此删掉了重编排，理由是收益不抵维护成本。
- 补丁要迭代：直接让模型写补丁，功能对但常常代码过多、偏离代码风格、漏掉同类变体；加指令与迭代后变好。建议用模型对人与 AI 写的补丁做对抗式审查。
- 测试基础设施本身会被发现漏洞：analyst agent 顺带找到并利用了 QEMU TCG 的一个漏洞。建议做攻防研究之前先测基础设施。

- 「先测基础设施」与 `risk-calib-read`（标定运行时被测模型读得到答案）同类：被测模型会利用环境里的漏洞。没有新动作。

归结起来，「对照验收逐条看」在全审里已经有了，靠的是审查者（LLM）；没有的是两样：harness 自己做的、不靠 LLM 的路径核对，以及轻审与不审时的路径核对。

建议：提一个节点（M7 设计待决，挂 `m7`，agent 可定）：交回处理第 7 条读出改动清单之后，harness 加一项确定性的路径核对，改动全落在测试文件里，或验收条件里用反引号写出的路径一个都没被改时，有效深浅升为全审并在批注里写明原因。理由：文章在「结果已被机器验证」的条件下仍有 10% 是走错路得来的；本项目的轻审与不审正好没有逐条对验收这一步；判定只用已经读出的改动清单，与 `floorHits` 同一处、同一种从严做法。局限：验收条件是散文，只有用反引号写出的路径能机器认，其余仍靠审查者。其余几条观望。

### D. harness engineering 新论文（2026-10-29 至 2026-11-05）

查法：arXiv 全文检索 `agent harness`（摘要内，按公布日期倒序，100 条，https://arxiv.org/search/?query=agent+harness&searchtype=abstract&order=-announced_date_first&size=100 ），窗口内约 90 条；按标题筛出与 harness 工程、压缩、规则、协调、证据相关的，再经 arXiv API（`http://export.arxiv.org/api/query`）取摘要。另用 Semantic Scholar 的引用接口查 §A 七篇的新引用（AHE 的引用里窗口内有 10 篇，多是自动演化方向）。所有条目只读了摘要，没有读全文，数字都是摘要里的。

窗口内的整体走向（转述，按标题与摘要数）：harness 自动演化与自我改进最多（Meta²、HarnessFlow、ParetoSaddler、EvoGroup、KARMA、RSI-Env、Recursa 等），其次是各领域的专用 harness 与基准，第三类是本项目最关心的「规则、证据、协调」，下面逐篇写的主要是第三类。

#### D1. arXiv 2611.03223《Do Agents Still Follow the Rules? Benchmarking Rule Compliance under Agent Context Compaction》（2026-11-02）

链接：https://arxiv.org/abs/2611.03223 。

讲了什么（转述）：在开源的 pi harness 上做了一个基准 ARCBench，从执行时的动作量规则遵守，而不是问答。发现：压缩很少把规则删掉，压缩后的违规大多发生在规则仍在压缩后的历史里的时候，模型把后来的请求当成许可、无视规则照做；规则怎么交付决定了不压缩时是否也会违反，压缩策略与预算决定规则是否活下来；针对压缩器的最强攻击把摘要里的规则改坏，违规翻倍以上；最强的防御能把规则恢复进大部分摘要，但仍有违规。最后一条最重：规则保留下来的压缩运行，违规仍是完整历史运行的两倍以上。

对本项目有什么用：和 B2 是两路独立证据，指向同一处。

- 本项目的 guard 与规则板在 `tools/pre-execute` 上由代码判（`ORCHESTRATION.md` §18.8 的文件门、`main-agent-no-write` 等，§6），不经模型记忆规则，压缩对它们没有影响。这一类不用动。
- 只写在提示词或每步 notice 里的规矩会受影响：每步投影、环境提醒、todo 提醒都是历史里的 notice（`DESIGN.md` §2.4a 的对照表：合成 notice 与用户消息同形），会被压缩掉，所以本项目在压缩后重注（`ORCHESTRATION.md` §2.5 第 1 条 `compaction`；env 行也在压缩之后的下一步注入，`DESIGN.md` 行表 `glm-hourness/env`）。论文说「规则还在也照样违反」，即只靠摘要保留不够，要由 harness 在压缩后从自己持有的出处重新陈述。本项目的投影重注就是这种做法，缺的仍是 B2 写的那一块（重锚时的规范摘要与本会话违规计数）。
- 「改坏摘要里的规则」这条攻击对本项目的对应物是压缩提示词：GLM 压缩用的是 ZCode 的提示词，其中有安全指令保留一条（`DESIGN.md` §5.6）。本项目没有测过 GLM 的摘要是否保留了图投影以外的约束。

建议：并入 B2 提的那个节点，不另开。理由：同一个缺口，两篇独立来源；节点验收里可以加一条「压缩之后的一步，被拦过的规则 id 出现在注入里」。

#### D2. arXiv 2611.04367《Do Coding Agents Follow AGENTS.md? The Effect of Policy Wording on Instruction Compliance》（2026-11-03）

链接：https://arxiv.org/abs/2611.04367 。

讲了什么（转述）：把同一条策略按四种写法插进 86 个基准任务的 agent 上下文文件，跑四种 harness 与模型的组合。条件式的写法（「如果……就……」）最不容易被遵守，指令式与解释式更好，两者谁更好随组合而变。

对本项目有什么用：本项目给模型的规矩分两处：代码判的门（纠偏四段：事实、越界、正路、例外，`ORCHESTRATION.md` §6.1，`main-agent-ask` 一条照此写），与只在提示词里的节（`glm:guard` 声明节、主 Agent 身份节、`glm:persona`）。四段式纠偏是在违规之后给的，属于指令式加解释式，与论文更好的两种一致。提示词里的节有没有写成条件式，本次没有逐句查。

建议：观望。摘要没有给效应大小，样本是基准任务里的一条策略；等 M3 主 Agent 身份节定稿审稿时，把「条件式改成指令式」作为一条审稿检查项提给审稿人即可，不需要节点。

#### D3. arXiv 2610.38392《Masked Erosion: How Acceptance Gates Lose Redundant Safeguards in Self-Improving Agents》（2026-10-28，窗口前一天，上次没读）

链接：https://arxiv.org/abs/2610.38392 。

讲了什么（转述）：自我改进的 agent 改自己的 harness（固定模型外的提示词与规则），只有在一批任务上得分更高的改动才被接受门禁留下。门禁只看当前模型下 harness 做了什么，看不到某条保护失效时其余保护还能挡住什么；保护有重叠时删掉一条是被掩盖的，门禁只按任务成功率判，冗余就在看不见的地方被侵蚀。四条成文保护的每个子集都量了伤害，跑 411 次改进循环、十种门禁规则。被另一条仍有效的保护挡在后面的删除几乎不增加可见伤害；换更弱的模型复用这个 harness 时，丢掉的深度就变成真实伤害；GEPA 优化器逐字保留了所有安全规则，三个最终 harness 里仍有两个在更弱的模型下误用了凭证。冻结安全文本或审计单层消融能保住深度。

对本项目有什么用：两处。

- 撤下代码规则：m4 的批注写了「补上撤下一条代码规则的路（§3.5）」（`docs/graph/nodes/m4.json`），M5 学习流水线把人的纠正变成规则提议（`ORCHESTRATION.md` §8.5）。论文说明撤规则时不能只看「撤了之后有没有出事」，因为别的规则可能在替它挡着。本项目 guard 的多条规则确实重叠（`file-tools-only` 与 `main-agent-no-write` 都判写文件的 shell 命令，`ORCHESTRATION.md` 「`main-agent-no-write`」一条写明两者用同一个判断）。
- 和 C2 的「模型变强就拆脚手架」放在一起读：拆脚手架的依据是「拆了以后结果没变差」，正是论文说的被掩盖的情形。本项目的标定若做逐行消融（上次摘要 §4 第 3 条），关掉一行没变差不等于这一行可以删，要看它挡的那类错误是否有别的行替它挡着。

建议：不另开节点，作为 A5 那个节点（规则提议加「预期效果」一栏）的配套条款写进去：撤下一条规则的提议，要写明还有哪条规则覆盖同一类调用，没有替补就要人看过单层消融的结果再撤。理由：成本是撤规则时多写一行，防的是论文量出来的那种看不见的退化。

#### D4. arXiv 2611.04100《The Agent Board: Kanban for Machines; Durable Coordination for Agents That Outlive the Conversation》（2026-11-03）

链接：https://arxiv.org/abs/2611.04100 。

讲了什么（转述）：harness 普遍收敛到单线程形态（一个 agent、一段历史、一台机器、一次坐下），做不了跨多个 agent、活过单次模型调用、要等非 agent 系统的工作。Corvic harness 的 Agent Board 是一张持久共享的任务表：少数系统据以路由的精确字段，加一段只有模型读的自由正文。agent 发任务、盯任务、挂在任务上等，结束本轮、不占进程，有匹配的发帖时被叫醒。一个系统 agent（Board Keeper）把 harness 里非 agent 部分的事件搬上板，读正文把它们匹配到等待的任务。策略内核可加载，决定状态与角色的含义，板本身不强制。试点里板的等待成本不随等待时长变，朴素轮询涨了约 165 倍，但一个简单的外部 watcher 比板还便宜；Board Keeper 匹配正文等待者时没有误唤醒，但漏了 3.6% 的真实唤醒。

#### D5. arXiv 2610.39468《Soei: Structured Observability of Evidence and Intent for Multi-Agent AI Software Engineering》（2026-10-29）

- arXiv 2611.03434《Optimize the Harness, Not the Model》（2026-11-02，https://arxiv.org/abs/2611.03434 ）：CLEO 只接纳能提高准确率又通用、可审计的工具、护栏、记忆策略与循环部件，给固定的自托管模型配出最小 harness，在保留集上 83.8%，离最强的 Claude Code SDK 基线 1.2 个百分点，体量小两个数量级。对本项目：与上次摘要 §4 第 3 条（逐行消融）同向，读时要和 D3 一起读。建议：不做。
- arXiv 2610.41172《Context as Infrastructure》（2026-10-30，https://arxiv.org/abs/2610.41172 ）：只给 BM25 或 grep 的检索 harness 已经很准，缺的是上下文纪律；结构化的知识编译不提准确率，是供给层，能在证据够时把查询 token 降 91%。对本项目：和 A2 的「十一个系统都不用向量检索」一致，M5 记忆召回走确定性检索的路没问题。建议：不做。
- arXiv 2611.06727《Airlock》（2026-11-04，https://arxiv.org/abs/2611.06727 ）：多 agent 系统里一个 agent 的错误输出会沿下游扩散，用只追加的出处 DAG 记录跨 agent 的数据消费，报警时向前隔离受污染的执行、向后缩小根因。对本项目：M7 设计的简报门禁只在派发那一刻查依赖都完成（`.agents/tasks/m7/design.md` §3.5.1 的 `deps_open`），依赖先完成、后来被重开或判错时，已经派出或已经做完的下游任务怎么办，按关键词没有查到写法〔只按关键词查了 m7 设计，没有通读〕；项目图有依赖连线，下游可以推出。建议：观望，M7 设计复审时问一句。
- arXiv 2611.01950《CertClaim》（2026-11-01，https://arxiv.org/abs/2611.01950 ）：编码 agent 服务按声称的模型计价，提供方可以合法地改采样预设、推理模式或系统提示词而不换模型，旧的审计方法因此要么冤枉诚实的提供方、要么漏掉便宜的替身。对本项目：与 B1 同属「回答出自哪个模型」，是提供方与用户之间的事。建议：不做。
- arXiv 2611.06506《Trace2Eval》（2026-11-04，https://arxiv.org/abs/2611.06506 ）：从真实交互轨迹重建任务、还原工作区、建等价执行环境，用对齐过人的评分准则与评审 agent 打分。对本项目：上次候选第 8 条说新标定题取自真实失败，这篇给了一条自动化的做法；本项目规模小，手工出题足够。建议：不做。
