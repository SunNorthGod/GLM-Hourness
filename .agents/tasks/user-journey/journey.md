## 0. 这张图怎么用

用途（来自节点 `user-journey` 的正文）：

1. 每份设计的一页放行稿标出自己落在哪几格。评审时对照：缺格、两个模块抢同一格、和这张图说法不一致，都算问题。
2. 自举（`dogfood`）与真实项目试用（`field-trial`）按这张图逐格走一遍，当作怎样算做完的核对。
3. 和方向清单（§7）放在一起看，人就知道产品长什么样。

编排方在设计之间做的接缝裁定（agent 定、可推翻，不是人的方向）补上了几处格子，逐条落在哪一格见 §6.2；格子里写「接缝裁定」的就是它。

读法：横着是十个阶段（§2、§3），每个阶段竖着四行：用户做什么、用户看到什么、系统自己做什么、什么时候来问用户。每一条后面的〔〕写负责它的模块。

问用户的方式只有三种，表里照这三个词写：

- 对话：主 Agent 用一两句开放的问题问「要什么、做成什么样」，带上它的猜测（`d-chat-not-cards` 2026-10-29T17:16Z）。
- 四行：一件事一个方案，题目单独一段，下面背景、推荐、疑问、不做四行各自成段，每行把重点几个字加粗，问话放在整条回复最后；一条回复至多三件，编号 ①②③（`d-chat-not-cards` 17:27Z 定稿，M3 附录 0.5 §3.3、§3.4）。人说同意、补一句或否掉；人随口回答时主 Agent 先复述「那我记成：……」再记。
- 不问：只告诉，或者什么都不说。

人自己打的命令（`/wish`、`/rules peak`、`/loops delete` 等）不算问人，表里写在「用户做什么」。

- 写在代码里的规则（guard 的规则、M4 新加的规则、循环板与指标流水各自写在代码里的规则、接管项目读仓库时不开 shell 的规则）不设试运行：从它所在的插件行启用那天起就拦，没有「只记下，不挡」一档，也没有攒样本再转正的阶梯（`d-code-rules-enforce`，你的话：「试运行规则啥的直接拦就行了，这样反而有问题好发现」）。新的插件行仍默认禁用、验证过才启用（`AGENTS.md`），这管的是行，不是规则。每一次拦下都写进项目 `.llm/` 里 guard 已经在写的那份违规流水，带规则 id、时刻、拦了什么和为什么，规则页和晨报按规则 id 计数，拦错了因此能发现；撤下一条规则只有一条路（编排方裁定 `d-one-lift-path`，2026-10-31，可逆，不是人定的）：你跟主 Agent 说一句话，或打 `/rules lift <规则 id>`；你同意过的板上条目和写在代码里的规则都走它，规则页把这两种说法都列出来；恢复同样是一句话或一条命令。写在代码里的规则，规则板把撤下交给拥有这条规则的插件行：M4 的规则交给 M4 的撤下记录（`docs/guard/lifts.jsonl`，`guard_lift`）。M4 保留这份记录和门里的判断，不另设面向人的命令（M4 0.6 §3.5：服务 `glmHournessLifts`、工具 `guard_lift`，第一版的 `/guard lift` 已删）。这是 `d-defaults-readonly` 的例外：插件自带的写在代码里的规则，你可以撤下，不能改（`d-code-rules-enforce` 要的「一句话或一条命令就能撤」，§7）。接管项目的读项目门禁 `bootstrap-read-no-shell` 同样走这一条路，接管不另设命令（接管项目 0.6 的复核 F2 删了 `/hourness-init unlock-shell`）。规则板 0.10 的 `/rules lift <id>` 今天只管板上的条目，代码规则目录里的条目只读，§1.4 第 12 条写着「没有解除」；M3 的八条与 M7 的门改经 `installRuleGate` 安装之前也不在撤下的范围内。三处：规则板 0.10、M3 的八条、M7 的门，见 §6.1 G26。只能事后发现的规则拦不住（例：一轮结束才看到 shell 写了不该写的文件），不装作拦：M4 0.6 把这类兜底改成在那个 agent 的下一步之前送一条纠正提醒，并记一条晚到的拦下（§3.4，G27）。〔M4〕〔规则板 §9.1〕〔循环板〕〔指标流水〕〔接管项目〕
- agent 可以读登录密钥文件：不设读密钥的规则，也不记录谁读了（`d-credentials-readable`，你的话：「密钥文件能读。而且不是都能读吗？什么叫没拦？」）。没变的是密钥不进日志与提交的检查，和 GLM 登录信息只放在用户级目录（S2）。〔M4〕〔GLM 通道〕
- 拦路的脚本（工具调用之前、派活之前、主干前进之前）用退出码说放行、拦下或排队。超过超时先按条目写明的做法判，缺省放行、主干前进之前缺省拦下；脚本在后台接着跑至多 10 分钟，晚到的拦下当场告诉主 Agent 理由，由它改或回退（`d-script-timeout`）。超时是几秒，见下一条。〔规则板 §6.7〕〔循环板 §6.6〕
- 超时怎么定（人定，`d-timeout-measured`；你问的是：「要不让llm自己写时间或者实际跑过一次后再由llm写时间？」，定的是：「超时那就这样定。不过还是我说的现在拿不准的事情，要做到优雅失败以及可追溯性」。第一个数是什么，由编排方 2026-10-31 裁定，可逆，不是人定的，见 `d-timeout-measured` 08:17Z 的批注）。这一条是规则全文：
  - 怎么算：写脚本或检查的 agent 估这条命令跑一次大约要几秒，叫预计用时。超时一律是预计用时的 3 倍。第一次用它的估计；真跑过之后，harness 改用最近几次里最慢一次的运行时间，不让 LLM 把实测数手抄回去。没有估计时用下面各处的缺省值。
  - 你看到什么：批准脚本或检查时，看到的是超时，旁边写它依据哪个预计，例如「超过 12 秒算没跑完（写脚本的 agent 估计跑一次 4 秒）」，和脚本原文（检查是命令原文）一起。跑过之后超时变了，规则页和循环板页写新的值和它依据的几次实测。
  - 最长值与缺省：3 倍超过最长值时保持最长值，并告诉主 Agent 一次，不自己抬高最长值。数是今天各设计里写的：拦路的脚本（工具调用之前、派活之前、主干前进之前）缺省 10 秒、最长 30 秒（规则板 0.10 §1.3 与 §6.7、循环板 0.6 §6.6 的 `GATE_TIMEOUT_MS`、`GATE_TIMEOUT_MAX_MS`；编排方 2026-10-31 裁定按这两个数）；不拦路的脚本缺省 60 秒、最长 1800 秒（循环板 §6.6）；改完文件就跑的检查每个最长 60 秒、一步最多等 20 秒，没有估计时取最长值（M4 §6.3.1；M4 另有 5 秒的下限，别的设计没有，G28）；合入前的检查每条最长 30 分钟，没有估计时取 30 分钟（M7 §3.8.1）；人加的检查在循环板的执行器里另有超时和上限（循环板 §6.6），同样按这一条。
  - 接管来的命令：没有 agent 为它们写预计，预计取试跑实测（系统量的，冷缓存，会偏慢），不由主 Agent 估；超时同样是预计的 3 倍，不超过该类的最长值；没有试跑结果的，清单写「没预计」，超时写该类的缺省并标「（默认）」（接管项目 0.6 §2.5）。试跑自己的限时（每条 10 分钟，合计 45 分钟，S4）是固定的安全上限，不按这一条算。
  - 出了岔子不崩（优雅失败）：超时和出错都不让行崩、不丢已做的工作，结局照条目自己写明的办法走。拦路的脚本放行还是拦下按条目写的，缺省放行，主干前进之前缺省拦下，脚本在后台接着跑至多 10 分钟，晚到的拦下当场告诉主 Agent（`d-script-timeout`）；合入前的检查超时算没过；改完文件就跑的检查超时算没跑完，下一次改动照常再跑（后两条是接管项目 0.6 §2.5 与 M4 §6.3.1 的写法）。发出的消息写明是哪一条、限了多少秒、已经跑了多久、下一步怎么办。估错的数只影响下一次的值。
  - 看得出来历（可追溯）：每个超时值记着来源（agent 的估计，或按哪几次实测算的，被最长值截住时记想要的值）、时间和上一个值；每一次超时记下是哪一条、限了多少秒、实际跑了多久、结局。超时值、来历和每次超时在规则页、循环板页与晨报里看得到，周报本来就数超时次数。
  - 本稿各格子提到超时，都指向这一条；§6.1 G28 与 §6.3 是缺口与请求，数只写在请求要改的那一处；§6.4、§7、§8 是记录。M4 0.6 与接管项目 0.6 按这一条写，各写一处（M4 §6.3.1，接管项目 §2.5），细节不同的几处见 G28；已放行的规则板 0.10、循环板 0.6、M7 0.6 写的是第一个数就是超时本身或固定的数，改法是请求（§6.3，G28，自举之后办），办完之前它们照自己的写法跑。〔循环板 §6.6〕〔规则板 §6.7〕〔M4〕〔M7〕
- 高峰模式按档位执行，见 §5.3。档位与少做的上限归规则板，发给模型的提醒原文归 M6，M7 只在派活与数空转时各读一次（接缝裁定 1、3、8）。〔规则板〕〔M6〕〔M7〕〔循环板〕
- 子 agent 跑危险的 git 命令之前同样先存快照。〔M7 §3.2.4〕

## 5. 用户会碰到的失败

### 5.1 GLM 登录过期

用户看到什么：

- 主 Agent 跑在别的模型上时：主 Agent 在下一次回话里告诉人运行 `/glm-login`，每件说一次；这种整个账号的事只告诉最近一次干过活的那个主 Agent。〔循环板：登录失效时提醒你重新登录〕〔M6〕
- 主 Agent 自己跑在 GLM 上时：它也回不了话，人在 DSH 里直接看到请求失败（M6 一页稿）。失败时的报错是不是人话，见 §6 G14。〔GLM 通道〕〔M6〕
- `/glm-status` 那一段第一行写登录失效，后跟 `/glm-login`。〔M6〕

系统自己做什么：读额度时服务端拒绝登录只算一次失败，不重试、不重铸令牌（照 ZCode 的做法）；登录被拒记进指标流水，行健康写明。〔M6〕〔指标流水〕

什么时候问用户：不问，只告诉。人打 `/glm-login` 重新登录。

### 5.2 额度快用完（与用完）

用户看到什么：

- 5 小时或每周额度用到 80%，或者照现在的速度一小时内会用完：主 Agent 在下一次回话里说一句，每个额度周期只说一次。〔循环板：额度快用完时告诉你〕〔M6〕
- `/glm-status` 与 `/hourness` 写各个窗口用了多少、几点重置、预估何时用完。〔M6〕

系统自己做什么：读额度只在 GLM 正在用时，至多每 15 分钟一次；上游限额错误写进额度流水；这些数记进指标流水。〔M6〕〔指标流水〕

什么时候问用户：不问，用完时只告诉你，重置后自己接上。插件不替人换模型或套餐（`CHARTER.md` §6）。

额度真的用完时（你 2026-10-31 定：「额度重置后自动接上」）：自动推进停住，主 Agent 在对话里告诉你；额度重置之后推进自己接上，不等你说一声。这是人定的，设计还没有写：规则板 0.10、M3 附录 0.5、M7 0.6 里找不到额度或上游限额，循环板 0.6 只有「额度快用完时告诉你」这一项，M7 的空转、轮次上限与阻塞原因码里没有额度这一类；怎样知道额度重置了、主 Agent 自己跑在 GLM 上时谁来告诉你，也都没写，见 §6.1 G15。2026-10-31 凌晨账号用量超限（`Overage limit reached`），本项目自己的后台运行大部分步骤因此失败（图上 `orch` 的批注），是这个缺口在自举开发里的一次实例。

### 5.3 高峰时段，默认少做

时段：工作日 14:00–18:00（UTC+8），GLM 按全价计积分，其余时间半价（`docs/ORCHESTRATION.md` §11.1）。

### 5.4 崩溃或重启

用户看到什么：

- 一般什么都不用做。重启后自动推进接着走；晨报「规划」一节写哪件活在重启时丢了。你自己按的暂停不替你恢复；关桌面版前 30 秒内发生的暂停算关机带来的，重启后恢复，提醒里写明，你再停一次就行（M7 §3.9.1）。〔M7〕
- 主 Agent 的会话被归档或找不到时，首页与循环板最上面写「在一个会话里打 /wish here」。〔循环板〕〔M3〕
- 规则板的存档里出现不是它自己写的记录，或仓库里的规则文件被规则板以外改过（git 拉取、切换、回退、手改）时，规则页「提议与恢复」列出来，不生效，等你打 `/rules recovery` 照改或忽略。〔规则板〕
- 读不出模块的结构时（`src/graph/modules.ts` 出故障），分了模块的项目里一件活也派不出去、在跑的子 agent 也写不了，状态里写明原因，读得出来之后恢复；没分模块的项目不受影响。〔M7 §3.9.7〕

系统自己做什么：

- worker、审查与检查随宿主进程结束；状态在图与会话日志里，会话可以丢。〔M7〕
- 循环板「重启之后接上」触发 M7 的对账：推进中的 goal 恢复（人暂停的不恢复）；丢了的派活批注「在宿主重启时丢失」，下一次简报写分支上已有哪些提交；审查过、还没进主干的标「可以合入」；不会重复派活。〔循环板〕〔M7 §3.9.6〕
- 同一件事被报两遍只做一次；真的又重启一次照常再做。〔循环板〕
- DSH 定时服务的提醒跨重启保留；宿主没运行时到点的不补投，巡检报漏跑。〔循环板〕〔M7〕
- 主 Agent 是哪个会话，记在持有者记录里，重启后仍是同一个会话。这份记录今天（M3 附录 0.5 §2.4）放在用户级目录；宪章 0.8 §9 与 `d-rules-in-repo` 要它进项目的 `.llm/`，搬家留给 M3 的对齐轮，见 §6.1 G24。〔M3〕
- 规则板「在等的工作」从变更记录重建；条件解除后 30 秒内叫原来的 agent 再试，原来的子 agent 已结束就交给派它的主 Agent。〔规则板〕
- 换电脑、新克隆或删掉 `.llm/` 之后，规则与循环条目照仓库里的文件读回来；带脚本的只有图上有你看过原文、拍过板的记录才跑，没有的列出来等你再同意（`/rules recovery` 照改之后新加或改过的脚本同样等你同意）。〔规则板 §7.5〕〔循环板 §9.3〕
- git：会丢工作或改写历史的命令之前已存快照，可以按通知里的命令恢复。〔M3〕〔M7〕
- 申报的放行只存在内存里，重启后丢掉，agent 重新申报。〔M4〕
- 循环板对账只在没有主 Agent、会话已归档或找不到时删自己建的定时任务；持有者状态「在别处」「不明」（持有者记录读不出也算）时一律不删、不搬、不重建，页面标出、行健康报出；删之前先证明是自己建的、已经没用，并把全文写进 `removed-tasks.jsonl`（循环板 0.6 §6.2、§6.4、§9.1，关掉 0.3 的 F35，§6 G17）。〔循环板〕

什么时候问用户：不问。要人动手的只有两处，都是告诉：会话归档时打 `/wish here`；规则存档或规则文件异常时打 `/rules recovery <编号> 照改` 或 `忽略`。

### 5.5 方案被否掉

用户看到什么：

- 人说「不行，因为……」之后，主 Agent 按理由换一个方案再提；面板「需要你」里这一件一直列着，直到新的一版被同意。〔M3〕〔面板〕

系统自己做什么：

- `record_human_answer` 的 `reject`：在待决或目标上批注「人在对话里否掉：「原话」；主 Agent 记成：……」，状态不变。〔M3 附录 §3.5〕
- 改方案再提时，同一张待决改四行；人同意只算最新一版，对上一版的同意不算。〔M3 §3.5、§3.6〕
- 确认需求被否：改需求再提 `confirm`；放行被否：改方案再提 `release`（分了模块的目标，被否的是大循环那一次或某个模块那一次，只重提那一次）。目标或模块的阶段不变，子 agent 仍只读。〔M3〕
- 人要的是这件事不用定了：主 Agent 带人的原话把待决改为放弃。〔M3〕
- 放行之后才发现不对：只改某个模块的设计方向的，主 Agent 自己把这个模块的阶段改回设计，不要你的原话，你重新看一页放行稿；改到整个框架的，你说一句，主 Agent 带你的原话把目标退回设计，受影响的活先停；没分模块的目标按后一种走。退回之后新派发被拒、在跑的 worker 写不了、交回按过期处理，子 agent 因阶段回到设计而只读，别的模块不受影响；已经进主干的活不动，要不要重做是新设计的事。〔M3 附录 §3.14.6、§3.14.8〕〔M7 §3.9.7〕
- 规则或循环条目的提议被否：什么都不变。〔规则板〕〔循环板〕
- worker 的计划被主 Agent 打回：人不出场，晨报「理由」一节计数。〔M7〕
- 否掉的次数进指标流水。〔指标流水〕

什么时候问用户：新的一版仍是四行。

### 5.6 审查一再不过

### 6.4 人答过的两件事，和一件已定的超时

0.5 时这里是两件要人定的事，四份已放行的设计没写，也没有哪份设计替人定过。人 2026-10-31 都答了，下面三件都已定；设计还没写的部分留在 G15、G18、G28，请求在 §6.3。

额度用完时自动推进怎么办（人定）

你的话：「额度重置后自动接上」。

定的是：GLM 额度用完后，自动推进停住，主 Agent 在对话里告诉你；额度重置之后，推进自己接上，不等你说一声。不替你换模型或套餐（`CHARTER.md` §6）。设计要补的三处写在 G15 一行：阻塞原因码与恢复由谁触发，怎样知道额度重置了，主 Agent 自己跑在 GLM 上时谁来告诉你。

目标做完时怎样告诉你（人定）

你的话：「至于目标的话。。做完一点汇报一点，或者等收菜」。编排方把它读成下面三句，你回：「都没问题」。

定的是：目标的一部分做完时（一个模块，或接管来的项目里挂在目标下的一个里程碑；没分模块的新目标「一部分」按什么算，G18），主 Agent 用一两句话说一声；你不在的时候这些汇报先攒着，你回来时一起交给你（收菜）；整个目标做完时，一句话带上整体审查的结论。设计要补的写在 G18 一行：攒着的汇报由谁攒、怎样知道你回来了、和晨报的关系。

脚本与检查的超时怎么定（人定）

你的话：先问「还有超时的时间咋办？要不让llm自己写时间或者实际跑过一次后再由llm写时间？」，编排方推荐后你定：「超时那就这样定。不过还是我说的现在拿不准的事情，要做到优雅失败以及可追溯性」。

定的是 S7「超时怎么定」一条：写脚本或检查的 agent 估预计用时，超时一律是它的 3 倍（第一次用估计，跑过之后由 harness 用最近几次里最慢的一次，LLM 不手抄实测数），不超过上限；你批准时看到超时和它依据的预计；超时不崩、有说清楚的结局；每个值的来历与历史、每一次超时都留痕。第一个数是预计用时这一点是编排方 2026-10-31 的裁定（可逆），不是你的话。M4 0.6 与接管项目 0.6 按它写，已放行的规则板、循环板、M7 的改法见 §6.3 与 G28。

三件都不挡本稿的评审。
