## 0. 这张图怎么用

用途（来自节点 `user-journey` 的正文）：

1. 每份设计的一页放行稿标出自己落在哪几格。评审时对照：缺格、两个模块抢同一格、和这张图说法不一致，都算问题。
2. 自举（`dogfood`）与真实项目试用（`field-trial`）按这张图逐格走一遍，当作验收。
3. 和方向清单（§7）放在一起看，人就知道产品长什么样。

编排方在设计之间做的接缝裁定（agent 定、可推翻，不是人的方向）补上了几处格子，逐条落在哪一格见 §6.2；格子里写「接缝裁定」的就是它。

读法：横着是十个阶段（§2、§3），每个阶段竖着四行：用户做什么、用户看到什么、系统自己做什么、什么时候来问用户。每一条后面的〔〕写负责它的模块。

问用户的方式只有三种，表里照这三个词写：

- 对话：主 Agent 用一两句开放的问题问「要什么、做成什么样」，带上它的猜测（`d-chat-not-cards` 2026-10-29T17:16Z）。
- 四行：一件事一个方案，题目单独一段，下面背景、推荐、疑问、不做四行各自成段，每行把重点几个字加粗，问话放在整条回复最后；一条回复至多三件，编号 ①②③（`d-chat-not-cards` 17:27Z 定稿，M3 附录 0.4 §3.3、§3.4）。人说同意、补一句或否掉；人随口回答时主 Agent 先复述「那我记成：……」再记。
- 不问：只告诉，或者什么都不说。

人自己打的命令（`/wish`、`/rules peak`、`/loops delete` 等）不算问人，表里写在「用户做什么」。

## 3. 逐阶段

### S1 装上两个插件

用户做什么：

- 在 DSH 的插件管理里装 `dsh-glm-zcode`（GLM 通道）与 `dsh-hourness`（编排层），也可以只装一个（§4）。〔GLM 通道〕〔编排层各行：split，已合入〕
- 装完重启桌面版。插件管理器显示「已应用」只说明行被接受，重启之后才算启动（`AGENTS.md` 强制流程第 5 条）。〔GLM 通道〕〔编排层各行〕

用户看到什么：

- 插件页的描述各有一句从哪开始。编排层：「装好后：在新会话里点「把这个工作区交给主 Agent」，或打开右侧栏的「项目图」」。GLM：「装好后：在新会话里点「GLM · 上手」登录」。〔新手引导，面板 0.6 §6.2〕
- `/glm-status` 与 `/hourness-status` 列出每一行是否生效；出故障的行写明原因（`CHARTER.md` §3.1 第 3 条、§3.2 第 4 条）。〔GLM 通道〕〔编排层各行〕

系统自己做什么：

- 各行激活。配置缺失或出错时只告警、降级，不抛错，并在行健康里上报。〔GLM 通道〕〔编排层各行〕
- 两个包互不导入对方的代码与界面，只装一个照样能用（`CHARTER.md` §3、§5）。〔GLM 通道〕〔编排层各行〕

什么时候问用户：不问。

### S2 登录 GLM

用户做什么：

- 点开场画面工作区那一行右端的「GLM · 上手」，或输入框下方的 GLM 按钮。〔新手引导，面板 0.6 §6.3〕
- 点「登录」，在浏览器里授权（链接 5 分钟内有效）；在输入框右下角的模型选择器里选「GLM（ZCode 原生通道）」下的模型；发一句话试试。〔GLM 通道〕〔新手引导，面板 0.6 §6.3〕

用户看到什么：

- 对话框顶上「第一次用 GLM 通道」三步；读到已登录后第 1 步打勾，关上之后这一块不再出现，设置页「GLM-Hourness」里能重开。〔新手引导〕
- 没登录就发消息时，报错先是中文「还没登录 GLM：点输入框下方的 GLM 按钮登录」，后接原来的英文。〔GLM 通道，面板 0.6 §6.3〕
- `/glm-status`：现在是不是高峰、到几点；5 小时额度与每周额度各用了多少、几点重置、照现在的速度什么时候用完，每一行写明按什么算的。额度数字来自服务端，ZCode 等别的软件用掉的也算在内。〔M6 一页稿〕

系统自己做什么：

- 凭证加密存在用户级目录 `$DSH_HOME/glm-hourness/`（`CHARTER.md` §9）。〔GLM 通道〕
- 请求按 ZCode 3.17.1 发：身份头、版本号、签名、系统提示词与工具面都跟 3.17.1，用户的工程环境声明照旧（`d-zcode-3171`）。〔GLM 通道〕
- GLM 正在用的时候至多每 15 分钟读一次额度，没人用 GLM 时一次都不读；失败不重试。〔M6〕

什么时候问用户：不问。只有人点「登录」才执行 `/glm-login`。

## 5. 用户会碰到的失败

### 5.1 GLM 登录过期

用户看到什么：

- 主 Agent 跑在别的模型上时：主 Agent 在下一次回话里告诉人运行 `/glm-login`，每件说一次；这种整个账号的事只告诉最近一次干过活的那个主 Agent。〔循环板：登录失效时提醒你重新登录〕〔M6〕
- 主 Agent 自己跑在 GLM 上时：它也回不了话，人在 DSH 里直接看到请求失败（M6 一页稿）。失败时的报错是不是人话，见 §6 G14。〔GLM 通道〕〔M6〕
- `/glm-status` 那一段第一行写登录失效，后跟 `/glm-login`。〔M6〕

系统自己做什么：读额度时服务端拒绝登录只算一次失败，不重试、不重铸令牌（照 ZCode 的做法）；登录被拒记进指标流水，行健康写明。〔M6〕〔指标流水〕

什么时候问用户：不问，只告诉。人打 `/glm-login` 重新登录。

### 5.2 额度快用完（与用完）

用户看到什么：

- 5 小时或每周额度用到 80%，或者照现在的速度一小时内会用完：主 Agent 在下一次回话里说一句，每个额度周期只说一次。〔循环板：额度快用完时告诉你〕〔M6〕
- `/glm-status` 与 `/hourness` 写各个窗口用了多少、几点重置、预估何时用完。〔M6〕

系统自己做什么：读额度只在 GLM 正在用时，至多每 15 分钟一次；上游限额错误写进额度流水；这些数记进指标流水。〔M6〕〔指标流水〕

什么时候问用户：不问。插件不替人换模型或套餐（`CHARTER.md` §6）。额度真的用完时自动推进怎么办，没有设计写，见 §6 G15。

### 5.3 高峰时段，默认少做

时段：工作日 14:00–18:00（UTC+8），GLM 按全价计积分，其余时间半价（`docs/ORCHESTRATION.md` §11.1）。

- 14:00 高峰开始：GLM 会话的下一步收到一句计价提醒；无影响档与读不到档位时与今天逐字相同，少做、不做两档按 M6 0.4 §3.4 换末句（少做：挪开花积分多的可做可不做的活由主 Agent 定、必要的活照做；不做：GLM 的活等到 18:00，harness 会叫你接着做），都保留「不要换模型或套餐，除非用户要求」；提醒原文与各档措辞归 M6，档位由规则板经服务交出（接缝裁定 1）〔M6〕；主 Agent 每一步的提醒都写此刻是不是高峰、哪一档、这一档要它做什么，不靠模型自己看钟算（`d-peak-mode`）〔规则板〕；循环板「高峰开始时按档位收放」〔循环板〕。
- 高峰里：同时至多 1 个 GLM 子 agent，再派一个被挡回，写明到几点（数由规则板给、M7 派模型为 GLM 的子 agent 之前读一次，满了按「没有空位」拒绝；接缝裁定 3，M7 0.4 §3.1.2 第 3 步）〔规则板〕〔M7〕；自报可以挪的脚本（练习题、对照实验）不管谁去跑都先排队，说明 18 点以后再跑，加 `--wait` 就自己等；这次判定由规则板的 `checkCall` 记进指标流水，M6 那一侧不另记（接缝裁定 2）〔规则板〕〔M6〕〔指标流水〕；大的评审挪到 18 点以后〔规则板〕；必要的活照做，改了通道之后的真网核对算必要的活〔M6〕。
- 主 Agent 把能做的做完、只剩挪到 18 点以后的活：这样的目标轮不算空转；连着两轮就以 M7 自己的原因 `hourness-peak-wait` 停住推进，不叫主 Agent 问人（接缝裁定 8，M7 0.4 §3.9.5）〔M7〕〔规则板〕。
- 18:00 高峰结束：循环板上编排层的「高峰结束」一项（`loops.peak-end`）先恰好调一次 harness 动作 `execute.resume-drive` 把停着的推进接上，再叫醒主 Agent；少做与不做两档都这样（接缝裁定 4、8，循环板 0.4 文首）。叫醒只在它闲着、高峰里干过活、不在等你回话时，每个工作日至多一次。高峰结束 5 分钟后 M7 自己再看一次，没接上就自己接上并报出（M7 0.4 文首）〔循环板〕〔M7〕。
- 用户看到：首页「现在」一行「GLM 高峰中，到 18:00 · 高峰模式：少做」；规则板「在等的工作」列出被推迟的事、在等什么、从几点开始〔面板〕〔规则板〕。
- 别的档：无影响只提醒，照常做；不做是 GLM 会话的操作排队、它的自动推进暂停，18 点以后系统恢复并叫它接着做。不做的高峰里主 Agent 的回话也在排队，换档要打 `/rules peak`；只想让这个会话这次高峰照常做，打排队文字里给的 `/rules let <单号>`，档位不变（规则板 0.8 验收第 17 条与一页稿；上手页没写这一点，§6 G20）〔规则板〕〔循环板〕。
- 读不出是不是高峰时，三档都不拦，页上写明原因；规则板自己出问题时也放行并写出来〔规则板〕。
- 什么时候问用户：不问。默认少做是人定的，新手引导里讲过（`d-peak-mode`）〔新手引导〕。

### 5.4 崩溃或重启

用户看到什么：

- 一般什么都不用做。重启后自动推进接着走；晨报「规划」一节写哪件活在重启时丢了。〔M7〕
- 主 Agent 的会话被归档或找不到时，首页与循环板最上面写「在一个会话里打 /wish here」。〔循环板〕〔M3〕
- 规则板的存档里出现不是它自己写的记录时，规则页「提议与恢复」列出来。〔规则板〕

系统自己做什么：

- worker、审查与检查随宿主进程结束；状态在图与会话日志里，会话可以丢。〔M7〕
- 循环板「重启之后接上」触发 M7 的对账：推进中的 goal 恢复（人暂停的不恢复）；丢了的派活批注「在宿主重启时丢失」，下一次简报写分支上已有哪些提交；审查过、还没进主干的标「可以合入」；不会重复派活。〔循环板〕〔M7 0.4 §3.9.6〕
- 同一件事被报两遍只做一次；真的又重启一次照常再做。〔循环板〕
- DSH 定时服务的提醒跨重启保留；宿主没运行时到点的不补投，巡检报漏跑。〔循环板〕〔M7〕
- 主 Agent 是谁记在用户级目录的持有者记录里，重启后仍是同一个会话。〔M3 附录 §2.4〕
- 规则板「在等的工作」从变更记录重建；条件解除后 30 秒内叫原来的 agent 再试，原来的子 agent 已结束就交给派它的主 Agent。〔规则板〕
- git：会丢工作或改写历史的命令之前已存快照，可以按通知里的命令恢复。〔M3〕〔M7〕
- 申报的放行只存在内存里，重启后丢掉，agent 重新申报。〔M4〕
- 循环板对账只在没有主 Agent、会话已归档或找不到时删自己建的定时任务；持有者状态「在别处」「不明」（持有者记录读不出也算）时一律不删、不搬、不重建，页面标出、行健康报出；删之前先证明是自己建的、已经没用，并把全文写进 `removed-tasks.jsonl`（循环板 0.4 §6.2、§6.4、§9.1，关掉 0.3 的 F35，§6 G17）。〔循环板〕

什么时候问用户：不问。要人动手的只有两处，都是告诉：会话归档时打 `/wish here`；规则存档异常时打 `/rules recovery <编号> 照改` 或 `忽略`。

### 5.5 方案被否掉

用户看到什么：

- 人说「不行，因为……」之后，主 Agent 按理由换一个方案再提；面板「需要你」里这一件一直列着，直到新的一版被同意。〔M3〕〔面板〕

系统自己做什么：

- `record_human_answer` 的 `reject`：在待决或目标上批注「人在对话里否掉：「原话」；主 Agent 记成：……」，状态不变。〔M3 附录 §3.5〕
- 改方案再提时，同一张待决改四行；人同意只算最新一版，对上一版的同意不算。〔M3 §3.5、§3.6〕
- 确认需求被否：改需求再提 `confirm`；放行被否：改方案再提 `release`。目标的阶段不变，子 agent 仍只读。〔M3〕
- 人要的是这件事不用定了：主 Agent 带人的原话把待决改为放弃。〔M3〕
- 放行之后才发现不对：人说一句，主 Agent 带原话把阶段改回设计（M3 只拦往前改，不拦往回改，附录 §3.6）。已经开始的推进怎样收，见 §6 G16。〔M3〕〔M7〕
- 规则或循环条目的提议被否：什么都不变。〔规则板〕〔循环板〕
- worker 的计划被主 Agent 打回：人不出场，晨报「理由」一节计数。〔M7〕
- 否掉的次数进指标流水。〔指标流水〕

什么时候问用户：新的一版仍是四行。

### 5.6 审查一再不过

用户看到什么：

- 对话里的四行（和别的事攒成一批，至多三件）；晨报「规划」一节「卡住的」；面板「需要你」。〔M7〕〔面板〕

系统自己做什么：

- 第 1、2 轮不过：自动修、自动再审；第 2 轮还不过自动加第 3 轮（`question-11`）。〔M7 §3.7.3〕
- 挡路只认三类：「怎样算做完」没满足；收不回的损失没有预防；失败了发现不了、恢复不了、追溯不了（`docs/DEVELOPMENT.md` §1.1）。〔M7〕
- 必须改的条数一轮没减少，或第 3 轮仍不过：停下，这一轮的批注末尾写「· 停下」，这件活不再派，直到人回话。harness 把事实与一份四行草稿交给主 Agent；循环板「停下之后问你」提醒它。〔M7 §3.7.4〕〔循环板〕
- 合入前的检查一再失败同样处理；夜间主干检查失败记复盘「主干变红」。〔M7〕
- 同一件活第三次返工之前也停下问（§6 G8）。〔M4〕〔循环板〕

什么时候问用户：四行，由主 Agent 在对话里问。
