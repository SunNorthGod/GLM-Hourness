# m1-cache-flash：GLM-5.3-Flash 会话第 2 步缓存未命中调查

范围：只读、离线。未向 GLM 发任何请求，未运行 probe / calibrate，未读凭证文件。步号从 1 起：第 1 步是会话的第一次主请求（标题请求不计），第 2 步是其后第一次主请求。「最新前缀」= 上一步提示词长度向下取整到 64（DESIGN.md §4.5b 口径）。

## 结论摘要

1. 请求体没有问题。两份完整截包会话的 15 对相邻请求、另 3 个会话的摘要级截包（含 1 次第 2 步未命中）全部是只追加：tools、system、messages[0] 逐字节不变，第 2 步在渲染顺序上以第 1 步的完整提示词为前缀。原始 JSON 的第一个差异在字符偏移 12818（两个会话相同），是第 1 步末块上的 `cache_control` 断点被移到新的末块，来源 `src/glm-llm/anthropic.ts` `markLastMessage()`（由 `encodeRequest()` 调用）；之后每一步都有同样的移动，而第 3 步起 101/101 命中最新前缀，所以它不是原因。前缀里没有时间戳或逐步变化的提醒。
2. 只有 Flash 有这个现象。修复会话 id 之后（2026-10-28 两轮标定 + 5 次截包运行）：
   - GLM-5.3，12 个会话：第 1 步命中跨会话共用前缀 10/12（每批第一个会话为 0），第 2 步命中最新前缀 12/12，第 3 步起 76/77。
   - GLM-5.3-Flash，17 个会话：第 1 步缓存读 0 共 17/17（另有桌面 2/2）；第 2 步最新前缀 7、只命中跨会话前缀 8、整段未命中 2；第 3 步起 101/101。
   - Flash 第 2 步共损失 58,432 个本可命中的 token，平均每会话 0.60 积分（全价），约占一个标定 Flash 会话（全价均值 15.9）的 4%。第 1 步冷启动的损失更大：若像 GLM-5.3 那样读到约 8.2k 的共用前缀，每会话可省约 1.4 积分。
3. 「第 1 步异步写入未完成」这一说法与数据不符，至少不是全部原因。第 2 步的未命中值（8192、8256、8320、6784）恰好等于与更早会话共用的前缀长度；这些前缀在第 2 步之前几分钟就已存在，而第 1 步一个 token 都没读到。第 2 步因此是从另一个缓存位置读的，同一位置上的写入延迟解释不了它读到第 1 步读不到的内容。另外，脚本实验里冷写入 13.6k token、约 0.6 秒后发下一步（DSH 实测间隔 0.30 秒），17/17 命中最新前缀。剩下与全部数据相容的解释在路由层：新会话的第 1 步被放到冷节点，第 2 步有时转到持有共用前缀的另一节点，之后一直停在那里。路由层是否带时间延迟（例如会话绑定或前缀索引在请求结束后才更新）没有被现有数据排除，需要重放实验。
4. 标题请求与会话共用 x-session-id 时，可能造成整段未命中这一子类（读 0，损失约 12.1k）：共用 id 时 4/25 次，另起 id 或不发标题时 0/20 次（Fisher 单侧 p≈0.085，证据弱）。`8a08c1f` 撤回 `0814234` 的依据是「跨会话前缀」这一子类没有消失，没有区分这两个子类。
5. 已写好重放实验 `replay.mjs`（未运行）：核心对照为 0 秒与 10 秒延迟，17 个会话，51 次请求，约 82–118 积分（全价）；完整 6 臂为 49 个会话，163 次请求，约 238–340 积分。
6. ZCode（参考源码 3.16.2，见 §5 末尾的版本说明）没有提示词缓存预热或步间延迟；它在系统提示词的 stable、dynamic 两块和最新一条非 system 消息上放断点，带 `x-query-id`，标题请求与会话同 id 并发。这些都不能直接解决这个问题。

对照结论：

- 反对（强）：跨会话子类的 8 个值都等于与更早会话共用的前缀（与 GLM-5.3 第 1 步读到的 8256、8320、6784 同值），这些前缀在第 2 步之前几分钟已经写入；第 1 步 17/17 读 0。若第 2 步与第 1 步落在同一缓存位置，第 1 步就应读到它们。所以第 2 步读的是另一个位置，写入延迟只能解释「读到自己写入的一部分」，解释不了这组值。能同时解释这组值的写入类机制只有「新会话 id 的首个请求不查缓存，且只有一个异步提交的缓存池」，它与修复前的数据冲突：那时每个请求都带新 id，按这种机制每个请求都不查缓存，而当时 Flash 后续步 29/45 命中最新前缀。
- 反对（中）：脚本实验 exp3（S、U 变体）与 exp5（none 变体）固定会话 id、无标题、冷写入约 13.6k token、间隔 500 ms 加约 0.1 s 开销，第 2 步 17/17 命中最新前缀。这些会话的系统提示词以随机 nonce 开头，会话之间至多共用一个工具定义（不到两个 64 块），没有可退回的共用前缀，写入若未就绪会表现为读 0，一次也没出现。DSH 的间隔是 0.30–0.35 s，比实验短约 0.3 s，这个窗口不能完全排除。
- 反对（弱）：GLM-5.3 每批第一个会话的第 1 步同样冷写入整段 12.1k，第 2 步 3/3 命中最新前缀（`3cc12d83`、`5a939099`、修复前 `2770bbd7`）。第 1 步输出越长，解码越久，写入的时间越充裕，但 Flash 的 feature 会话输出更长，结果反而更差。
- 截包的 42 次主请求中 41 次在 3.96–5.78 s 收到响应头（另一次 1.50 s），与是否命中无关（tap-…555/1：冷启动 4.27 s，第 2 步命中 12k 时 4.18 s），说明首字节时间不由预填充决定。若这段时间是排队，第 2 步查缓存的时刻比到达时刻晚数秒，对写入延迟假设更不利；对在到达时做的路由决定没有影响。这一条是推断。
- 未排除：路由层带时间延迟（新会话的绑定或前缀索引在请求结束后才更新），只在别处有长共用前缀时才表现出来。脚本实验没有共用前缀，看不到这种效应；它与全部数据相容。

能确认或否定的证据：

- 持有共用前缀时，第 2 步延迟 0 / 3 / 10 秒的跨会话子类比例。比例随延迟下降到接近 0，说明存在时间成分，条件延迟可用；比例不随延迟变化，说明位置选择与时间无关，延迟无用。
- 没有共用前缀、延迟 0 秒时第 2 步是否出现读 0。出现，支持写入延迟；不出现（预期），再次否定写入延迟。
- 第 3 步命中的是第 2 步还是第 1 步的提示词，用来确认会话停在哪个位置。

| | 第 1 步 读/提示词 | 第 2 步：最新 / 跨会话 / 整段未命中 | 第 3 步：最新 / 回到第 1 步 |
| --- | --- | --- | --- |
| 数值 | 0 或约 8,256 / 约 12,178 | 约 12,160 / 约 8,192–8,320（只在共用前缀臂）/ 0 | 约 12,416 / 约 12,160 |

各假设对各臂的预测：

| 假设 | A0 | A3、A10 | B0 | T | W |
| --- | --- | --- | --- | --- | --- |
| 同位置写入延迟 | 读 0 或自身部分前缀增多 | 最新 | 读 0 增多 | 同 A0 | 同 A0 |
| 路由带时间延迟 | 跨会话约 50–60% | 随延迟下降，A10 接近 0 | 最新 | 同 A0，另有读 0 | 未定 |
| 路由与时间无关 | 跨会话约 50–60% | 与 A0 相同 | 最新 | 同 A0，另有读 0 | 第 1 步读约 8.2k、第 2 步最新时支持「首请求特殊放置」 |

判定：每臂 8 个会话。A0 跨会话 ≥4/8 且 A10 ≤1/8 时判为有时间成分（5/8 对 0/8 的 Fisher 单侧 p≈0.013）。A0 本身 <3/8 时现象没复现，先按时段重跑一轮（修复前凌晨运行时 Flash 第 1 步 4/6 命中共用前缀，时段可能有影响）。

| 方案 | 会话 | 请求 | 提示词 token | 积分（全价） | 用时 |

## 5. 缓解方案

| 方案 | 预期效果 | 代价 | ZCode（3.16.2 源码） |
| --- | --- | --- | --- |
| M1 条件延迟：第 1 步读 0 且提示词 ≥8k 时，第 2 步等到第 1 步结束后 d* 秒再发 | 只在 A3/A10 证实有时间成分时有效；每个受影响会话收回约 4.2k（桌面约 7k）命中，约 0.7–1.2 积分全价，约 60% 的 Flash 会话受影响 | 每会话一次 d* 秒延迟；实现在 `ZcodeAdapter.stream` 内按会话记上一步结果，不改 DSH 契约 | 无（未找到预热或步间延迟逻辑） |
| M2 标题请求另起会话 id（恢复 `0814234` 的请求头部分） | 若 T 臂证实，消除整段未命中子类（每次约 12.1k，约 2.1 积分全价；现有数据中 4/25） | 无运行代价；与 ZCode 不一致 | 标题 sidecar 在首条输入落库后并发启动（`core/src/runtime/methods/session-title.ts` 注释），走同一会话归因（`adapters/src/model/runner-attribution.ts` `createModelRequestAttributionHeaders`） |
| M3 绑定请求：会话首个主请求前先发一个 16 token 的小请求并等待 | 若 W 臂证实，第 1 步读约 8.2k（约 1.4 积分），第 2 步命中最新前缀（约 0.7 积分） | 每会话多一次请求（约 0.07 积分）；Flash 响应头约 4 s，会话开头多等 4–5 s | 无 |
| M4 断点位置：系统提示词按 ZCode 拆成 cli_prefix / stable / dynamic，后两块带断点 | 对本问题预期无效：问题出在缓存位置，不在断点；DESIGN §4.5b 测过有无断点命中相同 | 方言要标出分界（DESIGN §5.8 #14） | 有：`core/src/context/builder.ts`（stable 块第 267 行、dynamic 块第 281 行），加上最新一条非 system 消息（`runtime/helpers/provider-request-messages.ts` `finalizeLatestNonSystemMessageCacheControl`），共 3 个断点 |
| M5 调整首轮块顺序：把含 cwd 的运行时快照放到静态提醒之后，或把静态提醒放到用户提示词之前 | 标定形态下共用前缀从约 8.2k 增到约 12k：GLM-5.3 第 1 步多命中约 3.9k（约 2.0 积分全价），Flash 跨会话子类损失降到接近 0。桌面同一工作区的会话要把静态块放到提示词之前才有效（共用前缀从约 6.8k 增到约 11k） | 改变模型看到的消息顺序；顺序由 DSH 决定，只能在编码器里重排，偏离 ZCode；需要用户拍板 | 无：附件（技能清单等）同样在真实提示词之后（`core/tests/provider-request-messages.test.ts`） |
| M6 不处理 | Flash 第 2 步平均每会话损失 0.60 积分（全价），约占标定 Flash 会话的 4% | 无 | |

ZCode 列的出处是 `reference/ZCode/apps/zcode-cli/packages/` 下的源码，该源码树版本为 3.16.2（`reference/ZCode/package.json`）；本仓库以 3.16.3 安装包为基线，本包注释引用的 3.16.3 函数名（`createModelRequestAttributionHeaders`、`finalizeLatestNonSystemMessageCacheControl`）在 3.16.2 源码里都能找到，3.16.3 里的实现是否另有改动没有逐字核对。预热与延迟的检索范围是该目录下全部 `src/**/*.ts`，只找到会话草稿与进程预热，没有提示词缓存相关的逻辑。

其他与 ZCode 的差异：ZCode 在查询内的请求上带 `x-query-id`（`runner-attribution.ts` `createModelRequestAttributionHeaders`），本通道的 `buildTraceHeaders` 只在调用方给出 queryId 时才带，`requestAttribution` 从不给，所以 DSH 会话的请求都没有。ZCode 的请求有签名，本通道的签名握手一直 404，全部无签发送。两者对路由的影响都未知；`x-query-id` 可用可选 Q 臂测试，签名目前无法测试。

文档来源说明：DESIGN.md §4.5b 引用的「缓存异步生效」出自 `.llm/docs/_bigmodel_md/cn__guide__capabilities__cache.md` 示例 curl 请求体内的示范知识库文本（「八、最佳实践」第 2 条），不在该页的说明正文里。它出自服务方，但只是示例内容，作为依据偏弱。

## 6. 建议

1. 先跑核心对照（`ARMS=A0,A10`，17 个会话，约 100 积分全价）。有时间成分就做 M1，d* 取实验中跨会话比例降到 ≤1/8 的最小延迟；没有就跑 W 臂，评估 M3。
2. 同一批次跑 T 臂。若同 id 标题带来读 0，恢复 M2；`8a08c1f` 撤回时把跨会话子类和整段未命中子类算在一起，后者在另起 id 之后没有再出现（0/6）。
3. M5 的收益与服务端机制无关，对 GLM-5.3 也有效，但会改变模型看到的消息顺序，需要用户决定。
4. 修订 DESIGN.md §4.5b：把未命中分为两个子类；记录 Flash 第 1 步修复后 0/19 读到共用前缀，这是比第 2 步更大的损失；补上按任务的差异和「异步生效」的来源。本次只调查，没有改动。
