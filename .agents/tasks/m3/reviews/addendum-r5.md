### R5-M2 MEDIUM 大循环放行中途失败后的重放，在「已批准而都没写阶段」时走不到：`isSplit` 为假，会落进单层放行并一次批准所有模块的子树

位置：§3.14.1 的模块、候选与 `isSplit` 定义（附录:777–793）；§3.14.2 门禁第 2 条的例外与重放说明（附录:805、814）；§3.5 表「`release`，不带 `module`」一行的最后一句（附录:605）；§5 表「`record_human_answer` 的大循环放行」一行；第 9 步 L2 的重放用例（附录:1086）。

问题：

- 写入次序是先批准放行集合（含全部模块候选），再给每个候选 `edit` 设 `stage: 'design'`，最后 `edit` 目标设 `stage: 'release'`。附录声明中途失败可重放：「已批准而没有 `stage` 的模块照写 `design`」（附录:605、814），§5 把这一行标为「可恢复」。
- 但「模块」在 §3.14.1 里要求带 `stage`，「候选」要求状态 `proposed`，`isSplit` 是 `modulesOf` 或 `moduleCandidatesOf` 不空。所有候选都已批准、第一次阶段写入之前进程停了（崩溃、主机退出），这批特性是已批准而没有 `stage` 的：不是模块，也不是候选，目标的 `isSplit` 为假。`releaseGate` 按 `isSplit` 分支，于是走 0.4 的单层放行：`page` 被拒（「this goal is not split into modules」），放行集合是目标子树里全部 `proposed` 的节点，也就是每个模块的整个子树。主 Agent 去掉 `page` 重提，人说一句「可以」，所有模块子树被一次批准、目标进 `release`，每个模块的一页放行稿与逐个放行被绕过。人看到的只有四行。
- 第 9 步 L2 的重放用例是「目标 `edit` 注入 `stale_revision` 失败后重放」（附录:1086），那时模块的 `stage` 都已写上，`isSplit` 为真，覆盖不到上面这种次序。§3.14.2 门禁第 2 条的例外（有已批准而没有 `stage` 的模块）只在 `isSplit` 为真的分支里才会被读到，所以也救不了。
- 严重度：停在批准与第一次阶段写入之间的概率不高，但后果是静默绕过人定的「每个模块一次放行」（`d-design-onepage`），且附录自己声明这条路可恢复。按 §1.1 第三类（恢复办法不成立）记 MEDIUM。

改法（选一种）：

- A（推荐）调整写入次序：先对每个模块候选 `edit` 设 `stage: 'design'`（候选仍是 `proposed`，格式允许特性带 `stage`，`format.ts:378`；写入带 `relay`），再按修订号批准放行集合，最后写目标的 `release`。中途停下时留下的是「提议状态、已带 `design`」的候选，`moduleCandidatesOf` 仍返回它们，`isSplit` 为真，重放时门禁照常、`page` 照常；已带 `design` 的候选跳过阶段写入（引擎对什么都没改的 `edit` 返回 `invalid`，`engine.ts` 的「set changes nothing」，所以必须显式跳过）。§3.14.2、§3.5 表、§5 表同改，不再需要「已批准而没有 `stage` 的模块」这一种中间状态。
- B 扩 `isSplit` 与门禁第 2 条，把「目标的直接特性子节点、已批准或进行中、没有 `stage`、目标有效阶段为 `design`」也算分了模块。注意 0.4 流程里目标下已批准而没有 `stage` 的特性是常见形状，要加一个能把它们分开的判据（例如历史里最近一条批准的 `reason` 含 `record_human_answer`），否则会把普通特性误当半放行的模块。比 A 复杂，不推荐。
- 不论选哪种，第 9 步 L2 加一例：大循环同意后，在第一次阶段写入处注入失败（进程停在批准与阶段写入之间），重新提议带 `page`、人再同意：每个候选得到 `design`，目标得到 `release`，没有任何模块子树里的提议被批准。

### R5-N1 NIT 设计期只读在焦点是目标或其他非模块节点时仍放行，身份节第一部分仍只写「目标放行」

位置：§3.14.6（附录:859，「焦点不在任何模块里，或在已放行的模块里，放行」）与第 5 步 L2 钉住的用例（附录:973，「焦点在目标一级、不在任何模块下时放行」）；§10 的残余一条（附录:1396）只写了「焦点在已放行的模块 A、派去写模块 B」；§2.2 身份节第一部分（附录:114）`until the goal in your focus is released, the subagents you dispatch, and theirs, only read`；第 5 步变化里 `design-before-release` 的正路一句 `once the goal of its focus is released`；§3.11 表里 `design-before-release` 的标题「放行之前，主 Agent 派出去的 agent 只读」。

问题：分了模块的目标在大循环放行之后就是 `release`，此时所有模块都在设计。主 Agent 的焦点停在目标上（或任何不属于模块的节点）时，这条规则放行，子 agent 可以写文件，没有任何模块被放行。结构上的挡法有两层：还没放行的模块下的任务出生为 `proposed`（`initialStatus` 收窄），M7 0.5 §2.4 与 §3.2.2 的 `releaseOf` 在 M7 合入后取代这一行判定。M3 合入到 M7 合入之间只剩阶段提醒的一句话，附录没有把这种焦点写进残余。身份节与正路一句仍只提目标放行，主 Agent 读到的条件比实际执行的少一层。

改法：§3.14.6 与 §10 的残余一条加一句「焦点在目标一级时不拦，M7 合入前靠提示与『任务出生为提议』」；模块在 `design` 时的阶段提醒（§2.3）加一句 `Before you dispatch a subagent that writes, graph_focus to the module or the task it belongs to`；身份节第一部分与正路一句改为「until what you work on (the goal, or its module) is released」，长度仍在 1,500 之内（现 1,117）；§3.11 的标题改为「放行之前（目标或模块），主 Agent 派出去的 agent 只读」，仍不超过 40 个码点。
