## 纯文本版（可直接复制）

以前我们常说"代码要写给人看"，但很多程序员都嗤之以鼻。直到它们第一次给新同事做培训，第一次回答代码交接时的十万个为什么。我的领导很喜欢研究这种"程序员之间的合作效率问题"，简称如何让 1+1>2。

现在轮到我当领导了，问题更难了，直接升华到了"人机合作的效率问题"。这个问题难就难在 AI 这个新同事太老实巴交了：你给它看什么它就信什么，没给它的它就自己脑补。它从不会怀疑自己，也从不会主动举手提问十万个为什么。但这也意味着，你得等到 code review 的时候才会发现它哪儿不对劲。

那要怎么跟这种新同事配合? 从想法构思到产品落地的整条开发链路，对我们人类来说，无非就是切换几个工具、复制粘贴几下的事儿。但对于 AI 来说，每一步都相当于一个独立的信息孤岛，而这才是最让它难受的。毕竟现在的 AI 早就不怕上下文太长了，它只会嫌你给的不够，导致它要半蒙半猜。所以我们要帮它填补理解空隙，做好流程衔接。以前这些都是项目经理的工作，但就目前的大趋势来看，我们程序员都是半个项目经理了，所以我们也要学会转变思维。

有聪明的观众可能就会说了："问题那么多，无非就是代码写得太烂，让人看不懂!" 不可否认的是有些代码确实不行，但很多人容易忽略的一点是：代码只是最终呈现的东西，它写得再好，也无法告诉你一些东西为何而来（why）、是怎么来的（how）。这个话题我在两年前还发视频深入讨论过。著名程序员 Atomic Energy 受到我视频的启发，总结出了 Law of Knowledge Decay（知识衰退定律）：一是项目会累积越来越多的业务逻辑，以及它背后的决策考量等知识，但是这些散布在各种会议、邮件、聊天、issue 和 PR 的讨论，以及更多的没有被记录下来的思考过程，都必将会随着时间和人员的流动而被遗忘，从而无法完整地传承下去。第二是随着项目规模越来越大，角色的分工界限也会越来越明显，负责宏观的项目经理、产品经理和架构师之类的人只管大方向的设计决策和任务分配，而负责微观的开发、测试、运维只负责埋头敲代码做实现，这就导致了宏观知识和微观细节开始出现隔阂，各管各的，各做各的。

那么破解了衰减定律的开发会有什么效果呢? 空话不多说，直接实战演示。画面上是我们频道的老朋友，已经十岁的物联网终端系统。这里我已经让 Agent 给所有 11 个系统组件分别生成了配套的知识库：每个知识库都包含了一份详细的流程图、一份架构和选型的对照说明、一份根据 git 复现的完整的修改历史、一份包括了优化和修复的各种待办事项，以及一份面向 AI 的文字版的测试案例库。

聪明的观众会发现我把知识库和代码全混在一起了，看起来乱糟糟的。我没有按照传统做法那样把所有的文档都放在同一个根目录下，因为这种传统做法的"可读性"是面向于人类程序员来说的。当 AI 在执行任务的时候，它会一层一层地往上找资料，那么在每行代码的旁边就摆上它的知识库，自然就是最高效的做法。

比如我现在让 Agent 执行这几个组件开发的任务，打开它们的思考过程，你就会发现它们都没有像一般的任务那样上来就先用脚本把整个 repo 都翻个底朝天，而是会一秒定位到所有跟这个组件相关的文档。当然省 token 只是它的附加价值。就拿这个升级通信组件的任务来说，表面上看，我们用的 AMQP 协议是早就被淘汰了 0.9 版本，升级它是理所当然的事情。但 AI 在读取了架构选型资料之后，发现了云端用的是 RabbitMQ 框架，一个只兼容 0.9 版本的老古董。所以尽管 1.0 版本的协议更快更高更强，AI 也不会去升级它。这里甚至就连我逼着它去改，它也会义正言辞地拒绝我。这也算是一道额外的安全机制了吧。

还有这个处理缓存组件的崩溃恢复（crash recovery）的任务，本频道的老粉第一时间想到的肯定是用异步架构，毕竟它天生就是用来对付异常情况的。这里 AI 其实一开始也是这么想的，不过它分析半天之后，还是放弃了异步方案。为什么呢? 因为它在修改历史这个文章里面发现了一段往事：原来 5 年前缓存组件的架构就是异步的，但是当时为了满足用户最低延迟的要求，我们决定了牺牲灵活度来换取速度，从异步改成了同步。这段历史其实我自己都忘了，要不是被 AI 翻了出来，说不定哪天稀里糊涂地又改了回去。

而我觉得最有实战价值的是这些流程图。虽然我曾经出过一个视频送别 UML，但在 AI 时代，这些以 Markdown 格式存在的时序图，对于 AI 来说确实是一图胜千言。尤其是运行逻辑复杂的程序，比如我这个播放组件，除了主流程，还有各种特殊分支，这些流程在代码中是混杂在一起的。以往 AI 要做修改，在每次对话开始时都需要重新梳理一遍代码逻辑才能开始动手改，那就相当于反复的在脑内重画流程图，但你不能保证它每次画的都一样，那就很容易在细节上出错。现在有了流程图，AI 就可以直接参考，一步到位，速度和准确度都能够大大提升。

这里我还要特别推荐一下这种文字版的端到端测试案例库。以前我们习惯写 unit test 这一类底层细节的测试，是因为用代码去构造一个完整的端到端的测试案例太复杂了，写一个都很费时。但现在 AI 负责跑测试，那每个案例其实只需要几句话的描述，剩下的让 AI 自己准备就行了。

最后也是最不能漏掉的细节：当你启用多个 agent 对多个组件跑多个任务时，务必记得核实 AI 在改代码的同时也同步更新了相应的知识文档。毕竟每一个新对话都相当于一次全新的代码交接，我们要确保知识库一直都保持在最新的状态。

总的来说，在融合了这些知识文档之后，不管是任务的运行用时、token 用量，还是需要我们手动纠正的错误，通通都有肉眼可见的减少。有一个我以前经常遇到的痛点，估计不少观众也有：就是等它忙活了大半天完成任务，结果一看才发现它从一开始就有理解误差，导致后面所有的推理和设计都走歪了，改了几百上千行，结果一行都没法用，无奈只能让它重来一遍，我们也被迫再摸鱼等半天。好消息是有了知识库后，这些情况我基本上没有再遇到过了。坏消息是啥，你们都懂。

其实说到底就是一个习惯的问题。只是以前我们更多的思维习惯是："这些是我自己的工作风格，AI 你进来就要配合我，适应我"。而现在我们就需要转变为："AI 有这么一些工作风格，我要怎么给它一个更适应它的环境"。还有像开场说到的项目经理的角色，习惯后你会发现其实也就是顺手的事，比如说确认一下今天的更新都 commit 和 push 了没。我会设置一个自动化的定时任务，每天六点下班前会让 AI 扫描一遍所有的项目，避免有遗漏。

当你发现你的思维方式和行为习惯都已经逐渐开始改变时，你这才算是真正适应了和 AI 当同事的"美丽新世界"。
