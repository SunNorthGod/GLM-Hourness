# 执行、合入与运维：给你看的一页

这一块管的是你放行一份设计之后的事：主 Agent 自己派活、审查、合进主干、把目标做完，每天给你晨报，每周给你周报，夜里巡检一遍。项目分了模块的话，每个模块的设计先审一遍，再由你各放行一次；开发中冒出来的问题按轻重分三档处理。完整设计在同目录的 `design.md`（0.6），这一页只讲你会碰到的部分。

## 你会看到什么

- 你在对话里同意放行设计之后，DeepSeek Harness 的目标条上出现一个目标，主 Agent 接着就开始干活。你不用发任何命令。
- 项目分了模块的话，框架、模块清单和方向清单放行一次，之后每个模块各放行一次：主 Agent 给你一页这个模块的放行稿，你同意了，才派这个模块的活。没放行的模块，主 Agent 一件也派不出去；别的已放行的模块照常做。
- 每个模块的放行稿递给你之前，这个模块的设计先由另一个子 agent 对照你定过的方向清单独立审一遍，违背哪一条就指出哪一条；审的结论在这个模块上留一条记录。
- 面板「正在做」里看得到每个干活的子 agent 站在哪件活上。每件活派给了哪个模型、为什么选它，都记在项目图上，晨报里也列着。
- 每天 08:30 晨报、每周一 09:00 周报，都出现在主 Agent 的对话里。夜里 02:30 巡检，查出要你定的事攒到下一批再说。
- 循环板上多十项，写着「项目编排带来的 · 只能看」：设计放行之后开始推进、交回之后派审查、审查过了之后合入、停下之后问你、活都关了之后整体审一遍、合进主干之后跑一遍完整检查、重启之后接上，以及晨报、周报、夜间巡检。
- 规则板最上面那组会挡住动作的规矩里，列着合入前的检查清单和必须全审的清单。必须全审的那四条现在旁边写着「这几条还没有机器认得的写法，暂时每件都全审」。
- GLM 高峰里，目标条上的目标可能停着，写着「等 GLM 高峰结束，到 18:00」。

## 会自己发生的事

- 派活：每件活开一个单独的工作目录和分支，在后台跑。干活的子 agent 只能写这件活划定的那几个文件；要先交计划的活，主 Agent 批了计划才能动手。
- 审查：审多深由主 Agent 定，要写理由。改动碰到必须全审的那几类时，不管它定了什么都全审。现在那张清单系统还认不出，所以每件活都全审，直到你回答下面的第一件小事。
- 合入：先合哪件、冲突怎么解、要不要回退，都是主 Agent 用 git 做。系统只守一处：主干只能前进到系统自己检查过的那个提交，检查结果由系统记，模型说的不算。
- 从别处拉来的提交也一样要先检查，包括别人或你在另一台电脑上推上去的。主干上直接 `git pull` 会被拦下，主 Agent 改成先取下来、检查、再合。
- 用系统认不出的办法挪了主干（比如写在脚本里），或者把没检查过的提交推上了远端，系统在那条命令之后马上发现：记一笔，告诉主 Agent，这件活不算做完，直到补跑的检查过了。合进主干之后，系统也会确认这个版本的每条检查都跑过、都过了，坏了就叫主 Agent 修。
- 主 Agent 说目标做完了时，系统先核对每件活都进了主干、都有系统记的证据、没有还没放行的模块、整体审过了；缺什么列出来，不缺才算完。
- 开发中冒出来的问题分三档。只影响这一个模块、而且能撤回的，主 Agent 自己定，记在图上，下一批问你的时候一并告诉你。改到这个模块的设计方向的，这个模块退回去重新做设计，你看新的一页、同意了才继续，这个模块里在做的活作废重派，别的模块不受影响。改到整个框架的，整个目标退回去重新定框架，受影响的活先停下，等你同意。判不准时往高一档放：多花你一次放行，比在错的设计上接着做强。
- 系统读不出模块的结构时，分了模块的项目里一件活也派不出去，在跑的子 agent 也写不了，直到读得出来，状态里写明原因；没分模块的项目不受影响。
- 电脑或 DeepSeek Harness 重启之后接着推进；你自己按的暂停不替你恢复。如果关桌面版时是系统顺手把目标暂停了，重启后它认得出来，会恢复，并写明为什么。
- 高峰默认少做：同时最多 1 个 GLM 子 agent。主 Agent 手上只剩因此暂时派不出去的活时，推进先停着，不来问你；高峰过了自动接上。
- 循环板负责到点和碰到事就去做的那十项。它没装上、没收下某一项、或 5 分钟内没动手时，系统自己做，并在状态里报出来。
- 你用 `/wish here` 把主 Agent 换到另一个会话时，推进和子 agent 的问题都跟着过去。
- 派活、审查、检查、合入、问你的每一次，都由系统自己记下。记不进去时状态里会报出来，晨报在那一段注明「数不全」。

## 什么时候问你

都在主 Agent 的对话里问，不出卡片，一次至多三件，用四行（背景、推荐、疑问、不做）讲清楚。排不进这一批的，留到下一批。会来问你的只有这几种：

- 一个模块的放行页；某个模块或整个框架退回去之后，重新放行的那一页。
- 一件活审了三轮还没过，或者合入前的检查第三次没过，或者一个模块的设计审了三轮还没过：这件先停下，其余的照做。
- 目标整体审一遍没过。
- 剩下的事都在等你回话。
- 连着 3 轮什么都没变（高峰里等高峰结束的那几轮不算）。
- 周报里提议规矩该升该降、必须全审的清单该加一类，每周至多 3 件。

放行之后，主 Agent 还会在对话里问你两件小事，都不挡开工，你回答之前系统按严的一边做：一是必须全审的清单每一类后面写上系统认得的具体路径（现在认不出，所以每件活都全审）；二是只改项目图的提交不再每次都跑构建和全部测试（现在每次都跑）。

这一页最后有一件现在就要你看的：放行。

## 替你定了的方向

- 八条写在代码里、会拦住动作的规则，首日就直接生效，是对项目宪章 0.7「写在代码里的新规则先试运行再拦截」的破例，因为它们守的是你定过的保证，试运行期间这些保证等于没有；你说不行，就改成先试运行。
- 每个模块的设计放行前先由另一个子 agent 独立审一遍，这一版就做，不留到以后：这是你在设计循环里定过的一步。本仓库自己开发时，模块设计的审查仍由 Kiro 工作流做，不走这条路。
- 读不出模块的结构时宁可不派也不放行。代价：模块读法一旦出故障，分了模块的项目会停在那里，直到修好。
- 从别处拉来的提交也要先检查，主干上不能直接 `git pull`。代价：拉别人的提交多等几分钟。
- 拉来的提交改了必须全审的那几类时，这台电脑上没人派过审查，所以只要求检查，不要求再全审，晨报的「例外」里列给你看。你要是希望这种也在这里全审，就得多一种「审拉来的提交」的派法。
- 必须全审的清单里只要有一条系统认不出，就每件都全审。代价是你回答上面第一件小事之前多审一些，往稳的一边错。
- 审查还没过的活，主 Agent 可以先合进主干，但不算做完，审查过了才算。
- 循环板没在 5 分钟内动手时系统自己补做；高峰里连着 2 轮没事可做才停住推进，高峰结束 5 分钟后系统自己再看一次，没接上就接上，不来问你。
- 关桌面版前 30 秒内发生的暂停，算关机带来的，重启后恢复；你暂停后半分钟内就关掉的话也会被恢复，提醒里写明，你再停一次就行。
- 合进主干之后的完整检查，只补跑这个版本还没跑过的那几条；夜间巡检里的那次放到后台跑。

## 交给别的模块的

- 循环板：高峰结束时调的那个动作改个名字，只接上因为等高峰而停住的推进；「停下之后问你」那一项改成由系统现算四行草稿再交给主 Agent。
- 规则板：必须全审清单里认不出的那几条，旁边的字从「暂不强制」改成「暂时每件都全审」。
- 主 Agent 把事情交给你看的那一块：子 agent 的问题每次都送给当前的主 Agent；项目里还没有必须全审的清单时，提醒主 Agent 在放行前提一张；模块放行页提出来之前，多数一项这个模块的设计审查记录（记录的格式这边已定好交给它）。

## 十件活「怎样算做完」（草稿，等你逐条看）

你定过这十件活的「怎样算做完」要你看过才开工。下面是摘要；逐条的字句在 `graph-ops-v04-pending.json`，其中第 2、3 件和「合起来」三份已按 0.6 重写。你改了哪条，就照你的原话写上去。

1. 派活与说话（m7-1）：主 Agent 派活时写用哪个模型、为什么；子 agent 只能写划定范围里、计划写到的文件；计划不合格当场退回；子 agent 可以问主 Agent，两个子 agent 之间不能直接说话。
2. 派活前的检查（m7-2）：缺怎样算做完、前面的活没做完、有等你回话的事、模块或目标没放行、读不出模块结构、写同一批文件、在做的活已满、高峰少做的上限到了，都派不出去并说明差什么（审查模块设计的任务除外，模块没放行也能派）；有空位时提醒一次；派活工具说明里有一道完整的例子，除了编出来的模型名，真的派一次也能通过全部检查。
3. 自动推进与「目标做完了」（m7-3）：你同意放行后不用发命令，主 Agent 自己推进，分了模块的每放行一个就做这一个；做完前系统核对证据；剩下的事都在等你、连着 3 轮没变化，或高峰少做时只剩派不出去的活，就停下或先停着；重启后接着推进；开发中的问题按三档处理，要问你的事一次至多三件。
4. 审查（m7-4）：审多深由主 Agent 定并写理由，碰到必须全审的就全审；只在三种情况下挡路（没做到某一条、可能造成收不回的损失、出了错无从发现或恢复）；三轮没过就停下问你。
5. 合入（m7-5）：合并、先后、冲突、回退都是主 Agent 的；主干前进那一刻系统核对检查和全审都做过，拉来的提交也一样；用认不出的办法挪主干，事后马上发现并记下。
6. 晨报（m7-6）：每天早上四段加几项，数都由系统算；是循环板上的一项，只能看。
7. 夜间巡检（m7-7）：查工作目录、分支、主干、项目图，把主干完整检查一遍；漏跑的下次报出来；只能看。
8. 规矩的升降与周报（m7-8）：每周一份，哪类改动降低审查深浅后返工多，就提议加进必须全审的清单，每周至多 3 件，你同意才改。
9. 交付的四个数（m7-9）：每周合入几次、一件活从派出到进主干多久、进主干后出问题的比例、主干坏了到修好多久。
10. 练习题只查有没有改坏（m7-10）：练习题运行时读目录以外的文件被拦下并记一笔，那一次不算数；每道题写明是一直该做对的还是现在还做不好的；文档写明练习题不证明系统好用。

合起来（m7）：最小的一条完整链路在 DeepSeek Harness 桌面版上，对一个临时项目，从你许愿、聊需求、同意放行，到主 Agent 自己派活、审查、合入、目标完成，你中途不用发任何命令；之后本项目的开发改由它来做；分了模块的项目里，没放行的模块一件活也派不出去，每个模块的设计放行前先独立审一遍并留一条记录。

## 放行

① 放行执行与合入这一块的设计

背景：按评审改好了，分了模块的项目**每个模块各放行一次**，开发中的问题分三档、成批问你。

推荐：评审通过后**直接开工**，先做派活、写入范围和合入的检查，再接自动推进。

疑问：最没把握的是**八条规则首日就直接拦**，你更想先看它拦错几次，就改成先试运行。

不做：不把模块设计的**独立审查**留到以后，那是你定过的一步，留到以后等于删掉你的决定。

这样放行可以吗？
