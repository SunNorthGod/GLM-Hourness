## 2. 发现

### 1. MEDIUM：场景的先后顺序与页内的放行规则相互矛盾

位置：「一个图书馆项目」第一段，对照「对你有什么变化」第 3 条和 SVG 概览带。

第一段写的是：访谈里主 Agent 猜角色，「你说对，再补一句『借书前要先交押金』。几天后你打开面板……」，接着说「交押金」没人负责。读者会理解成：这一步在访谈里就有了，几天后面板上仍没人负责。第 3 条却写「每一步要有人负责……这些不齐就放不过去」。设计里 `flows:served`（§5.2）正是放行前的检查，放行时每个步骤至少有一个服务者（模块级连线也算）。所以按页上的先后，这一步在放行时就会被拦住，面板上不可能出现「服务者 0」。

只有放行之后再加这一步才成立（§4.3、D16、第 5 条）。页上这样写，读者只会得到两个互相打架的印象：要么放行规则是假的，要么这个画面不会出现。这一页的目的是让人看懂，所以应该改场景，不改规则。

修法：把第一段改成放行之后加步骤。参考写法：

> 你做什么：你用这个插件给一家社区图书馆做借还书系统。访谈时主 Agent 先猜：「我猜用它的有读者和管理员，读者登录、搜书、借书、还书，管理员录入新书、处理逾期，对吗？」你说对，放行，开发开始。几天后你想起一件事，对主 Agent 说「借书前要先交押金」，它复述「那我记成：借书加一步交押金」，你说对，它在图里加了这一步。之后你打开面板的「用户怎么用」页。

这样「新加的『交押金』」也有了来历，并顺带演示第 5 条。汉字约增加 40 个，总数仍远低于上限。

### 2. MEDIUM：把设计自己标为未核实的做法写成了确定的事

位置：「对你有什么变化」第 4 条；「要你定的」②。

第 4 条写「界面类的每步截图，由另一个 agent 对照『怎样算做成』看图。主 Agent 不能自己报通过。」没有一处说明两件事，而 `design.md` §15 把它们列成未核实或残余风险：

- A3、A6：独立复核的 agent 能不能可靠地看图判断，以及 DSH 的读文件工具能不能把图片交给模型，都没有测过。设计的退路是把「截图」这一种去掉，那些流程改用命令、终端或请人走（§15 A6）。
- A9：测试代码本身写错（比如无论如何都报通过），harness 看不出来，只靠写测试那件活的审查和整体审查把关。

这两点直接影响人在 ② 里要定的东西：② 把「走通」当作做完的条件，人需要知道「走通」只说明测试通过了，不是没有毛病；也需要知道界面类流程可能比页上说的更多地落到「请你亲自走」。页面现在的写法会让人以为有完整保护。

修法：在第 4 条「主 Agent 不能自己报通过。」后面加一句，例如：

> 有两处还没验证：模型能否可靠地看图判断（不行就去掉截图这一种，那些流程改用命令、终端或请你自己走）；测试本身写错了，系统只靠审查把关，可能漏过，所以「走通」说明测试通过了，不等于没有毛病。

汉字约增加 90 个，总数约 1,310，在上限内。

### 3. NIT：「逐轮降到了 0」与「另有 5 条」两处的措辞

位置：「要你定的」③。

- 趋势 12、4、2、2、0 里第 3、4 轮都是 2，不是逐轮下降。改成「从 12 条降到 0 条（12、4、2、2、0）」即可。
- 「另有 5 条不挡放行的低风险意见」只是最后一轮的数（`design-review.json`）；前几轮的低风险意见已在 0.2 至 0.4.1 处理。括号放在五轮之后，读者会当成五轮合计。改成「最后一轮另有 5 条不挡放行的低风险意见」。

### 4. NIT：③ 把已定的排期和放行写成一个问句

位置：「要你定的」③。

「实现排在 M3 和 M7 的骨架合入之后」是人 2026-10-31 已经答过的（`design.md` §1.1 第 2 点），放进问句里像是要重新定。把它挪到问句后面当告知，问句只问「照这一页放行可以吗」：

> ③ 我建议照这一页放行这份设计，因为五轮独立评审里挡路的问题从 12 条降到 0 条（12、4、2、2、0；最后一轮另有 5 条不挡放行的低风险意见），可以吗？代价是用户图画进项目以后，旧版本的插件读不了这张图，新旧版本不能混用同一张项目图。实现排在 M3（访谈与放行）和 M7（派活与执行）的骨架合入之后，这是你之前定过的。

### 5. NIT：SVG 里窄屏描述与设计不一致

位置：`onepage-mockup.svg` 底部说明最后一条。

写的是「页面窄的时候，两个视角改成上下两段，用开关切换」。设计 §6.2 与 §1.4 第 41 条是「单列，概览带下用『用户视角 · 开发视角』两段切换」，一次看一个，不是上下摞着。「上下两段」和「切换」互相矛盾。改成「页面窄的时候改成单列，用开关在两个视角之间切换，一次看一个」。

### 6. NIT：几处读起来要猜的地方

- 「怎样算做成」在第 4 条首次出现，页上没说每个步骤都带一条这样的话（设计 §5.1 的确认样稿会逐步写出）。在第 1 条「用你的话写」后面补「每一步还写一句怎样算做成」。
- 页内 `design.md` 没有目录，仓库里有多份同名文件。简报要求写文件名，所以保留，建议写成「本特性的 design.md」。
- 「另一个 agent」与「主 Agent」大小写不一，统一为「Agent」。

## 3. 已核实的假设

- 设计版本 0.4.1，`design-review.json` 为 APPROVED，评审在设计文件最后修改之后完成。
- 趋势 12、4、2、2、0 与 `design-review.json` 一致；5 条 LOW 是第 5 轮的数。
- 第 12 节 29 条，D10、D12 对应 ①②（§13），27 条是可逆取舍。
- 「走通」的定义（连着的活做完、真实运行的产品上从头走过、之后没再动过）与 §0、§2.5 一致。
- 「只在放行、走一遍之前、做完这三处拦」与 §2.6 一致。
- 放行时每步有人负责、每条流程写好走法（`flows:served`、`flows:walk`），同意作废的条件（步骤、负责的模块、命令原文变了才作废）与 §5.2、§5.3、D28 一致。
- 走一遍的做法（harness 跑放行时看到的命令、截图类由独立复核、人亲自走时告知提交）与 §2.7、A11 一致。
- 访谈多一问的做法（先猜后改、确认时给草稿）与 §5.1；已过确认的项目不受影响与 §7.3；首页「效果是」先写流程进度与 §6.1；加一步沿用三档与 D16。
- SVG 的数能对上：22 步（登录 4、搜书 3、借书 4、还书 3、录入新书 4、处理逾期 4），服务者合计 账号 5 + 书目 6 + 借阅 6 + 逾期与通知 4 = 21，余下的「交押金」服务者 0；借阅 6 = 借阅接口 1 + 借阅页面 3 + 归还接口 2；流程计数 1 走通、1 走不通、2 做完了、1 没人负责、1 排上了，与六条流程的状态逐条相符；借书一行「1 在做、2 排上了、1 没人负责」与四个步骤相符。状态字与 §2.5 的七个状态一致。
- 草图的并排、不画连线而用高亮加标记、概览带至多三条缺口，与 §6.2、D17 一致。

## 4. 未核实或不成立的假设

- 页内对截图复核的描述依赖 `design.md` A3、A6，设计自己标为未核实（发现 2）。
- 「测试写得对」依赖 A9，设计自己标为残余风险（发现 2）。
- 作者报的字数没有出现在目录或任务材料里，无法与文件逐数核对；本次实测为 1,181（含图片替代文字）。
- 草图里的名字和数字是举例，页上已声明；上面第 3 节的数字自洽是核对过的，但它们不对应任何真实项目。
- 「逐轮降到了 0」不成立（发现 3）；场景先后与放行规则不能同时成立（发现 1）。

## 5. 结论

HIGH 0 条，MEDIUM 2 条，NIT 4 条（发现 3 至 6，发现 6 含三小点）。MEDIUM 大于 0，结论为 CHANGES_REQUESTED。

两条 MEDIUM 都能在汉字上限内修完（预计 1,181 加约 130，约 1,310）。修完后按简报做第二轮复核；第二轮只复核发现 1、2 与新改动。
