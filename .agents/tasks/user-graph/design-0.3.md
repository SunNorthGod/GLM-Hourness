## 0. 摘要

人要的是：给用本插件开发出来的项目，画出它真实用户进去之后的样子，登录怎么走、借书怎么走，并且和开发图对着看。人定了两件事：一、用户的角色、流程、步骤是项目图里的节点，存在同一张图里，用同一个引擎、同一份历史、同一套证据与转述规矩，面板并排给两个视图；二、现在写设计，实现排在 M3 与 M7 骨架合入之后。

本稿的做法是在现有引擎上加法，不另起一套：

- 三种新节点：`role`（用户的一种身份，如读者）、`flow`（这个身份要办成的一件事，如借书）、`step`（流程里用户做的一步或看到的一个结果）。层级是目标 › 角色 › 流程 › 步骤，沿用 `parent`。不再加别的种类（§2.2）。
- 两种新连线：`next`（步骤到下一步，带可选的条件 `when`，同一条流程内，允许回环；流程到它的第一步，那条连线就是流程的入口）和 `serves`（做事的特性或任务指向它服务的步骤，存在做事的一边）。步骤最多 8 个服务者，任务最多服务 3 步，特性最多 20 步，写入时拒绝（§2.3、§2.4）。
- 步骤和流程的状态由连着的活推出，不存：没人负责、排上了、在做、做完了等走一遍、走通了、走不通，另有「待你定」。走通要同时满足两件事：连着的活全部做完，并且做完之后有一次通过的「走一遍」记录，之后这条流程连着的活没有再动过（§2.5）。被废弃的角色、流程、步骤，和它们下面的节点，一律不算（§2.5 的 `live`）。
- 走一遍的记录是新的证据种类 `walk`，写在步骤节点上。命令、截图、终端三种只有 harness 能写：它在门禁工作树里按人批过的 `norm-merge-gate` 里的 `walk` 命令（流程正文只写走法的种类和预计用时，不写命令）把整条流程跑一遍，作为后台作业，持门禁锁（总时长不超过 45 分钟，低于别的检查等锁的 60 分钟），钉住主干提交；截图与终端类再由沿用审查者边界的 `walk-review` 角色逐步判断。人亲自走的由主 Agent 带原话用 `graph_walk` 记。主 Agent 自己写不了前三种（§2.7）。
- 缺口两个方向都标：没人负责的步骤，不服务任何步骤的活。形状上的毛病（流程没有入口、分支缺条件）也标，自动走法的流程拆成任务之后还没有人写测试也标（`flow:no-test`）。缺口在写入时不拒绝，对话里一步步改的中间状态必须是合法的；放行、走一遍之前与做完三处才挡（§2.6）。
- 人在对话里改。主 Agent 复述一句「那我记成……」，带人的原话写图。一个步骤的出边（顺序与分支）用一次 `graph_relink` 改完，因为 M3 的转述核对要求同一句原话对每个节点只写一次；改已批准节点的标题、走法的种类、步骤顺序、「怎样算做成」都要人的原话。问人按 `d-ask-three-gates`：只问人的事，可逆的技术选择自己定、用一句话告知，停下来的时候一次至多三件，形状按要问的是什么来选（§3.5、§4）。面板只看。
- 进两层循环的位置：访谈里画角色与流程，需求卡加第 9 项；大循环放行页与每个模块的放行页列出「服务哪几步」，大循环放行页另列每条流程将被执行的走法命令原文和超时，放行页的这些段由 harness 生成，分成人要同意的稳定部分和「截至给你看的时刻」的现状部分，两部分都核对「给人看过」，人回话时只重新渲染稳定部分比较（别的模块的进展不会让同意失效）；派活的简报写明这件活服务哪几步；整体审查前 harness 把每条流程走一遍，目标「做完」要求每条流程走通；晨报按流程说进度（§5）。
- 面板：「用户怎么用」页，左边用户图（按角色和流程排步骤），右边开发图（目标、模块、任务），点一边，另一边高亮连着的；首页对有用户图的目标先写流程进度（§6）。
- 兼容：没有用户节点的图原样工作；只加枚举值与可选字段，旧节点文件逐字节不变，不迁移历史；旧版本读到新图会丢掉带 `serves` 的开发节点并拒绝写入，所以新旧构建不能混用同一张图（§7.4）。

要人定的只有两件（§13）；替人定了的方向 28 条，在 §12。

## 1. 需求与验收

### 1.1 来源

人 2026-10-29：「有没有用户图这个东西？就是从用户的视角来看产品的功能和流程的？」

人 2026-10-30，更正编排方的理解：「我说的用户图是针对项目的，比如用我们这个插件开发一个图书管理系统项目，用户图就是这个项目真正的用户进去的样子，比如用户的登录流程啊，操作流程啊之类的」

人 2026-10-31：「是图，依旧参考项目图的理念。你看要不要两个融合一下，还是就分两个对比着看？」编排方推荐两件，人答「都没问题」：

1. 存成一张图、看成两面。用户的角色、流程、步骤是项目图的节点，与目标、特性、任务同一个引擎、同一份历史、证据与转述规矩；面板并排两个视图，用户图按角色与流程排步骤，开发图是现在的目标、特性、任务树。步骤连到负责它的特性或任务，步骤的状态由连着的活推出（都做完并验过才算走通），没人负责的步骤和不服务任何步骤的活两边都标出来；人在对话里改哪一边都行。不采用：两张独立的图对照着看。
2. 现在写设计、走评审与放行，实现排在 M3 与 M7 骨架合入之后，第一个自举的项目用不上它；不往正在实现的 M3、M7 里塞（`d-freeze-until-dogfood`）。

另：节点 `user-journey`（插件使用流程，`journey.md`）说的是人怎样用这个插件，不是本特性；它是本项目自己的用户图的第一份素材，人是它的用户。本稿在 §14 写它怎样搬，现在不搬。

### 1.3 非功能需求

- 小：图停在意图层（`CHARTER.md` §2）。一个目标的用户图一般 2 个角色、6 条流程、40 步上下；流程超过 12 步标「太长」，建议拆。
- 读得出：状态与缺口全部是图的纯函数（`src/graph/user-graph.ts`），宿主与面板用同一份代码；同样的图得到逐字相同的结果。
- 不拖慢：状态推导是 O(节点 + 连线 + 相关历史条数)，300 个节点以内在面板里一次算完不卡（实测见 §9，未实测的写进 §15）。
- 失败出声：读不出、算不出时降级但上报（§8）。
- 可追溯：每次走一遍、每次连线、每次对用户图的改动都是带身份、时间、理由的历史条目，经转述的带人的原话（`CHARTER.md` §7.1 条款 11）。
- 人话：面板和报告里给人看的字用 §6.5 的词表，不出现换词表上的词。

### 1.4 验收条件（实现任务用，每条可机检）

实施步 U1 至 U7（U5 拆成 U5a、U5b）在 §10，未核实的假设 A1 至 A11 在 §15。每条验收写明用哪一层的测试验证（L1 编译与静态检查，L2 假宿主与纯函数，L3 真运行时探针，L4 桌面版）。

**U1 数据格式（`schema.ts`、`format.ts`、`validate.ts`、`walk-spec.ts`、`user-live.ts`）**

1. `docs/graph/nodes` 里现有的全部节点文件读入后没有新增的校验问题，`serializeNode` 写出的文本与原文件逐字节相同（L2，黄金测试，用仓库当前的图）。
2. `role`、`flow`、`step` 三种节点通过校验当且仅当父节点类型是目标、角色、流程；不满足时报错，错误带文件与字段 `parent`（L2）。
3. `serves` 连线只能出现在特性或任务上，目标是步骤，且起点与目标属于同一个目标；跨目标的 `serves` 报错（L2，各一例通过、一例失败）。
4. `next` 连线只能出现在步骤或流程上：步骤的 `next` 目标是同一条流程里的另一个步骤；流程的 `next` 目标是以这条流程为父节点的步骤；`when` 只能出现在 `next` 上，单行，1 至 40 个码点（L2，每条各一例通过、一例失败）。
5. `depends` 的两端都不能是用户节点；用户节点的 `source` 只能指向 `question` 节点（指向 `decision` 或其他类型报错）（L2）。
6. 用户节点的 `status` 不能是 `doing` 或 `done`（读入时报错，写入时 `bad_transition`，`hint` 指向「走一遍」）（L2）。
7. `walk` 证据只能出现在步骤上；`ref` 单行、至多 200 个码点、合 `WALK_REF_PATTERN`；`exit` 必填；`note` 必填、单行、至多 300 个码点；带 `when` 的连线、带 `walk` 证据的节点各读入再写出，字节不变；历史里 `op: 'walk'` 的条目通过校验（L2）。`note` 里 `@提交` 的格式读入时不查（手改文件不该因此整张图写不进去），写入时查（第 14 条）。
8. `parseWalkLine`（`walk-spec.ts`）：`走法：命令 · 预计 40 秒`、`走法：截图 · 预计 90 秒`、`走法：终端 · 预计 20 秒`、`走法：你来走` 解析成功；缺种类、种类不在四种之内、预计不是 1 至 1800 的整数、`你来走` 后面还有内容、有多行 `走法：` 各一例 `unparsed`（带原因）；`walkCommandsOf` 只认 `` `walk <种类> $ <命令>` `` 形式的行，命令不含 `{flow}` 的行不认并带原因（L2）。

**U2 引擎（`engine.ts`、`mutation.ts`、`tools.ts`、`src/shared/tool-names.ts`）**

9. 提议用户节点：`llm` 不带转述得 `proposed`，带转述或 `human` 得 `approved`（L2）。
10. 权限（身份矩阵，L2）：`llm` 不带转述不能批准、否决、废弃、恢复用户节点；不能改已批准用户节点的 `title`、`acceptance`、`parent`；不能改已批准流程 `走法：` 一行里的种类（改预计秒数、改 `前提：` 与别的正文允许）；不能增删或替换已批准步骤或流程的 `next`；带转述都可以；自己提议且仍为 `proposed` 的用户节点，`llm` 可以改全部字段、增删、替换 `next`。
11. `serves` 写入拒绝（`invalid`，`field` 与 `hint` 写明正路）：服务者不是特性或任务，或是 `kind` 为 `review` 的任务；目标不是 `live` 的步骤；跨目标；一个步骤已有 8 个 `live` 的服务者；一个任务已有 3 条、一个特性已有 20 条 `serves`（L2，边界值各一例：第 8、3、20 条成功，第 9、4、21 条被拒；特性被拒的 `hint` 指向「把连线连到它的任务」）。
12. `relink` 操作：一次替换一个步骤的全部 `next` 出边，或一条流程的入口连线（最多一条）；引擎只提交一次，对写后的整图校验一次；历史对真实被摘掉的连线各记一条 `unlink`（`edge` 取节点上原有的那条，含 `when`），对新加的各记一条 `link`，时间、`reason`、`relay` 相同，不动的连线不记；新旧相同返回 `conflict`；列表里有重复的 `to`、超过 8 项、流程超过 1 项、目标不是同一条流程的步骤各一例 `invalid`；`rev` 过期 `stale_revision`；权限同第 10 条（L2）。
13. 转述核对（L2 加 L3）：§3.5 示范的两次调用（提议步骤「交押金」，`relink`「点借阅」）用同一句人的原话，通过真实的 `main-agent-graph-relay` 核对（假的会话投影，人的消息晚于「点借阅」的最后一条非批注历史）。测试用一张只有「借书」三步（点借阅、确认借阅、看到应还日期）的小图，不用 §2.9 夹具（夹具里「交押金」已经存在）；第二次调用的 `to` 取第一次 `graph_propose` 返回的节点 id，不写死；反例：对「点借阅」连写 `link`、`unlink` 两次，第二次被同一规则拒绝，说明为什么要有 `relink`。

18. 「走通」之后这条流程连着的活有任何一条非批注的历史（状态改变、改字段、连线增删、证据追加），状态变为「做完了，要重走」（`outdated`）；服务者给别的步骤加或摘连线不算（L2，每种历史各一例）。
19. `live`：废弃或被取代一条流程、一个角色、一个步骤之后，它们下面的步骤不再出现在状态、计数、缺口、放行项、完成检查里；指向非 `live` 步骤的 `next` 在形状判断里被忽略（中间一步被删而前一步没改连线，后一步报 `flow:unreachable`）；各有一例（L2）。
20. 服务者的粒度：特性作服务者、它下面没有任务连到这个步骤时，叶子取它的全部 `live` 叶子任务；它下面有任务连到这个步骤时只取这些任务；特性没有 `live` 子节点时叶子是它自己；`kind` 为 `review` 的任务不是叶子。用 §2.9 夹具里的「借阅」（任务级连线、部分在做）与「账号」（模块级连线、全部做完）各验一遍（L2）。
21. 不服务任何步骤：祖先特性服务了步骤则算有人用；被一个有人用的活依赖则算有人用；`kind` 为 `review` 的任务不算活；服务的步骤都已不 `live` 的活标出并写明原因；孤儿特性下面的孤儿任务不单列，只列最上面那个（L2）。
22. 入口与回环：流程恰有一条指向 `live` 步骤的 `next` 才有入口；没有、有两条各报 `flow:entry`；「没搜到，回到搜索」这种回到入口的 `next` 不报错（§2.9 的「搜书」）；`next` 构成环的流程，推导、排序、可达性都终止；显示顺序从入口深度优先（L2）。
23. 图里加入用户节点之后，开发图的进度数（做完几件、还剩几件）、`gatesOf` 的「子节点未全部关闭」、`listOpenItems` 的 `ready` 与 `doing`、`graph.svg` 与现有测试的期望值都不变（L2）。

**U4 访谈与放行（M3 一侧）**

27. 需求卡第 9 项「用户怎么用」：目标下至少有一个 `live` 的角色，其下至少一条 `live` 的流程，其下至少一个 `live` 的步骤；或目标正文有一行 `用户流程：无，<原因>`。两者都没有时 `propose_to_human` 的 `confirm` 返回 `gate_unmet`，并写明缺项；两者都有时前者生效，后者忽略（L2）。

29. 大循环放行门禁多六项：`flows:shape`、`flows:expect`、`flows:served`、`flows:modules`、`flows:walk`、`flows:page`（每项的 `label` 与 `hint` 见 §5.2）。缺任何一项时 `gate_unmet`；没分模块的目标的单次放行没有 `flows:modules`（L2）。放行页末尾由 harness 加三段，不截断，不计入 `page` 的 `PAGE_LIMITS.max`：「每条流程由哪个模块负责」与「每条流程怎么走一遍」（命令原文、预计秒数、超时的算法）是稳定部分，「截至给你看的时刻」（每条流程当前的超时上限及来源）是现状部分；三段整体计入「给人看过」的核对，合计超过 8,000 个码点时 `flows:page` 不过；人回话时只对稳定部分重新渲染比较，现状部分不比较（L2）。另有三例（L2，大循环页给人看之后）：别的模块里的任务状态变了，或主 Agent 给已经负责这些步骤的模块加了任务并用 `serves` 连上（归属没变），同意仍然有效；某个步骤标题、某条流程由哪个模块负责、某条命令原文变了，同意失效（`not_shown`）；现状部分的数（超时上限）变了，同意仍然有效。
30. 模块放行门禁多一项 `module:serves`：模块自己或它的任务至少服务一步，或模块正文有 `服务：无，<原因>`；放行页末尾由 harness 加「这个模块服务哪几步」一段，分稳定部分（按流程分组的步骤标题与顺序、条件、怎样算做成、模块正文 `服务：无` 的原因）和「截至给你看的时刻」的现状部分（每步现在的状态、别的模块是否也在做、模块里不服务任何步骤的任务数），整段计入「给人看过」的核对，回话时只比较稳定部分（L2）。另有两例（L2，模块放行页给人看之后）：别的模块的任务状态变了、这个模块自己的任务状态变了，同意仍然有效；这个模块服务的步骤集合变了或某步标题变了，同意失效（`not_shown`）。

**U5 执行、走一遍与晨报（M7 一侧）**

32. 派发的简报在 Context 里写明「这件活服务的步骤」：流程名 › 步骤名；`kind` 为 `test` 且服务了步骤的任务，简报多一段走一遍的约定（报告文件格式与 `norm-merge-gate` 里该种类的 `walk` 命令，常量只在 `walk.ts` 一处定义）（L2）。
33. 走一遍作业（L2，假命令、假时钟、假 git；L3）：`dispatch_task <目标 id>` 在目标 `present` 时先查前提（目标下没有 `proposed` 的 `live` 用户节点，没有 `step:unserved`、形状缺口、`flow:no-walk`、`flow:no-test`，否则 `walk_unready` 并列出缺项），再对没有有效通过记录的自动走法流程起一个后台作业，立即返回 `{status: 'walking', job, flows, waitingForPerson, head}`（`head` 是项目根 `HEAD` 的前 7 位），不在工具调用里等；同一个目标已有作业在跑时返回同一个 `job`；作业开始时钉住主干提交 `T`，在门禁工作树检出 `T` 并按 M7 §3.8.3 第 5、6 步准备，持门禁锁，等锁同 M7；作业总时长从取到锁起算、含准备，不超过 45 分钟（`walk.ts` 的 `WALK_JOB_MS`，测试断言它小于 `gate-lock.ts` 的 `GATE_WAIT_MS`）：每条流程开始之前，已用时间加这条流程的超时上限超过 45 分钟的不开始，在事件里标 `not_run`（一个作业的第一条流程总是开始），下一次 `dispatch_task` 为它们接着起作业；这期间别的目标的 `check_commit` 照 M7 的规则等锁；极端情况（准备命令加第一条流程合计超过 60 分钟）别的检查得到 `gate_busy`，主 Agent 重试，不丢工作（假时钟，各验一遍）；完成时发出事件 `hourness.walk-done` 叫醒主 Agent；作业运行与结束都算空转计数里的活动。
34. 走一遍的证据规则只有一条（L2）：命令超时或被杀，只在入口步骤写 `exit` 为 1 的证据；报告缺失或不合格，在入口步骤写 `exit` 为 1 的证据；报告合格时，对报告里列出的每个步骤写一条，`exit` 为 0 当且仅当该步 `ok` 为真，否则取命令的退出码，命令退出码为 0 时取 1；命令退出码不是 0 而报告里列出的步骤全是 `ok` 时，入口步骤的 `exit` 取命令的退出码；报告没列的步骤不写证据。各一例：退出 0 加一步 `ok: false`；退出非零加部分报告；退出非零而全部 `ok`；超时；报告缺失。
35. `walk-review`（L2，复核替身给固定回复）：`截图`、`终端` 两种走法在命令完成后，由 harness 起 `walk-review` 激活，输出 `hourness-walk-review-v1`（`{steps: [{id, ok, why}]}`，必须覆盖这条流程每个 `live` 且已批准的步骤）；`walk-review` 登记为审查者，走 M7 对审查者的同一份边界与工具面过滤（只写 `.hourness/`，对图只读加批注，没有图写工具，包括 `graph_relink`、`graph_walk`），产物的路径写在它的 prompt 里，不另设目录级读权限；`ok` 为真映射 `exit` 0，为假或缺步骤映射 1，`why` 进 `note`；`截图` 流程的作业开始时 `dispatch_task` 带的模型不在目录里标明支持图片输入的，拒绝 `walk_model_no_images`；复核激活失败重试至多两次，仍失败的流程不写证据，事件里标 `review_failed`，同一流程连续三次这样，发出 `hourness.stopped`（`kind: 'acceptance'`）。
36. 超时（L2）：第一次的超时是预计秒数的 3 倍，不低于 10 秒、不高于 30 分钟；跑过之后取最近三次里最慢一次的 3 倍，同一范围；3 倍超过上限时保持上限，事件对主 Agent 写明，不问人；每次变更在 `<exec>/walk-limits.jsonl` 记 `{flow, old, new, source: 'agent' | 'harness', basis, at}`，每次运行在 `<exec>/walks.jsonl` 的 `flow-end` 行记 `{limitMs, elapsedMs, outcome}`；超时事件的文字写明哪一条流程、上限与来源、实际耗时、接下来怎么办。
37. 你来走（L2）：`你来走` 的流程在没有有效通过记录时，`dispatch_task` 返回 `walk_unready` 并列在 `waitingForPerson`，`hint` 要求主 Agent 用 `propose_to_human` 的 `question` 一种建待决，问句里写明请人走的是哪一个提交（`dispatch_task` 的结果带 `head`），他走的不是它就先重新部署；人回话后 `record_human_answer` 记下回答，`graph_walk` 带原话把这条流程每个步骤的结果记上；记录的 `note` 以工具生成的 `@提交` 开头，内容取人原话的第一行，超过 200 个码点取前 199 个加 `…`（一例：第一行 300 个码点的转述，`note` 不超过 242 个码点，合 `WALK_NOTE_PATTERN`）；`steps` 少一个步骤、或多了不是这条流程 `live` 且已批准的步骤时 `invalid`；人说某一步不对时，该步骤的 `ok` 为假，写 `exit` 为 1。
38. 完成：`goalCompletion` 多一项（`userCompletionItems`）：目标 `present` 时，每个 `live` 的已批准步骤是 `walked`，且最近一次通过的走一遍所记的提交是整体审查所记主干提交的祖先（或相同），两者之间改动的路径全在 `docs/graph/` 下；函数或 git 调用抛错时拒绝完成并写明；`用户流程：无` 且没有角色时不适用（L2，git 用假实现）。

- 不在面板里编辑、不在面板里放行（`d-ui-look-not-operate`）。
- 不迁移 `user-journey`（§14），不改任何已放行设计的文件。
- 不做 `user-graph.svg` 图片。`graph.svg` 只需要不出现用户节点（§3.8）。
- 不做跨流程的依赖（流程 B 要先走流程 A）。前提写在流程正文的 `前提：` 一行，走法脚本自己处理（§2.2）。

## 2. 概念与总体设计

### 2.1 一张图，两个视图

```
目标 goal
 ├─ 角色 role ─ 流程 flow ─ 步骤 step ──next（带条件）──▶ 步骤 step
 │                              ▲
 │                              │ serves（存在做事的一边）
 └─ 特性 feature ─ 任务 task ────┘
```

用户图是目标下的 `role › flow › step` 这一支；开发图是同一个目标下的 `feature › task`（两层循环里的模块是特性）。两支共用 `parent`、`edges`、`evidence`、`history`，共用同一个 `apply`。两支之间只有一种连线：`serves`。面板按节点类型把同一份节点分成两个视图（§6）。

要点是用户图不新建存储、不新建引擎、不新建权限体系；差别只在三种节点类型、两种连线类型、一种证据类型，和一套从图推出状态与缺口的纯函数。

### 2.2 节点

| 类型 | 父节点 | 是什么 | `title` | `acceptance` | 正文约定 |
| --- | --- | --- | --- | --- | --- |
| `role` 用户 | 目标 | 从外面碰这个产品的一种身份 | 读者、管理员 | 不用 | 一两句：他是谁、来做什么 |
| `flow` 流程 | 角色 | 这个身份要办成的一件事 | 借书 | 做成时他拿到什么（可检查），例「读者借到一本书，看到应还日期」 | `前提：`（例：已登录），`走法：`（§2.7） |
| `step` 步骤 | 流程 | 流程里他做的一步，或他看到的一个结果 | 在书的详情页点「借阅」 | 这一步做成时他看到什么（可检查），例「页面提示借阅成功」 | 可空 |

标题用用户自己的话：一句话，不带节点编号、文件名、函数名、界面组件的内部名。内部模块永远不是步骤（§2.8）。

存下来的 `status` 只有四种取值：`proposed`（提议，还没人定）、`approved`（人定了，算进产品）、`dropped`（人不要了）、`superseded`（被新节点取代）。用户节点从不存 `doing` 与 `done`：进度由连着的活推出（§2.5），存一份只会和推出的对不上（`CHARTER.md` §10.1 单一事实源）。读入时 `doing` 或 `done` 是校验错误；写入时 `status` 操作要这两个值，返回 `bad_transition`，`hint` 写「a user step is walked, not finished: its state comes from the work that serves it and from walk evidence」。

其余字段：`slope`、`stage`、`verification`、派发属性（`kind` 等）、待决的字段都不用，现有的「只有某类节点才带」规则本来就拒绝它们。`outputSchema` 同属派发属性，不用。

正文标签沿用 `labeledSections`（`src/graph/stage.ts`）：流程的 `前提：` 是写给人看的一行，harness 不查；`走法：` 的格式见 §2.7；目标正文多一个标签 `用户流程：`（只在「这个目标没有终端用户」时写，值以「无」开头，§5.1；目标已经有 `live` 的角色时这一行不生效）；特性（模块）正文多一个标签 `服务：`（只在「这个模块不直接服务任何步骤」时写，值以「无」开头，§2.6）。

### 2.3 连线

现有连线类型 `depends`、`source`、`supersedes` 不变。新增两种：

| 类型 | 存在哪个节点上 | 指向 | 含义 | 附加 |
| --- | --- | --- | --- | --- |
| `next` | 步骤 | 同一条流程里的另一个步骤 | 做完这一步，下一步可以是 `to` | `when?`：走这条路的条件，用户的话，单行，至多 40 个码点，例「没交押金」 |
| `next` | 流程 | 以这条流程为父节点的一个步骤 | 这条流程从 `to` 开始：这条连线就是流程的入口 | 无 `when` |
| `serves` | 特性或任务 | 步骤 | 这件活是做出这个步骤的一部分 | 无 |

`next` 的规则：

- 一个步骤有 0 条（流程的终点）、1 条（顺序走）或多条出边（分支）。出边多于一条时每条都要写 `when`，且互不相同。这是形状上的要求，不是写入时的拒绝（§2.6）：在对话里插一步要分几次写，中间状态必须合法。
- **入口是显式的**：流程节点自己带一条 `next` 指向它的第一步，不由「没有入边的步骤」推算。所以「没搜到，回到搜索」这种回到第一步的环不影响入口（第一步有入边也照样是入口），在最前面插一步就是改流程节点上的这一条连线。流程上这种连线不是恰好一条，或目标不是 `live` 的步骤，是缺口 `flow:entry`（§2.6）。流程节点上的 `next` 不带 `when`。
- 允许环：「没搜到，回到搜索」是一条回到前面步骤的 `next`。推导、排序、可达性都按有环的图写（§3.3、§9）。步骤不能连向自己（现有的「连线不指向自己」），原地重试写成一个单独的步骤，例如「看到错误提示」再回到输入。
- 显示顺序：从入口深度优先走，同一步的出边按目标步骤的创建时间（第一条历史），再按 id；先走完一支再走下一支，已走过的步骤不重复列；走不到的步骤按创建时间排在最后并标「走不到」。
- 不用序号字段排序：在中间插一步要改后面所有步骤的序号，分支也表达不了。

`serves` 的规则与理由：

- 存在做事的一边（特性或任务），不存在步骤上。理由：人的用户图不应该因为开发那边每加一个任务就改写步骤节点；步骤节点上的写入会和别人的写入撞 `stale_revision`；去掉一个任务时它的连线跟着它走。
- 不复用 `source`。`source` 的意思是「本节点因 `to` 而存在」，M3 的五栏门禁用指向设计决策的 `source` 数「规划」（`stage.ts` 的 `designColumns`）。两种意思混在一种连线上会让两边的计数互相污染。
- 服务者可以是特性（包括模块和模块候选）或任务。**两级的含义不同**：任务级的连线说「这个任务做出这一步」，是进度的依据；模块级的连线说「这个模块负责这一步」，是放行时的归属声明。分解时主 Agent 把任务连到它做的步骤（§4.3）；模块下有任务连到某一步时，这一步的进度只看这些任务，没有时看模块的全部任务（§2.5）。

`depends` 的两端都不能是用户节点。`source` 的目标不能是用户节点；用户节点自己可以带 `source`，但目标只能是 `question` 节点（例如「借书前要先交押金」那一步指向人说这句话时记下的待决，用来追溯）。不允许指向 `decision`：M3 的「规划」栏数的就是指向设计决策的 `source`，一个步骤指着设计决策会让「规划」栏在没有任何特性或任务被规划时成立（`designColumns` 不改，由这条规则兜住）。

### 2.4 条数

| 对象 | 条数 | 超出时 |
| --- | --- | --- |
| 一个步骤的服务者（`live` 的 `serves` 入边） | 0 至 8 | 0 条是缺口（没人负责）；第 9 条的 `link` 或 `propose` 被拒，`hint`「this step is too big: split it into smaller steps」 |
| 一个任务的 `serves` | 0 至 3 | 第 4 条被拒，`hint`「a task serves a few steps; if it serves more, split the task」 |
| 一个特性的 `serves` | 0 至 20 | 第 21 条被拒，`hint`「a feature owns at most 20 steps by its own links; connect the tasks that build the steps instead (task links give the progress), or, before the big-loop release, split the module」 |
| 一个步骤的出边 `next` | 0 至 4 | 第 5 条记为缺口 `step:too-many-branches`，不拒绝；一次 `relink` 最多 8 项 |
| 一条流程的步骤数 | 建议不超过 12 | 超过标 `flow:too-long`，不拒绝 |

`serves` 的上限是写入时的拒绝，因为上限本身是防线：一个任务连到所有步骤，会让「不服务任何步骤」的检查什么都查不出来。特性的上限比任务高，因为模块级的连线只是归属声明，一个模块真的会负责十几步（「借阅」模块负责借书、还书、续借、预约，共十来步）。第 21 条被拒时正路不是拆模块（模块清单只在大循环里定），是把连线连到做这些步骤的任务上：任务级连线不受特性上限约束，进度本来也该看任务。数字是 agent 定的，可推翻（§12 D5），都放在 `schema.ts` 的 `USER_LIMITS` 一处。

### 2.5 步骤与流程的状态：推出，不存

纯函数模块 `src/graph/user-graph.ts`，不用 Node 内置模块，宿主与面板共用。

**`live`。** 节点 `live`，当且仅当它的 `status` 是 `proposed` 或 `approved`，并且沿 `parent` 到目标之前的每个祖先也满足同样的条件。引擎的 `planStatus` 没有级联，废弃一条流程不改它下面步骤的存下来的状态；所以所有判定都用 `live`，不看单个节点的 `status`：状态、计数、缺口、`present`、放行项、完成项、写入规则 W2 都只取 `live` 的节点；`next` 连线的另一端不 `live` 时，在形状与可达性判断里当作没有这条连线。被取代（`superseded`）同理。特性与任务也用同一个函数（废弃一个特性，它下面的任务不再算活）。

**步骤的服务者与活。** 步骤 S 的服务者（`serversOf`）是所有指向 S、`live` 的特性与任务，`kind` 为 `review` 的任务除外。服务者的叶子（`leavesOf`）：

- 任务服务者：它自己。
- 特性服务者 F：F 下面有 `live` 的任务连到 S（任务级连线）时，取这些任务；没有时取 F 的全部叶子，也就是递归取 `live`、`kind` 不是 `review` 的特性与任务子节点里的叶子（任务本身是叶子），F 一个这样的子节点都没有时取 F 自己。

`kind` 为 `review` 的任务不是活（设计评审、整体审查不做出用户能看到的东西）。叶子的状态：`done` 是做完，`doing` 是在做，其余（`proposed`、`approved`）是还没开始。

**步骤的状态**，按下表顺序取第一条成立的：

| 状态 | 条件 | 面板上的字 |
| --- | --- | --- |
| `proposed` | 步骤自己的 `status` 是 `proposed` | 待你定 |
| `unserved` | 没有服务者 | 没人负责 |
| `planned` | 叶子都不是 `doing` 或 `done` | 排上了 |
| `building` | 叶子没有全部 `done` | 在做 |
| `failed` | 叶子全部 `done`，最近一次走一遍没过，之后这条流程连着的活没有动过 | 走不通 |
| `walked` | 叶子全部 `done`，最近一次走一遍通过，之后这条流程连着的活没有动过 | 走通了 |
| `built` | 叶子全部 `done`，从没走过，或走过但之后连着的活动过（此时 `outdated` 为真） | 做完了，等走一遍（`outdated` 时写「做完了，要重走」） |

不是 `live` 的步骤不推导，不进流程的统计。

「走一遍」的记录：步骤的历史里 `op` 为 `walk` 的条目，只认身份是 `harness` 或 `human` 的，或身份是 `llm` 且带转述的（手改的文件里别的身份写的 `walk` 不认）。一个条目通过，当且仅当它的每一条证据 `exit` 都是 0。取最后一条。

「连着的活动过」按整条流程算，因为走一遍是把整条流程走一遍，一个步骤的服务者变了，别的步骤的结果就不能再信。流程 Φ 里的步骤 S，它的集合 X(S) 是：流程 Φ 自己、Φ 的全部 `live` 步骤、这些步骤的全部服务者、这些服务者的叶子。X(S) 里有任何一个节点有一条历史，`op` 不是 `comment` 和 `walk`，时间不早于 S 最近那次走一遍，S 就是「动过」。例外：服务者上 `serves` 连线的增删，只算指向 Φ 的步骤的那些（模块给别的流程的步骤加一条连线，不该让这条流程重走）。时间相等也算动过（保守的一侧）。这是纯图上的时间比较，不查 git；与主干提交的核对在 M7 的完成检查里做（§5.5）。

**流程的状态**，对 `live` 且已批准的步骤（`proposed` 的步骤还没算进产品，只在计数里单列一项「待你定」）：流程自己 `proposed` 时是 `proposed`；没有已批准的步骤时是 `empty`；有 `failed` 的步骤时是 `failed`；全部 `walked` 时是 `walked`；其余取步骤里最靠前的那个状态（次序 `unserved`、`planned`、`building`、`built`）。流程同时带每种状态各几步，面板写「6 步：4 走通 · 1 在做 · 1 没人负责」。缺口的判定（§2.6）对 `live` 的步骤（`proposed` 或 `approved`）做，因为放行时这些步骤正是一起被批准的。

**角色**与**目标**只汇总。角色的状态用同一个折叠：其下 `live` 的流程里有 `failed` 就是 `failed`，全部 `walked` 是 `walked`，其余取最靠前的（次序 `proposed`、`empty`、`unserved`、`planned`、`building`、`built`），没有流程是 `empty`；目标另带每种流程状态各几条。目标「用户流程」一项走通当且仅当没有 `empty` 的流程，且每条已批准的 `live` 流程都是 `walked`（§5.5）。`present` 是目标下至少有一个 `live` 的角色。

状态不存，所以没有「状态与现实不一致」这种故障：连着的活重开了，下一次读就是「在做」。

### 2.6 缺口：两个方向都标

`gapsOf(graph, goal)` 返回缺口列表，每个缺口有稳定的 `key`、涉及的节点、给人看的一句（中文）和给模型的 `hint`（英文，说明正路）。以下全部只看 `live` 的节点。

| `key` | 含义 | 方向 | 在哪里挡 |
| --- | --- | --- | --- |
| `step:unserved` | 步骤没有服务者 | 用户到开发 | 放行门禁；走一遍的前提；做完检查 |
| `work:orphan` | 特性或任务不服务任何步骤（定义见下） | 开发到用户 | 模块放行门禁（只对模块）；其余只标出 |
| `step:no-expect` | 步骤没写 `acceptance` | 形状 | 放行门禁 |
| `step:failed` | 最近一次走一遍没过 | 证据 | 做完检查 |
| `flow:empty` | 流程没有 `live` 的步骤 | 形状 | 放行门禁；走一遍的前提 |
| `role:no-flow` | 角色没有 `live` 的流程 | 形状 | 放行门禁；走一遍的前提 |
| `flow:entry` | 流程上指向 `live` 步骤的入口连线不是恰好一条 | 形状 | 放行门禁；走一遍的前提 |
| `flow:unreachable` | 步骤从入口走不到 | 形状 | 放行门禁；走一遍的前提 |
| `step:branch` | 指向 `live` 步骤的出边多于一条，有的没有 `when` 或 `when` 重复 | 形状 | 放行门禁；走一遍的前提 |
| `flow:no-walk` | 流程没有可解析的 `走法：`，或这个种类在 `norm-merge-gate` 里没有 `walk` 命令，或种类是 `截图` 而目录里没有支持图片输入的模型（`walkSpecOf` 的 `unparsed` 原因） | 证据 | 放行门禁；走一遍的前提；做完检查 |
| `flow:no-test` | 自动走法（命令、截图、终端）的流程，每个 `live` 的步骤都已有任务叶子（拆成了任务），而这些步骤的叶子里没有一个 `kind` 为 `test` 的任务（`leavesOf`，§2.5）：走一遍要跑的端到端测试没有人在写，等到整个目标做完才会发现 `no_report`。判据故意等到每一步都拆成了任务才成立，放行时任务还不存在，不会在每条流程上都冒出来 | 证据 | 走一遍的前提（`walk_unready`）；不挡放行，不挡写入；分解提醒与派发状态提醒里出现（§5.4） |
| `flow:too-long`、`step:too-many-branches` | 超过建议的大小 | 形状 | 只标出 |

「不服务任何步骤」的判定（`work:orphan`）：一个 `live` 的特性或任务（`kind` 不是 `review`）算有人用，当且仅当下列之一成立：它自己有指向 `live` 步骤的 `serves`；它的某个后代有（模块只有任务级连线时，模块不是孤儿）；它的某个祖先（到目标为止，不含目标）有；某个有人用的活依赖它（`depends` 反向可达）。四条合起来，基础设施类的活（建库、搭脚手架）只要被某个服务步骤的活依赖，就不会被误标。四条都不成立的才是孤儿。`serves` 只指向不 `live` 步骤的活，同样是孤儿，原因写「它服务的步骤都不要了」。孤儿的父节点也是孤儿（特性）时，只列最上面那个，它下面的不单列。

模块是例外：模块（分了模块的目标的直接特性子节点和模块候选）是人放行的单位，所以孤儿模块要显式交代：模块正文有一行 `服务：无，<原因>`（例：搭建项目骨架与持续集成）就不算缺口，放行页上原样显示这个原因。任务级的孤儿只标出，不挡：标出就是让人和主 Agent 看见，是该去掉的多余的活，还是漏了一个步骤。

缺口在写入时不拒绝，这是有意的。对话里加一步要几次写入：先提议步骤，再改前一步的出边，中间每一刻的图都要是合法的，面板上同时看得见还差什么。只有这几处挡：放行（形状、没人负责、没写怎样算做成、没写怎么走一遍）、走一遍之前（同样的缺口，再加 `flow:no-walk`、`flow:no-test`，以及目标下还有 `proposed` 的 `live` 用户节点，§5.5）和做完（没人负责、走不通、没写走法）。

### 2.7 走一遍：什么算验过

「验过」的意思是：这一步在真实运行的产品上被走到，并且留下了别人能复核的东西。三种自动的走法，加上人亲自走：

| 走法 | 谁跑 | 留下什么 | 判定 |
| --- | --- | --- | --- |
| `命令` | harness 在门禁工作树里跑 `norm-merge-gate` 里的 `walk 命令` 行（端到端测试） | 退出码；每一步的断言结果（报告） | 报告里这一步 `ok`（规则见下） |
| `截图` | harness 跑 `walk 截图` 行，把每一步截下来（界面类项目） | 每步一张图 | 报告 `ok`，并且 `walk-review` 对照这一步的 `acceptance` 看图后判通过 |
| `终端` | harness 跑 `walk 终端` 行，记下命令、退出码、输出（命令行或库） | 每步一段输出 | 同上，复核看输出 |
| `你来走` | 人 | 人的原话 | 人说走过、没问题；主 Agent 带原话用 `graph_walk` 记 |

**流程怎么写走法。** 流程正文的 `走法：` 一行只写种类和预计用时，不写命令：

```
前提：读者已登录，馆里已有这本书
走法：命令 · 预计 40 秒
```

格式是 `走法：<命令|截图|终端> · 预计 <N> 秒`（N 是 1 至 1800 的整数），或 `走法：你来走`。`parseWalkLine` 解析（`src/graph/walk-spec.ts`，纯函数）。

**命令从哪来。** 命令写在规范节点 `norm-merge-gate` 的 `acceptance` 里，每个种类一行：

```
`walk 命令 $ npm run e2e -- --flow {flow}`
`walk 终端 $ npm run walk:cli -- {flow}`
```

`{flow}` 换成流程的节点 id（id 只含小写字母、数字、连字符，进 shell 命令不需要转义）。`walkCommandsOf(acceptance)`（同一个文件）只认这一种写法。理由：`norm-merge-gate` 的验收只有人的权限能改，别的项目里它随放行一起被人同意（M7 §3.8.1），所以人批过什么命令会被 harness 执行是现成的机制；流程正文是主 Agent 随时能改的文字，不能让 harness 照着它执行。流程只选种类，选不出命令外的东西。`walkSpecOf(flow, commands)` 合并两处，返回 `{kind, seconds, command}`、`{kind: '你来走'}` 或 `{unparsed: 原因}`（没有 `走法：` 一行、格式不对、这个种类在清单里没有 `walk` 行、`截图` 而目录里没有支持图片输入的模型），`unparsed` 进缺口 `flow:no-walk`。对 M7 的请求：`parseGateNorm` 认 `` `walk <种类> $ <命令>` `` 这种写法并跳过它，`check_commit` 与巡检不跑它（§11）。

命令由 harness 起：沿用 M7 §3.8.1 的方式，`child_process.spawn(command, {shell: true, cwd: 门禁工作树})`，超时结束整棵进程树（Windows 用 `taskkill /T /F /PID`），输出写日志文件；从不在主检出里跑。命令本身是普通的测试代码，由 `kind` 为 `test` 的任务写，这些任务也用 `serves` 连到它覆盖的步骤，经过合入前检查与审查才进主干；每条自动走法的流程拆成任务之后还没有这样的任务时，缺口 `flow:no-test` 在分解时就点名，不等整个目标做完、走一遍报「报告缺失」才发现（§2.6）；harness 保证的是「主 Agent 不能改成跑别的东西，也不能自报通过」，测试代码本身写得对不对由审查和整体审查看（§15 A9）。

**报告文件。** 种类是命令、截图、终端的走法，命令跑完要在门禁工作树里写 `.hourness/walk/<流程 id>/report.json`；harness 每次跑某条流程之前先删掉这个目录，免得读到上一次的：

```json
{ "flow": "flow-3",
  "steps": [ { "id": "step-9", "ok": true, "artifact": "step-9.png", "said": "详情页有「借阅」按钮，可点" } ] }
```

`artifact` 是同目录下的文件名（不许带路径分隔符与 `..`），`said` 一行至多 120 个码点，可空。harness 核对：`flow` 与目录一致；每个 `id` 是这条流程的 `live` 且已批准的步骤、不重复；截图与终端的每一步必须有 `artifact`，文件存在、非空、图不超过 5 MB、文本不超过 200 KB；然后把整个目录复制到 `<exec>/walks/<作业号>/<流程 id>/`（运行时的东西，不进 git），证据指向这个副本。报告里没列的步骤不写证据，这一步仍是「做完了，等走一遍」，做完检查会指出「报告没覆盖这一步」。报告的格式只在 `walk.ts` 一处定义，写测试的任务从简报里读到它（§5.4）。

**证据怎么写。** 新的证据种类 `walk`，写在步骤节点上。字段格式在这里一处写死，读入（V7）、写入（W4）、解析（完成检查）都引用它：

| 字段 | 内容 |
| --- | --- |
| `kind` | `walk` |
| `ref` | 单行，至多 200 个码点，合 `WALK_REF_PATTERN`：`command:`、`screenshot:`、`transcript:`、`person:` 之后接内容。前三种接命令文字（超过 150 个码点截断加 `…`）或副本里的文件路径；`person` 固定是 `person:conversation` |
| `exit` | 0 通过，非 0 没过 |
| `note` | 必填，单行，至多 300 个码点，合 `WALK_NOTE_PATTERN = /^@[0-9a-f]{7,40} .+$/u`：`@<提交>` 之后是内容。harness 写的内容是 `sha256:<文件摘要前 8 位，没有文件写 ->` 加一个空格和一行结果（例：`@3f2a91c sha256:9bd1c0e2 通过`）；人走的内容是人原话的第一行，超过 200 个码点时取前 199 个加 `…`（总共 200 个）；整条 `note` 因此至多 242 个码点，在 300 的上限之内 |

节点上的 `evidence` 只保留最近 10 条 `walk` 证据，更早的从节点上去掉；历史里的条目完整保留（状态推导读历史）。

**谁能写。** 只有新操作 `walk`，且限定身份（§3.4）：`harness` 写前三种；`human` 写任意一种；`llm` 只有带人的原话转述时才能写，只许 `person:conversation`。主 Agent 自己不能写命令、截图、终端三种证据：这三种的真假是「门禁只认证据，不认自述」（`CHARTER.md` §6）要防的地方，由 harness 跑、由独立复核看。`graph_walk`（主 Agent 的工具）：参数 `id`（流程）、`rev`（流程的）、`steps`（这条流程每个 `live` 且已批准的步骤一项 `{id, ok}`，少一个、多一个都 `invalid`；流程里还有 `proposed` 的 `live` 步骤时 `bad_transition`，先请人批准或拒绝它，§5.5 第 1 步在 `dispatch_task` 一侧同样挡住）、`reason`、`relay`（必填）；工具自己读各步骤的 `rev`，自己生成证据（`person:conversation`，`exit` 为 `ok` 的 0 或 1，`note` 是 `@` 加项目根 `HEAD` 的提交加 `relay` 的第一行，超过 200 个码点按上表截断），逐步骤各写一次 `walk`；`HEAD` 读不到时 `unavailable`，一个都不写；中途有一次写失败时返回已写和未写的步骤，主 Agent 重试未写的。模型提供的只有 `ok` 和人的原话，提交号不由模型填。**记下的提交是项目根此刻的 `HEAD`，不一定是人实际走的那个构建**（例如他开着一个旧的开发服务器）：所以请人走一遍时，主 Agent 要在问句里告诉他走的是哪一个提交（`dispatch_task` 的结果带 `head`，`graph_walk` 的结果带写下的提交），他走的不是它就先重新部署再走；这句话写进 `graph_walk` 的说明。转述核对的起点（M3 附录 0.5 §3.8 第 1 条）对 `graph_walk` 取这条流程和它全部 `live` 步骤最近一条非批注历史的最晚时间，而不是流程节点自己的：证据写在步骤上，只看流程节点会让人很早以前说过的一句「我走过了」被拿来再记一次；这样一句原话只能记一次走一遍，harness 自己写的走一遍之后也要人重新说（§11 M3 请求）。

**一条规则：每一步的 `exit`。** 命令、截图、终端三种走法共用这一条（`截图`、`终端` 先过 `walk-review`，下面的 `ok` 是「报告里 `ok` 且复核判通过」）：

1. 命令超时或被杀：只在入口步骤写 `exit` 为 1 的证据，`note` 的内容写「超时」；其余步骤不写。
2. 报告缺失或不合格：只在入口步骤写 `exit` 为 1 的证据，`note` 的内容写「没走完：<原因>」。
3. 报告合格：对报告里列出的每个步骤写一条。`exit` 为 0 当且仅当这一步 `ok` 为真；否则是命令的退出码，命令的退出码为 0 时是 1。
4. 命令的退出码不是 0，而报告里列出的步骤全是 `ok`（报告和命令互相矛盾）：入口步骤的 `exit` 取命令的退出码，按没过算。
5. 报告没列的步骤不写证据。

所以一个测试运行器在第 4 步失败后非零退出，前 3 步仍记通过，第 4 步记没过；退出 0 而报告里有一步 `ok: false`，这一步记没过。这样流程一定显示「走不通」或「做完了，等走一遍」，原因看得见，修好之后整条流程重走。一个步骤连续三次走不通，整体审查按「停下」处理，交 `hourness.stopped`（`kind: 'acceptance'`）让主 Agent 问人（M7 §3.7.3 的收敛，三轮）。

**`walk-review`（独立复核）。** 截图与终端两种走法的通过与否取决于一个独立的复核 agent，它是 M7 登记表里的一个新角色，按审查者登记：

- 谁启动：走一遍作业（下面）里的 harness，用与整体审查相同的 `startActivation`，不由主 Agent 派。
- 模型：用启动这次作业的那次 `dispatch_task` 带的 `model` 与 `why`（`d-main-agent-models`：模型由主 Agent 选，harness 只核对）。核对多一条：`截图` 流程要求这个模型在 provider 目录里标明支持图片输入，否则 `dispatch_task` 拒绝 `walk_model_no_images`（目录里一个这样的模型都没有时，`walkSpecOf` 把 `截图` 判为不可用，`flow:no-walk` 写原因，流程改用 `终端`、`命令` 或 `你来走`；目录是否标明图片输入没有核实，§15 A6）。
- 边界：沿用 M7 对审查者的边界，不另造机制。M7 的角色边界是两样东西：工具面过滤（`faces.ts`）和写入前规则（`worker-scope` 第 4 条：审查者只能写 `.hourness/`；`worker-graph-readonly`：对图只读，只能批注）。`walk-review` 在登记表里按审查者登记，所以同样没有图写工具（包括 `graph_relink`、`graph_walk`，M7 的名单要加这两个名字，§11），只能写 `.hourness/`。M7 没有按目录限定读权限的机制，本设计也不加：产物的路径（报告里的 `artifact` 在副本目录里的位置）写在它的 prompt 里，要求它只看这些文件。它读了别的东西不改变证据的来源：证据由 harness 以 `harness` 身份写，复核只交 `{id, ok, why}`。
- 看图靠 DSH 的读文件工具能把图片交给模型。这一环没有核实（§15 A6）：U5b 的 L3 场景 `glm-exec-walk` 放一张真实的小图片，让复核照图说出图上的字，说不出就把 `截图` 从 `WALK_KINDS` 去掉（常量一处，`flow:no-walk` 写原因）。
- 输出：`outputSchema: hourness-walk-review-v1`，`{steps: [{id, ok, why}]}`，必须覆盖这条流程每个 `live` 且已批准的步骤，`why` 一行至多 120 个码点；缺步骤或 schema 不合算这次激活失败。
- 映射：`ok` 为真时这一步的复核判通过；为假或缺步骤时判没过，`why` 进证据 `note` 的结果。
- 失败：激活失败（崩溃、超时、输出不合 schema）重试至多两次；仍失败的流程不写证据，作业事件里标 `review_failed`，整体审查不派；同一流程连续三次 `review_failed`，发出 `hourness.stopped`（`kind: 'acceptance'`）让主 Agent 问人。
- 测试里复核用固定回复的替身。

**走一遍作业：什么时候走，谁来触发。** 目标下的活都关了之后（`hourness.tasks-closed`），主 Agent 派整体审查（`dispatch_task <目标 id>`，M7 §3.9.4）。有用户图的目标，这一步先走一遍。走一遍是后台作业，仿 `check_commit`（M7 §3.8.2 至 §3.8.3），不在一次工具调用里等：

1. `dispatch_task <目标 id>` 先查前提（§5.5 第 1 步）。通过后，对每条没有有效通过记录的自动走法流程起一个作业，立即返回 `{status: 'walking', job, flows, waitingForPerson, head}`（`head` 是项目根 `HEAD` 的前 7 位，请人走一遍时用，见下面「你来走」）。「有效通过记录」的判定见 §5.5 第 2 步；同一个目标已有作业在跑时返回同一个 `job`。
2. 作业开始时钉住主干末端提交 `T`，取门禁锁（等锁同 M7：每 5 秒一次、至多 60 分钟；锁的陈旧判定 6 小时远在第 4 步的上限之上），在门禁工作树里检出 `T` 并按 M7 §3.8.3 第 5、6 步准备（包括有改动时先存快照、新建或监视文件变了就跑 `setup` 命令）。
3. 按次序对每条流程：解析走法、清报告目录、起命令、等到超时、读报告、核对、复制产物、必要时起 `walk-review`、按上面的规则给每个步骤写证据（harness 身份，写进主检出的 `docs/graph/nodes`，由主 Agent 像别的图记录一样提交；`norm-merge-gate` 的 `only docs/graph/` 一条让这种提交不用重跑检查）。证据的 `reason` 写 `<作业号> 流程「<名>」走一遍`。写某个步骤遇到 `stale_revision`（主 Agent 同时在改图）时读最新的 `rev` 再写，最多三次；仍失败的留着，由对账补写（下面）。
4. 作业总时长（从取到锁起算，含准备）不超过 45 分钟，常量 `walk.ts` 的 `WALK_JOB_MS`。理由：作业占着门禁锁的时候，别的目标的 `check_commit` 最多等 60 分钟（`gate-lock.ts` 的 `GATE_WAIT_MS`），等不到就得到 `gate_busy`，worker 的合入停住；45 分钟低于它，测试断言 `WALK_JOB_MS < GATE_WAIT_MS`。做法：每条流程开始之前，已用时间加这条流程的超时上限超过 45 分钟的，不开始，在事件里标 `not_run`；一个作业的第一条流程总是开始（超时上限最长 30 分钟，所以不会因为一条流程让作业远超 45 分钟）。没轮到的流程下一次 `dispatch_task` 只为它们起新作业，接着走。极端情况：准备命令（M7 §3.8.3 第 6 步，每条至多 10 分钟）加第一条流程合计超过 60 分钟时，别的检查得到 `gate_busy`，主 Agent 照 M7 现有的做法重试，不丢工作；准备命令的上限归 M7，本设计不改。
5. 放锁，发出事件 `hourness.walk-done`，叫醒主 Agent：`{job, commit: T, trunkMoved, flows: [{id, outcome, steps, limitMs, elapsedMs}]}`，`outcome` 是 `passed`、`failed`、`timeout`、`no_report`、`review_failed`、`not_run`；`trunkMoved` 是 `T` 之后主干上改过 `docs/graph/` 以外的路径（这时这次的结果在完成检查里不会被采信，要重走）。
6. 主 Agent 再调 `dispatch_task <目标 id>`：所有流程都有有效通过记录时，才派整体审查。

作业的进展和结束算空转计数里的活动（M7 §3.9.5 的「检查」一类，请求见 §11），一次几十分钟没有主 Agent 回合的走一遍不会被当成空转。运行记录在 `<exec>/walks.jsonl`：`start`、每条流程的 `flow-end`（带 `limitMs`、`elapsedMs`、`outcome`）、`evidence`（该流程的证据已写完）、`end`，每行落盘后 `fh.sync()`。宿主在作业中途退出：重启对账（M7 §3.9.6）把没有 `end` 的作业记为 `abandoned`；有 `flow-end` 而没有 `evidence`、产物副本在的流程补写证据（用 `reason` 去重，已有同样 `reason` 的 `walk` 就不再写）；其余的下一次作业重跑。

**你来走。** `你来走` 的流程没有自动的结果。`dispatch_task` 在这类流程没有有效通过记录时返回 `walk_unready`（或 `walking` 里的 `waitingForPerson`），`hint` 要求主 Agent 用 `propose_to_human` 的 `question` 一种把「请你走一遍」建成待决（节点在目标下，所以面板的「需要你」看得见，§6.1），用「确认建议」的形状，问句里写明请他走的是哪一个提交（取 `dispatch_task` 结果里的 `head`），他走的不是它就先重新部署（例：「借书这一条没法自动测，我建议你亲自走一遍，用提交 3f2a91c 的版本，走完告诉我结果，可以吗？」），占那一批三件里的一件。审查在人走完之后才派。人回话后，主 Agent 用 `record_human_answer` 记下回答，再用 `graph_walk` 带原话记走一遍的结果。`graph_walk` 记下的提交是记录那一刻项目根的 `HEAD`，工具无从知道人实际走的是哪个构建，所以这一句靠主 Agent 在问句里交代，完成检查把它当作「人走的就是这个提交」（残余风险，§15 A11）。

**超时（`d-timeout-measured`，含编排方 2026-10-31 的两条裁定）。** `走法：` 里的预计秒数由写这条流程的 agent 估；超时等于预计的 3 倍，不低于 10 秒、不高于 30 分钟（同 M7 合入前的检查）。跑过之后改用最近三次里最慢一次实际耗时的 3 倍，范围相同，由 harness 算，不让模型手抄；估错的数只影响下一次的值。3 倍超过上限时保持 30 分钟，作业事件对主 Agent 写明（拆小这条流程，或把预计收窄），不来问人，不自己抬高上限。只有超时的运行不当作实测，没有三次实测时用预计。可追溯：每次超时值变化在 `<exec>/walk-limits.jsonl` 追加 `{flow, old, new, source: 'agent' | 'harness', basis, at}`，`basis` 是那条流程的估计所在的节点历史时间，或算出它的运行的作业号；每次运行在 `walks.jsonl` 的 `flow-end` 行记上限、耗时、结局。超时不让作业崩、不丢工作：已跑完的流程的证据照写，超时的流程按规则的第 1 条处理，事件文字写明哪一条流程、上限与来源、实际耗时、接下来怎么办。人在放行页上看到每条流程的命令原文、超时、估计来源（§5.2）；晨报与面板的流程行也看得见（§5.6、§6.2）。

**不覆盖的。** 走一遍要求每个步骤被走到；不要求每条 `next` 连线都被走到，也不管同一步在不同路径上的差别。分支多的流程由写走法的人在测试里覆盖各条路；整体审查的复核按流程的 `acceptance` 看。

### 2.8 没有界面的项目

用户不一定点按钮。判据是同一条：用户是从产品外面碰它的一方，步骤是在产品边界上发生的一次交互，内部模块、数据结构、函数从来不是步骤。

| 项目形态 | 角色 | 步骤写成 | 走法 | 证据 |
| --- | --- | --- | --- | --- |
| 网页或桌面应用 | 读者、管理员 | 点什么，看到什么 | `截图`，或 `命令`（浏览器测试） | 每步一张图，或断言结果 |
| 命令行工具（例：馆员批量导入书目的 `libctl`） | 馆员（命令行） | 运行 `libctl import books.csv` › 看到「导入 120 本」› 运行 `libctl list` › 看到新书 | `终端` | 每步一段命令与输出，退出码 |
| 库或 SDK（例：书目解析库） | 调用库的开发者 | 引入库 › 调用 `parse(…)` › 拿到书目对象 › 传坏数据得到明确的错误 | `命令`（示例脚本当测试跑） | 示例脚本的输出 |
| 后台服务或接口 | 调用接口的系统 | 发一个请求 › 收到响应 › 收到错误响应 | `命令`（契约测试） | 请求与响应记录 |

### 3.3 文件校验与整图校验

读入时（硬伤，报 `error`，每条带文件与字段路径）：

| # | 规则 | 位置 |
| --- | --- | --- |
| V1 | `role` 的父节点是 `goal`，`flow` 的是 `role`，`step` 的是 `flow` | `validate.ts` |
| V2 | 用户节点的 `status` 在 `USER_STATUSES` 里 | `format.ts`（`nodeRuleIssues`） |
| V3 | `serves` 只出现在 `feature` 或 `task` 的 `edges` 里，目标是 `step`，且服务者与步骤属于同一个目标（沿 `parent` 到根相同） | `format.ts`（起点类型）、`validate.ts`（目标类型与同目标） |
| V4 | `next` 只出现在 `step` 或 `flow` 的 `edges` 里，目标是 `step`：步骤的 `next` 要求两者的 `parent` 相同；流程的 `next` 要求目标的 `parent` 就是这条流程 | `format.ts`（起点类型）、`validate.ts`（目标类型与父节点） |
| V5 | `when` 只出现在步骤的 `next` 上，单行非空，至多 `USER_LIMITS.when` 个码点；流程的 `next` 不带 `when` | `format.ts` |
| V6 | `depends` 的起点和目标都不是用户节点；`source` 的目标不是用户节点；用户节点的 `source` 目标只能是 `question` | `format.ts`、`validate.ts` |

| V8 | 同一节点上同类型同目标的连线不重复（现有规则，`when` 不同也算重复；改条件用 `relink`，或先 `unlink` 再 `link`） | `format.ts` |

V3 的「同一个目标」要沿 `parent` 走到根，遇环截断（现有的分解环检查会先报）。`next` 构成的环不报错（§2.3）。`walk` 的 `note` 以 `@提交` 开头的格式不在读入时查，那是写入规则（§3.4），手改文件不该因为这个整张图写不进去；完成检查解析不出提交的 `note` 当作没有提交，不放过（§5.5）。

`format.ts` 的 `edge` 检查器多一个可选字段 `when`；`canonicalEdge` 写出 `{type, to, when?}`，字段顺序固定，`when` 缺省不写，所以没有 `when` 的旧连线字节不变。排序仍按（类型，目标）。

### 3.4 写入规则与权限（`engine.ts`）

用户节点的权限，对应 §2.9 的表。「转述」指 `llm` 的写入带了人的原话（`CHARTER.md` §2.9.1），有 `human` 的权限。「自己的草稿」指 `planEdit` 里已有的 `ownProposal`：状态 `proposed`、第一条历史是同一个身份的 `propose`。

| 操作 | `human` | `llm`、`harness` 不带转述 | `llm` 带转述 |
| --- | --- | --- | --- |
| `propose` 角色、流程、步骤 | `approved` | `proposed`（`initialStatus` 里不在任何例外里，取默认） | `approved` |
| `approve`、`reject` | 可以 | 拒绝，正路同今天 | 可以（`reject` 把状态改成 `dropped`，不级联：只改这一个节点） |
| `status` 废弃、恢复（只对已批准的节点） | 可以 | 拒绝（`forbidden`）：废弃或恢复角色、流程、步骤是计划外，同特性与目标 | 可以 |
| `status`（对 `proposed` 的节点） | 一律 `bad_transition`（引擎现有规则，`planStatus`：提议由人批准或否决） | 同左 | 同左；撤掉没批准的用户节点只有 `reject` 一条路（§4.2） |
| `status` 到 `doing`、`done` | 拒绝（`bad_transition`） | 同左 | 同左 |
| `edit`：`body`（不改 `走法：` 里的种类） | 可以 | 可以 | 可以 |
| `edit`：`title`；`body` 且改了 `走法：` 的种类（含从无到有、从有到无） | 可以 | 只有自己的草稿；其余 `forbidden` | 可以 |
| `edit`：`acceptance`、`parent` 及其余字段 | 可以 | 只有自己的草稿 | 可以 |
| `link`、`unlink` 的 `serves` | 可以 | 可以（开发那一侧的登记，不改产品是什么样） | 可以 |
| `link`、`unlink`、`relink` 的 `next`（步骤或流程上） | 可以 | 只有自己的草稿；其余 `forbidden` | 可以 |
| `walk` | 任意 `ref` | 拒绝；`harness` 可以写非 `person:` 的证据 | 只许 `person:conversation` |
| `comment` | 可以 | 可以 | 可以 |
| `supersede` | 可以 | 拒绝，正路同今天（提议新节点并带 `supersedes`） | 可以 |

理由：`title` 就是步骤本身，改名可以把「点借阅」换成别的动作，所以放行之后改它和改 `acceptance`、`next` 一样属于人（`norm-decision-tiers` 第 1 类：改目标、验收条件或非目标）。`走法：` 的种类决定走一遍的证据怎么来（`命令` 换成 `你来走` 就等于换掉了「验过」的含义），所以也属于人；预计秒数不属于（估错了主 Agent 要能改，上限由 harness 兜住，§2.7）。`serves` 不在其内：它记的是谁在做哪一步，是开发那一侧的账，主 Agent 随开发推进随时要写。种类的比较用 `walk-spec.ts` 的 `parseWalkLine` 取改前改后各一次。

写入规则（`invalid`，`field` 和 `hint` 写明正路），在 `commit()` 里对要写的节点用写后的整图检查，位于「待决的写入规则」之后、「整图校验」之前：

| # | 规则 | `hint` 要点 |
| --- | --- | --- |
| W1 | 一个步骤 `live` 的服务者不超过 `servesPerStep`；一个任务的 `serves` 不超过 `servesPerTask`；特性不超过 `servesPerFeature` | 拆步骤，或拆任务；特性：把连线连到它的任务 |
| W2 | `serves` 的目标是 `live` 的步骤，不是已废弃、被取代或祖先已废弃的 | 先恢复那一步，或连到取代它的步骤 |
| W3 | `serves` 的起点是 `feature` 或 `task`，且任务的 `kind` 不是 `review` | 设计评审与整体审查不做用户能看到的东西 |
| W4 | `walk` 操作：节点是 `live` 的已批准步骤；`evidence` 1 至 `walkEvidence` 条，`kind` 全是 `walk`；每条的 `note` 合 `WALK_NOTE_PATTERN`；`harness` 写的 `ref` 不是 `person:`；带转述的 `llm` 只写 `person:conversation` | 例：`harness` 写 `person:` 被拒，`hint`「only a person's own walk is recorded with their words」 |
| W5 | `next` 的目标是 `live` 的步骤；`relink` 的列表里 `to` 不重复、至多 `relinkEdges` 项，流程至多 1 项 | 先恢复那一步 |

`walk` 写入的内容：目标节点追加这些证据（节点上只保留最近 `walkKept` 条 `walk` 证据，更早的去掉），历史追加一条 `{op: 'walk', actor, reason, relay?, evidence}`，状态不动。`reason` 必填，一句话。修订号检查与其他操作相同。检查次序在 §2.9 的基础上，「要人权限的操作」之后加「`walk` 的身份」，「写后的节点校验」之后加 W1 至 W5。

`unlink` 的历史条目里的 `edge` 取节点上真实被摘掉的那条（含它的 `when`），不取请求里的（请求只有类型和目标）：条件文字不必到 git 里找。

不改的：`initialStatus` 对用户类型不加例外（`llm` 不带转述提议得 `proposed`，M3 的访谈靠这一点，§5.1）；`LLM_EDITABLE` 不变，用户节点的限制写在 `planEdit` 里 `ownProposal` 判定之后的一处（不能为了用户节点去改这个集合，特性与目标的 `title` 现在就在里面）；`HUMAN_ONLY` 不变；M3 的 `main-agent-graph-relay` 与 `main-agent-graph-stage` 对用户节点自动适用（用户节点不在它们的例外类型里），`graph_relink`、`graph_walk` 加入 `GRAPH_TOOL_NAMES` 之后它们的 `relay` 也由 harness 核对是人的原话（§11 M3 请求）。

### 3.5 请求结构（`mutation.ts`）与图工具（`tools.ts`）

- `link`、`unlink` 的 `type` 取 `depends`、`source`、`serves`、`next`；`link` 多一个可选字段 `when`（只对步骤上的 `next`，其余类型带它是 `invalid`）。`unlink` 按（类型，目标）找，不看 `when`。
- 新操作 `relink`：`{op: 'relink', id, rev, reason, next: [{to, when?}…], relay?}`，一次替换一个步骤的全部 `next` 出边，或一条流程的入口连线（列表至多一项）。引擎对它只算出一个节点的草稿，`commit()` 对写后的整图校验一次；历史对真实被摘掉的连线各记一条 `unlink`，对新加的各记一条 `link`（`edge` 含 `when`），时间、`reason`、`relay` 相同；前后相同的连线不记，整个列表与现状相同返回 `conflict`。**为什么要有它**：M3 附录 0.5 §3.8 第 1 条的转述核对，起点是目标节点最后一条不是 `comment` 的历史的时间，人的话要在这之后。对同一个节点连写两次，第二次的起点已经晚于人说那句话的时间，会被 `main-agent-graph-relay` 拒绝。所以改一个步骤的出边必须是一次写入；加一步、删一步、换顺序都能落成「每个节点在同一句转述下只写一次」（§4.2）。
- 新操作 `walk`：`{op: 'walk', id, rev, reason, evidence, relay?}`，`evidence` 必填。`parseMutation` 里的可选字段表按操作分：`evidence` 对 `status` 与 `verify` 可选，对 `walk` 必填。`evidence` 的检查函数拒绝 `decision` 类的现有规则不变，另加：`walk` 的每一条必须是 `walk` 类，别的操作里带 `walk` 类证据是 `invalid`（`hint` 指向 `walk`）。
- `tools.ts`：`graph_propose` 的节点类型枚举来自 `NODE_TYPES`，自动带上新类型，它的 `edges` 项的 `type` 枚举手写，加上 `serves`、`next`，并加可选的 `when`；`graph_link`、`graph_unlink` 的 `type` 枚举手写，加上 `serves`、`next`；`graph_link` 加 `when` 参数；新工具 `graph_relink`，参数 `{id, rev, reason, next, relay}`（`next` 是 `{to, when?}` 的数组，形状与 `EVIDENCE` 同属 rc.3 子集里的对象数组）；新工具 `graph_walk`，参数 `{id, rev, steps, reason, relay}`，语义见 §2.7「谁能写」，`relay` 必填，说明一句「Record that the person walked a flow themselves. Only the person's own words count: pass them as relay. Command, screenshot and transcript walks are recorded by the harness, not by you.」。
- 说明里的示范（`d-agent-examples`）：`graph_relink` 的说明带一道完整示范。人说「借书前要先交押金」，主 Agent 复述、人说对之后，次序写死，两次调用，每个节点只写一次：

  1. `graph_propose`：`{node: {type: 'step', parent: 'flow-3', title: '交押金', acceptance: ['页面提示押金已收'], edges: [{type: 'next', to: 'step-9'}]}, reason: '借书前要先交押金', relay: '借书前要先交押金'}`（新节点，转述的起点是 0；不带 `id`，引擎取下一个空号，结果里返回它，下面写作 `<新步骤的 id>`）。
  2. `graph_relink`：`{id: 'step-8', rev: <刚读到的>, reason: '没交押金的先去交押金', next: [{to: 'step-9', when: '已交押金'}, {to: <新步骤的 id>, when: '没交押金'}], relay: '借书前要先交押金'}`（「点借阅」只写这一次；`to` 取第一次调用返回的 id，不能自己编）。

  说明里把 `<新步骤的 id>` 写成 `the id the first call returned`，示范正文里的 id 都是占位。最后一句提醒：新步骤没有服务者，要给负责借书的模块加任务并用 `serves` 连上。示范过真实检查：引擎的写入规则、`plainWordsIn`，**以及真实的 `main-agent-graph-relay` 核对**（假的会话投影，§1.4 第 13 条），L2 钉住，规则一变示范先坏。示范用的是图书管理系统。

### 3.6 `src/graph/user-graph.ts` 与 `src/graph/walk-spec.ts`（新）

纯函数，不用 Node 内置模块，不读文件，宿主、面板、报告共用。`user-live.ts` 导出 `liveOf(graph, node)`（§2.5；不叫 `live.ts`，main 上已有那个名字的文件，§3.1）。`walk-spec.ts` 导出 `WALK_KINDS = ['命令','截图','终端','你来走']`、`parseWalkLine(body)`（取 `走法：` 一行，返回 `{kind, seconds?}` 或 `{unparsed}`）、`walkCommandsOf(acceptance)`（取 `norm-merge-gate` 里 `` `walk <种类> $ <命令>` `` 的行，返回种类到命令的表；命令里没有 `{flow}` 的行跳过并带原因）。`user-graph.ts` 导出：

### 3.7 投影、标签与不数用户节点的地方

## 4. 人怎样改：在对话里，经主 Agent

面板只看（`d-ui-look-not-operate`）。人想改用户图的任何一处，对主 Agent 说；主 Agent 写图，规矩是 M3 已放行的那一套（附录 0.5 §3.4 至 §3.8）。子 agent 对图只读，靠 M7 的两份按名字写死的名单：`worker-graph-readonly` 的拒绝名单（M7 0.6 §3.2.3）和工具面过滤的去除名单（§2.3.2），各列九个图写工具（`graph_propose`、`graph_status`、`graph_edit`、`graph_link`、`graph_unlink`、`graph_verify`、`graph_decide`、`graph_approve`、`graph_reject`）。本特性新增的 `graph_relink`、`graph_walk` 不在这两份里，所以两份名单都要加这两个名字，扩成十一个：U2 同批改（M7 骨架合入之后才开工，§10），M7 一侧的请求见 §11。加上之后，用户图才只有人和主 Agent 写。加上之前，子 agent 的工具面里会多出这两个工具的 schema；按名调用时现在能挡住的是 M3 的 `main-agent-graph-relay`（对子会话的 `relay` 一律拒绝，`graph_walk` 因此调不成）和引擎的草稿规则（`graph_relink` 对不是自己草稿的节点没有转述就 `forbidden`），那是恰好挡住，不是设计要依赖的保证。`walk-review` 按审查者登记，进同一份过滤（§2.7）。

### 4.1 三种来源，三种写法

| 来源 | 例 | 怎么写 |
| --- | --- | --- |
| 人自己说的 | 「借书前要先交押金」「不要押金这一步了」「还书要能续借一次」 | 主 Agent 在同一条回复里复述一句「那我记成：……」并问对不对（M3 §3.6 的随口回答规矩）。人说对之后，主 Agent 用图工具写，`relay` 引人的原话（原来那句，不是「对」）。harness 按 `main-agent-graph-relay` 核对原话确实是人在该节点最后一次变动之后说的 |
| 主 Agent 的建议 | 「我建议把『借书』拆成『借书』和『预约』」 | 一件要人定的事，经 `propose_to_human`，写法按 §4.4 的形状。人同意后 `record_human_answer` 记下，主 Agent 再照方案改图，`relay` 引人同意时说的话 |
| 访谈里的草稿 | 访谈时画出的角色、流程、步骤 | 不带转述的提议，状态 `proposed`，是主 Agent 自己的草稿，随时可以整个改（引擎对「自己提议且仍为 proposed」的节点本来就放开全部字段）。人读了样稿、说「第二条流程少了续借」，主 Agent 直接改草稿 |

### 4.2 常见的改动怎样落

放行之前（目标在 `wish`、`interview`、`design`）所有改动都是改自己的草稿，不需要转述，同一个节点可以写任意多次；唯一的例外是撤掉一个还没批准的节点：`reject` 是人的操作，放行前后都要人的原话（见表中「撤掉还没批准的节点」一行）。放行之后，每次写入带人的原话，而 M3 的转述核对（附录 0.5 §3.8 第 1 条）要求人的话晚于目标节点最后一条非批注的历史：**同一句原话对每个节点只能写一次**。所以下面每一行的次序都落成「每个节点写一次」：一个节点要改多处，放进同一次 `graph_edit` 的 `set`；一个步骤的出边，用一次 `graph_relink`；之后还要改同一个节点，需要人再说一句。

| 人说的 | 写图的次序（每步取刚读到的 `rev`，同一句原话作 `relay`） | 要转述 |
| --- | --- | --- |
| 在中间加一步 | ① `graph_propose` 新步骤（带 `next` 到后面那步，新节点的转述起点是 0）；② `graph_relink` 前一步，出边改成指向新步骤，有分支时带 `when`（§3.5 的示范） | 是 |
| 在流程最前面加一步 | ① `graph_propose` 新步骤（`next` 到原来的第一步）；② `graph_relink` 流程节点，入口改指新步骤 | 是 |
| 删一步（已批准的步骤） | 对每个指向它的前一步各一次 `graph_relink`（去掉它，补上它的后继；它是入口时对流程节点）；再对被删的步骤一次 `graph_status` 为 `dropped`。涉及的都是不同的节点。步骤还是 `proposed` 的，见下面「撤掉还没批准的节点」 | 是 |
| 换顺序、加分支 | 对涉及的每个步骤各一次 `graph_relink`（A→B→C 改成 A→C→B 是 A、C、B 三个节点各一次） | 是 |
| 不要这条流程、这个角色了（已批准的） | 只对流程或角色一次 `graph_status` 为 `dropped`；它们下面的节点自动不再 `live`（§2.5），不用逐个废弃；下面仍是 `proposed` 的节点保持原状态，但不再 `live`，所以面板的等待数、「需要你」和放行集合都不数它们（§3.7 的 `waitingProposals`、`releaseSet`）。流程或角色还是 `proposed` 的，见下一行 | 是 |
| 撤掉还没批准的节点：草稿阶段人说「预约这条流程不要了」「那一步不要了」，或放行之后主 Agent 加的待批准步骤人不要了 | 对这条流程和它下面每个 `proposed` 节点各一次 `graph_reject`，同一句原话作 `relay`，各自取刚读到的 `rev`，次序不限。`reject` 把状态改成 `dropped`，不级联，所以必须逐个拒绝；每个节点只写一次，满足同一句原话对每个节点只写一次。这是唯一的路：`graph_status` 对 `proposed` 节点一律 `bad_transition`，`llm` 不带转述又不能 `reject`。反过来，已批准的节点不能 `reject`（`bad_transition`），用上面两行。指向被撤掉步骤的前一步的 `next` 仍指着它：`live` 把指向非 `live` 步骤的 `next` 当没有（§2.5），后一步因此从入口走不到，标 `flow:unreachable`，要再对前一步 `graph_relink`（前一步是自己的草稿时不要转述，是已批准的节点时用同一句原话，它是另一个节点） | 是 |
| 加一条流程、一个角色 | 这是一段设计，不是一句话：主 Agent 用不带转述的提议画出草稿（`proposed`，自己的草稿，入口 `next` 与步骤之间的 `next` 随便连），把 `renderUserGraph` 的 `confirm` 与 `walks` 的稳定部分当样稿（用户图，和这条流程将被执行的命令原文）给人看，问「哪里不对？」；人说对之后，对草稿里每个节点各一次 `graph_approve`，`relay` 引人确认时的话 | 是（批准时） |
| 改一步「怎样算做成」、改标题、改走法的种类 | 一次 `graph_edit`（要改几个字段就放几个进 `set`） | 是 |
| 改预计秒数、补正文、改 `前提：` | 一次 `graph_edit` 的 `body` | 否 |
| 谁在做哪一步 | `graph_link` 的 `serves` | 否 |

主 Agent 自己改主意、想去掉自己刚画的草稿节点，没有不经人的路：`reject` 需要人的原话，`status` 对 `proposed` 节点不行。能做的是把这个草稿改成需要的内容（自己的草稿全字段可改，包括标题和 `parent`），或者把它留在样稿里问人要不要去掉，人说去掉之后再逐个 `reject`。不能放着不管：没拒绝的草稿会随放行被一起批准，所以确认页与放行页上要让人看到它（§5.1、§5.2 的稳定部分列出全部 `live` 节点）。

改了之后图自己显示后果（§2.5）：这条流程连着的活变了，已有的走一遍记录失效，状态回到「做完了，要重走」；新步骤没人负责，两个视图都标出来；改了出边之后后面的步骤从入口走不到时标 `flow:unreachable`，说明还差一次 `graph_relink`。

### 4.3 加了一步以后，开发这一侧怎么跟

「借书前要先交押金」落下来，图上多一个没人负责的步骤。主 Agent 接着做的是开发这一侧的事，沿用 M7 的三档（§3.9.7），本特性只补一句判断提示，加在 M7 给主 Agent 的分档说明里（请求见 §11）。第一档不问人，下一批用一句话告知：「我定了：给「借阅」加两个任务做交押金，因为不改它已定的设计，不对就说」。

- 这一步能用已放行模块里再加几个任务做出来，且不改那个模块已定的设计方向：第一档，主 Agent 自己定，给那个模块加任务并 `serves` 连上，下一批告诉人。
- 它改到某个已放行模块的设计（例如「借阅」的设计里根本没有押金）：第二档，模块退回设计，人重新看一页放行稿。
- 它需要一个新模块：第三档，退回大循环，模块清单只在大循环里定（M3 §3.14.1）。
- 判不准时往高一档放（M7 §3.9.7 已定）。

**分解时把任务连到步骤。** 模块放行时，模块级的 `serves` 只是归属声明（§2.3）。模块分解成任务的时候，主 Agent 把每个任务用 `serves` 连到它做出来的步骤；这样「借阅」里 `task-7` 在做、`task-8` 还没开始，各自的步骤才显示各自的进度（§2.9 的「借书」）。同一时刻，每条自动走法的流程要有一个 `kind` 为 `test` 的任务，连到它覆盖的步骤（走一遍要跑的端到端测试由它写，§2.7）；每一步都拆成了任务而还没有这样的任务时，缺口 `flow:no-test` 在分解提醒里点名这条流程。分解提醒里加这两句（请求见 §11）。没有连任务的步骤，进度按模块的全部任务算，偏保守，不会误报走通。任务级连线的增加不受特性上限约束（§2.4）。

删一步或删一条流程，服务它的活变成孤儿，图上标出；主 Agent 再决定这些任务是废弃还是改去服务别的步骤，废弃任务不需要人，废弃特性或模块要转述（现有规则）。已经进主干的活不动。

### 4.4 问人的写法（`d-ask-three-gates`，试行）

人 2026-10-31 定了怎样问：三道关，四种形状，取代四行的固定写法（`design-context.md`「How the agent asks the person」）。用户图的各个问人处按它写：

| 道关 | 用户图里的落点 |

## 5. 在两层循环里的位置

### 5.1 访谈（M3）

访谈的八步（§4.2）在第 2 步「做成以后，你的日子会有什么不一样」后面多一步 2b：「谁会用它，他们进来先做什么」。按 `d-ask-three-gates` 的「问人要什么」形状（§4.4）：主 Agent 先从人前面说过的话里猜，写成「我猜用它的有读者和管理员……，对吗？」让人改；什么线索也没有时才问一个开放的问题。起草时：

- 角色 1 至 4 个，每个角色的流程 2 至 8 条，每条流程 3 至 10 步；都是用户的话。没有终端用户的目标（内部重构、纯库的内部模块），问一句「这个有没有终端用户」，没有就把 `用户流程：无，<原因>` 写进目标正文。
- 草稿全部是不带转述的提议；画法、数量、命名的提示放在访谈阶段的阶段提醒里（`src/design/stage-notice.ts`），不放身份节（身份节第一部分上限 1,500 字符，M3 附录 §0 第 3 条）。
- 画的时候，主 Agent 一次不超过一问；人说的话里的流程与步骤原样用人的词。

需求卡（§4.2）从 8 项变 9 项，新的一项排在「给谁」之后：

| 项 | 落点 | 齐的判据 |
| --- | --- | --- |
| 用户怎么用 | 目标下的角色、流程、步骤；或目标正文的 `用户流程：` | 目标下至少有一个 `live` 的角色，其下至少一条 `live` 的流程，其下至少一个 `live` 的步骤；或正文有 `用户流程：` 一行，值以「无」开头并带原因（已有 `live` 的角色时这一行不生效） |

`requirementCard` 返回的 `GateItem` 多一项 `key: 'flows'`，`label` 是「用户怎么用（谁来用、一步步做什么）」，`hint` 告诉主 Agent 访谈 2b 该问什么、写到哪里。`CARD_LABELS` 加 `用户流程`。这一项适用于还在 `wish` 或 `interview` 的目标：门禁只在离开这两个阶段时看，所以实现上线时已经过了确认的目标不受影响，正在访谈的目标多问一轮（§7）。

`propose_to_human` 的 `confirm`：目标 `present`（有用户图），或有 `用户流程：无` 时，harness 把 `renderUserGraph(ug, 'confirm')` 的 `stable` 当样稿附在结果里（结果正文另带 `userPage: {stable, state}`，`confirm` 的 `state` 为空：样稿里只有角色、流程、步骤、条件和每步的「怎样算做成」，没有现状），主 Agent 原样放进回复，问「哪里不对？」（§4.4 的「给样稿问哪里不对」）；这一段就是「人确认之前必须看到的原文」；`record_human_answer` 的 `confirm` 照放行页的做法核对这一段整段出现在主 Agent 紧接着的回复里（M3 §3.5 第 5b 步），不在时 `not_shown`；回答时还用当时的图重新渲染 `stable`，与结果里记下的规整后逐字比较，不同（展示之后图又改过）同样 `not_shown`（§5.2 末段）。样稿不截断，超过 `USER_LIMITS.appended`（8,000 个码点）时 `confirm` 返回 `gate_unmet`，缺项 `flows:page`。例（读者两条流程节选，每步后面〔〕里是它的「怎样算做成」）：

```
用户怎么用
读者
 登录：1 打开登录页〔看到账号和密码两个输入框〕→ 2 输入账号密码〔点登录后页面有反应〕→（密码对）3；（密码错）4。3 进入首页〔看到自己的名字〕。4 看到错误提示〔提示写明账号或密码不对〕→ 2
 借书：1 在书的详情页点「借阅」〔弹出确认框〕→（已交押金）2；（没交押金）4。2 确认借阅〔提示借阅成功〕→ 3。3 看到应还日期〔日期在借出之后 30 天〕。4 交押金〔提示押金已收〕→ 2
管理员
 录入新书：……
```

### 5.2 设计与大循环放行（M3）

用户节点不属于任何模块，在大循环放行集合里（`bigLoopSet` 取目标子树里除模块与模块候选的子孙以外的全部提议，用户节点在内，`releaseSet` 过滤掉不 `live` 的），放行时和框架决策、模块候选一起批准。没有分模块的目标，单次放行集合同理。

`userReleaseItems(graph, goal)` 给放行门禁加这几项（`GateItem` 的 `ok` 为假才挡；`label` 是人读的中文，`hint` 是给模型的英文）：

| `key` | `label` | 判据 | `hint` | 对应缺口 |
| --- | --- | --- | --- | --- |
| `flows:shape` | 用户流程的形状（每个角色有流程，每条流程有步骤和一个入口，分支写了条件） | 每个角色有 `live` 的流程，每条流程有步骤、入口连线恰好一条、没有走不到的步骤、分支都带互不相同的 `when` | `fix the shape gaps first: <第一条缺口的 hint>` | `role:no-flow`、`flow:empty`、`flow:entry`、`flow:unreachable`、`step:branch` |
| `flows:expect` | 每一步写了怎样算做成 | 每个 `live` 的步骤有至少一条 `acceptance` | `set acceptance on <第一个缺的步骤>: what the person sees when this step is done` | `step:no-expect` |
| `flows:served` | 每一步都有人负责 | 每个 `live` 的步骤至少有一个服务者（模块候选、模块、特性、任务都行） | `connect <第一个没人负责的步骤> to the module or task that builds it, with graph_link type serves` | `step:unserved` |
| `flows:modules` | 每个模块至少服务一步，或写明为什么不服务 | 每个模块候选至少服务一步（它的任务服务也算），或正文有 `服务：无，<原因>` | `connect the module or its tasks to a step with serves, or add a line "服务：无，<reason>" to its body` | `work:orphan`（模块） |
| `flows:walk` | 每条流程写了怎么走一遍，合入前检查清单里有对应的命令 | `parseWalkLine` 成功，且 `norm-merge-gate`（已批准的，或在这次放行集合里的）有该种类的 `walk` 行；`你来走` 不需要命令 | `write "走法：<命令\|截图\|终端> · 预计 <N> 秒" in the flow body, and add a line walk <kind> $ <command with {flow}> to norm-merge-gate` | `flow:no-walk` |
| `flows:page` | 放行页里的用户图部分放得下一页（合计不超过 8,000 字） | 下面三段合计不超过 `USER_LIMITS.appended` 个码点 | `the user graph is too big for one release page: split the goal, or shorten flow and step titles` | 无 |

只对 `present` 的目标生效。目标正文有 `用户流程：无` 而没有 `live` 的角色时这六项不出现；两者都有时 `present` 生效，`用户流程：无` 当作没写。前三项加 `flows:walk`、`flows:page` 也加进没分模块的目标的单次放行门禁（服务者是特性或任务）；`flows:modules` 只对分了模块的目标出现。缺项时 `propose_to_human` 返回 `gate_unmet`，缺项列在 `message` 里，每项带怎么补的 `hint`。

放行页：`page` 是主 Agent 写的那一页（1 至 `PAGE_LIMITS.max`，2,000 个码点，限制的是主 Agent 写的这一页），harness 在它后面接三段，由 `renderUserGraph` 生成，不计入 `PAGE_LIMITS.max`，不截断，三段合计不超过 `USER_LIMITS.appended`（8,000 个码点）；超出由 `flows:page` 挡住，主 Agent 拆目标或缩短标题，不让人看到被截掉的放行页。三段合起来是「人放行之前必须看到的原文」（M3 §3.14.5），核对「给人看过」时整段都要出现。三段分成两块：前两段是**稳定部分**（`stable`，人要同意的内容：谁负责、将被执行的命令原文与预计秒数、超时的算法），第三段是**现状部分**（`state`，「截至给你看的时刻」，不是人要同意的内容）。分开的理由是放行发生在别的模块已经在开发的时候（两层循环）：人隔几十分钟或一夜才回话，这期间别的模块的任务状态、主 Agent 按开发进度登记的 `serves`（不需要转述）、超时上限都会变，如果把它们和人要同意的内容放在同一段里比较，人的同意会反复失效。

第一段（稳定），每条流程由哪个模块负责。模块一栏取服务者的最近特性祖先，没有特性祖先的任务写任务标题。这一段不写「某一步现在有没有人负责」：那是现状，而且放行门禁 `flows:served` 已经保证每一步都有人负责。例：

```
每条流程由谁负责
 读者 › 登录：账号模块
 读者 › 搜书：书目模块
 读者 › 借书：借阅模块
 管理员 › 处理逾期：逾期与通知模块
不服务任何步骤的模块：搭建项目骨架（正文写明的原因：搭建项目骨架与持续集成）
```

第二段（稳定），每条流程怎么走一遍。命令原文取自 `norm-merge-gate` 里该种类的 `walk` 行（`{flow}` 已换成流程的节点 id），人放行时看到的就是将要被执行的命令。例：

```
每条流程怎么走一遍（命令来自合入前检查清单，放行之后执行的就是这些）
 读者 › 登录：命令 · npm run e2e -- --flow flow-1 · 预计 30 秒
 读者 › 借书：命令 · npm run e2e -- --flow flow-3 · 预计 40 秒
 管理员 › 处理逾期：命令 · npm run e2e -- --flow flow-6 · 预计 40 秒
 读者 › 搜书：命令 · npm run e2e -- --flow flow-2 · 预计 30 秒
超时是预计秒数的 3 倍，跑过几次之后按最近三次里最慢的一次的 3 倍，不低于 10 秒、不高于 30 分钟。写着「你来走」的流程不跑命令，这里写「没法自动测，做完时请你亲自走一遍」。
```

第三段（现状），当前的超时上限及它从哪个估计算出来（`d-timeout-measured`：人放行时要看到数和来源）。例：

```
截至给你看的时刻（这一段只是给你看现状，不是你要同意的内容，之后会变）
 超时上限：登录 90 秒、借书 120 秒、处理逾期 120 秒、搜书 90 秒，都是预计的 3 倍，还没有跑过
```

展示之后图又改过，人的同意不一定不再对得上他看到的那一页：同意的是稳定部分，现状部分的变化不改他同意的东西。所以 `record_human_answer` 对 `release` 与 `confirm` 分两步核对。一、给人看过：提议时结果里记下的 `stable` 与 `state` 整段（规整：NFKC、空白合一）都要出现在主 Agent 紧接着的回复里（M3 §3.5 第 5b 步，`Shown` 为此多记 `userPage`，取自结果正文）。二、没变：用当时的图重新渲染 `stable`，与结果里记下的 `stable` 规整后逐字比较；不同时返回 `not_shown`，`message` 写「页在给你看之后变了」，图不变，主 Agent 重新 `propose_to_human` 再给人看一次。`state` 不重新渲染、不比较。这两步与 M3 已有的放行集合核对（每个节点的 `{id, rev}`，改过的节点进 `skipped`）互补：集合核对管被批准的节点自己变没变，稳定部分比较管人读到的用户图变没变。

### 5.3 模块放行（M3）

模块放行门禁（附录 §3.14.3）加一项 `module:serves`：`label` 是「这个模块服务至少一步，或写明为什么不服务」，判据是模块自己或它的任务至少服务一步，或模块正文有 `服务：无，<原因>`，`hint` 是 `connect the module or its tasks to a step with serves, or add a line "服务：无，<reason>" to the module body`。放行页末尾由 harness 接两块，同样分稳定与现状（§5.2），不计入 `PAGE_LIMITS.max`、不截断、整段计入「给人看过」的核对。稳定部分：这个模块服务的步骤（模块自己的 `serves` 与它下面任务的 `serves` 的并集），按流程分组，每步写标题、先后与分支条件、「怎样算做成」，模块正文有 `服务：无，<原因>` 时写这个原因。现状部分，标题行「截至给你看的时刻」：每步现在的状态，「这些步骤还有别的模块也在做：……」，「模块里不服务任何步骤的任务：N 个」。放行前只用当时的图重新渲染稳定部分比较（§5.2 末段）：别的模块的任务推进、这个模块自己的任务状态变了，都不让同意失效；这个模块服务的步骤集合变了、某步标题或条件变了，同意失效，主 Agent 重新给人看。人放行一个模块，看到的就是「我同意它去做这几步」。例：

```
这个模块服务哪几步
 借书：1 在书的详情页点「借阅」〔弹出确认框〕→（已交押金）2；（没交押金）3。2 确认借阅〔提示借阅成功〕。3 交押金〔提示押金已收〕→ 2
 还书：1 打开我的借阅〔看到自己借的书〕→ 2 选一本点「归还」〔弹出确认框〕→ 3 看到归还成功〔提示归还成功〕
截至给你看的时刻（这一段只是给你看现状，不是你要同意的内容，之后会变）
 这 6 步现在都是「排上了」；这些步骤没有别的模块在做；模块里不服务任何步骤的任务：0 个
```

模块的设计评审（M7 §3.7.5，对照方向清单的独立评审）的简报多一段：这个模块服务的每个步骤的 `acceptance`，要求评审判断模块设计有没有覆盖它们，没覆盖的算挡路。这样用户图的缺口在设计阶段就被一个独立的 agent 看一遍，不用等做完才发现（请求见 §11 M7）。

### 5.4 开发中（M7）

- 派活的简报（M7 §3.5.2）的 Context 多一段：这件活服务的步骤，写成「借书 › 在书的详情页点「借阅」」，让 worker 知道自己做的东西用户怎么用。`kind` 为 `test` 且服务了步骤的任务，简报再多一段走一遍的约定：这些步骤所在的每条流程的走法种类、`norm-merge-gate` 里该种类的 `walk` 命令（`{flow}` 已换成流程 id）、报告文件的路径与格式（§2.7），让写测试的 worker 知道命令会怎样调用它、报告要写成什么样；这些常量只在 `walk.ts` 一处定义。任务不服务任何步骤（自己、后代、祖先、被依赖的活都没有）时，`dispatch_task` 的结果多一行提示，不拒绝。
- 每步投影（`graph_focus` 在任务上）多 `serves` 一行，在步骤上多 `servedBy`、`next`。
- 派发状态提醒（M7 §3.5.4）在有缺口时多一行：`Steps nobody serves: 借书 › 交押金 (step-11); work that serves no step: 导出年度报表 (feat-export); flows with no test task: 搜书 (flow-2), 还书 (flow-4)`，只在内容变化时注入。
- 分解提醒多两句：把任务连到它做出来的步骤；自动走法的流程要有一个 `kind` 为 `test` 的任务连到它覆盖的步骤，`flow:no-test` 点名还缺的流程（§4.3）。
- 三档的判断提示见 §4.3。

### 5.5 汇合之后：走一遍与「做完」（M7）

目标下的活都关了，`hourness.tasks-closed` 叫主 Agent 派整体审查。有用户图（`present`）的目标，`dispatch_task <目标 id>` 在派审查之前多做一段：

1. **前提。** 两条都要成立，否则拒绝（`walk_unready`），列出缺项，主 Agent 补活、补走法、补连线或请人批准：（a）目标下没有除 `step:failed`、`work:orphan`、`flow:too-long`、`step:too-many-branches` 以外的缺口，所以 `flow:no-test`（自动走法的流程拆成任务之后没有测试任务）在这里挡住，这是它的第一道门，放行时它还不成立；（b）目标下没有 `proposed` 的 `live` 用户节点（角色、流程、步骤）：放行之后主 Agent 不带转述加的步骤是 `proposed` 而且 `live`，它还没算进产品，`walk` 写入（W4）只收已批准的步骤，走一遍的作业与 `graph_walk` 都会在它那里 `bad_transition`，所以先请人批准或拒绝它（对话里经 `propose_to_human` 问，或人在面板的「需要你」里看到它）。放行之后加的流程与步骤可能带着形状缺口，这里是第二道门。`你来走` 的流程同样要过这一步。
2. **有效的通过记录。** 流程的每个 `live` 且已批准的步骤，推出的状态是 `walked`（没有 `outdated`），并且它最近一次通过的走一遍的 `note` 解析得出提交 `W`，`W` 被当前主干末端 `H` 覆盖：`W` 是 `H` 的祖先或就是 `H`，并且 `git diff --name-only W H` 列出的路径全在项目图目录（本仓库是 `docs/graph/`）下（走一遍的证据自己就是图文件，写进去提交之后主干会前进，所以只差图文件的主干算同一份代码）。`覆盖` 这一步要用 git，由 M7 实现并作为 `covers` 传给 `userCompletionItems`；纯函数一侧不碰 git。
3. **起作业。** 对没有有效通过记录的自动走法流程（命令、截图、终端），起走一遍作业（§2.7），立即返回 `{status: 'walking', job, flows, waitingForPerson, head}`，不在工具调用里等。作业结束后事件 `hourness.walk-done` 叫醒主 Agent，主 Agent 再调一次 `dispatch_task <目标 id>`。
4. **你来走。** `你来走` 的流程在没有有效通过记录时列在 `waitingForPerson`（只剩这类流程时返回 `walk_unready`）；主 Agent 用 `propose_to_human` 的 `question` 建待决，问句里写明请人走的是哪一个提交（`head`），人走完回话，`graph_walk` 记（§2.7）。
5. **派审查。** 所有流程都有有效通过记录时，才派整体审查；审查的简报带每条流程这次走一遍的结果（哪些步骤过了、没过的原因、复核的判断）；`checked` 要覆盖每条 `acceptance:<i>` 和每条 `flow:<流程 id>`。
6. 审查通过之后，`goalCompletion` 才可能成立。

`goalCompletion` 多第 8 条（`userCompletionItems(graph, goal, covers)`）：目标 `present` 时，目标下每个 `live` 的已批准步骤都是 `walked`（还是 `proposed` 的步骤由现有的第 4 条挡住，那一条只数 `live` 的用户节点）；每个步骤最近一次通过的走一遍的 `note` 解析得出提交 `W`，`W` 被最近一条通过的整体审查批注记下的主干提交 `A` 覆盖（`W` 是 `A` 的祖先或就是 `A`，且 `W` 到 `A` 之间改动的路径全在 `docs/graph/` 下）；`note` 解析不出提交的当作没有，不放过。函数或 git 调用抛错时拒绝完成并写明（失败时关门，同 R5-F3 的做法）。目标没有 `live` 的角色（`用户流程：无`）时这一条不适用。M7 现有的七条不变。这一条给出两项 `GateItem`：`flows:walked`（`label`「每一步都走通了」，`hint`：`walk the flows again with dispatch_task on the goal; steps that are not walked: <id 列表>`）和 `flows:fresh`（`label`「走一遍的结果对得上现在的代码」，`hint`：`the code changed after these steps were walked: walk them again`）。

### 5.6 晨报（M7）

`fourAnswers`（M7 §3.10）对 `present` 的目标，第一节「目标」按流程写，不再只写任务数：

```
图书管理系统 · 6 条流程：1 走通 · 1 走不通 · 1 做完了要重走 · 1 做完了等走一遍 · 1 没人负责 · 1 排上了
 读者：登录 走通；搜书 做完了，等走一遍；借书 有 1 步没人负责（交押金）；还书 排上了
 管理员：录入新书 做完了，要重走；处理逾期 走不通（「发提醒或登记赔偿」）
 不服务任何步骤的活：特性「导出年度报表」
 走一遍：本期 5 次，超时 1 次（借书：上限 120 秒，实际超过 120 秒，原因写在日志里）
```

规则：每个角色一行，每条流程一个状态词；有缺口的流程在括号里点出第一个缺口；本期走通的流程另列「本期走通：……」；走一遍一行写本期跑了几次、超时几次，超时的点名流程、上限（及它来自预计还是实测）、实际耗时；本期超时值有变的流程另写旧值、新值与依据（取自 `walk-limits.jsonl`，`d-timeout-measured` 要求每个超时值可追溯）；开发那一侧的数（任务完成几件、进主干几次）照旧在后面。同样的图和同样的运行记录逐字相同的输出（L2 钉住）。给人看的字过 `plainWordsIn`。第二节「规划」多一行缺口计数（没人负责几步、不服务任何步骤的活几件）。

## 6. 面板

面板只看。本节补充面板设计 1.1（`.agents/tasks/plain-ui/design.md`）；1.1 未放行，改动写成请求（§11）。

### 6.1 入口与先看到什么

- 首页「效果是」：目标 `present` 时，目标那一项的第一行改写流程进度，开发进度退到第二行。例：

```
图书管理系统

```

点第一行打开「用户怎么用」页。没有用户图的目标显示不变。这是人说「依旧参考项目图的理念」之后最直接的落点：效果是用户走通了什么，不是开发做了几件。
- 「用户怎么用」是第 2 层的一页（面板 1.1 §4.1 的页清单多一项），进入方式：首页那一行、目标与步骤等节点页页头的「用户怎么用」、页脚入口。

- 「上次看之后」多三种行：「借书」走通了；「处理逾期」走不通：「发提醒或登记赔偿」；新加一步「交押金」，还没人负责。

- 用户视角：角色，其下流程，流程可折叠；展开的流程按 §2.3 的顺序列步骤，编号、标题、状态字；分支的出边在步骤下面缩进写「条件 › 到第 n 步」；回环写「回到第 n 步」。流程行右侧写状态和几步。流程上次走一遍的结果写一小行：「10-31 14:20 · 命令 · 4/4 通过」；走不通的写出哪一步和原因；展开的流程另写走法（种类、预计秒数、当前的超时上限及它来自预计还是实测，取自 `walk-limits.jsonl`，§2.7）。

## 7. 兼容与迁移

### 7.1 只加不改

本特性对数据格式的全部改动是：三个节点类型枚举值，两个连线类型枚举值，连线上一个可选字段 `when`，一个证据种类，两个操作名（`walk` 进历史；`relink` 只是请求，历史里记成 `link`、`unlink`）。没有字段改名、没有语义改变、没有删除。所以：

- 现有的任何节点文件，读入、写出都逐字节不变（黄金测试，§1.4 第 1 条）。没有 `when` 的连线写出时不带这个字段。
- 现有的历史条目不重写、不补字段。`docs/graph/` 不迁移。
- 没有用户节点的图：`userGraphOf` 对每个目标返回 `present: false`；所有新增的门禁项、投影字段、面板入口、晨报行在 `present` 为假时不出现；`graph.svg` 字节不变；M3、M7 现有的测试不改且通过。这是行为不变的证据。

### 7.2 哪些可选

| 事项 | 可选吗 |
| --- | --- |
| 一个目标有没有用户图 | 对新目标不可选，但可以显式声明没有：需求卡第 9 项要求要么画出来，要么在目标正文写 `用户流程：无，<原因>`。声明写在人看到的确认页上，所以「没画」永远是人看见并同意过的 |
| 步骤的 `acceptance` | `present` 的目标，放行时必填 |
| 流程的 `走法：` | 画草稿的时候可选；放行时必填（`flows:walk`，人在放行页看到命令原文）；每个种类要在 `norm-merge-gate` 里有一行 `walk` 命令，`你来走` 不要 |
| 步骤的服务者 | 访谈与设计阶段可以没有；放行时必须有；做完时必须走通 |
| 模块服务步骤 | 必须，或写 `服务：无，<原因>` |
| 任务服务步骤 | 可选，只标出不服务任何步骤的活 |
| `when`、`前提：` | 可选；分支必须带 `when`（形状） |

### 7.3 已经在途的目标

- 已经过了确认（`design` 及以后）的目标：第 9 项不再看，门禁不回头；这些目标没有用户图也可以做完。主 Agent 可以在对话里问人要不要补画，人说画，就按 §4 当作放行之后的增补：这时没有放行页，所以主 Agent 给人看的样稿要同时带 `confirm` 与 `walks` 的稳定部分（用户图和将被执行的命令原文），人确认后才逐个批准；`norm-merge-gate` 加 `walk` 行要人的原话（清单的验收只有人的权限能改）。一旦 `present`，大循环已放行的目标上加的步骤按 §4.3 走，做完时就要求走通。
- 还在 `wish`、`interview` 的目标：实现上线之后，确认前多问一轮第 9 项。
- 本仓库自己的两个目标 `glm-house`、`hourness`：不受影响，何时搬 `user-journey` 见 §14。

### 7.4 旧版本读到新图

旧版本（没有这一特性的构建）读到新图，后果不止是「读不到用户节点」。`format.ts` 的 `edge` 检查器用 `oneOf(EDGE_TYPES)`：旧版本读到一条 `serves`（或 `next`）连线，这个节点的整个 `edges` 数组非法，该特性或任务节点整个读不进节点表，它的子节点还会报「未知父节点」。丢掉的是全部用户节点，加上所有带 `serves` 的开发节点；面板显示错误数和第一处，开发图缺块。写入一律被拒（引擎遇到任何校验错误都返回 `graph_invalid`），所以不会写坏文件，也不丢数据：节点文件都还在，用新构建读回来是完整的。补救是升级到带这一特性的构建，或者 `git revert` 写入用户节点和 `serves` 连线的那些提交。

会发生的场景只有一种：本项目的构建装在 `~/.dsh` 的 profile 里，同时在 Kiro 里用仓库源码的命令行改了图。U1 至 U3 合入之后还没有谁写用户节点，窗口从 U4 合入、第一个目标画出用户图开始，到每份安装都换成新构建为止。装之前的三道门禁（`npm run build`、`npm run preflight`、`npm test`）和安装流程把两份保持同一版（`AGENTS.md` 强制流程），所以缓解措施是同版本安装；U4 合入的那次安装后，才在对话里让人画第一张用户图。本稿不加版本标记：加了旧版本也不认，没有帮助；错误信息已经点名第一处出问题的文件与字段。

### 7.5 引擎里的次序

U1 至 U3 合入之后，引擎认得用户节点，但没有谁会写它们：访谈（U4）才是第一个写入者，手写节点文件被 `graph-files-only` 拦下。所以引擎改动先上、行为改动后上，不会有「引擎不认的节点出现」的窗口。

## 8. 失败、校验与不变量

### 8.1 失败预案

按 `d-failure-plans`：先查得出，再退得下，事后追得到。

| 操作 | 失败条件 | 可恢复 | 调用方收到 | 记录 |
| --- | --- | --- | --- | --- |
| 写入用户节点或连线 | 违反 W1 至 W5 或权限 | 是 | `{ok: false, error}`，`hint` 写正路 | 引擎不写文件；无日志（同其他写入拒绝） |
| 并发写同一节点 | `stale_revision` | 是 | 同上，读投影再试 | 无 |
| 推导（`userGraphOf` 等）抛错 | 节点读不懂、bug | 是（不影响图） | 面板：页面写「读不出用户图」与原因，开发视角照常；晨报：该目标一行写「用户图读不出：<原因>」；阶段提醒：不加缺口行；放行与做完检查：拒绝并写明（失败时关门，因为放过去等于没有检查） | 行健康 degraded，原因写进 `/hourness-status` |
| 走一遍作业起不来 | 前提不满足（含 `proposed` 的 `live` 用户节点、`flow:no-test`）、门禁锁等了 60 分钟（`gate_busy`）、准备命令失败（`setup_failed`）、`git` 读不到主干 | 是，重试 | 前提不满足时 `dispatch_task` 同步返回 `walk_unready`；其余在事件 `hourness.walk-done` 里标 `not_run` 并写原因 | `walks.jsonl` 的 `start`、`end` 两行；`execute.walk` 指标事件 |
| 走一遍：作业占着门禁锁时别的检查来了 | 别的目标的 `check_commit` 要锁；作业最长 45 分钟（`WALK_JOB_MS`），低于别的检查等锁的 60 分钟（`GATE_WAIT_MS`） | 是，不丢工作 | 别的检查照 M7 每 5 秒重试、等到作业放锁；极端情况（准备命令加第一条流程合计超过 60 分钟）得到 `gate_busy`，主 Agent 重试 | 检查记录照 M7；作业的 `start`、`end` 行带取锁到放锁的时长 |
| 走一遍：命令超时、非零退出、报告缺失或不合格、产物缺失或过大 | 见 §2.7「一条规则」 | 是，重跑 | 按规则写的证据（入口步骤上 `exit` 为 1，或逐步骤的结果）；事件里写 `outcome` 与原因 | 日志在 `<exec>/walks/<作业号>/<流程 id>/`；`flow-end` 行带上限、耗时、结局；不抛错 |
| 走一遍：作业期间主干前进 | 别的提交在作业中途进了主干 | 是 | 证据照写（是关于 `T` 的事实）；事件 `trunkMoved` 为真时写明改过的路径；完成检查用 `覆盖` 判断，改过 `docs/graph/` 以外路径的采信不了，要重走 | `end` 行 |
| 走一遍：写证据前宿主退出 | 命令跑完、证据没写 | 是 | 重启对账（M7 §3.9.6）读 `walks.jsonl`：有 `flow-end` 行、副本在、证据没写的补写（用 `reason` 去重）；没有副本的下一次作业重跑；没有 `end` 的作业记为 `abandoned` | 对账结果进复盘 |
| 走一遍：复核 agent 失败或不可用 | 截图与终端类 | 是 | 激活重试至多两次；仍失败的流程不写证据，仍是「做完了，等走一遍」，事件标 `review_failed`，整体审查不派；同一流程连续三次，发出 `hourness.stopped`（`kind: 'acceptance'`）问人 | 复核的失败按 M7 §3.7.3 记 |
| 走一遍：`截图` 流程的模型不支持图片 | `dispatch_task` 带的模型在目录里没标图片输入 | 是 | `dispatch_task` 同步拒绝 `walk_model_no_images` | 无 |
| `graph_walk` 失败 | 原话核对不过、`hournessTalk` 读不到、项目根 `HEAD` 读不到、逐步骤写到一半失败 | 是 | 核对不过：拒绝，纠偏文字同 `main-agent-graph-relay`（读不到时 fail-closed）；`HEAD` 读不到：`unavailable`，一个都不写；中途失败：返回已写与未写的步骤 | 违规流水一行 |

### 8.2 外部输入的校验

| 输入 | 必填 | 类型与上限 | 失败时 |
| --- | --- | --- | --- |
| 节点类型、父节点（`graph_propose`） | `type`、`parent` | 枚举；父节点类型见 V1 | `invalid`，`field: node.parent` |
| `title`（用户节点） | 是 | 单行非空；人话检查归面板 1.1 的 `plain.ts`（警告，两阶段） | `invalid` |
| `acceptance`（步骤、流程） | 放行时必填 | 字符串数组，现有规则 | 放行门禁项 `flows:expect` |
| `next` 的 `when` | 出边多于一条时 | 单行，1 至 40 个码点，不含换行；流程节点上的 `next` 不带 | `invalid`，`field: when` |
| `graph_relink` 的 `next` | 是（可为空数组，流程至多 1 项） | `{to, when?}` 的数组，`to` 不重复，至多 8 项，`to` 是 `live` 的步骤且属于同一条流程 | `invalid`，`field: next[i]` |

| 流程正文 `走法：` | 放行时 | `命令\|截图\|终端 · 预计 <N> 秒`（N 为 1 至 1800 的整数）或 `你来走`，单行 | 放行项 `flows:walk`、缺口 `flow:no-walk`，`unparsed` 原因 |
| `norm-merge-gate` 里的 `walk` 行 | 有自动走法的流程时 | `` `walk <种类> $ <命令>` ``，命令含 `{flow}`，至多 300 个码点，单行 | 该行不认，带原因进 `flow:no-walk` |
| `report.json` | 命令类走法 | JSON 对象，`flow` 与目录一致，`steps` 至多 50 项，`said` 至多 120 个码点，`artifact` 不含路径分隔符或 `..` | 视为报告不合格（见 §2.7） |

| `walk` 证据 | 是 | 1 至 5 条；`ref` 合 `WALK_REF_PATTERN`，单行，至多 200 个码点；`exit` 整数；`note` 合 `WALK_NOTE_PATTERN`（写入时），单行，至多 300 个码点（读入时） | `invalid` |

| 目标正文 `用户流程：`、模块正文 `服务：` | 否 | 值以「无」开头并带原因 | 不合格按没写 |
| `graph_walk`、`graph_relink` 的 `relay` | `graph_walk` 是，`graph_relink` 否（人的权限需要时才要） | 同其他 `relay`（至多 2000 字符，人的原话） | 引擎 `invalid`；harness 核对不过则拒绝 |
| 放行页里 harness 生成的三段（稳定两段加现状一段）；确认页的样稿 | — | 放行页三段合计至多 8,000 个码点；样稿至多 8,000 个码点；都不截断。`record_human_answer` 只重新渲染并比较稳定部分，现状部分不比较 | 放行项 `flows:page` 不过（样稿超限时 `confirm` 返回 `gate_unmet`）；稳定部分变了 `not_shown` |

### 8.3 不变量与所在层

| 不变量 | 谁守 | 为什么在这一层 |
| --- | --- | --- |
| 用户节点只有四种存下来的状态，从不是 `doing`、`done` | `format.ts` 读入时、`engine.ts` 写入时 | 单一事实源：进度只有一个来处（推出） |
| 步骤的状态只由连着的活和走一遍的记录推出 | `user-graph.ts` 一处实现，宿主与面板共用 | 两处实现会对不上 |
| 一个服务者不会一个人服务所有步骤 | 引擎写入（W1） | 防止什么缺口也查不出 |
| 命令、截图、终端三种走一遍的证据只有 harness 写 | 引擎写入（W4） | 门禁只认证据，不认自述 |
| harness 执行的走法命令只来自 `norm-merge-gate` 的 `walk` 行，不来自流程正文 | M7 的 `walk.ts` 只读 `walkCommandsOf`；清单的验收只有人的权限能改（引擎） | 流程正文主 Agent 随时能改；清单是人批过的 |
| 走一遍的证据是关于被检出的那个提交 `T` 的事实，完成时才核对它是否还算数 | `覆盖` 判断（M7，git）；纯函数一侧只解析 `note` | 写证据本身让主干前进，不能要求提交相等 |
| 缺口不挡写入，只挡放行、走一遍之前与做完 | 引擎不查形状；M3 的放行门禁与 M7 的做完检查、走一遍前提查 | 对话里一步步改，中间状态必须合法 |
| 放行之后改用户图（含标题、走法的种类、出边、`acceptance`）要人的原话 | 引擎权限 + M3 的原话核对 | 它是产品对用户长什么样、怎样算验过，属于人 |

| 废弃的角色、流程、步骤和它们下面的节点不参与任何判定（含面板的「等批准」） | `liveOf` 一处实现（`user-live.ts`）；面板的 `waitingProposals` 也用它 | 引擎不级联（`reject` 与 `status` 都只改一个节点），推导一处就够 |
| 子 agent 不写图 | M7 的 `worker-graph-readonly` 与工具面过滤，按名字列的图写工具要从九个扩成十一个（加 `graph_relink`、`graph_walk`），U2 同批改（§4 开头、§11 m7）；在此之前只有 M3 的 `main-agent-graph-relay` 与引擎的草稿规则恰好挡住，不算数 | 规划状态只有主 Agent 与 harness 两个写入方；名单是 M7 的，新增写工具时必须同批加进去，由 `tests/contracts.spec.ts` 对 `GRAPH_TOOL_NAMES` 里的写工具与 M7 的两份名单做一次对照钉住 |
| 没有用户节点的图行为不变 | 黄金测试与 `present` 为假时的空操作 | 兼容 |

## 13. 要人定的事

两件，都是人的事（`d-ask-three-gates` 第一道关：什么算做成、每个新项目怎么走）。写法按这条新规则的形状：① 是「确认建议」，② 有真实取舍，是「选方向」。放行页上人看到的是 `onepage.md` 的版本。

① 新项目都要画「用户怎么用」吗？

我建议**都画**：没有终端用户的项目写一句「无，原因」就跳过。代价是每个新项目的访谈多一轮；不画的话，这个功能多半没人用。可以吗？

② 画了用户图的项目，怎样算做完？

- **每条流程走通才算做完**（推荐）：没走通的流程会让目标停在最后一步，晨报点名；没法自动测的流程要请你亲自走一遍。
- 只提醒：目标照样做完，晨报里标出没走通的流程。

人回「可以」或选推荐，就是 D10、D12 成立；回「选填」或「只提醒」，D10 或 D12 改成不拦的一边：需求卡第 9 项变成提醒，`userCompletionItems` 的结论只进晨报、不挡 `update_goal complete`，其余设计不变。

## 14. `user-journey` 怎样搬

节点 `user-journey`（插件使用流程，`journey.md` 0.6）描述的是人怎样用本插件。它不是本特性，但它是一份合格的用户图素材：人是这个产品的用户，每个阶段本来就写着「用户做什么、用户看到什么、系统自己做什么、什么时候问用户」，加上每条后面的〔模块〕标签。现在不搬，搬法如下，等本设计放行、U7 合入之后由主 Agent 和人在对话里做一次。

| journey.md 里的 | 搬成 |
| --- | --- |
| 阶段 S1、S2（装插件、登录 GLM，归 GLM 通道） | 目标 `glm-house` 下的角色「用 GLM 通道的人」，两条流程 |
| 阶段 S3 至 S10（归编排层） | 目标 `hourness` 下的角色「用编排层做项目的人」，每个阶段一条流程；步骤多于 12 的阶段（S7）拆成两三条 |
| 「用户做什么」「用户看到什么」的条目 | 步骤（只留用户能观察到的动作与结果）；条目的先后是 `next` |
| 阶段里的分岔（S4 新项目或接管；§5 的失败：额度快用完、高峰、崩溃、方案被否掉、审查一再不过） | `next` 的 `when` 分支，或各自成流程 |
| 每条后面的〔M3〕〔M7〕〔规则板〕…标签 | 对应特性（`m3`、`m7`、`rules`、`schedules` …）到步骤的 `serves` |
| 「系统自己做什么」 | 不进用户图；是服务者那一侧的任务与它们的验收条件 |
| §6 缺口表 G1 至 G28 | 其中「没有哪份设计写这一格」的变成没人负责的步骤，「设计之间对不上」的仍写成对设计的批注；搬完之后缺口表由图推出，不再手写 |
| 走法 | 起初全是 `你来走`（人是用户，自己用自己的插件）；有 L3 探针的格子以后改成 `命令` |

规模估计：两个目标共约 2 个角色、14 条流程、80 步上下，比图书管理系统大一圈，所以搬的时候每条流程压到 8 步以内，细节仍留在 `journey.md` 的正文里。搬完之后单一事实源要选一处：步骤列表在图上，`journey.md` 保留叙述和读法，阶段小节里的条目改成指向节点；这一条到时候由人定（它是文档去留，不是本设计的事）。
