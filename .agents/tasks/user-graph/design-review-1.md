# 用户图设计 0.1：第 1 轮独立评审

被审：`.agents/tasks/user-graph/design.md` 0.1（第 1 稿），`graph-ops-design.json`（13 条批注草稿）。
评审轮次：1。评审者：与作者不同的 agent。
结论：CHANGES_REQUESTED。HIGH 3 条，MEDIUM 9 条，LOW 5 条。挡路 12 条。

核对方式：读了 design.md 全文、`graph-ops-design.json` 全文；对照读了 `src/graph/`（`schema.ts`、`format.ts`、`validate.ts`、`engine.ts`、`mutation.ts`、`projection.ts`、`stage.ts`、`execute-stage.ts`、`tools.ts`、`reminder.ts`）、`src/shared/tool-names.ts`、`ui/src/graph/model.ts`、M3 附录 0.5（§3.5、§3.8、§3.14）、M7 0.6（§2.4、§3.8、§3.9.2 至 §3.9.7）、面板 1.1 §4.3、循环板 0.6 §5.1、`norm-review-floor`、`d-timeout-measured`、`d-code-rules-enforce`、`d-freeze-until-dogfood` 和 `design-context.md`。另外跑了一次现状核对：`docs/graph/nodes` 的 208 个文件经 `checkNode` 与 `serializeNode` 全部逐字节不变、零校验问题。

本稿对简报要定的各项（节点与连线种类、条数、推导与缺口、什么算验过、没有界面的项目、对话里怎么改、进两层循环的位置、两个视图、兼容、对已放行与未放行设计的请求）都有交代，没有明显的范围蔓延。下面的发现集中在三处：入口与回环的定义、对话式修改与已放行的转述核对之间的冲突、走一遍这条验证路径的信任边界与执行方式。

## 发现

### 1. HIGH：流程入口的定义与「回到第一步」的环冲突

位置：§2.3（入口是「没有入边的那个步骤」，恰好一个）、§2.6 的 `flow:entry`、§1.4 第 16 条。

问题：§2.3 自己举的回环例子是「没搜到，回到搜索」。搜书流程里第 1 步「在搜索框输入」是入口，第 2 步「看到结果列表」带一条回到第 1 步的 `next`，这时每个步骤都有入边，没有一个步骤满足「没有入边」。结果是 `flow:entry` 触发，大循环放行门禁 `flows:shape` 挡住，显示顺序「从入口深度优先走」也没有起点。§2.9 的登录流程回的是第 2 步，所以夹具没有碰到这种形状。F2 要求「流程内允许回到前面的步骤」，最常见的重试回到起点却被判成形状错误。

修法：入口显式化，不靠入边推算。允许 `flow` 节点带一条 `next` 指向它的第一步（V4 增加「起点是 `flow`、目标是同一条流程的 `step`」这一支）。`flow:entry` 的判据改为：这条流程上的这种连线不是恰好一条，或目标不是活的步骤。显示顺序与可达性都从它出发。「在最前面插一步」就是改这条连线。在 §1.4 第 16 条和 §2.9 夹具里各加一例「回到入口」。若不想加连线，备选是：入口取唯一一个没有来自强连通分量之外入边的分量里最早创建的步骤，并写明并列时按 id；但改入口时没有一个可对话编辑的落点，建议用显式连线。

### 2. HIGH：对话式修改的多次写入过不了已放行的转述核对，§3.5 的示范跑不通

位置：§3.5 的「四次调用」示范，§4.2 的「加一步」「删一步」「换顺序、加分支」三行，§3.4 的 `next` 一行，§15 U5。

问题：M3 附录 0.5 §3.8 第 1 条规定，主 Agent 带 `relay` 的图工具调用，要用 `personSaid(状态, 段, 起点)` 核对，起点是「目标节点最后一条不是 `comment` 的历史的 `at`」，要求人的话发在这个时间之后。示范里对「点借阅」这一个节点连续写三次：先 `graph_link` 连到新步骤，再 `graph_unlink` 摘旧连线，再 `graph_link` 连回去。第一次写入之后，「点借阅」的最后一条历史比人说那句话晚，第二次和第三次用同一句原话就被 `main-agent-graph-relay` 拒绝。§4.2 的「删一步」（对前一步 link 加 unlink）同样中招。§3.5 说示范「过真实检查（引擎的写入规则、`plainWordsIn`）」，没有包含这条守卫，L2 发现不了，只会在 L3 或 L4 暴露。人最典型的那句「借书前要先交押金」恰好走不通。§15 U5 只假设了改 `acceptance` 的单次写入。

修法：把一个步骤的出边修改做成一次写入。新增操作与工具 `graph_relink`：`{id, rev, reason, relay, next: [{to, when?}…]}`，一次替换这个步骤的全部 `next` 出边，引擎对写后的整图只校验一次，历史记一条（含删掉的与加上的）。「加一步」变成：`graph_propose` 新步骤（自带 `next`，起点为 0）加一次对前一步的 `graph_relink`；「删一步」变成一次 `graph_relink` 加另一个节点上的 `graph_status`。每个节点在同一句转述下只被写一次。同步改 §3.4、§3.5 的示范、§4.2、U2 验收第 8 至 11 条，`GRAPH_TOOL_NAMES` 的请求（M3 批注）加 `graph_relink`，并在 L3 加一个让示范走过真实守卫的场景。备选是向 M3 请求放宽同一句原话连续写入的起点，但那是重开已放行的设计，不推荐。

### 3. HIGH：走法命令来自主 Agent 可随时改的文本，harness 直接执行；已批准节点的 `title` 与 `body` 不受 D13 保护

位置：§2.7（`走法：` 一行与「命令由 harness 跑」）、§3.4 表中 `edit` 的 `title`、`body` 一行与「`LLM_EDITABLE` 不变」、§1.6、§12 的 D8 与 D13。

问题：`走法：` 写在流程的 `body` 里。`engine.ts` 的 `LLM_EDITABLE` 含 `title` 与 `body`，`planEdit` 对非自己提议的已批准节点只检查字段是否在这个集合里，所以放行之后主 Agent 不带人的话就能改写任何流程的 `走法：` 一行，harness 随后执行这段文字。仓库里其余 harness 执行的命令都经过人：M7 §3.8.1 的合入前检查「命令文本来自人批过的规范」，M3 对会跑东西的提议要把原文给人看过才算数，`d-timeout-measured` 写明估的时间「人同意时和脚本原文一起看到」。这里人从没看到命令，被检查的一方又同时写命令和报告，D8 想防的「由被检查的一方报结果」没有防住。harness 自己起的进程也不经主 Agent 的工具守卫。另外 D13 说放行之后改步骤要人的原话，但 `title` 就是步骤本身，改名可以把「点借阅」换成别的动作而不留人的话。

修法：
- 对已批准的 `role`、`flow`、`step`，`edit` 改 `title`，或改 `body` 且 `走法：` 一节发生变化（用 `labeledSections` 比较），要求有人的权限（`human` 或带转述）。在 `planEdit` 里加这一检查，改 §3.4 表与 U2 验收第 8 条；自己提议且仍为 `proposed` 的草稿不受限。
- 大循环放行页与模块放行页里，由 harness 追加每条流程的走法命令原文与预计秒数，计入「给人看过」的核对（做法同 M3 对脚本的 `detail.mustShow`）。人放行时看到的就是将要被执行的命令。
- §2.7 写明命令怎样起：沿用 M7 §3.8.1 的 `spawn`、shell 与环境处理，工作目录是门禁工作树，从不在主检出里跑。
- 备选：把允许的走法命令限在一张人批过的规范节点（例如 `norm-merge-gate` 里已有的命令或新的 `norm-walk-commands`）里，`走法：` 只能引用其中的条目。

### 4. MEDIUM：走一遍的退出码规则前后矛盾，§2.9 的例子靠矛盾的那一支才成立

位置：§2.7「判定」列（命令退出 0 且报告里这一步 `ok`）与「失败」一段，§2.9「处理逾期」一行，§8.1，§1.4 第 25 条。

问题：「失败」一段先说命令没有退出 0 就不给任何步骤写通过的证据，又说报告里标 `ok: false` 的步骤各写一条 `exit` 为「命令实际退出码」的证据。命令退出 0 而报告里某步 `ok: false`（自定义 reporter 常见）时，这一步的证据 `exit` 就是 0，等于通过，与「判定」矛盾。§2.9「处理逾期」写的是三步 `walked`、一步 `failed`，这个结果在「命令非零退出就不给通过证据」的规则下得不到（三步没有证据，停在「做完了，等走一遍」），只有靠退出 0 加 `ok: false` 那一支才得到，而那一支恰好给出通过的证据。例子与规则对不上。

修法：只留一条规则。对报告里的每个步骤：命令超时或被杀，只在入口步骤写 `exit` 1 的失败证据；其余情况报告合格时按步骤写，`exit` 为 0 当且仅当该步 `ok` 为真，否则为「命令退出码，若为 0 则 1」。这样一个测试运行器在第 4 步失败后非零退出，前 3 步仍记通过，§2.9 的例子成立。报告缺失或不合格时仍在入口步骤写 `exit` 1。把这条规则同步到 §2.7、§2.9、§8.1，并在 §1.4 第 25 条加三个用例：退出 0 加一步 `ok: false`、退出非零加部分报告、超时。

### 5. MEDIUM：「你来走」的证据既不带提交，又要满足「做完」检查的提交相等，顺序也没定

位置：§2.7「证据怎么写」表的 `note`、「谁能写」、W4（§3.4 末表）、§5.5 第 2、3 步与 `userCompletionItems`（第 8 条）、§6.1「需要你」一段、§13 ①。

问题：
- 人走的证据 `note` 写「人原话里的一句」，W4 只对 `harness` 要求 `@<提交>` 开头。§5.5 第 8 条要求每个步骤最近一次通过的走一遍，其 `note` 里的提交等于整体审查记下的主干提交。`你来走` 流程的步骤因此永远满足不了第 8 条，目标无法完成。§13 ① 自己建议没法自动测的流程请人走。
- §5.5 第 2 步让主 Agent 把「请人走一遍」放进下一次提问，第 3 步同时把结果交给整体审查。审查要不要等人走完、`flow:<id>` 对没人走过的流程怎么覆盖，没有写。
- §6.1 说请人走一遍在「需要你」里是待决，但面板读的是图上的待决节点和 `awaiting` 里的确认与放行，§2.7 描述的是聊天里的一句话，两头都没有建节点。

修法：`graph_walk` 由工具或引擎自己补 `note` 开头的 `@<当时的主干提交>`，模型只提供转述的原话；W4 的 `@` 检查对所有 `walk` 条目生效。顺序写死一种：`dispatch_task <目标 id>` 在有 `你来走` 的流程没有对当前主干的通过记录时返回 `walk_unready` 并列出这些流程，审查在人走完之后才派。请人走一遍用 `propose_to_human` 的 `question` 一种建待决，这样 §6.1 的说法才成立；否则删掉 §6.1 这句。

### 6. MEDIUM：走一遍的执行方式没定，`walk_flow` 只有名字

位置：§5.5、§2.7（「和 `check_commit` 抢同一把检出锁」）、§10 U5b、§11 的 M7 一行、`graph-ops-design.json` 的 m7 第二条。

问题：
- U5b、§11 与批注把 `walk_flow` 叫「动作」，§5.5 却把整件事放在 `dispatch_task <目标 id>` 里，没有签名、结果形状和事件。
- 流程顺序执行，每条最长 30 分钟，一个目标可能有 6 条以上，累计数小时。放在一次工具调用里：M7 §15 U4 把「工具调用 `await` 30 分钟不被切断」列为未核实的推断；长任务在 M7 里用后台作业加通知（巡检，§3.11.2）；驱动器连续 3 个没进展的轮会以 `hourness-idle-rounds` 阻塞（M7 §3.9.5），一个长时间无输出的走一遍会被误判成空转。
- 门禁锁在 M7 里持锁上限 6 小时、等待 60 分钟；走一遍占锁期间 `check_commit` 全部排队。
- 在哪个提交上走：证据要写 `@<主干提交>`，但没有说 harness 把主干末端检出到门禁工作树、先跑 `norm-merge-gate` 的准备命令（安装、构建）、期间主干动了怎么办。走一遍写的是 `docs/graph/nodes/*.json`，这些文件按 M7 §3.9.2 合入阶段的说法通过主干提交，一提交主干就前进，而第 8 条要求提交相等。
- 写走法测试的 worker 要生成 `.hourness/walk/<流程 id>/report.json`，格式只写在本设计里，没说它怎样到达 worker 的简报。

修法：把 `walk_flow` 定义成 harness 动作，由 `dispatch_task <目标 id>` 启动为后台作业，立即返回 `{status: 'walking', job}`，完成时发事件叫醒主 Agent，作业进展算作活动（不触发空转）。作业开始时钉住主干末端提交，检出到门禁工作树，先跑准备命令，持门禁锁并受同样的等待与持锁上限，作业期间主干前进则作废重来。第 8 条改为「走一遍的提交是审查所记提交的祖先，且两者之间改动的路径全在 `docs/graph/` 下」。`report.json` 的格式放进 `kind: test` 且 `serves` 了步骤的任务的简报 Context，常量只在 `walk.ts` 一处定义。

### 7. MEDIUM：「独立复核的 agent」是一个新角色，设计里没有定义

位置：§2.7 表中 `截图`、`终端` 两行，§8.1「复核 agent 失败或不可用」，§15 U3，§1.4 第 25 条。

问题：截图与终端类走法的通过与否取决于一个复核 agent，但没有写：谁启动（harness 内部还是主 Agent 派）、登记表里的角色、用哪个模型（M7 §3.1.3 规定每次派发由主 Agent 选模型并记理由，这里 harness 在起）、输出 schema、只读边界、每步的判断怎样映射成 `exit`、「三次后停下」按什么计数。能力也没核实：GLM 模型能否接收图片是前提，§15 U3 只提了可靠性。

修法：在 §2.7 定义一个 `walk-review` 角色：由 harness 在走一遍作业里用与整体审查相同的 `startActivation` 启动，只读，`outputSchema: hourness-walk-review-v1` 为 `{steps: [{id, ok, why}]}` 且必须覆盖该流程每个未废弃步骤；模型取 provider 目录里标明支持图片输入的一个，目录里没有时 `walkSpecOf` 拒绝 `截图` 并在缺口 `flow:no-walk` 里写原因，流程改用 `终端`、`命令` 或 `你来走`；`ok` 映射 `exit` 0，`ok` 为假或缺步骤映射 1，`why` 进 `note`。复核替身（固定回复）在 L2 里测。

### 8. MEDIUM：服务者的粒度没定，§2.9 的夹具不能逐行复现，特性条数上限与模块大小冲突

位置：§2.5「步骤的活」（叶子的取法）、§2.4 条数表、§2.9 全表、§1.4 第 12 条。

问题：步骤的叶子是各服务者下面的全部叶子。服务者是模块（特性）时（大循环与模块放行时的自然粒度，§5.2、§5.3），它服务的所有步骤要等整个模块做完才一起离开「在做」。§2.9「借书」一行里，同在特性「借阅」下的「点借阅」是 `building`，「确认借阅」「看到应还日期」是 `planned`，这只有任务级的 `serves` 才做得到，但表里没写服务者是谁，§5 也没写分解之后由谁、按什么规则把模块级连线细化成任务级。§2.9 全表用「特性「账号」下的任务全部 `done`」这类描述，没有节点 id、父子、状态、`serves` 连线、时间，而 §1.4 第 12 条要求输出「与表逐行相同」，实现者必须自己编夹具。另外特性的 `serves` 上限是 12；「借阅」这类模块服务借书 4 步、还书 3 步，再加续借、预约就超过，第 13 条被拒，而放行门禁 `flows:served` 又要求有人负责。

修法：
- §2.5 与 §4.3 加一条规则：分解时主 Agent 把任务连到它做的步骤（任务级）；模块级连线是放行时的归属声明。若某步骤在同一模块内有任务级服务者，叶子只取这些任务，否则取模块的全部叶子。
- 特性的上限对模块说明怎么办：提高到与目标规模匹配的值，或模块级连线不受上限、只对任务限制；至少写明第 13 条被拒时的正路，不能是「拆模块」，因为模块清单只在大循环里定。
- 把 §2.9 改成显式夹具表：每个节点的 id、类型、父节点、状态、`serves` 目标、关键历史时间，行里的状态能由它推出。

### 9. MEDIUM：没有定义「活着的用户节点」，废弃流程或角色之后它下面的步骤仍被统计

位置：§2.5（「步骤自己的 `status` 是 `dropped` 或 `superseded` 时不推导」）、§2.6（「未废弃的步骤」）、W2、§4.2、§4.3 末段。

问题：所有判定只看节点自己的 `status`。引擎的 `planStatus` 没有级联，废弃一条流程或一个角色不会改它下面步骤的状态，这些步骤仍是 `approved`，继续产生 `step:unserved`，挡放行和 `goalCompletion`，也计入流程与目标的统计。步骤被废弃之后，别的步骤指向它的 `next` 连线仍参与入口、可达性、分支的判断。§4.2 有「删一步」一行，没有「删一条流程」「删一个角色」。被取代（`superseded`）同理。

修法：定义 `live(node)` 为状态是 `proposed` 或 `approved`，且沿 `parent` 到目标的全部祖先也 `live`。§2.5、§2.6、§5、§6 的统计、缺口、`present`、完成检查、W2 的目标检查全部用 `live`。远端不 `live` 的 `next` 连线在缺口判断里忽略。§4.2 加两行：废弃流程（只在流程上一次 `graph_status`，子孙自动不再 `live`）、废弃角色。§1.4 第 15 条旁加用例。

### 10. MEDIUM：用户节点带 `source` 指向设计决策，会污染方案五栏的「规划」栏

位置：§2.3 末段（用户节点自己可以带 `source`，指向待决或决策）、V6、§12 D4 的理由；对照 `src/graph/stage.ts` 的 `designColumns`。

问题：`designColumns` 把目标下任何未废弃的后代只要带指向该决策的 `source` 连线，就计入「规划」栏（`plan.length > 0`）。D4 正是因为这个原因不复用 `source` 做 `serves`，随后又允许步骤带 `source` 指向「决策」。一个步骤指着设计决策，「规划」栏就成立了，而此时没有任何特性或任务被规划，放行门禁被削弱。

修法：V6 改为用户节点的 `source` 只能指向 `question` 节点；或在 `designColumns` 的规划过滤里排除用户类型。二选一，在 §1.4 第 3 条加一例，在 `tests/graph-stage.spec.ts` 加一个用例钉住「用户节点的 `source` 不让规划栏成立」。

### 11. MEDIUM：走法命令的超时与 `d-timeout-measured` 不一致，可追溯没有做

位置：§2.7（超时是预计的 3 倍）、§1.6 方向清单一行（声称走法命令照此定）、§8.1、§5.6、`graph-ops-design.json` 的 metrics 与 m7 条目。

问题：`d-timeout-measured` 的内容是：第一次的超时由写脚本的 agent 估，那个数本身就是超时，跑过之后才由 harness 改成近几次最慢一次的 3 倍，不超过上限；3 倍超过上限时保持上限并告诉主 Agent；每个超时值要记来源、时间与旧值，每次超时记条目、上限、实际耗时与结局，在规则页、循环板页与晨报里看得见；人同意时与脚本原文一起看到。本稿：第一次就取预计的 3 倍（与决定不同）；没有记来源与旧值；晨报（§5.6）不显示超时；缺「3 倍超上限保持上限并告诉主 Agent」；人看不到命令与数字（见发现 3）。§1.6 却声称符合。

修法：§2.7 这一段按决定改写：首次超时取 agent 的估计值，之后取实测。新增运行文件记 `{流程, 旧值, 新值, 来源: 'agent' | 'harness', 依据的运行, 时间}`。§5.6 晨报加一行超时情况，metrics 请求加 `execute.walk-timeout`（条目、上限、耗时、结局），放行页带估计数字（与发现 3 同批）。

### 12. MEDIUM：面板开发视角的「不服务任何步骤」标记规则与缺口定义不一致

位置：§6.2 开发视角一条（「没有 `serves` 且没有人依赖的标……」）对照 §2.6 `work:orphan` 的三条判定。

问题：面板写的规则漏了「祖先有 `serves` 就算有人用」。按它，特性「借阅」下的每个任务（借阅接口、借阅页面、归还接口）自己没有 `serves`、也没人依赖，都会被标成孤儿，而 §6.2 的草图只标了「导出年度报表」。草图与规则互相矛盾，面板是这个功能的主要入口。

修法：开发视角的标记一律取 `gapsOf` 返回的 `work:orphan`，不在视图模型里另写判定。§6.2 写明，U6 验收第 29 条加一例「服务某步的特性下的任务不被标记」。

### 13. LOW：走一遍证据无限增长；`unlink` 的历史丢掉被摘连线的 `when`

位置：§3.4 的 `walk` 一段、§3.5 的 `link`/`unlink`。

问题：每次走一遍在每个步骤上追加 `evidence` 条目，同一批证据又复制进历史，步骤文件随运行次数一直变大，且每次整批重写 40 个文件。`unlink` 按（类型，目标）找，历史里的 `edge` 取自请求，不含被摘连线上的 `when`，条件文字只能从 git 里找回，与「可追溯」冲突。

修法：写 `walk` 时节点的 `evidence` 里只保留最近 N 条（建议 10）`walk` 类，历史照旧完整；`unlink` 时历史的 `edge` 取节点上真实的那条（含 `when`）。

### 14. LOW：若干格式与取值没有写死

位置：§2.7 证据表与 `note`、W4、§8.2、V7、§3.6 的 `RoleView`、§5.2、§5.3、§2.7 超时。

问题：
- `note` 的语法分散在三处：§2.7「`@<主干提交>` 开头，接 `sha256:<…>`，再接一行结果」、W4（`@` 加 7 至 40 位十六进制）、§8.2（非空一行至多 300 个码点）。读入时的 V7 没有一行至多 300 的检查，而第 8 条要解析 `note` 里的提交。`ref` 一处说文字至多 100，一处说整个 `ref` 至多 200。

- 目标既有角色又写了 `用户流程：无` 时，「这四项不出现」与 `present` 为真矛盾。

修法：在 §3.2 或 §2.7 用一段正则与上限把 `note`、`ref` 写成一处；V7 补一行检查；给 `RoleView.state` 一条取值规则（建议取其下流程里最靠前的状态，同 §2.5）；给追加段一个明确的码点上限并说明不计入 `PAGE_LIMITS.max`；补四项门禁的 `label` 与 `hint`；规定 `present` 为真时 `用户流程：无` 不生效。
